# Releasing Speedwave

Speedwave ships a beta from the tip of `dev` once a night (or on demand) and promotes a tested beta to stable from the "Run workflow" button of the `Release` workflow, which creates the `release/0.M` branch. There is no `main`, no release-please, and no manual version bump.

## Channels and versions

- **`dev`** is the default and only long-lived integration branch. A beta `GitHub Release` is built from its tip at 00:17 UTC (01:17 CET, 02:17 CEST) on Tuesday to Saturday when commits landed since the previous beta, or at once from the "Run workflow" button of the `Beta` workflow: `v0.<M+1>.0+N`, flagged `prerelease`, with macOS (Apple Silicon) and Windows installers, CLI archives and `latest.json`. `N` is the number of commits reachable from the tip of `dev` (`git rev-list --count HEAD`); it never resets. The CLI archives contain the binary bundled into the app: on macOS it carries the app's Developer ID signature, on Windows an Azure Artifact Signing signature.
- **`release/0.M`** is the line for stable minor `M`. It is created by the promotion workflow; creating it by hand is not supported. A person from the promoter list runs "Run workflow" on `Release` with `dev` selected and a `commit` input, the SHA of a `dev` commit that already has a published beta. The workflow checks every precondition, creates `release/0.M` at that commit (`M` is one more than the highest existing line), then flips that exact beta's `prerelease` flag to `false` and sets `make_latest`: same build, same tag, same bytes, no rebuild.
- A **hotfix** is a PR to the highest `release/0.M` line. Its merge publishes `0.M.Z` immediately, with no beta stage, and opens a PR that backports it into `dev`.
- The version always comes from git (`crates/speedwave-version`, the `speedwave-version` binary's `version`/`notes-range`/`validate-promotion` subcommands). Every tracked version field in the repo stays at the literal `0.0.0`; nothing about a release is ever written back to a tracked file.

## Secrets, environments and the automation token

- **Environment `release`**: one environment for both channels (beta and stable builds, promote, hotfix, backport PR, changelog PR all run in it). Deployment branch policy: `dev` and `release/*`. No reviewers, no bypass. The existing Azure federated credential (`repo:speednet-software/speedwave:environment:release`) and its 6 `AZURE_*` variables are unchanged — one signing identity serves both channels, because a stable release is the exact same build as its beta, never a rebuild.
- **Environment `promotion`**: required reviewers are the promoter list, the people allowed to promote. The `approve` job of a promotion run waits on it, so nothing runs until one of them approves; a person on the list can approve their own run. It holds no secrets.
- **Environment `e2e`** (SPEED-738/739): branch policy `dev` (the beta run calls `e2e.yml` from there), secrets `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, `LOCAL_LLM_BASE_URL`, `LOCAL_LLM_API_KEY`, `LOCAL_LLM_MODEL`. A pull request branch never gets these secrets — only a run from `dev` (a beta or a maintainer's `workflow_dispatch`) qualifies.
- **Rig runners** (SPEED-738): `speedwave-runner-macos` and `speedwave-runner-windows` run `e2e-macos`/`e2e-windows` under the account `gh-runner`, each over SSH to itself. On Windows `gh-runner` is not an administrator, because the job runs the `npm ci` and `build.rs` of every dependency in the queue. The machine-wide toolchain (VS Build Tools, CMake, LLVM, Ninja, the Vulkan SDK, Node, Python (Chocolatey, as `make setup-dev-windows` installs it) for the PII NER model converter, and the machine `LIBCLANG_PATH`/`VULKAN_SDK`/`INCLUDE`/`LIB`) is installed by an administrator account with `SPEEDWAVE_WINDOWS_HOST="<admin>@127.0.0.1" bash scripts/e2e-vm-setup.sh windows` from Git Bash on the rig; that account's key goes in `C:\ProgramData\ssh\administrators_authorized_keys`. Rerun it after a change of `.node-version`, `scripts/install-vulkan-sdk.ps1` or the CMake/LLVM versions in `scripts/e2e-vm-setup.sh`, and after a VS Build Tools update. In CI the Windows lane fails at once when the toolchain is incomplete instead of running the setup as `gh-runner`. `gh-runner` itself needs `cargo install tauri-cli --locked`, Defender exclusions for its `.cargo` and `.rustup`, and `/home/windows` owned by its WSL user in the `Ubuntu-22.04` distro (the lane fetches its own pinned bats-core there and in `~/.local` on macOS). On both rigs `gh-runner` must own the console session (automatic logon): the Windows lane starts the app through an interactive scheduled task, and the macOS lane installs it to `~/Applications` and starts it from the SSH session. Smart App Control must be off (`HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy`, `VerifiedAndReputablePolicyState` = 0, then a restart): it blocks every unsigned `build-script-build.exe`, and the lane checks it before anything else. OpenSSH for Windows opts `sshd.exe` into RedirectionGuard (Image File Execution Options `sshd.exe`, `MitigationOptions` byte 18 = `0x10`), so every process of an SSH session refuses the junctions `npm ci` creates as `gh-runner` for the `mcp-servers` workspaces (error 448, untrusted mount point); an administrator sets that byte to `0x00` and runs `Restart-Service sshd`, again after an OpenSSH update if it comes back. The lane probes it with a junction of its own and fails at once while it is on. The lane adds the `wasm32-unknown-unknown` target and installs `wasm-pack` for its own account on both rigs; on macOS the toolchain check, like the build, loads `brew shellenv` and `~/.cargo/bin`, because a non-interactive SSH session reads neither. Both lanes keep their cargo target between runs (SPEED-865) and nothing removes it automatically: `C:\cb` on the Windows rig and `~/speedwave-e2e-target` on the macOS rig, both owned by `gh-runner`. Remove it when the rig runs low on disk or a build fails with linker or fingerprint errors that a clean build does not show; the next run builds from scratch: `Remove-Item -Recurse -Force C:\cb` (PowerShell as `gh-runner`) or `rm -rf ~/speedwave-e2e-target` (as `gh-runner`), while no e2e job runs on that rig.
- **`GH_AUTOMATION_PAT`**: one fine-grained personal access token (owner: Mikołaj Kąkol), scoped to this repository only, with Contents: write, Pull requests: write, Workflows: write, Metadata: read, and no admin permission on the token. It is the credential behind every release write (creating `release/0.M` at promotion, tag push, draft creation, asset upload, publish, flipping `prerelease`/`make_latest`) and every automated PR (changelog, backport), because a PR opened with the default `GITHUB_TOKEN` does not trigger CI on itself. Issued 2026-10-07; renew before 2027-10-08 (tracked as [SPEED-745](https://speedwave.atlassian.net/browse/SPEED-745)). Replacing it with a GitHub App is [SPEED-746](https://speedwave.atlassian.net/browse/SPEED-746), no deadline.
- **`GITHUB_TOKEN`** stays at its default read scope everywhere in the release workflows; jobs that need to write use `GH_AUTOMATION_PAT` explicitly, and jobs that log into Azure add `id-token: write`. No workflow references `RELEASE_TOKEN` any more; the secret itself is deleted from the repository in phase 5 ([SPEED-737](https://speedwave.atlassian.net/browse/SPEED-737)), once the old workflows that used it are gone.
- The PAT is passed only to the steps that push a branch/tag or call `gh`, never persisted by `actions/checkout` (every checkout is `persist-credentials: false`, no `token:` input), so it never sits in `.git/config` while third-party code (cargo builds, `make audit-*`, `cargo install cargo-audit`) runs in the same job.
- **`DEPENDABOT_ALERTS_TOKEN`** (Dependabot secret, not an Actions secret): a fine-grained token scoped to this repository with Dependabot alerts: read only. `dependabot-triage.yml` reads open alerts with it to decide whether a Dependabot PR carries a critical fix (`scripts/dependabot-triage.py`); the workflow token cannot read alerts, and runs started by Dependabot see only Dependabot secrets, so `GH_AUTOMATION_PAT` never reaches them.
- Signing secrets (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, the six `APPLE_*` secrets) stay at the repository level, unchanged, available to same-repo branch builds as before (never to forks or Dependabot).
- Immutable releases are enabled: once a release is published, its assets and tag are frozen (title, notes and flags stay editable, which is how `promote` rewrites the beta's notes). Tags matching `v*` cannot be moved or deleted.

## Creating a stable release

Preconditions, all checked by the workflow before it writes anything:

- The commit is in the history of `dev` and has a published beta (the Releases page or `gh release list` lists them). It does not have to be the latest beta; testers may have validated an earlier one.
- The commit is not older than the tip of the previous release line (`validate-promotion`).
- The line has no stable release yet.
- The Beta run that built that beta (the one whose `publish` job was not skipped; runs that ended with `skip=true` are ignored) has finished green, rig e2e included. A Beta run still in progress, or none found, fails the promotion at once; the workflow does not wait.
- `make audit` is clean (npm and cargo advisories without a valid exception).

Steps:

1. Check by hand what the e2e suite cannot cover, because it runs on an API key: sign in to Anthropic with a subscription (OAuth) and open the usage popover and confirm the plan windows are listed in order with values between 0 and 100.
2. Run "Run workflow" on `Release` with `dev` selected in "Use workflow from" (any other branch fails) and the commit SHA in `commit`.
3. A person from the promoter list approves the run in the `promotion` environment.
4. The workflow creates `release/0.M` at the commit, then the beta's `GitHub Release` loses `prerelease`, gains `make_latest`, and its notes are rewritten to the list of changes since the previous line (hotfixes of that line excluded). A `changelog/0.M` PR to `dev` is opened with the `CHANGELOG.md` section; merge it like any other PR.
5. File a Jira task for the landing "What's new" entry (EN and PL); update `install.mdx` on the landing to drop the macOS Intel row once this is the first stable of the cutover.

There is no bypass. If the rig is down or e2e is red, the stable waits. Do not create or push `release/0.M` by hand: the workflow creates it with `GH_AUTOMATION_PAT` and computes `M` itself. A hand-created branch publishes nothing (the push trigger ignores branch creation), but if it sits on another commit the promotion refuses until an admin removes it (see the recovery steps below).

**Red or missing e2e, or a Beta run that is not green**: open the Beta run that built the beta and use "Re-run failed jobs" until it is green, then run the promotion again. A Beta run in progress fails the promotion; run it again when that run finishes.

**No beta on the commit**: the beta build is still running (run the promotion again once it publishes), or the commit landed between two betas and never gets one. Pick a commit that has a beta, or run the `Beta` workflow ("Run workflow" on `dev`) and promote the new beta.

**Older than the previous release line's tip**: the new stable would be lower-versioned than the one it replaces. Promote a commit at or after the previous line's tip.

**A red audit**: fix with a bump PR to `dev`, let a new beta build, then promote the new beta's commit.

### Failure and resume

A rerun with the same `commit` continues from the first step whose effect is not there yet; each step checks that first. A rerun still needs a new approval in `promotion`.

| Step                                           | Writes                                         | State after a failure                                           | Rerun with the same commit                                                                        | Start over on another commit                                                       |
| ---------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Preconditions and audit                        | nothing                                        | unchanged                                                       | repeats the checks                                                                                | dispatch with the other commit                                                     |
| Notes range and release notes (computation)    | nothing                                        | unchanged                                                       | recomputes                                                                                        | dispatch with the other commit                                                     |
| Create `release/0.M`                           | the branch at the commit                       | no branch, or the branch at the commit without a stable release | a branch already at that commit is taken as its own and not created again; the run continues      | no branch yet: dispatch the other commit; branch exists: an admin deletes it first |
| Flip `prerelease`/`make_latest`, rewrite notes | the release flags and body                     | the beta is still a prerelease, or already stable               | continues if the flag was not flipped; once flipped, skips every precondition including the audit | impossible: the flip is the point of no return                                     |
| Changelog PR                                   | the `changelog/0.M` branch and the PR to `dev` | stable is out, the PR may be missing                            | force-pushes `changelog/0.M` and reuses the open PR, or opens one                                 | not applicable                                                                     |

- Starting over is possible only before the flip. An admin temporarily disables the `release-lines` ruleset (it forbids deleting `release/0.*` and has no bypass), deletes `release/0.M`, and enables the ruleset again; then the promotion is dispatched with another commit. A promotion that finds `release/0.M` at a different commit without a stable release refuses until this is done.
- The flip is the point of no return: undoing it is a downgrade for every installation that already updated. Go forward only (rerun to finish the changelog PR), and do not set the flag back: that is not part of the process, and it would offer stable users a downgrade.
- After the flip a rerun skips all preconditions, the audit included, because the stable is already out.

## Hotfixing a stable release

1. Branch from the tip of the highest `release/0.M`, fix the bug, open a PR against `release/0.M`. It goes through the same gate as a PR to `dev`.
2. On merge, the `hotfix` job runs `make audit` on the squashed commit — a red advisory blocks the publish exactly as it does for a promotion.
3. The audit passing, it tags `v0.M.Z`, builds, and publishes `0.M.Z` immediately — no prerelease stage, because the PR gate is already the bar for stable.
4. A `merge/release-0.M-into-dev` PR opens automatically, with the `CHANGELOG.md` section for `0.M.Z`, auto-merge on, assigned to whoever authored the hotfix. If it shows conflicts, resolve them by pushing to that PR's branch — never push directly to `release/0.M` (that is the next hotfix) and never resolve on the release branch.
5. A second hotfix to the same line may show the same conflict the first one already resolved, in its own backport PR; that is expected.

**A Dependabot security fix** is merged into `dev` like any other PR. When `dependabot-triage.yml` labels it `security` (alert scope `runtime` and CVSS at least 9 or EPSS percentile at least 0.95), its beta is a critical release and the fix also belongs on the highest release line: cherry-pick the squashed commit from `dev` onto a branch from `release/0.M` and open the hotfix PR from step 1. Every fixed advisory also gets a GitHub issue per manifest, with the scores and links to its alerts; nothing closes it on merge, so close it with the fix PR.

Only the highest `release/0.*` line takes hotfixes. `release/0.20` (the cutover base marker) never does.

## Beta

Nothing to operate: the `Beta` workflow runs at 00:17 UTC, Tuesday to Saturday, and builds the tip of `dev` when commits landed since the previous beta; a run on a tip that already has a beta ends green without building. To ship a beta at once, use "Run workflow" on the `Beta` workflow with `dev` selected (a dispatch from any other branch fails before tagging). A dispatch while a scheduled run is building waits in `concurrency: beta` (no cancellation). The notes of a beta list the PRs since the previous beta that `cliff.toml` keeps (`feat`, `fix`, `perf`, breaking changes, the `security` label); when none landed, the notes read "No user-facing changes since <previous beta>." so the release page does not fall back to the tagged commit's message. Commits between two betas never get a release of their own. A beta never blocks on an audit (an environmental advisory already blocked merges once before this process existed, SPEED-674 ticket 20); a stable promotion or hotfix does.

## Cutover steps (one-time, phase 2b)

These ran once, when this file replaced the release-please process (SPEED-674 ticket 17):

1. Phase 0 (admin, done 2026-10-07): the `release` environment's deployment branch policy extended to `dev` and `release/*` (`main` stayed until phase 5); `GH_AUTOMATION_PAT` issued; immutable releases turned on; `release/0.20` pushed at the `v0.20.0` commit as a base marker — before this workflow or any ruleset change touched `release/**`, so nothing built from it.
2. Phase 2a ([SPEED-734](https://speedwave.atlassian.net/browse/SPEED-734)): version-from-git landed on `dev`.
3. Phase 2b (this change, [SPEED-735](https://speedwave.atlassian.net/browse/SPEED-735)): `beta.yml`, `release.yml`, `build-publish.yml` and `cliff.toml` added; `desktop-release.yml`, the three `release-please*.yml` workflows, `backmerge.yml`, `merge-strategy-check.yml`, `dependabot-auto-rebase.yml` and their configs and scripts removed. Merging this PR is the cutover: the next merge to `dev` is the first beta of the new process, `0.21.0+N`.
4. Phase 5 (admin, right after 2b): classic `main` branch protection removed, `main` deleted (its tip, `v0.20.0`, is identical to the `release/0.20` marker), `RELEASE_TOKEN` deleted.
5. In parallel: phase 3 (the channel PRs above) and phase 1 (the `e2e` environment and merge-gate PRs above).
6. Phase 4, first stable of the new process: `release/0.21`, after phases 1 and 3 land, so the first stable already carries the channel switch and went through the full gate including rig e2e.

0.20.0 was the last release of the old process. A hotfix needed before the cutover went out as an emergency `0.20.1` through the old `main`-based process; `release/0.20` never receives a hotfix through this process.

## macOS Intel

The new process builds and publishes no `x86_64` artifact for macOS, on any channel — application or CLI. 0.20.0 remains the last release with an Intel build. Installed 0.19.0/0.20.0 on Intel keep running; auto-check logs an error and stays quiet, a manual check shows the raw `TargetsNotFound` error from the updater. This is accepted: no in-app messaging, no changelog entry, no farewell release. The installation page drops the Intel row without a note, starting with the first stable of the new process (until then `releases/latest` still points at 0.20.0, which has it).
