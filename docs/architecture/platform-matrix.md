# Platform Matrix

Speedwave supports macOS and Windows with platform-specific VM, container, and
OS integration strategies. Linux as a host platform was dropped in
[ADR-059](../adr/ADR-059-drop-linux-support.md).

## Overview

| OS      | VM              | Containers              | mcp-os                    | Installer |
| ------- | --------------- | ----------------------- | ------------------------- | --------- |
| macOS   | Lima + Apple VZ | nerdctl                 | AppleScript / EventKit    | .dmg      |
| Windows | WSL2 + Hyper-V  | nerdctl (wsl.exe proxy) | WinRT + mapi-rs (Outlook) | .exe      |

## macOS

- Lima manages the VM using Apple Virtualization Framework (same hypervisor as Docker Desktop 4.15+)
- Lima is bundled inside `.app/Contents/Resources/lima/` with `LIMA_HOME=~/.speedwave/lima` for isolation (see [ADR-021](../adr/ADR-021-bundled-dependencies-and-zero-install-strategy.md)). The bundled version is pinned by `.lima-version`; the nerdctl it ships must stay aligned with the Windows pin (see CLAUDE.md SSOT-alignment for nerdctl)
- **VM disk format is forward-only across the Lima 2.0→2.1 bump.** A VM created or migrated under Lima 2.1 will not boot under an older `limactl`, so rolling the Speedwave app back to a pre-bump version after the VM has migrated requires deleting and recreating the VM (Maintenance → reset, or remove `~/.speedwave/lima`). Existing `~/.speedwave-dev`/`~/.speedwave` VMs are migrated in place on first launch after the bump; containers are recreated from images already on disk, so no project state is lost.
- IDE lock files: Speedwave's bridge writes its lock on the host at `~/.speedwave/ide-bridge/<port>.lock` and bind-mounts that directory into the container as `~/.claude/ide/`. The container-side `~/.claude/ide/<port>.lock` is what an external IDE (VS Code / JetBrains) discovers to attach.
- **Corporate VPN compatibility:** Lima provides two networking interfaces inside the VM: `eth0` (Apple VZ NAT) and `lima0` (Lima usernet bridge). Only `eth0` inherits the macOS host's full routing table — every host VPN tunnel (IPSec, WireGuard, Tailscale) and the public Internet. The slirp-based `lima0` runs a user-mode TCP stack on the host and reliably reaches plain public destinations but silently times out on VPN-routed traffic. Lima's stock netplan sets `lima0` metric 100 (preferred) and `eth0` metric 200, so by default all egress goes through `lima0`. Speedwave's generated `lima.yaml` ships a `provision` block that drops a higher-priority netplan file (`/etc/netplan/99-speedwave-prefer-vznat.yaml`) overriding DHCP route metrics: `eth0` becomes metric 100, `lima0` becomes metric 300 with `use-routes: false` (kernel never re-adds `lima0` as default after DHCP renew). The override is declarative — no hard-coded IPs or MACs, no in-place edits to the lima-managed netplan file. Without this, services on corporate networks (custom LLM endpoints, internal Slack, self-hosted GitLab) are unreachable from inside the VM even when the host can reach them. Existing VMs missing the override trigger a one-time migration in `lima_vm_config_needs_update`. Tracking the upstream regression: [lima-vm/lima#2984](https://github.com/lima-vm/lima/issues/2984).
- **CloudStorage TCC:** Project directories under `~/Library/CloudStorage/` (OneDrive, Dropbox, Google Drive) and top-level home folders like `~/OneDrive…` are gated by the macOS Files-and-Folders Transparency Consent and Control (TCC) permission. When permission is missing, `read_dir` returns EPERM and Speedwave surfaces a dedicated `CloudStorageModal` (with a deep-link to System Settings → Privacy & Security → Files and Folders, plus a one-click Retry). Detection runs at all four project-mutation entry points (`add_project`, `start_containers`, `recreate_project_containers`, `restart_integration_containers`) plus defense-in-depth in `render_and_save_compose`. SSOT: `crates/speedwave-runtime/src/cloudstorage.rs`.

## Windows

- `wsl.exe -d Speedwave -- nerdctl ...` called from Tauri/Rust
- `windows-rs` (Microsoft-maintained) for WinRT API access
- `mapi-rs` (Microsoft-maintained) for Outlook mail/calendar
- Setup Wizard auto-installs WSL2, imports Ubuntu rootfs, and sets up nerdctl-full
- IDE lock files: Speedwave's bridge writes its lock on the host at `%USERPROFILE%\.speedwave\ide-bridge\<port>.lock` and bind-mounts that directory into the container as `~/.claude/ide/`. The container-side `~/.claude/ide/<port>.lock` is what an external IDE (VS Code / JetBrains) discovers to attach.
- **Corporate VPN compatibility:** WSL2's default NAT networking does not propagate the Windows host's VPN routes into the Linux distro — corporate-VPN-protected services are unreachable from inside WSL2 unless `networkingMode=mirrored` is enabled in `%USERPROFILE%\.wslconfig`. Speedwave's `ensure_wslconfig_vpn_compat()` (called from `init_vm_windows()` for fresh installs and from `main.rs` startup for upgrades) writes a merged `.wslconfig` that adds three keys to `[wsl2]`: `networkingMode=mirrored`, `dnsTunneling=true`, `autoProxy=true` (preserving any other user-defined keys). Mirrored mode requires Windows 11 22H2+; older builds silently ignore the unknown keys and continue using legacy NAT (VPN remains unreachable). For fresh installs the change is picked up automatically. For upgrades of an existing `Speedwave` distro, the new `.wslconfig` only takes effect after `wsl --shutdown` — Speedwave logs a warning instead of triggering the shutdown itself because `wsl --shutdown` restarts every WSL distro on the system, which would surprise users running unrelated WSL workloads. See [Microsoft docs — Mirrored mode networking](https://learn.microsoft.com/en-us/windows/wsl/networking#mirrored-mode-networking).
- **Nested virtualization:** WSL2 uses Hyper-V, which requires hardware virtualization. Running WSL2 inside a VM (VMware, VirtualBox, QEMU/KVM) is nested virtualization and may degrade I/O performance during container image builds. Speedwave applies a four-layer resilience strategy (see [ADR-032](../adr/ADR-032-nested-virtualization-resilience.md)): (1) `Containerfile.claude` uses `--force-unsafe-io` and `Acquire::Retries=3` to harden apt installs; (2) transient I/O errors trigger an automatic retry without a prune; (3) Speedwave detects the VM environment via `Get-CimInstance Win32_ComputerSystem` and shows a non-blocking warning in `speedwave check` and Desktop logs; (4) a bounded parallel worker pool limits I/O amplification during concurrent image builds.
- **Line endings:** `actions/checkout` on `windows-latest` defaults to `core.autocrlf=true`, which corrupts shell-script shebangs in the NSIS bundle (issue #603). `.gitattributes` forces LF repo-wide; `scripts/bundle-build-context.{sh,ps1}` strip residual CR from `*.sh` before the bundle is packed. The `runtime-windows` CI job re-clones with `core.autocrlf=true` and asserts no CRLF survives, so a missing/regressed `.gitattributes` fails CI before reaching the release pipeline.
- **Uninstall cleanup:** The NSIS uninstaller offers an opt-in cleanup prompt that, when accepted, unregisters the `Speedwave` WSL2 distro (`wsl --unregister Speedwave`) and removes `%USERPROFILE%\.speedwave`. Default for silent uninstalls (`/S`) is to preserve data. If `SPEEDWAVE_DATA_DIR` is set (ADR-031), only the WSL distro is removed and the user is told to remove the custom data directory manually. See [ADR-048](../adr/ADR-048-windows-uninstall-cleanup.md).
- **Update — orphan `node.exe` handling:** Host-side MCP workers (`mcp-os`, `oauth`) run as `node.exe` processes launched from the bundled `$INSTDIR\nodejs\node.exe`. Two layers prevent a stale worker from blocking the next installer with "Error opening file for writing": (1) a Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK` is attached to every worker at spawn (`host_mcp_process::job_object`), so a parent crash kills its children automatically; (2) the NSIS `NSIS_HOOK_PREINSTALL` hook kills `Speedwave.exe` and any `node.exe` workers whose `ExecutablePath.StartsWith($INSTDIR\nodejs\, OrdinalIgnoreCase)` — ordinal byte comparison, immune to wildcard metacharacters (`[`, `?`, `*`) in legal NTFS paths. The sweep is strictly scoped — `node.exe` instances from other locations (VS Code, nvm, user shells) are never touched. Layer (1) only protects upgrades from v0.11+ (the version that ships the Job Object); layer (2) covers upgrades from any prior version. See [ADR-048](../adr/ADR-048-windows-uninstall-cleanup.md) §"PRE-INSTALL orphan worker sweep" for the architectural rationale and TOCTOU known-limitation.
- **CLI on PATH:** `setup_wizard::link_cli()` copies `speedwave.exe` to `~/.speedwave/bin/` and adds the directory to `HKCU\Environment\Path` (PowerShell/CMD only — not the Speedwave WSL distro). The OAuth setup command shown in the Desktop UI is rendered in PowerShell syntax (`Set-Location 'C:\…'; speedwave`). See [ADR-016](../adr/ADR-016-cross-platform-cli-path.md).

## Cross-platform Rust gating

`speedwave-desktop` compiles for both supported platforms above. The local `make check-desktop-clippy` only exercises the host target, so Windows-only compile errors (typically `cfg(unix)`-gated imports referenced by cross-platform function signatures) must be caught by the `desktop-windows-check` job in `.github/workflows/test.yml`. See [contributing/development-setup.md → Cross-platform Rust gating](../contributing/development-setup.md#cross-platform-rust-gating) for the rules every PR touching gated code must follow.
