# Bundled Resources

Speedwave bundles a set of Claude Code resources that are synced into `~/.speedwave/claude-resources`, mounted read-only into the Claude container at `/speedwave/resources/`, and injected into `~/.claude/` by `entrypoint.sh` at container start. This document is the single reference for **what** is bundled, **how** it reaches the container, and **how** teams can override it.

## Resource Catalog

The **Editable in place?** column is about the user-scope copy in the container: symlinked resources point at the read-only mount, so they cannot be edited there (they auto-update with new Speedwave versions instead). Every resource is still **overridable** by the team at the project scope via the listed method — read-only-in-place does not mean un-overridable.

| Resource                     | Source path                       | Target in `~/.claude/`       | Mechanism                 | Editable in place?   | Override method                                                                |
| ---------------------------- | --------------------------------- | ---------------------------- | ------------------------- | -------------------- | ------------------------------------------------------------------------------ |
| `output-styles/Speedwave.md` | `claude-resources/output-styles/` | `output-styles/Speedwave.md` | symlink (file)[^1]        | No (read-only mount) | Project-level `.claude/output-styles/`                                         |
| `statusline.sh`              | `claude-resources/`               | `statusline.sh`              | symlink[^1]               | No (read-only mount) | Project-level `settings.json` with custom `statusLine.command`                 |
| `settings.json`              | `claude-resources/`               | `settings.json`              | copy (seed if absent)[^3] | Yes (writable copy)  | Edit in-session (`/effort`, `/model`) or project-level `.claude/settings.json` |
| `mcp-config.json`            | generated by entrypoint           | `mcp-config.json`            | generate (always)[^2]     | No (regenerated)     | Regenerated on every container start                                           |
| `CLAUDE.md`                  | `claude-resources/`               | `CLAUDE.md`                  | symlink[^1]               | No (read-only mount) | Project-level `.claude/CLAUDE.md` or `/workspace/CLAUDE.md`                    |
| `skills/`                    | `claude-resources/skills/`        | `skills/`                    | per-entry symlinks[^1]    | No (read-only mount) | Project-level `.claude/skills/` takes precedence                               |
| `commands/`\*                | `claude-resources/commands/`      | `commands/`                  | per-entry symlinks[^1]    | No (read-only mount) | Project-level `.claude/commands/` takes precedence                             |
| `agents/`\*                  | `claude-resources/agents/`        | `agents/`                    | per-entry symlinks[^1]    | No (read-only mount) | Project-level `.claude/agents/` takes precedence                               |
| `hooks/`\*                   | `claude-resources/hooks/`         | `hooks/`                     | per-entry symlinks[^1]    | No (read-only mount) | Project-level `.claude/hooks/` (hooks merge across scopes)                     |

**Per-entry symlinks** means `~/.claude/<type>/` is a real directory and each entry inside `claude-resources/<type>/` (a skill folder, a hook file, …) is symlinked individually into it. Top-level entries under `<type>/` are core resources and are linked unconditionally. Entries under the special `<type>/integrations/<config_key>/` subdirectory are integration-bound. MCP-service entries (e.g. `office`, `gitlab`) are linked only when `<config_key>` is in the `ENABLED_SERVICES` env var injected by `compose::apply_integrations_filter`. The four OS sub-services (`calendar`, `mail`, `notes`, `reminders`) live in the same directory but are gated differently — linked only when `os` is in `ENABLED_SERVICES` AND the sub-service is not in `DISABLED_OS_SERVICES`. The entrypoint owns a state file (`~/.claude/.speedwave-managed-links`) that tracks every link it created so the next run can clean them up when an integration is toggled off. **Generate (always)** means the file is regenerated on every start because it depends on runtime variables (never edit it manually). `mcp-config.json` is generated inline; `settings.json` is a writable copy (seeded only when absent); every other `~/.claude/` resource is symlinked from `claude-resources/`. (`~/.claude.json` is also generated inline, but it lives in `$HOME`, not under `~/.claude/`, and is not a bundled resource — see the entrypoint.)

\* `commands/`, `agents/`, and `hooks/` directories do not exist in `containers/claude-resources/` yet — the entrypoint logic is ready (`[ -d ... ]` guard) and will activate once they are populated. Symlinks are only created when the source directory exists.

## Bundled Skills

The `skills/` directory ships the `speedwave-code-review` orchestrator and its 13 specialized worker skills, plus the standalone web-authoring skills `speedwave-sitemap`, `speedwave-site-audit`, and `speedwave-product-showcase`. Every production Speedwave install exposes them inside the Claude container, with no per-project setup required.

| Skill                               | Purpose                                                                     |
| ----------------------------------- | --------------------------------------------------------------------------- |
| `speedwave-code-review`             | Orchestrator — runs the 13 workers in parallel and aggregates results       |
| `code-review-basic`                 | Project guidelines and style-guide compliance                               |
| `code-review-security-checker`      | Injection, auth bypass, crypto weaknesses, data exposure                    |
| `code-review-silent-failure-hunter` | Silent failures, inadequate error handling, inappropriate fallback behavior |
| `code-review-kiss-detector`         | Over-engineering and unnecessary complexity                                 |
| `code-review-yagni-detector`        | Speculative features, unused code, premature optimization                   |
| `code-review-duplication-detector`  | DRY violations and refactoring opportunities                                |
| `code-review-ssot-detector`         | Single-Source-of-Truth violations (scattered configs, constants)            |
| `code-review-solid-detector`        | SRP, OCP, LSP, ISP, DIP violations                                          |
| `code-review-type-design-analyzer`  | Type design, encapsulation, invariant expression                            |
| `code-review-comment-analyzer`      | Comment accuracy, completeness, long-term maintainability                   |
| `code-review-documentation-checker` | Code ↔ documentation synchronization                                        |
| `code-review-test-analyzer`         | Test coverage quality and critical gaps                                     |
| `code-review-simplifier`            | Clarity, consistency, and simplification opportunities                      |

These skills mirror the review workflow developers use on this repo via `.claude/skills/`. The two trees are maintained manually — when editing one copy, update the other (they are not auto-synced, and may drift, as the orchestrator currently does).

| Skill                        | Purpose                                                                                                                                                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `speedwave-sitemap`          | URL-inventory provider for other skills. Extracts an existing `sitemap.xml` (robots.txt + common paths, expanding indexes) or, failing that, crawls the site via Playwright. Returns JSON only — no analysis.                              |
| `speedwave-site-audit`       | Audits a site against a bundled best-practice checklist (`rules.json`) spanning 10 categories. Pairs with `speedwave-sitemap` for whole-site scope; always runs a final verifier pass. Reports pass/fail/skip with evidence — never fixes. |
| `speedwave-product-showcase` | Builds a self-contained, dependency-free animated "live product" demo (HTML + scoped CSS + one inline rAF script) recreating the real app UI for a landing page. Pins `model: opus` for UI fidelity.                                       |

`speedwave-sitemap` is a data source, not an auditor: it answers "what are the pages of this site?" for any skill that needs a page list. `speedwave-site-audit` is the consumer that closes the loop — it asks the user for scope (one URL or the whole sitemap) and categories, evaluates each page against the rules, and writes a verified report to `/workspace/.speedwave/site-audit/`. Both skills gate browser-dependent work on the `playwright` integration: 13 of the audit rules need a live browser (contrast, focus, Core Web Vitals, …) and are marked `skipped` when Playwright is off; the other 115 run via `WebFetch` (including DNS checks over DNS-over-HTTPS). When Playwright is disabled, both skills degrade rather than guess.

## Filesystem Layout

After `entrypoint.sh` completes, the container filesystem looks like this:

```
/home/speedwave/.claude/              ← user-level (Speedwave-controlled)
├── output-styles/
│   └── Speedwave.md → /speedwave/resources/output-styles/Speedwave.md  ← symlink (file)
├── statusline.sh    → /speedwave/resources/statusline.sh               ← symlink
├── settings.json                  ← writable copy, seeded from resources (Claude Code writes /effort, /model here)
├── CLAUDE.md        → /speedwave/resources/CLAUDE.md                   ← symlink
├── mcp-config.json                   ← generated (MCP hub endpoint)
├── .speedwave-managed-links          ← state file: paths the entrypoint owns (one per line)
├── skills/                           ← real dir of per-entry symlinks
│   ├── code-review-basic   → /speedwave/resources/skills/code-review-basic   ← always linked
│   ├── code-review-…       → …                                                ← always linked
│   └── office              → /speedwave/resources/skills/integrations/office  ← gated by ENABLED_SERVICES
├── commands/                         ← real dir, empty until a plugin or project adds entries
├── agents/                           ← real dir, empty until a plugin or project adds entries
├── hooks/                            ← real dir, empty until a plugin or project adds entries
└── ide/                              ← read-only mount (IDE Bridge lock files)

~/.claude.json                        ← generated by entrypoint (trust dialog pre-accepted for /workspace; onboarding flag when logged in)

/workspace/.claude/                   ← project-level (optional, team-committed via git — Speedwave never creates this)
├── agents/
├── commands/
├── skills/
├── settings.json
└── CLAUDE.md
```

The volume mounts that produce this layout are defined in `compose.template.yml`:

```yaml
volumes:
  - ${CLAUDE_HOME}:/home/speedwave:rw # persistent home
  - ${PROJECT_DIR}:/workspace # project directory
  - ${RESOURCES_DIR}:/speedwave/resources:ro # bundled resources (read-only)
  - ${IDE_LOCK_DIR}:/home/speedwave/.claude/ide:ro # IDE Bridge lock files (read-only)
```

## Bundle Reconcile Lifecycle

The desktop bundle ships `build-context/containers/claude-resources/` plus a generated `bundle-manifest.json`. On app startup, the backend compares the installed `bundle_id` with `~/.speedwave/bundle-state.json`.

When the bundle changed, the desktop app:

1. Validates the bundled `claude-resources`
2. Atomically syncs them into `~/.speedwave/claude-resources`
3. Rebuilds built-in images for the current `bundle_id`
4. Recreates previously running projects if the update flow stored them in `pending_running_projects`

This means compose always mounts the stable host path `~/.speedwave/claude-resources`, but the content of that directory is managed by the startup reconcile rather than read directly from the installed app bundle on every container start.

## Bundle Asset Gate

Desktop packaging now treats the staged Tauri resources as a validated runtime contract, not a best-effort copy step. Before `cargo tauri build` runs, the desktop build verifies:

- bundled `build-context/` and `mcp-os/` trees exist and are non-empty
- the platform runtime is present (`node`, CLI, Lima or nerdctl/WSL assets)
- macOS bundles include `reminders-cli`, `calendar-cli`, `mail-cli`, and `notes-cli`

The gate (`scripts/verify-bundled-assets.sh`) is a filesystem presence/shape check — file exists, non-empty, and (for binaries) executable. It does not verify file contents, signatures, or that `tauri.<platform>.conf.json` declares each resource (that SSOT alignment is enforced separately).

This closes the failure mode where a release could build successfully even though a runtime helper was missing from the final app bundle.

## Scope Hierarchy

Claude Code has five settings scopes, highest precedence first: **Managed** (`/etc/claude-code/managed-settings.json`, unoverridable) → **CLI flags** → **Local** (`.claude/settings.local.json`) → **Project** (`.claude/settings.json`) → **User** (`~/.claude/settings.json`). Speedwave only uses two:

| Scope   | Container path             | Source                | Priority |
| ------- | -------------------------- | --------------------- | -------- |
| Project | `/workspace/.claude/`      | Team's git repository | Higher   |
| User    | `/home/speedwave/.claude/` | Speedwave bundle      | Lower    |

Speedwave's bundled resources sit at the User scope (the lowest), so teams can override any of them by committing a same-named file to `.claude/` in their repo. Hooks are an exception — hook arrays merge across scopes (both user-level and project-level hooks fire).

**Note on `settings.json`:** It is the one bundled file Claude Code writes at runtime — `/effort` and `/model` save the user's choice to `~/.claude/settings.json`. So it is a **writable copy**, not a symlink (a symlink into the read-only mount made those writes fail with `EROFS`). The entrypoint seeds the copy from the bundle only when it is missing, so the user's choice persists across restarts. Teams that want shared, pinned settings can still commit a `.claude/settings.json` at the project level — project scope takes precedence over user.

See [ADR-022](../adr/ADR-022-bundled-claude-resources-and-project-coexistence.md) for the full design rationale and rejected alternatives.

## Plugin Resources

When plugins are installed (`SPEEDWAVE_PLUGINS` env variable), `entrypoint.sh` symlinks entries from each plugin into the user-level directories. Only each plugin's `claude-resources/` subdirectory is mounted — at `/speedwave/plugins/<plugin-slug>/` (host source: `~/.speedwave/plugins/<plugin-slug>/claude-resources/`):

```
/speedwave/plugins/<plugin-slug>/        ← container path (host: ~/.speedwave/plugins/<plugin-slug>/claude-resources/)
├── commands/    ← per-entry symlinks into ~/.claude/commands/
├── agents/      ← per-entry symlinks into ~/.claude/agents/
├── skills/      ← per-entry symlinks into ~/.claude/skills/ (a skill folder is one dir symlink)
└── hooks/       ← per-entry symlinks into ~/.claude/hooks/
```

Plugin resources use the same per-entry symlink mechanism as core resources (since `~/.claude/<type>/` is always a real directory of per-entry symlinks). The entrypoint records each plugin link in the same `.speedwave-managed-links` state file, so disabling a plugin on the next run removes its links. Plugin resources support all four resource types: `commands`, `agents`, `skills`, and `hooks`. Plugins run inside the container (sandboxed with `cap_drop: ALL`, `no-new-privileges`, `read_only`), so plugin hooks have the same trust boundary as plugin skills and commands.

See [ADR-015](../adr/ADR-015-plugin-system.md) for the plugin system design.

## Persistence Across Container Restarts

The Claude container's home directory (`/home/speedwave/`) is backed by a persistent volume (`${CLAUDE_HOME}:rw`). This affects resource behavior on restart:

- **Symlinked file resources** (`statusline.sh`, `CLAUDE.md`, `output-styles/Speedwave.md`) — re-created on every start via `ln -sf`. They point to the read-only mount, so their content updates automatically when Speedwave ships new versions. Teams override via project-level `.claude/` (ADR-022 scope precedence).
- **`settings.json` (writable copy)** — seeded from the bundle only when absent, so a user's in-session `/effort` / `/model` choice persists across restarts. A stale symlink from an older build is replaced with a copy on the next start. Trade-off: unlike the symlinks above, a new Speedwave default does not reach a user who already has a copy (they keep their own).
- **Per-entry symlinked directory resources** (`skills/`, `commands/`, `agents/`, `hooks/`) — `~/.claude/<type>/` is a real directory; each entry inside is symlinked individually. Top-level entries are linked unconditionally; MCP-service `integrations/<config_key>/` entries are linked when their config key is in `ENABLED_SERVICES`; OS sub-services (`calendar`, `mail`, `notes`, `reminders`) are linked when `os` is enabled and the sub-service is not in `DISABLED_OS_SERVICES`. Plugin entries are layered on top via the same mechanism.
- **Managed-links state file** (`.speedwave-managed-links`) — the entrypoint records every link it creates so the next run can drop links that are no longer wanted (integration toggled off, plugin disabled). User-placed files inside `~/.claude/<type>/` are never tracked and never touched.
- **Always-regenerated resources** (`mcp-config.json`) — overwritten on every container start, because the MCP hub port may change between runs. It is generated inline by `entrypoint.sh` (as is `~/.claude.json`, which lives in `$HOME` and is not a bundled resource).
- **Host-side resource sync** (`~/.speedwave/claude-resources`) — re-synced whenever the installed `bundle_id` changes (a SHA-256 over app version + the build-context hash of `containers/` + `mcp-servers/` + `claude_resources_hash` + the Claude Code version), or when built-in images are detected missing. So bumping the Claude version or editing `mcp-servers/` also triggers a re-sync, not just a `claude-resources` edit. The sync stages into a temp dir then renames, so the compose mount never points at a partially copied tree.

## Adding a New Bundled Resource

Checklist for contributors:

1. Add the file or directory to `containers/claude-resources/`:
   - **Core resource** — place it at `containers/claude-resources/<type>/<name>/`. It will be linked into `~/.claude/<type>/<name>` unconditionally.
   - **Per-integration resource** — place it at `containers/claude-resources/<type>/integrations/<config_key>/` (see [Integrations Guide](../guides/integrations.md#per-integration-claude-resources)). `<config_key>` must match an entry in `TOGGLEABLE_MCP_SERVICES` or `TOGGLEABLE_OS_SERVICES`, or be `host_exec`. An MCP-service resource links when its key is in `ENABLED_SERVICES`; an OS sub-service (`calendar`, `mail`, `notes`, `reminders`) links when `os` is enabled and the sub-service is not in `DISABLED_OS_SERVICES`.
   - **New top-level file** (e.g. a sibling of `statusline.sh`) — add the symlink line in `containers/entrypoint.sh` using `ln -sf`.
2. Add BATS tests in `_tests/entrypoint/` covering the new resource:
   - For per-entry symlinks: assert `[ -d ~/.claude/<type> ]`, `[ ! -L ~/.claude/<type> ]`, `[ -L ~/.claude/<type>/<entry> ]`, and verify the symlink target with `readlink`.
   - For integration-gated resources: include the on/off toggle in the test — symlink present when enabled, absent when disabled.
3. Update the [Resource Catalog](#resource-catalog) table in this document
4. Run `make test-entrypoint` to verify
