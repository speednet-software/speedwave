# ADR-060: Host-Side OAuth Refresh Worker (`oauth`)

**Status:** Accepted

**Date:** 2026-05-15

## Context

SharePoint is currently the **only** worker in Speedwave mounting `/tokens:rw`. The container refreshes its own OAuth access token by reading `refresh_token` from `/tokens` and writing the new pair back (`mcp-servers/sharepoint/src/token-manager.ts`). ADR-009 documented this as the single accepted exception to the `:ro` token-mount invariant in CLAUDE.md / `.claude/rules/security.md`. The exception was enforced as a dedicated security rule `SharepointTokenMountMode` (`crates/speedwave-runtime/src/compose.rs:1461`, `:2390`).

The exception now creates two concrete problems:

1. **Scope creep.** A planned scope bump from `Sites.Read.All` to `Sites.Manage.All` (required for `createList` per Microsoft Graph delegated-permissions docs[^create-list]) extends the blast radius of a SharePoint-worker compromise. If the worker is compromised while `:rw` to `/tokens`, an attacker can not only exfiltrate the refresh token but also rewrite it to one they control, persisting access across user revokes that target the original token.
2. **Bug-class exposure.** Every code path inside the SharePoint worker that reads from `/tokens` is a potential refresh-token leak via accidental logging or error messages. There is no systemic gate — only convention. The recent audit of the worker turned up zero such bugs **today**, but the file is right there in the mount.

A parallel concern: SharePoint stores `client_id` and `tenant_id` (the application identity for the device-code flow[^device-code]) in the same `/tokens` directory the worker reads. While `client_id` is not strictly secret for a public client[^public-client] and `tenant_id` is visible in OAuth metadata anyway, mounting them inside the worker has no operational value once token refresh moves out of the worker — only the refresh path needs them, and that path is what this ADR moves.

The audit also confirmed a worker → external-worker communication path that the codebase already uses successfully: `host_exec` (ADR-054) is a per-project host-side MCP worker spawned by the Rust supervisor (`crates/speedwave-runtime/src/host_exec_process.rs`); its URL is injected into the hub via `WORKER_HOST_EXEC_URL`. `mcp-os` (ADR-013) follows the same shape but is global. The mechanics — `127.0.0.1` bind, gateway DNS aliases, bearer token in a `/secrets/<name>-auth-token:ro` mount, dynamic port via stdout JSON handshake — are stable infrastructure proven by both predecessors.

## Decision

Add **`oauth`**: a **per-project** host-side MCP worker (Node.js, no container) that holds OAuth `refresh_token`, `client_id`, `tenant_id` for each OAuth-using service in that project. It exposes two tools to authenticated callers — `refresh` and `forget` — and is **not visible to Claude** (it is never enumerated to the model, never appears in `ENABLED_SERVICES`, never appears in the hub's tool registry). Callers are **other workers in the same project** (today: SharePoint).

Communication is **worker → oauth worker direct**, bypassing the hub. The hub stays "zero tokens" per the invariant in CLAUDE.md. Bearer authentication is **per-service** — each OAuth-consuming worker gets its own bearer token (`/secrets/oauth-auth-token-<service>:ro`); the oauth worker maps incoming bearer → service via a host-side map and refuses to refresh a service the caller doesn't own. The `refresh` / `forget` tools therefore take **no `service` parameter from the model**.

`refresh_token`, IdP-specific application identity (Microsoft: `client_id`, `tenant_id` — nested under `providerData` post-OAuthProvider refactor), `scopes`, `expiresAt`, `lastRefreshAt`, `grantedScopes` live in a new host-only directory `~/.speedwave/oauth/<project>/<service>.json` (mode 0o600), created with parent mode 0o700 by the Rust supervisor (`oauth_process.rs`). This directory is **never mounted into any worker container**. The oauth worker reads/writes it as a normal host filesystem path via `writeRestrictedSecret` (PR1). The exact on-disk shape is documented in §"Implementation notes".

The SharePoint container's `/tokens` mount becomes `:ro` like every other worker. After PR3 it contains only `access_token`, `site_id`, `base_path`.

### Why per-project (not global)

The audit of `host_exec` (ADR-054 §"Implementation") established the per-project model: state is per-project, project context lives in the worker's URL (compose injects this project's URL into this project's workers), there is no model-controlled `project` parameter to forge. OAuth state is per-project for the same reason — different projects can connect different SharePoint sites with different identities. A global oauth worker would need a `project` parameter, which a compromised caller could forge.

### Why direct worker → oauth (not via hub)

Two reasons:

1. **Hub zero-tokens invariant.** The hub is the only MCP server Claude sees (CLAUDE.md "Key Architecture"). It must hold no service tokens. Making the hub a refresh proxy means giving it a bearer to the oauth worker — a regression.
2. **Hub direction.** `callWorker()` (`mcp-servers/hub/src/http-bridge.ts:640`) is one-way: hub → worker. Reversing it to worker → hub adds an architectural complication for no gain.

### Why public-client / device-code only

The existing SharePoint flow is device code (`desktop/src-tauri/src/oauth_cmd.rs:194`), which is a public-client flow per Microsoft Identity docs[^device-code]. No `client_secret` exists in the codebase today. This ADR does not introduce one — confidential-client migration is a separate effort (would require Azure AD app re-registration, a different consent UI, and credential rotation). The oauth worker's Microsoft provider takes `client_id` + `refresh_token` and POSTs to the v2 token endpoint[^token-endpoint]; the response is the same shape device code already returns.

## Consequences

### Positive

- `SharepointTokenMountMode` rule and the `:rw` exception are removed in PR3. The token-mount invariant ("`/tokens` is `:ro` everywhere") is restored systemically rather than by convention.
- `client_id` and `tenant_id` are no longer mounted into the SharePoint container.
- Future OAuth integrations (Google Workspace, Atlassian Cloud, etc.) reuse the same shape: widen the `ProviderId` discriminated union in `mcp-servers/oauth/src/providers/types.ts`, register a provider module under `providers/<id>.ts` with its own `requiredFields` list, declare the service in the oauth descriptor, compose injects `WORKER_OAUTH_URL` + per-service bearer. IdP-specific identity nests under `providerData` in oauth.json (driven by `FieldStorage::OAuthStateProviderData` in `consts.rs`). No new `:rw` exception per provider; no Rust edits to add a new provider's identity field — just one descriptor entry.

### Negative

- **Live compromise is not closed.** See the threat-model table. An RCE in the SharePoint worker still buys an attacker an indefinite series of access tokens (rate-limited and audit-logged). This ADR is explicit about that limit; users counting on isolation should not interpret the change as "compromise expires after 1h" — it does not. The architectural gain is the offline-exfiltration class of attack and the code-path-bug class, not the live-compromise class.
- **One more host-side worker per active project.** A user with N projects open in Speedwave has N additional Node processes running (one oauth worker per project). The supervisor spawns lazily (only if the project enables an OAuth-using integration); inactive projects pay nothing.
- **Bearer-map state.** A new file `~/.speedwave/oauth/<project>/.bearer-map.json` ties bearer tokens to services. It is mode 0o600 and only the oauth worker reads it, but losing or corrupting it strands the project's OAuth refresh path until the user reauthorizes the affected service.

### Neutral

- No new permission scopes are requested at the OAuth level. Scope changes (e.g., the `Sites.Manage.All` bump in PR3) are orthogonal to this ADR — they happen in `crates/speedwave-runtime/src/consts.rs::SHAREPOINT_OAUTH_SCOPES`, which is the SSOT consulted by both the device-code flow (`oauth_cmd.rs`) and the oauth worker.
- The entire `~/.speedwave/oauth/<project>/` tree (state json, bearer-map, per-consumer bearer files, supervisor port/pid/auth-token files, audit log + rotated copy) is enumerated by `fs_security::collect_security_paths` and therefore validated by `SecurityCheck::FileSecurityViolation`. A regression to world-readable mode bits on any of those files trips the check on the next `speedwave check` run and is auto-fixed by `ensure_data_dir_permissions` on container startup.

## Implementation notes

- Service id: **`oauth`** (no `mcp-` prefix, matching the convention of existing host-side workers `os` and `host_exec`).
- Env var: `WORKER_OAUTH_URL` (PR0 normalization ensures kebab-case service ids work; here the id has no hyphens, so normalization is a no-op).
- Bearer mount: `/secrets/oauth-auth-token-<service>:ro` — per service, NOT a shared bearer. This is intentional: a generic `/secrets/oauth-auth-token:ro` would let a compromised caller forge any `service` param.
- Process supervisor: new `crates/speedwave-runtime/src/oauth_process.rs`, parallel to `host_exec_process.rs`, sharing `crate::fs_perms::write_restricted_file` (PR1) for token / port / pid files.
- Spawn lifecycle: spawned by Tauri (`desktop/src-tauri/src/main.rs`) and CLI (`crates/speedwave-cli/src/run.rs`) on project switch / `compose_up` when at least one OAuth-using service is enabled in the project.
- `oauth.json` schema: `{ provider, providerData: { /* IdP-specific keys */ }, scopes, grantedScopes, refreshToken, expiresAt, lastRefreshAt }`. For Microsoft, `providerData` holds `{ clientId, tenantId }`. The dispatcher (`mcp-servers/oauth/src/tools.ts`) reads `provider` from this file and routes the refresh through `providers/registry.ts` — adding a new IdP is one new file under `providers/<id>.ts` plus one entry in the registry. Written atomically via `writeRestrictedSecret` from PR1.
- Audit log: `~/.speedwave/oauth/<project>/audit.log`, append-only, mode 0o600. Entries: ISO-8601 timestamp, project, service, action (`refresh` | `forget`), outcome (`ok` | `error:<code>`). No token contents in the log. Rotated to `audit.log.1` past ~1 MiB; one historical copy retained.

### Audit log error codes (post-OAuthProvider refactor)

The dispatcher emits the following `error:<code>` values into `audit.log`. Operators and `speedwave check` use them as stable strings — renaming requires a deprecation pass.

| Code               | Surface                                                | Meaning                                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `malformed_state`  | `loadOAuthState` threw (post-OAuthProvider validation) | The on-disk `oauth/<project>/<service>.json` does not match the documented shape: not an object, missing `provider`, `providerData` not a plain object, non-string `refreshToken` / `expiresAt`, etc.           |
| `no_state`         | File absent                                            | No oauth.json on disk for the caller's service — initial flow never completed or `forget` ran.                                                                                                                  |
| `unknown_provider` | `getProvider` returned `undefined`                     | The stored `provider` id is not in `providers/registry.ts`. Indicates a downgraded build or a hand-edited file. Same fix as `malformed_state`: re-authorize.                                                    |
| `missing_field`    | Pre-call validation against `provider.requiredFields`  | A field the IdP requires (Microsoft: `clientId` / `tenantId`) is missing or empty in `providerData`. Surfaces before the HTTP call so a misshapen request never reaches the IdP.                                |
| `rate_limited`     | `refresh` called while access token still valid        | Defense against refresh-in-a-loop after worker compromise. See the live-compromise row of the threat-model table.                                                                                               |
| `scope_mismatch`   | Microsoft 200 with strict subset of granted scopes     | The user granted fewer scopes than requested OR consent was withdrawn at the IdP. UI surfaces the re-authorize banner.                                                                                          |
| `invalid_grant`    | Microsoft 400 / `invalid_grant` without scope wording  | Refresh token revoked or expired. Same UI as `scope_mismatch` — re-authorize.                                                                                                                                   |
| `http`             | Any other non-2xx Microsoft response                   | Includes 5xx, throttling, and unknown error codes. Free-text `error_description` is redacted to its `AADSTSnnnnn` trace prefix to avoid leaking UPN / tenant / Conditional Access policy names post-compromise. |
| `network`          | `fetch` rejected (DNS, TCP, TLS, timeout abort)        | No HTTP response was received. Includes the 30s timeout firing on a hung Microsoft endpoint.                                                                                                                    |
| `malformed`        | Response was not valid JSON or required fields missing | Indicates either a network mid-stream truncation or an upstream incident. Transient retry-by-rate-limit is appropriate.                                                                                         |
| `unlink_failed`    | `forget` couldn't delete state / access-token file     | EPERM / EBUSY when removing `oauth/<project>/<service>.json` or the worker-mounted access-token file. The tool now returns an error to the caller instead of falsely reporting `forgotten`.                     |

## Addendum: `providerData` self-heal migration

Files written before the OAuthProvider refactor (or by a credential-form save whose device-code flow never completed) can carry `clientId` / `tenantId` at the **top level** of `oauth/<project>/<service>.json` instead of under `providerData`. Three independent consumers then break together: the worker's strict `assertOAuthState` throws `malformed_state`; `is_service_configured` reads the identity as empty and reports the card "Not Configured"; and because the re-authorise banner was gated on `configured`, the only recovery affordances were hidden or disabled — the user was stuck.

Resolution (two parts, both shape-only — **secrets are never fabricated, moved between services, or synthesized**; a refresh token that is absent stays absent):

- **Startup migration** (`crates/speedwave-runtime/src/oauth_state_migration.rs`, run from CLI and Desktop right after `legacy_token_cleanup`). Best-effort, idempotent, per-file: if `providerData` is not already a plain object and a top-level identity string exists, it is nested under `providerData` and the top-level copy removed; every other key is preserved verbatim; the file is rewritten 0o600. Unparseable / non-object / no-recoverable-identity files are left untouched. The in-process repair path (Desktop `merge_oauth_state_json` calls the same `oauth_state_migration::ensure_provider_data_object`) performs the same lift so a credential re-save heals rather than orphans — one shared implementation, not a mirror.
- **Banner ungating.** `oauth_action_required` is now computed regardless of `configured`, so a file too damaged to migrate (e.g. no refresh token) still surfaces the "Re-authorise SharePoint" banner. A fresh, never-configured service has no file and shows no banner.
- **`offline_access` coverage.** The desktop coverage check (`detect_scope_mismatch_or_stale`) excludes `offline_access` from the required set: it is an OIDC control scope that Microsoft never echoes in the token-response `scope` field[^offline-access], so it never appears in `grantedScopes`. Requiring it produced a false-positive banner for fully-working integrations. This mirrors the worker's own check in `mcp-servers/oauth/src/providers/microsoft.ts`; the request-scope SSOT (`consts::SHAREPOINT_OAUTH_SCOPES`) still includes `offline_access` because it must be **requested** to obtain a refresh token.

This **refines** the "user must re-authorize manually / no silent data migration" stance above: that stance governs _secrets_ (the v1 worker-mounted `refresh_token` / `client_id` / `tenant_id` files are still deleted, never migrated). The self-heal touches only the structural placement of the non-secret IdP identity in the host-side state file, converging it onto the schema in §"Implementation notes".
