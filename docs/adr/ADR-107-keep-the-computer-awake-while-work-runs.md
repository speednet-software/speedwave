# ADR-107: Keep the computer out of idle sleep while a recording, an offline pass or a chat turn runs

> **Status:** Accepted (2026-11-02).
> **Context:** SPEED-917. Speedwave did not stop the computer from sleeping when it sat idle. A meeting left to record, a long offline transcription pass or a chat turn the user walked away from ran until the operating system's idle timer put the machine to sleep. The recording then had a gap that the capture driver fills with silence after wake (SPEED-474), the offline pass stopped halfway, the chat turn ended with "Your computer went to sleep mid-response" (SPEED-571), and on wake the VM clock drifted (SPEED-459). Nothing in `crates/`, `desktop/src-tauri/` or `native/` called a sleep API; users worked around it with `caffeinate` in a terminal.

## Decision

1. **One idle-sleep assertion for the Desktop process, counted by holders.** `desktop/src-tauri/src/keep_awake.rs` keeps one operating-system assertion and a count of holders (`keep_awake::hold` returns an RAII `Hold`). The first holder takes the assertion; when the last one drops, it is released after `RELEASE_GRACE` (30 s) unless new work started in the meantime (a generation counter decides, `Keeper::release_if_idle`). The grace covers the step from a stopped recording to its offline pass and the step from one chat turn to the next queued one, so the assertion is not dropped and taken again between them. The assertion has one fixed name, "Speedwave is recording, transcribing or running a chat" (`ASSERTION_NAME`); which work took it goes only to the Desktop log.
2. **Only idle sleep, never the display, never a child process.** macOS takes `PreventUserIdleSystemSleep` through `IOPMAssertionCreateWithName` and releases it with `IOPMAssertionRelease` (`keep_awake/macos.rs`, crate `objc2-io-kit` with its `pwr_mgt` feature, and `objc2-core-foundation` with `CFString` for the type and name strings)[^1][^2][^3]. The header says the display may still dim and sleep under it, and that the system still sleeps for lid close, the Apple menu and low battery[^1]. Windows creates a power request with a simple reason string (`PowerCreateRequest`, `REASON_CONTEXT` with `POWER_REQUEST_CONTEXT_SIMPLE_STRING`) and sets `PowerRequestSystemRequired`, which keeps the system running "instead of entering sleep after a period of user inactivity"; the drop clears it with `PowerClearRequest` and closes the handle (`keep_awake/win.rs`, `windows-sys` features `Win32_System_Power` and `Win32_System_SystemServices`, plus `Win32_UI_WindowsAndMessaging` for the notification flags of decision 6)[^4][^5][^6][^7]. Neither path starts `caffeinate` or any other process.
3. **Three holders: the capture, the offline pass and the chat turn.**
   - The capture driver holds from the start of `TranscriptDriver::run` to its return (`transcription_cmd.rs::spawn_driver`), so a recording holds from Start or Resume to Pause or Stop.
   - Every offline pass holds from the moment it knows it will run to its end (`transcription_cmd.rs::spawn_offline_pass`, after `wait_while_recording` and before `take_offline_pass_turn`). `stop_transcription`, `transcribe_transcript` and `import_transcription` all start the pass there, so a stopped recording, a re-transcription and an imported file are covered by one hold, and the pass lets go on Done, Failed, Postponed, Deleted and Superseded alike. A pass queued behind another one holds while it waits.
   - A chat turn holds from the message written to Claude Code's stdin to the end of that turn (`chat.rs::AwaitedResult`). `send_message_with_emit` takes the hold before it writes and drops it again when the write fails; the reader takes it for a queued message after `drain_queued_message`. `AwaitedResult::observe` releases it on a `Result` or a turn-ending `Error` (`turn_end_event`), and `release_turn` releases it at the end of the stdout stream and in `ChatSession::stop`, which may leave a hung reader behind. An `AskUserQuestion` keeps its turn open until the user answers, but nothing runs while it waits, so the reader releases the hold when it shows the question and `submit_question_answer` takes it again before it writes the answer. An idle session that waits for its first message holds nothing.
4. **A user switch, on by default, that applies at once.** `ui.keep_awake` in the user config (`config.rs::SpeedwaveUserConfig::keep_awake_enabled`, unset means on, user-only like `ui.notifications`) is shown as "Keep the computer awake" in a Settings section "Sleep" that is not behind beta, because chat is not. The section says what still puts the computer to sleep. `set_keep_awake` stores the value and applies it to the work already running: off releases the assertion at once, on takes it when something holds. The value is read from disk once, at the first hold.
5. **Released on exit before the slow teardown.** `reconcile::run_exit_cleanup` calls `keep_awake::release_on_exit` before it starts the container teardown thread, which can run for minutes. The assertion lives in a static that no exit path drops, and the signal handler ends the app with `std::process::exit`, which runs no `Drop` at all. Windows closes every kernel object of a process that ends, a crash included[^8]. Apple documents no such statement for an assertion whose process died; a `kill -9` measurement found it released (see Known limitations).
6. **On Windows a wake renews the request.** Measured on a Windows 11 (26100) laptop with Modern Standby on battery (SPEED-917, 2026-11-04): about 5 minutes after the sleep timeout the system froze the running work although the request was still reported as set, and a few minutes later, at a standby transition Kernel-Power logs as "Austerity Battery Drain Budget Exceeded", it cleared the request. The work was frozen, not cancelled, and continued once the user woke the machine, but the request stayed cleared, so the work after the wake ran unprotected and stalled again at the next sleep timeout. `keep_awake::install` therefore subscribes to `GUID_SESSION_DISPLAY_STATUS` through `PowerSettingRegisterNotification` with a callback (`keep_awake/win.rs::watch_display`), the display state of the app's session that Microsoft names for interactive user-mode applications[^11][^12]. Every time the display turns on while work holds the computer and the switch is on, `Keeper::renew` creates a new request and only then drops the old one; with nothing running, with the switch off or after exit it takes nothing. The display turning on means the user is back, so a renewal never extends the battery limit while nobody is at the machine. Windows calls the callback with the current state right after the registration[^11], which renews nothing at startup because nothing holds yet. macOS has no such limit and no such hook.
7. **No indicator beyond Settings.** The recording bar and the tray tooltip stay as they were: the assertion exists only while work the user started runs, and it is gone 30 s after that work ends.

## Why

- A count over one assertion is the only shape in which three independent kinds of work, several chat tabs among them, share one operating-system object without one holder releasing what another still needs.
- `PreventUserIdleSystemSleep` is the assertion Apple names for "prevents the system from sleeping automatically due to a lack of user activity"[^1]. The older `PreventSystemSleep` is marked in the same header "Deprecated in 10.9. This assertion is not supported in any OS X releases."[^1]
- A Windows power request carries a reason that `powercfg /requests` lists next to the process, which Microsoft asks for in its best practices[^4], and it is a process object, so it does not matter which thread takes or releases it. The request is created by whichever thread takes the first hold (a blocking-pool task, a Tauri command, the chat reader) and closed on the `keep-awake-release` thread, in `set_keep_awake` or in `run_exit_cleanup`.
- Default on: the user started the recording, the pass or the turn and expects it to finish. Turning it off is one switch away.

## Known limitations

- The lid, the Apple menu, the power button, Sleep from the Start menu and a low battery still put the computer to sleep on both systems[^1][^4]. Windows on Modern Standby terminates system-required requests on battery 5 minutes after the sleep timeout expired[^4]. Settings says both. Decision 6 renews the request once the user is back; between the battery limit and that wake, the work stays frozen.
- Apple does not document whether an assertion is released when its process crashes. Measured on a Mac (SPEED-917, 2026-11-04): after `kill -9` of Desktop during a recording, `pmset -g assertions` listed no Speedwave assertion.
- macOS's `coreaudiod` may already hold an assertion for a process with open audio input; whether it does for Speedwave's capture helper is unmeasured. The capture holds its own either way, since the offline pass and the chat turn need one.
- The native modules compile only in the macOS and Windows CI lanes; `keep_awake::tests::the_operating_system_grants_and_takes_back_the_assertion` takes and releases a real assertion there. The effect on an idle machine is checked by hand (`pmset -g assertions`, `powercfg /requests`).

## Rejected alternatives

- **The `keepawake` crate.** Its Windows backend calls `SetThreadExecutionState`[^9], which takes flags and no reason text[^10], so nothing would name Speedwave in `powercfg /requests`, and it has no count over several holders.
- **`caffeinate -i` as a child process.** macOS only, a process to supervise and kill on every exit path.
- **One switch per kind of work, or one assertion name per kind.** More state for the same effect on the idle timer; the log names the work.
- **A "keeps the computer awake" note on the recording bar or the tray.** Decision 7.
