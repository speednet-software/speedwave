# ADR-108: Access policy in the hub and the read-only mode

> **Status:** Accepted
> **Date:** 2026-11-06
> **Context:** SPEED-598 (SPEED-309, SPEED-58, SPEED-67). A user had no way to take away the agent's right to change state in external services, other than disabling an integration and losing its reads. This ADR records the access policy module in the hub, the global read-only mode that is its first rule, and the contract that carries the rules from the host to the hub. The per-integration mode (SPEED-58) and the git push block (SPEED-67) are implemented.

## Context

- Every restriction on writes had its own place and shape: `ENABLED_SERVICES` in the hub, the Jira project allowlist in the Atlassian worker, the `confirm_*` flags the model sets itself, the repository allowlist in the proxy (ADR-106 amendment).
- Every tool call, including the calls inside `execute_code`, passes through one function, `buildExecutorWrappers` in `mcp-servers/hub/src/tool-registry.ts`. The hub exposes only the two meta-tools `execute_code` and `search_tools` (`mcp-servers/hub/src/meta-tools.ts`). Before this change that function made no decision. The hub knew the category of a tool from its MCP annotations (`executor.ts::deriveAuditCategory`) and used it only for the audit line. ADR-105 states that the hub has no confirmation policy.
- Calls reach a worker only through `http-bridge.ts::callWorker`. Its production callers are the bridges `buildServiceBridge` creates, and `executor.ts::createToolWrappers` is the only place that hands those bridges to the sandbox, each one wrapped by `buildExecutorWrappers`. `search_tools` calls no worker. The `create*Bridge` exports of `http-bridge.ts` have no production caller. There is no second path from a model-written call to a worker.
- `policy.json` is the PII contract (ADR-082, ADR-083, ADR-084). The hub loads it through `@speedwave/policy-engine` (`mcp-servers/hub/src/policy.ts`, `POLICY_FILE`, fail-closed), the proxy and Desktop read the same document, and `crates/pii-engine` owns it. The host writes it into the per-project policy directory that the hub mounts at `/policy:ro`, with the tokenization `key` beside it.
- Organization policy is carried by `ManagedConfig` (`crates/speedwave-runtime/src/managed_config.rs`), where the presence of a key is the lock (`.claude/rules/managed-policy-config.md`).

## Decision

1. **One access policy module in the hub.** `mcp-servers/hub/src/access-policy.ts` has one decision function, `decideAccess(rules, metadata)`, that returns allow, or deny with a reason and a teaching message. It is pure over the composed rules and the tool's registry metadata. `buildExecutorWrappers` asks it for every tool of a service when it builds the wrappers of an `execute_code` run, so direct calls and calls inside `execute_code` are one path. A denied tool gets a wrapper that rejects before the bridge, so the worker is never called. The decision has two outcomes, allow and deny. A `confirm` outcome is not built; it belongs to SPEED-513.
2. **Read-only passes only what is annotated read-only.** In a read-only service a tool passes when `annotations.readOnlyHint === true`, and every other tool is denied. A tool without annotations is denied. A custom MCP server (a `custom-*` service) is judged by its annotations like any other integration. Read-only guards the external services and the host, not the project workspace, so in Speedwave `readOnlyHint: true` means that the tool changes nothing outside `/workspace`. A tool that only writes files into the workspace (a download, a generated document) carries `WORKSPACE_WRITE_ANNOTATIONS` from `@speedwave/mcp-shared` (`readOnlyHint: true`) and passes. The constant has the same values as `READ_ONLY_ANNOTATIONS` and is a separate object, so the workers' metadata tests tell the two classes apart by identity (`toBe`). This is narrower than the MCP definition, "does not modify its environment"[^1]. Narrowing it changes no other consumer, because the hub is the only MCP server Claude sees and the only reader of worker annotations, and it matches the boundary of the mode, which already leaves the agent's own writes to the workspace outside (section "Boundaries of the mode").
3. **Annotation trust.** The MCP schema describes tool annotations as hints that are not guaranteed to describe the tool's behavior, and tells clients not to base tool use decisions on annotations from untrusted servers[^1]. The hub trusts the annotations of the built-in workers, of plugins signed by Speednet (ADR-015, ADR-051) and of custom MCP servers. The mode protects against mistakes of the agent, not against the person who configures the project: whoever adds a custom MCP server knows what it does, so its tools are not blocked by default and its annotations decide like those of any integration. No annotation counts as blocked, so a new or badly described plugin does not pass by default. Every worker the hub enforces on has a test that lists each tool as reading, writing only into the workspace, or changing and asserts `readOnlyHint` accordingly (`metadata.test.ts` of slack, sharepoint, redmine, atlassian and office), so a new tool must be classified and a wrong annotation fails the build.
4. **Rules live in `access.json`.** The host writes the composed rules to `access.json` in the policy directory, next to `policy.json` and `key`, and the hub reads them as a sibling of `POLICY_FILE` (no new environment variable). The file has this shape:

   ```json
   { "version": 1, "default": "full", "services": { "slack": "read_only" } }
   ```

   `version` is 1; `default` and the values of `services` are `full` or `read_only`; `services` keys are service ids (`^[a-z][a-z0-9-]{0,63}$`, at most 256); the file is at most 65536 bytes and has no other keys. A service not named in `services` has the `default` mode. An absent file means every service is `full`, and the host writes no file while every service is `full`. The file is the composed result: the hub does no precedence logic. The format (serialization, parse and validation) is defined once in the leaf crate `crates/access-policy` (`to_access_file`, `parse_access_file`), without IO; the runtime does the file IO (`access_policy.rs::write_access_config_in`, which also removes a stale file). The hub validates the file in TypeScript with the same rules (`mcp-servers/hub/src/access-config.ts`, `parseAccessRules`), and both sides run the cases of `crates/access-policy/tests/fixtures/access-file-cases.json`. A file that is present but cannot be read or fails validation (unknown mode, unknown key, bad service id, wrong version, too large) makes the loader throw, so the hub refuses to start through the same startup failure path as an invalid `policy.json`; the host refuses to write an invalid policy. Why a separate file: `policy.json` is the PII contract and its parser, `crates/pii-engine`, the WASM binding and the proxy handle PII only; access is a different domain, so it has its own file and its own crate, and the PII engine does not know it.

5. **Precedence is computed in Rust.** `speedwave_access_policy::compose_access_policy` (leaf crate `crates/access-policy`, next to the types and the validation; the runtime feeds it the inputs) takes the MDM switch, the project's global switch and a map of per-service modes, and the most restrictive mode wins: MDM over the global mode over the service mode. Entries equal to the resulting default are left out. The map comes from the `access` field of the integration entries of the project (decision 6). `access_policy.rs::write_access_config_in` writes the file, and omits it while every service is `full`. `POLICY_DIGEST` (`pii_policy.rs::policy_state_digest_in`) is computed from `policy.json` and `access.json` together, so a change of the access mode recreates the hub.
6. **Configuration.** The global switch is `read_only` in the project's entry of the user config (absent means off, `ProjectUserEntry::read_only`). The organization forces it with `access.read_only: true` in `managed-config.json`: the key's presence locks the switch on in Desktop, a malformed key is a hard error like every other managed key, and `read_only: false` is rejected because presence is the lock and the file has no way to force the mode off. The save path refuses a change while MDM locks the mode (`access_policy::set_read_only`), so the lock is not only a greyed control. No managed mount is added, so `SecurityCheck` has no new rule.
7. **Denial is a teaching error.** The message names the mode, the service and the tool, says why the tool is blocked (it changes data, or it has no read-only annotation), says that reads from the service still work, and says that a person can turn the mode off in Speedwave Desktop. The hub tells a per-service entry (`rules.services[service]`) from the global default: `compose_access_policy` writes a per-service entry only for a service stricter than the default, so a read-only default never produces one. A per-service mode points to the Always read-only switch of the integration. A global one points to Settings, Read-only integrations, and also to the integration's switch if it is on, because `compose_access_policy` drops a per-service entry equal to a read-only default, so the hub cannot tell whether the integration would stay read-only once the project switch is off. An `os` tool is named by its category as Desktop shows it (Reminders, Calendar, Mail, Notes). The global text adds that the organization may enforce the mode, because the hub cannot tell an organization lock from the project switch; the per-service text omits it, because a lock sets the default and so leaves no per-service entry. The text names the service at most twice and stays under the 500 characters `executeCode` keeps of an error, also for a 64-character service id.
8. **Audit.** A denied call writes the existing audit line with `outcome=denied reason=read-only` and keeps its READ, WRITE or DELETE category, which still comes from the annotations. The in-memory entry carries `outcome` and `reason`. A call that passed writes the line as before.
9. **`search_tools` keeps blocked tools visible.** A blocked tool stays in the results with `blocked: "read-only"`. While any enabled service is read-only, the result starts with a `notice` field of one sentence that names the read-only services, so a model does not plan steps that will fail.
10. **Applying a change.** The Desktop save asks for a restart of the project (`ProjectStateService.requestRestartFor`), the same path a change of the PII policy takes: the restart re-renders `access.json`, `policy.json` and `proxy.json` and recreates every container, so the hub and the proxy start on the new rules and the chat resumes its conversation afterwards. An earlier version recreated only the `mcp-hub` and `proxy` services in place: a message sent during that restart hung on the proxy coming back, and on macOS the proxy, started right after the re-render, read `policy.json` through virtiofs before the renamed file was visible and refused every request with 503 until it was recreated. The runtime now also leaves `policy.json`, `access.json` and `proxy.json` untouched when their content did not change (`fs_perms::write_restricted_file_atomic_if_changed`), and the proxy reads its policy and key again for a few seconds while they are not found (`containers/proxy/src/pii.rs`).
11. **Default off, no beta flag.** Without the switch nothing changes: `access.json` is absent and every service is `full`.
12. **Integration mode in the config.** Every integration entry of the project in the user config (`IntegrationConfig`, `GitForgeIntegrationConfig`, and so the OS services and the plugin entries) has an optional `access` field, `"full"` or `"read_only"`, absent meaning full and written only while read-only (`AccessMode` from the `speedwave-access-policy` crate, one type for all). `IntegrationsConfig::access_modes` turns the entries into the per-service map of `compose_access_policy`, keyed by the name the hub knows the service by: the config key of a built-in integration, the `service_id` of a plugin, and `os-<key>` for a macOS native service (`os-reminders`, `os-calendar`, `os-mail`, `os-notes`). The hub has one `os` service, so `access-policy.ts` resolves an `os` tool through the `os-<category>` entry of its `osCategory` (a tool without a category takes read-only when any `os-<category>` entry is read-only) and lists the enabled read-only OS sub-services in the `search_tools` notice. Only the user's own entry sets a mode: the repository's `.speedwave.json` shares the type but its `access` values are not read. Toggling an integration on or off keeps its mode (`set_service`, `set_plugin_enabled` merge `enabled` into the stored entry). A plugin without annotations loses all its tools in Read-only, as in the global mode.
13. **Desktop control.** The panel of each integration (the expanded card of a built-in integration, a row under an enabled OS integration, the detail screen of an installed MCP plugin) has one switch, "Always read-only" (`shared/integration-access`, the `app-toggle` of Settings). Off stores `full` and means the integration follows the project setting; on stores `read_only`. The switch names the rule, not the result, because the result also depends on the project switch (the most restrictive wins). A status line under it says the result: "Currently full. Follows the project setting.", "Currently read-only.", or, when the project switch decides it, "Currently read-only, from the project setting in Settings" with a link to the switch (`/settings#section-access`), or "set by your organization for all integrations" under MDM. The switch stays editable while the project switch is on, also under MDM, because turning it on can only narrow access. A change calls `set_integration_access_mode`, which stores the mode, and then asks for a restart of the project like the global switch (decision 10). An OS integration row has its own on/off switch, so the access switch sits in a second line that opens under the row while the integration is enabled, never as a second switch in the same line. Two earlier versions were dropped: one showed the result in a Full / Read-only control, disabled it while the project switch was on and explained it in a banner on the Integrations and Plugins screens, which hid the stored choice and made the panels jump back to Full when the switch was turned off; the next named the rule with two pills ("Follow project", "Always read-only"), which read as status tags rather than a choice. The lists show no access state: on Integrations the switch is in the expanded card, on Plugins in the plugin's detail screen. Read-only blocks every Playwright tool that opens a page or acts on it (`@playwright/mcp` 0.0.70 gives `readOnlyHint` only to its `readOnly` and `assertion` tools[^3]), so the browser does not work in this mode: the help line of the Playwright panel says so.
14. **Desktop wording.** The global switch is the section "Read-only integrations" in the project settings, with the switch "All integrations and plugins read-only". The title names the feature and its scope, so a reader scanning Settings finds it without opening it; an earlier "Integration access" did not say what was set there, and "Integration access (read-only)" was rejected because a heading in parentheses reads as a current state, which is false while the switch is off. Under the title, as in the other sections, one paragraph says what the section is for: read-only stops the agent from changing anything in the connected services, and it can still read from them. The line under the switch names its scope. The details sit in a folded box, "What read-only blocks and allows": what is blocked in every integration, macOS integration and installed plugin, that the agent keeps working in the project (editing files, running commands, saving downloads and documents into the project folder), so that the switch does not read as a mode of the whole agent, what the switch does not cover, and how to limit one integration only. The switch stays in Settings and not on the Integrations screen, because plugins have their own screen and the switch covers them too.

## Boundaries of the mode

Read-only mode limits what the hub's tools may do. It does not cover:

- the native tools of Claude Code in the container (Write, Edit, Bash, WebFetch);
- internet access from the container, which a separate offline mode limits (SPEED-967);
- a credential put into the container by hand (a personal access token in a remote URL, a credential helper in `$HOME`), which goes through the open egress; SPEED-967 closes it;
- changes to the local repository (commit, checkout, reset). A read-only `.git`, the first shape of SPEED-67, is rejected: it breaks fetch and worktrees whose `.git` is a file, and it blocks only changes that can be undone;
- confirmation of a single write, which is SPEED-513;
- the repository scope of the GitHub and GitLab MCP tools, which is SPEED-961;
- an MDM rule per integration; MDM forces only the global mode.

MCP servers outside the hub are not governed by this policy. Claude Code starts with `--mcp-config` and `--strict-mcp-config` (`crates/speedwave-runtime/src/defaults.rs`, guarded by tests in `defaults.rs` and `config.rs`), and the flag makes it use only the servers from `--mcp-config` and ignore all other MCP configurations[^2]. Whether MCP servers of Claude Code plugins and claude.ai connectors still load under the flag is not checked and not guarded: the mode protects against mistakes of the agent, not against a person who can change the configuration, and such servers are added by that person.

## Integration mode and git push

Integration mode (SPEED-58, decisions 12 and 13) and the push block (SPEED-67) are implemented:

- Every integration has one mode, Full or Read-only. The user sets it in the integration's panel in Desktop (the "Always read-only" switch); it enters `compose_access_policy` as an entry of the per-service map.
- For GitHub and GitLab, Read-only blocks the write tools in the hub and also the push through the proxy to that forge. The push token is the integration's token (ADR-106), and without the integration there is no push through Speedwave. A separate push switch is rejected: the combinations "tools yes, push no" and the reverse have no use case.
- The proxy gets the mode in the forge's entry of `proxy.json`: `access` is `"read_only"` or absent (full). `compose/proxy.rs::git_forges_in` takes it from the composed `AccessPolicy` (`mode_of("github")`, `mode_of("gitlab")`), so MDM, the project switch and the integration mode meet in `compose_access_policy` and nowhere else.
- For a read-only forge `containers/proxy/src/git.rs` rejects both `git-receive-pack` requests (the ref discovery `GET` and the `POST`) with 403 and a `text/plain` body that git shows as `remote:` lines. The body says the integration is in Read-only mode, that fetch and pull still work, and where a person turns the mode off (Desktop, Settings, Read-only integrations, and the integration's Always read-only switch if it is on; when the organization enforces it, only the organization can). No request goes upstream. `git-upload-pack` is unchanged.
- The check runs before the repository allowlist of ADR-106 for `git-receive-pack`: adding a repository to the list would not make the push work, so the refusal names the mode and not the list. Upload-pack requests keep the allowlist.
- A denied push is one row in `audit-proxy.jsonl` with `layer: "git"`, `status: 403`, `outcome: "denied"` and `reason: "read-only"`, the same two fields the hub writes. Other git rows carry neither field.
- A save of the project switch or of an integration's mode in Desktop asks for a restart of the project; every container is recreated and the chat resumes its conversation, so background work of the running Claude Code process ends.

## Consequences

- Hub-side enforcement depends on the annotations of the workers. A worker that annotates a write tool as read-only passes it in read-only mode. The built-in workers are reviewed in this repository; the annotations of Speedwave plugins are checked before release (the figma plugin has an annotation test).
- A plugin without annotations loses all its tools in read-only mode.
- A tool that writes only into the workspace passes in read-only mode: `downloadFile` of Slack and SharePoint and every Office tool. The audit labels such a call READ, because the label comes from `readOnlyHint` (`executor.ts::deriveAuditCategory`). A plugin that follows the MCP definition and marks such a tool `readOnlyHint: false` gets it blocked, which errs on the safe side; the plugin contract states the Speedwave meaning (`.claude/rules/plugins.md`).
- The hub's `os` service has one name, so the OS integrations are separated by the `osCategory` of the tool; a tool of an OS service without a category is read-only when any `os-<category>` entry is read-only, and full otherwise.
- The decision is taken when the wrappers of an `execute_code` run are built, from the rules loaded at hub start. A change takes effect through the hub restart, not in a running hub.
- A tool call made while the hub restarts fails, and the agent can retry it once the hub is back.
- The hub reads a second file from the policy directory. The contract is documented in `.claude/rules/mcp-servers.md` and `.claude/rules/managed-policy-config.md`.
- The service id and size rules exist twice, in Rust and in TypeScript, and the shared fixture cases are what keeps them equal.

## Alternatives rejected

- **A condition and an environment variable in the wrapper.** SPEED-513, SPEED-961 and SPEED-968 would each add a condition in the same place, and the precedence of MDM, the global mode and the integration mode would diverge between the host and the hub.
- **Precedence in the hub.** The host has to know the effective mode for the UI and for the proxy; two implementations would drift.
- **Blocking every tool of a `custom-*` service in read-only mode.** The source of its annotations is not signed by Speednet, but the person who adds the server chose it, and the mode does not guard against that person.

## To be verified on a running instance

These checks need `make dev DEV_INSTANCE=speed-598` run by a person; they are not verified by the code or the tests of this change.

- A write through an integration is denied with the teaching message, a read passes, and the denied call appears in the audit.
- A push to a GitHub or GitLab remote while the integration is Read-only prints the `remote:` lines and the audit row appears; `git fetch` works; turning the mode off lets the next push through.
- Turning on Always read-only in the panel of one integration (a built-in one, a macOS one, a plugin) restarts the project, blocks that integration's writes and leaves the others, and the Always read-only switch stays editable once the global mode is on while its status line says that the project setting decides.
