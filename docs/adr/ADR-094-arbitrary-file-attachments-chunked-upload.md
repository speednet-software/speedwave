# ADR-094: Arbitrary file attachments streamed to disk through chunked raw-body IPC

> **Status:** Accepted (2026-10-16). Amends ADR-065.
> **Context:** ADR-065 made pasted and dropped images reach Claude as files under `<project>/.speedwave/pastes/` referenced by an `@/workspace/...` text token. The composer accepted only JPEG, PNG, GIF and WebP. Each went through the renderer's image pipeline (resampled when over the model's native long edge or 2 MB, a GIF saved as it is, `desktop/src/src/app/services/image-preprocessor.service.ts`) and one `save_pasted_image` invoke whose payload was a JSON array of numbers (`Array.from(bytes)`), under a 3 MB renderer cap and a 10 MB host cap (`desktop/src-tauri/src/paste_cmd.rs`). SPEED-801 asks for any file type, without the whole file in memory and without a size cap that has no reason once the bytes only need to land on disk.

## Decision

1. **Every file type is accepted by paste and drop.** `isSupportedImageType` (`image-preprocessor.service.ts`, over `IMAGE_MEDIA_TYPES` in `models/chat.ts`) routes the four raster types through the unchanged ADR-065 image pipeline; everything else, SVG and TIFF included, goes through the file pipeline below.
2. **Non-image files are streamed, never buffered.** `FileAttachmentService.stage` (`desktop/src/src/app/services/file-attachment.service.ts`) opens an upload with `begin_paste_upload`, which returns its id, reads the `File` in `UPLOAD_CHUNK_BYTES` (8 MiB) slices through `Blob.slice().arrayBuffer()`[^1][^2] and sends each slice as the raw body of an `append_paste_upload` invoke, addressed by an `x-upload-id` request header, then calls `finish_paste_upload`. Tauri's `invoke` sends an `ArrayBuffer` or `Uint8Array` argument as an `application/octet-stream` body and forwards request headers to the command[^3]; the command reads them through `tauri::ipc::Request` (`body()` as `InvokeBody::Raw`, `headers()`)[^4]. Once a custom-protocol request has failed, Tauri's IPC script sends every later invoke of the page through `postMessage`[^9], which serializes a `Uint8Array` as a JSON array of numbers[^10], so `append_paste_upload` also accepts `InvokeBody::Json` holding such an array. The renderer holds one slice at a time, and each upload holds one request body at a time while it appends the slice to `<name>.part` under the pastes directory (`paste_cmd.rs::append_chunk`). wry delivers custom-protocol request bodies on macOS (`HTTPBody`, or `HTTPBodyStream` when WebKit streams it) and on Windows (`Content()` as an `IStream`)[^5][^6].
3. **The append writes on the blocking pool, under a lock of its own upload.** A sync command marked `#[tauri::command(async)]` runs inside the future Tauri spawns on its async runtime[^7][^8], so a file write there would hold a runtime worker that every async command shares. `append_paste_upload` is therefore an `async fn` (an async command with a borrowed argument such as `Request<'_>` returns a `Result`[^7]) that copies the body and runs the write through `spawn_blocking`, like `save_pasted_image`, `begin`, `finish` and `discard`. Every open upload sits behind its own mutex; the registry of open uploads is locked only to look one up, insert it or remove it, so one upload's write never waits for another's, and a discard waits only for the write of the upload it ends.
4. **Bounds that remain.** There is no total size cap. The size the renderer declares at `begin` is the upper bound of the appends (one byte over discards the upload and its part file), and `finish` refuses an upload short of its declared size. There is no cap on one append on the Rust side: wry hands the handler the body already read into one buffer[^5][^6], so a cap checked there would bound nothing; the renderer's `UPLOAD_CHUNK_BYTES` is what bounds one request. A failed write, `ENOSPC` included, is the text the command rejects with, and the composer shows it under the file's name (`ComposerAttachments.add`). The image path keeps its 3 MB and 10 MB caps, because those bytes reach the model inline through Claude Code's `Read` tool, where Anthropic's per-image limits apply (ADR-065).
5. **On-disk name.** Images keep `paste-<ts>-<seq>.<ext>`. Files get `paste-<ts>-<seq>-<stem>.<ext>` (`paste_cmd.rs::generate_upload_filename`): path components are dropped (`../x` becomes `x`), the stem keeps Unicode alphanumerics plus `_` and `.`, maps every other run of characters to one `-`, and is cut at 64 characters; the extension keeps up to 16 lowercase ASCII alphanumerics, else it is folded into the stem. No whitespace survives, so the `@path` token stays one word. The chat shows the original name, for images too.
6. **Cancellation.** Each `ComposerAttachments` record owns an `AbortController`; `remove`, `clear` and `dispose` abort it, the upload loop stops at the next slice and calls `discard_paste`, which deletes the part file. The part file is created new and owner-only (`PinnedDir::create_new_file`) and made durable under its final name only by `PinnedDir::persist`: fsync (`F_FULLFSYNC` with its fallback on macOS, `fs_perms::fsync_file_durable`), close, rename, directory fsync.
7. **Display.** The state tree gains `MessageBlock::File { filename, size_bytes }` (`crates/speedwave-runtime/src/stream/state_tree.rs`), mirrored in `models/state-tree.ts` and rendered as a pill (`user-message-file`); the composer strip renders a name-and-size pill (`composer-attachment-file`) instead of a thumbnail. `FileDropDirective` emits the files and the directory names of one drop together (`dropped`, read through `webkitGetAsEntry`[^11]), and a paste goes through the same split (`partitionItems`), so a directory is reported by name instead of producing an empty file named after it, and that notice stays next to the errors of the same drop's files.
8. **The wire is unchanged.** A file reaches Claude as the same `@/workspace/.speedwave/pastes/<name>` text token ADR-065 uses for images; `chat.rs`, `send_message` and the one-slot queue are untouched.
9. **Writes never follow a link the container planted.** The claude container mounts the project read-write, so it can replace `.speedwave` or `pastes` with a symlink or a junction to a directory outside the project, which the Desktop process would follow. Every writer of the pastes directory (the image save, the upload and the CLI `paste_watcher`, which writes `clip.png`) opens it through `speedwave_runtime::pastes::open_pastes_dir`, which uses `speedwave_runtime::pinned_dir::PinnedDir::open_beneath`. It refuses a component that is a symlink, a junction or not a directory, and it keeps the directory held: on Unix every later create, rename and removal resolves its name against the held directory descriptor with `O_NOFOLLOW`[^12], so swapping the path after the check changes nothing; on Windows each component stays open without `FILE_SHARE_DELETE`, and since delete access is what both delete and rename operations need[^13], no component can be renamed or replaced while the files are written. Files are created with `O_CREAT | O_EXCL` (`create_new` on Windows), so a link planted at the file name itself fails the create instead of being written through.
10. **Unsent attachments do not stay behind.** `save_pasted_image` and `finish_paste_upload` return a `paste_id` (the upload's id for a file) that the backend keeps, with the file's name, for the latest 256 attachments. Removing an attachment from the composer, closing its tab or switching project before it is sent calls `discard_paste` with that id, never with a path from the renderer, and the file is deleted. Each `begin_paste_upload` deletes `.part` files nothing has written for an hour (an upload the app did not live to end), and `open_pastes_dir` gives the directory a `.gitignore` of `*`, so pasted files stay out of the user's repository. A sent attachment stays where Claude read it.
11. **The proxy accepts request bodies up to the Messages API limit.** An attached file reaches the model as the result of Claude Code's `Read` tool, which every later request of the conversation carries, and the proxy read `/v1/messages` through axum's `Bytes` extractor with its 2 MB default limit[^14], so a large result failed the turn with a 413 before it reached the provider. `containers/proxy/src/main.rs::build_router` sets `DefaultBodyLimit` to 32 MiB, the size limit of the Messages and Token Counting endpoints[^15].

## Why

- Native drag-drop stays off (`dragDropEnabled: false` in `desktop/src-tauri/tauri.conf.json`, SPEED-636), so a drop reaches the app only as HTML5 `File` objects without host paths; copying through IPC is the only route, and slicing is what keeps a multi-gigabyte file out of memory on both sides.
- Raw-body IPC is the transport Tauri's own `plugin:fs|write_file` uses[^16], so the body path is exercised on every platform Speedwave ships on; a JSON array of numbers would multiply the bytes crossing the bridge by about four.
- A declared-size bound is enough on the Rust side: the renderer is first-party code behind the webview CSP, the file lands under the project's own pastes directory, pinned against links, with a generated name and owner-only permissions, and a real disk-full is reported, not prevented.

## Known limitations

- A sent attachment stays in `<project>/.speedwave/pastes/` until the user deletes it; the backend tracks only the latest 256 attachments, so an older unsent one is no longer discarded.
- A `.part` file left by a crash or a quit stays until the next `begin_paste_upload` of that project, at least an hour later.
- On Windows the share-mode pin holds where the container's file operations go through Windows itself, as for a project on a Windows drive. Whether the Plan 9 server that serves a project inside the WSL file system (`\\wsl.localhost`) honours it, and whether it presents a Linux symlink to Windows as a reparse point, has not been verified; for such a project the check at open may be all the protection there is.

## Rejected alternatives

- **Re-enabling Tauri native drag-drop for host paths.** Would let Rust copy or link the file with zero bytes through IPC, but it swallows the drop before the webview sees it[^17], so the composer's HTML5 drop handling and its visual feedback stop working (SPEED-636), and paste still has no path.
- **One invoke with the whole file as a raw body.** Avoids the chunk loop but puts the full file in the renderer (`arrayBuffer()`) and in one Rust request; it reintroduces the memory ceiling the ticket removes.
- **A custom URI scheme with `fetch(..., { body: file })`.** The webview would stream the blob, but wry hands the handler the body as one buffer[^5][^6], so the Rust side still holds the whole file, and it adds a second IPC channel next to `invoke`.
- **A global size cap (for example 2 GiB).** No bound follows from the design; a cap would only turn a working copy into a refusal. Disk space is the real limit and it reports itself.
- **A per-append size cap on the Rust side.** The body is in memory by the time the command can measure it, so the cap bounds nothing, and it ties the renderer's slice size to a second constant that a change on one side breaks.
- **Checking the directory with `symlink_metadata` and then writing by path.** The container can swap the directory for a link between the check and the write; only a held directory closes that gap.
- **Keeping the original filename verbatim.** Spaces break the `@path` token and path separators would be a traversal; the sanitized stem keeps the name readable for the model without either.
