# ADR-100: Native OS notifications for chat-session events

> **Status:** Accepted (2026-10-26).
> **Context:** SPEED-522 asks Desktop to tell the user, through the operating system's own notifications, when a chat session finished its task, waits for the user's input, or stopped with an error, while the window is in the background. A click raises the window and opens that session; Settings carries a master switch, one switch per event, and a readable permission state that names where the user unblocks notifications. Before this change Desktop showed nothing outside its window (no notification plugin, no capability, no native code for it).

## Decision

1. **Delivery, permission and clicks go through each platform's native notification API, called from Rust.** macOS uses `UNUserNotificationCenter` through `objc2-user-notifications` (`desktop/src-tauri/src/notifications/macos.rs`), the same `objc2`/`block2` stack `mic_permission_cmd.rs` uses for the microphone. Windows uses WinRT `ToastNotification` through the `windows` crate (`desktop/src-tauri/src/notifications/win.rs`). One API per platform answers what may be shown, shows it, and reports the click, so the permission the Settings row shows is the permission the delivery runs under.
2. **The backend decides.** The stdout reader of each chat session (`chat.rs::ChatSession::start_with_retry`) hands an event to `notifications::notify_session_event`: `AwaitingInput` when it emits an `AskUserQuestion` (the only point where a session waits for the user; every other `can_use_tool` request is answered by `build_tool_permission_response`), `TurnFinished` for a `Result` that no queued message follows (`drain_queued_message` returned false), and `SessionError` for an `Error { turn_ended: true }` or a stream that ended while a result was awaited. The notification runs on a blocking task, so the reader never waits on it, and turning notifications off changes nothing in how a session runs.
3. **Shown only while the main window is in the background.** `notifications::is_background` counts the window as background when it is hidden (closed to the tray), minimized, or not focused. The switches live in the user config (`ui.notifications`, `config.rs::NotificationPrefsConfig`); an unset switch resolves to on (`SpeedwaveUserConfig::notification_prefs`), and the key is user-only like `ui.beta_enabled`. They are read from disk for each event, so a change in Settings applies to the next event. Notifications ship behind beta: while `ui.beta_enabled` is off, `notifications::decide` withholds every event before it reads the permission (so no prompt appears) and Settings shows no Notifications section.
4. **The notification carries the project name and a fixed sentence, never session text.** `notifications::content` gives the title (the project) and one of three bodies. On macOS the request carries `UNNotificationSound.defaultSound` in `sound`, the property that names the sound played on delivery[^10]; without it the banner arrived silent in the manual test on 2026-10-26. A notification's text is shown outside the app and kept by the notification center, so no message text, question, error detail or tool output goes into it.
5. **Permission is read natively and asked for once.** On macOS the first event that would notify, or the "Ask for access" button, calls `requestAuthorization` when the status is `notDetermined`, one request at a time (events that arrive while the prompt is open wait for its answer and re-read the status); Settings reads the status without prompting (`getNotificationSettings`). `classify_authorization_status` maps `authorized`, `provisional` and `ephemeral` to granted, `denied` to denied, and any unknown future value to denied. On Windows there is no prompt: `ToastNotifier.Setting` says whether the app, the user, a group policy or the manifest blocks toasts[^4], and `SHQueryUserNotificationState` reports a full-screen app, presentation settings or the first hour after a new sign-in, which Settings shows as "holds notifications back" (`classify_toast_setting`)[^5]. A notification is shown only while the permission is granted or held back; a denied one is logged at info and Settings says where to change it, with a button that opens the macOS Notifications pane or `ms-settings:notifications`. Settings re-reads the state when the window regains focus (`window_focused`).
6. **A click raises the window and opens the tab.** Each shown notification gets a fresh UUID mapped to `{project, tab_id}` in a bounded list (`TrackedNotifications`, 64 entries). On a click the backend shows, focuses and unminimizes the main window and emits `notification_activated` with the target; `NotificationsService` (started by `ShellComponent`) navigates to `/chat` and calls `ChatStateService.activateTab` when the target's project is still the active one. A project switch ends every session of the old project (`project_cmd.rs::clear_chat_sessions`), so a click on a notification from another project than the active one only raises the window and leaves the view as it is.
7. **Windows clicks are handled while the process lives.** The `Activated` handler of each toast is registered in the running app[^6], and the toasts are kept alive under the same 64-entry cap as their targets (`push_bounded`), so every toast whose target is still known can still answer a click. A click after Speedwave exited only lands in Windows. Handling that case needs a COM server registered with the installer, which Windows launches when the user responds to a toast from the notification center[^6]; this change adds none.
8. **Development builds report "unavailable".** `UNUserNotificationCenter.currentNotificationCenter` raises an exception in a process that is not an app bundle[^2][^3], so `macos.rs::center` returns nothing unless the main bundle path ends in `.app`. On Windows a desktop app raises toasts only with a Start menu shortcut that carries its AppUserModelID[^11]; Tauri's NSIS installer stamps the bundle identifier on its shortcuts[^7], so the installed app uses `app.config().identifier`, and a `tauri dev` binary (`tauri::is_dev()`) reports unavailable. Notifications are therefore tested on an installed build.

## Why

- `tauri-plugin-notification` 2.7.0 does report clicks on desktop, but its desktop `permission_state()` and `request_permission()` always return `Granted`[^1], so it cannot show "blocked by the system" and a native read would be needed anyway. On macOS its send path (`notify-rust`) would then go through a different API than the one the permission is read from, and in development it posts under Terminal's bundle identifier[^1]; one native API per platform avoids two sources of truth for one permission.
- Deciding in the backend keeps the event source next to the stream that knows the turn ended and which project and tab it belongs to, and leaves the webview out of the path, so a throttled background webview cannot delay or drop a notification.
- A fixed body keeps chat content off the lock screen and out of the notification database (decision 4).

## Known limitations

- macOS Focus is not reported. `INFocusStatusCenter` (macOS 12+) tells an app whether Focus is on only after its own authorization request[^8]; Speedwave does not ask for it, so Settings says "Allowed." while Focus silences banners.
- Windows Focus Assist ("Do not disturb") is not reported: the documented `SHQueryUserNotificationState` states do not include it[^5].
- A Windows click after the app exited does nothing in Speedwave (decision 7).
- No notification from a development build on either platform (decision 8).
- The opening URL of the macOS Notifications pane, `x-apple.systempreferences:com.apple.Notifications-Settings.extension`, is not documented by Apple; it is the one community references give for macOS 13 and later[^9].
- Manual verification on an installed macOS and Windows build is recorded in SPEED-522, not in CI: the build container has no macOS or Windows host, and the native modules compile only in the macOS and Windows CI lanes.

## Rejected alternatives

- **`tauri-plugin-notification`.** No permission state on desktop (Why).
- **Frontend-driven notifications** (the webview's `Notification` API or the plugin's JS side). The webview decides only after it processed the chunk, and a throttled background webview can delay or drop it (Why).
- **A COM activator for Windows clicks after exit.** Installer and registry changes for a case that only matters once the app is closed (decision 7).
- **Session text in the notification.** Decision 4.
