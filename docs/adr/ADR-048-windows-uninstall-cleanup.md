# ADR-048: Windows Uninstall Cleanup — Unregister WSL Distro and Opt-in Data Removal

**Status:** Accepted

**Date:** 2026-05-06

## Context

On Windows, uninstalling Speedwave via Add/Remove Programs (NSIS uninstaller) or triggering "factory reset" from Settings → Danger Zone removes the `~/.speedwave/` data directory but does not unregister the `Speedwave` WSL2 distribution. The distribution entry remains in `wsl.exe --list`, leaving a phantom distro that the user must manually remove with `wsl --unregister Speedwave`. After a fresh re-install, the `verify_wsl_distro_origin()` security check (`setup_wizard.rs`) detects the pre-existing distro and blocks setup until the user performs the manual unregister step (GitHub issue #613, reported against v0.10.0).[^1]

Two distinct cleanup paths are affected:

1. **In-app factory reset** (`Settings → Danger Zone → Factory Reset`) — calls `setup_wizard::factory_reset()` in the Tauri process.
2. **OS-level uninstall** (Add/Remove Programs → Uninstall) — runs the NSIS uninstaller generated by Tauri's bundler.[^2]

Speedwave also publishes an MSI for managed enterprise deployments. MSI custom actions for uninstall require a dialog/sequencing fragment, per-machine vs. per-user decisions, and impersonation configuration — substantially more work than the NSIS hook. This was deferred to a follow-up issue to avoid blocking the desktop-install fix.

## Decision

### In-app factory reset

Add a `reset_vm()` method to the `ContainerRuntime` trait (default no-op) and override it in `WslRuntime`. The override runs:

1. `wsl.exe --terminate Speedwave` (10 s timeout, best-effort — failure is warn-logged and does not abort)
2. `wsl.exe --unregister Speedwave`[^3] (25 s timeout — "no distribution" errors are treated as success (unverified); timeout and unexpected errors are surfaced to the caller as `Err`)

The call is inserted in `setup_wizard::factory_reset()` between the macOS Lima VM teardown and `wipe_data_dir()`, so the WSL VHDX is still at its expected path when `wsl --unregister` runs. Errors from `reset_vm()` are logged as warnings and do not abort the data-dir wipe — the primary remediation must complete regardless.

`LimaRuntime` inherits the default no-op, so the call site in `factory_reset` is ungated (no `#[cfg(target_os = "windows")]`). `NerdctlRuntime` was removed when Linux was dropped — see ADR-059.

### NSIS uninstall hook

Create `desktop/src-tauri/windows/installer-hooks.nsh` with two macros consumed by Tauri's NSIS template:[^4]

- `NSIS_HOOK_PREUNINSTALL` — prompts the user with a `MessageBox MB_YESNO` (`/SD IDNO` for silent installs). If `SPEEDWAVE_DATA_DIR` is set (ADR-031[^5]), a distinct second prompt is shown that explicitly names the env var and states the uninstaller will not delete that path.
- `NSIS_HOOK_POSTUNINSTALL` — always runs `RMDir /r "$LOCALAPPDATA\Speedwave\nodejs"` followed by `RMDir "$LOCALAPPDATA\Speedwave"` (the latter only succeeds if empty) to remove bundled binaries that Tauri's resource extractor leaves behind — these are app payload, not user data, and were reported as orphaned in #613. Then, when the user accepted the cleanup prompt: probes distro existence with `nsExec::Exec '"$SYSDIR\wsl.exe" -d Speedwave -- true'` (skips terminate + unregister if the distro was never imported); runs `nsExec::ExecToLog '"$SYSDIR\wsl.exe" --terminate Speedwave'` (best-effort, exit code ignored) and `nsExec::ExecToLog '"$SYSDIR\wsl.exe" --unregister Speedwave'` (non-zero exit code emits a `DetailPrint` warning — unexpected at this point since existence was just confirmed); both use `$SYSDIR` (System32) to prevent PATH-based binary substitution. If `SPEEDWAVE_DATA_DIR` is unset, runs `RMDir /r "$PROFILE\.speedwave"`.

The `/SD IDNO` flag causes unattended `uninstall.exe /S` installations to default to "preserve data", so MDM-driven uninstall pipelines cannot silently destroy user data.[^6]

### PRE-INSTALL orphan worker sweep (added in v0.11+)

A third macro, `NSIS_HOOK_PREINSTALL`, was added to the same `installer-hooks.nsh` file to fix a separate Windows upgrade failure: when a host MCP worker (`mcp-os`, `host_exec`, or `oauth`) holds an open handle to the bundled `$INSTDIR\nodejs\node.exe`, the installer fails with "Error opening file for writing". The fix is two-layered:

1. **Windows Job Object** (`crates/speedwave-runtime/src/host_mcp_process/job_object.rs`) — every worker child is attached at spawn to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK`.[^7] When the parent (`Speedwave.exe`) exits — gracefully, on crash, or via Task Manager — the kernel closes the Job handle and terminates the worker. `BREAKAWAY_OK` is set because `host_exec` recipes legitimately need to spawn subprocesses that escape the job (UAC prompts, MSI subprocesses). Known limitation: a TOCTOU window exists between `std::process::Command::spawn` and `AssignProcessToJobObject`; the atomic fix (`PROC_THREAD_ATTRIBUTE_JOB_LIST` or `CREATE_SUSPENDED` + `ResumeThread`) requires bypassing `std::process::Command` and is deferred.[^8] The host MCP workers do not spawn grandchildren during their synchronous startup phase, so residual risk is low.

2. **NSIS PRE-INSTALL hook** — backstop for workers spawned by versions before v0.11 (which have no Job Object), or for any orphan that slipped through the TOCTOU window. Materializes a PowerShell sweep script to `$PLUGINSDIR\speedwave-sweep.ps1` and invokes it with `powershell.exe -File`. The sweep:
   - Receives `$INSTDIR` via the `SPW_INSTDIR` environment variable (avoids PowerShell `-Command` argv concatenation, which would break on apostrophes in the profile path).
   - Enumerates processes with `Get-CimInstance Win32_Process` (crosses sessions; crosses elevation when the installer runs elevated).[^9]
   - Filters by `ExecutablePath.StartsWith($INSTDIR\nodejs\, OrdinalIgnoreCase)` and `ExecutablePath.Equals($INSTDIR\Speedwave.exe, OrdinalIgnoreCase)` — strict literal-path comparison immune to wildcard metacharacters (`[`, `?`, `*`) that break `-like` on legal NTFS paths.
   - Polls the target files via `[System.IO.File]::Open(..., FileShare::None)` for up to 20 s (covers slow EDR / AV post-close handle holds).
   - Exits non-zero on failure; NSIS checks the exit code with `Pop $0` + `${If} $0 != 0` and emits `DetailPrint` diagnostics so AppLocker / WDAC / GPO failures show up in the install log.
   - `SPW_INSTDIR` is cleared from the installer environment after the sweep returns.

The sweep is strictly scoped — it never touches `node.exe` instances from other locations (VS Code, nvm, user shells). Both `Speedwave.exe` and `node.exe` are filtered by `ExecutablePath` against `$INSTDIR`, never by image name alone. Regression tests in `desktop/src-tauri/src/installer_hooks.rs` pin all security-critical invariants (env-var passing, CIM enumeration, ordinal comparison, absolute powershell.exe path, no global `/IM` taskkill, `FileShare::None` lock probe, exit-code surfacing).

### MSI parity (resolved)

Speedwave publishes both NSIS `.exe` and MSI for managed deployments. MSI parity is now achieved through a shared PowerShell sweep script (`windows/sweep.ps1`) and a thin WiX fragment (`windows/sweep.wxs`). The sweep logic lives in **one** PowerShell file; both NSIS PRE-INSTALL and the MSI WiX CustomAction invoke it (`scripts/generate-installer-nsh.sh` embeds it into the NSIS hook at build time; the MSI ships it as a bundled resource and calls it via a deferred `CAQuietExec64` CustomAction after `InstallFiles`). Tauri Desktop additionally invokes the same script at every startup (`setup_wizard::run_pre_link_sweep`) as defense-in-depth for the post-install window where the installer has finished but a stale CLI was spawned by a container. Drift between the NSIS hook and its inputs is caught by the Rust pin tests in `desktop/src-tauri/src/installer_hooks.rs`.

## Consequences

- **After this change:** Uninstalling via Add/Remove Programs and answering "Yes" to the cleanup prompt, or triggering factory reset from the Desktop UI, will leave no phantom WSL distro. A fresh re-install proceeds through `verify_wsl_distro_origin()` without errors. The bundled Node.js directory at `$LOCALAPPDATA\Speedwave\nodejs` is removed unconditionally (regardless of the cleanup prompt) because it is application payload, not user-generated data.
- **Before this change (users on v0.10.0):** One-time manual `wsl --unregister Speedwave` is still required for users who already have a phantom distro. The fix prevents the next occurrence but does not auto-clean pre-existing phantom distros.
- **Idempotency:** `wsl --unregister` on a non-existent distro returns a "no distribution" error, which both the Rust `reset_vm()` implementation and the NSIS hook treat as success.
- **`SPEEDWAVE_DATA_DIR` (ADR-031):** Users with a redirected data directory get a distinct NSIS prompt that names the env var and instructs manual removal of the override path. The uninstaller does not attempt `RMDir /r` on an env-var-sourced path to avoid path injection.
- **MSI users:** Receive the same PRE-INSTALL sweep + Hyper-V firewall rule as NSIS users; the SSOT for both is `windows/sweep.ps1` + `windows/firewall.ps1`.
- **Per-user scope:** WSL2 distros are per-user; `$PROFILE\.speedwave` resolves to the uninstalling user's home. The hook does not require elevation.
- **Repair mode (Tauri 2.x NSIS template):** The standard MUI2 maintenance flow routes "Repair" to a separate Maintenance section that does not invoke `un.Uninstall` and therefore does not invoke the uninstall hooks.[^4] This must be verified during the manual smoke test before merge. If "Repair" unexpectedly invokes the hooks, this ADR will be updated with a mitigation.

## Amendment (2026-09-23): PRE-INSTALL resets the bundled resource trees

**Context.** Tauri's NSIS installer skips the previous version's uninstaller in update mode (only a migration from a WiX install still uninstalls first)[^10], and the in-app updater always launches it with `/UPDATE`[^11]. A silent (`/S`) install skips that uninstaller as well: it is started from the reinstall page's leave callback, and a silent installer calls no page callback[^12]. The install section then only writes the files of the new release (one `File /a` per bundled resource)[^13], so every file a release stops shipping stays under `$INSTDIR`. The runtime builds container images straight from `$INSTDIR\build-context` (`build.rs::resolve_build_root`, through the `resources-dir` marker), so such a leftover reaches `nerdctl build`. After an in-place 0.17.0 to 0.18.1 update, the hub image compiled `mcp-servers/hub/src/pii-tokenizer.ts`, which 0.18.0 had removed, against the new `hub-types.ts` and failed with `TS2305`, so no project could start. Uninstalling and reinstalling did not help, because the uninstaller deletes only the files its own release shipped and removes the resource directories without `/r`[^14].

**Decision.** After a successful sweep, `NSIS_HOOK_PREINSTALL` materializes `windows/reset.ps1` and runs it before Tauri writes the new files[^13]. The script removes every directory resource that `tauri.windows.conf.json` declares (`build-context`, `mcp-os`, `oauth`, `THIRD-PARTY-LICENSES`) and the retired `host_exec`, a directory resource from v0.11.0 to v0.13.3 that no hook or uninstaller has removed since. These trees are application payload that every install lays down in full.

- The trees are deleted with `[System.IO.Directory]::Delete(path, true)`, which does not recurse through a reparse point[^15]. NSIS `RMDir /r` was rejected: NSIS 3.11, the version Tauri 2.11.4 bundles, recurses into every entry marked as a directory without checking for a reparse point[^16], so a junction inside a tree would lose its target's contents.
- The reset runs only when `$INSTDIR` is Tauri's default per-user location, `$LOCALAPPDATA\${PRODUCTNAME}`[^17]. A check on the folder name alone was rejected: the directory page appends the product name only when the browsed folder is named differently, and a typed or `/D=` path is taken as is[^18], so a user's own `...\Speedwave` folder could lose a subfolder that happens to be called `oauth`. An install anywhere else keeps the previous behavior.
- The reset is skipped when the data dir (`SPEEDWAVE_DATA_DIR`, else `$PROFILE\.speedwave`) is the install dir, because the data dir keeps its own `oauth` subdirectory (`consts::OAUTH_SUBDIR`).
- The reset is skipped while any `speedwave-desktop` process runs. The hook runs before Tauri's name-based `CheckIfAppIsRunning`, which aborts the install when the user cancels its prompt or the kill fails[^19]; a reset followed by that abort would leave the installed app without its resource trees. The sweep stops the Desktop installed in `$INSTDIR` before that point. It used to target `Speedwave.exe`, a name Tauri 2 never installs: without `mainBinaryName` the main binary keeps the name Cargo gives it[^20], `speedwave-desktop.exe`, which the sweep now targets.
- A failed sweep skips the reset, so a file that is still locked cannot leave a half-deleted tree behind.

**Runtime guard.** The reset cannot reach every install, so the build does not depend on it. Each staged build-context tree (`build-context/containers`, `build-context/mcp-servers`) carries `.speedwave-shipped-files`, the list of the files its release ships, which `bundle-build-context.{sh,ps1}` write once staging is complete. On Windows, Desktop reconcile runs `bundle::prune_unshipped_files` under the build lock before the manifest hashes the build context, and removes every file of those trees that the list does not name. It never follows or removes a link, compares names case-insensitively (an NTFS overwrite keeps the old file's name), and refuses an empty list, or one naming a file its tree does not hold, before it removes anything. A leftover therefore never reaches `nerdctl build` or the `claude-resources` sync, whether the install sits at a custom location, its data dir is the install dir, a Desktop stayed running, the sweep failed, or an MSI was installed over an NSIS install.

**MSI.** An MSI that replaces an MSI needs no reset: Tauri's WiX template schedules `MajorUpgrade` after `InstallInitialize`[^21], and Windows Installer then removes the entire previous product, including files the new one no longer ships[^22]. An MSI installed over an NSIS install is different: the WiX template takes `INSTALLDIR` from the location the NSIS installer registered[^23], there is no MSI product to remove, and the NSIS reset never runs, so the runtime guard is what removes those files. The MSI custom actions also never ran: `windows/sweep.wxs` and `windows/firewall.wxs` pointed at `[INSTALLDIR]resources\windows\…`, but the WiX bundler installs each resource at its `tauri.windows.conf.json` target directly under `INSTALLDIR`[^24], so both actions failed silently (`Return="ignore"`). They now run `[INSTALLDIR]windows\sweep.ps1` and `[INSTALLDIR]windows\firewall.ps1`.

**Guards.** `desktop/src-tauri/src/installer_hooks.rs` pins that the tree list of `reset.ps1` equals the directory resources of `tauri.windows.conf.json` plus the retired roots and covers every directory-kind bundled asset (`bundle::required_bundled_assets`), that the script deletes only through `Directory.Delete` and reads all of its guards, that PREINSTALL runs it only in the successful-sweep branch and never calls `RMDir`, and that the sweep targets the installed Desktop binary. `_tests/desktop/installer-reset.bats` runs `reset.ps1` under `pwsh` against every guard and against a linked directory. The `prune_unshipped_files_*` tests in `crates/speedwave-runtime/src/bundle.rs` pin the runtime guard, `bundle_scripts_write_the_shipped_files_list_into_every_shipped_tree` and `_tests/desktop/bundle-build-context.bats` pin that both bundle scripts write a complete list, `reconcile_prunes_unshipped_files_on_windows_before_hashing_the_build_context` pins where Desktop runs it, and `msi_custom_actions_run_the_scripts_where_the_msi_installs_them` pins every script path an MSI custom action runs to a resource target. The Windows leg of `.github/workflows/desktop-build.yml` (push builds, and pull requests that touch the Windows installer or bundle inputs) runs `scripts/check-nsis-update-reset.ps1` against the installer it just built: install with `/S` and require the installed build-context trees to match their lists, plant a file the release does not ship and a junction to a directory outside the install dir, install again with the updater's `/P /UPDATE`, and fail unless the planted file is gone and the junction target is intact.

**Consequences.** An update or reinstall at the default location replaces the resource trees wholesale, and on every Windows install the runtime guard removes, before the next build, any build-context file its release does not ship, so no such file reaches the image build or the `claude-resources` sync. Installs that already carry one (the 0.17.0 `pii-tokenizer.ts` under 0.18.x) are cleaned by their first update to a release with this amendment; until then, deleting that file restores the hub build. Leftovers outside the build-context trees (`mcp-os`, `oauth`, `THIRD-PARTY-LICENSES`, `host_exec`) are removed only by the reset, so they stay on disk wherever the reset does not run; no build reads them. Enabling the MSI custom actions means an MSI install now runs the sweep and installs the firewall rules, as the MSI parity section above intended.

## Amendment (2026-09-24): the sweep probed the `nodejs` directory, not `node.exe`

**Context.** The first Windows run of `scripts/check-nsis-update-reset.ps1` failed: the planted file survived the `/P /UPDATE` install. A minimal installer built from the same `installer-hooks.nsh` on the same runner image showed why. The PRE-INSTALL sweep waited its full 20 s and exited non-zero, although a probe run by the same installer opened `speedwave-desktop.exe` and `nodejs\node.exe` with `FileShare::None` right before and right after it. The sweep built its lock-probe list as `@($desktopExe, $nodePrefix + 'node.exe', $cliExe)`, and PowerShell's comma operator binds tighter than `+`[^25], so the list held the Desktop binary, the `nodejs\` directory itself, the relative name `node.exe` and the CLI. Opening a directory as a file always fails, so wherever `$INSTDIR\nodejs\` already existed (every update and reinstall) the sweep reported the targets as locked after 20 s and never probed `node.exe`, and the hook skipped the reset, as the amendment above specifies for a failed sweep. The PRE-INSTALL sweep has built its list this way since it was added in v0.12.0 (#712)[^31], so every update since then spent 20 s in the sweep and recorded a failure that a silent or passive install never shows. Its error exits did not report their codes either: under `$ErrorActionPreference = 'Stop'`, `Write-Error` becomes a script-terminating error[^26], which ends a `-File` script with exit code 1[^27] before the `exit 2`, `exit 3` or `exit 4` that follows it.

**Decision.** `sweep.ps1` builds its paths with `[System.IO.Path]::Combine`, probes `$INSTDIR\nodejs\node.exe` through its own variable, and reports a failure with `[Console]::Error.WriteLine` before its `exit`, so exit codes 2, 3 and 4 reach the NSIS hook, the MSI custom action and the Desktop pre-link sweep log (`setup_wizard.rs::run_pre_link_sweep`).

**Guards.** `_tests/desktop/installer-sweep.bats` runs `sweep.ps1` under `pwsh` with the process list stubbed: an update layout that nothing holds passes at once, a target another process holds with `FileShare::None` ends in exit 4 after the full wait, only the Desktop binary, the workers and the CLI of this install are stopped (runtime mode stops only the CLI, a named instance only its own CLI), and a failed process listing or a missing input ends in exit 3 or 2. The paths are built with `Combine` so that the suite runs the script unchanged on macOS. `scripts/check-nsis-update-reset.ps1` still runs the real installer on Windows.

## Amendment (2026-09-24): the hooks start PowerShell without Windows Script Host

**Context.** The hooks started every PowerShell run through `wscript.exe` and a materialized `run-hidden.vbs`, which handed its first argument to `WshShell.Run` so that no console window appeared during an install. Windows Script Host drops the double quotes when it splits its command line into script arguments, so the quoted `-File "$PLUGINSDIR\sweep.ps1"` reached PowerShell unquoted, and a space in `$PLUGINSDIR`, which sits under the installing user's `TEMP`, cut the path short. On `windows-latest`, with `TEMP` set to `C:\sw temp`, PowerShell received `-File C:\sw` and exited with `0xFFFD0000`, so the sweep failed and the reset was skipped, while the same sweep started with its quotes intact passed[^28]. The shim also depends on VBScript, which Windows is retiring through a feature on demand[^29].

**Decision.** `SPEEDWAVE_RUN_HIDDEN` (`installer-hooks-template.nsh`) starts each hook's PowerShell run through the NSIS System plugin with `CreateProcessW`, which receives the command line unchanged, and `CREATE_NO_WINDOW`, which runs a console application without a console window[^30]. It waits for the process and leaves its exit code in `$0`, where the hooks read it as before. `run-hidden.vbs` is removed; the hooks keep `nsExec` only for `wsl.exe`.

**Guards.** `install_hooks_run_powershell_without_a_console_window` (`installer_hooks.rs`) pins the four PowerShell runs (sweep, reset, firewall install and uninstall) to the macro and the macro to `CREATE_NO_WINDOW`, `WaitForSingleObject` and `GetExitCodeProcess`, and rejects `wscript`, a `.vbs` file, or a PowerShell run through `nsExec`. `scripts/check-nsis-update-reset.ps1` runs the `/P /UPDATE` install with `TEMP` and `TMP` pointing at a directory whose name contains a space.
