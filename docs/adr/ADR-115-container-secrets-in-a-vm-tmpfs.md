# ADR-115: Container secrets in a VM tmpfs

> **Status:** Accepted
> **Date:** 2026-11-20
> **Context:** SPEED-1015, a step of SPEED-579 (secrets at rest). Containers read credentials from host directories mounted through virtiofs (macOS) or `/mnt/c` (Windows), and some credentials were container env.

## Context

Before this change a credential reached a container in one of two ways. Token directories, the PII policy and the rendered `proxy.json` were bind-mounted from the data directory, so the files sat on the host disk and every container read them through the host-to-VM share. The Anthropic key and token, the custom headers, the git proxy caller secret and each worker's bearer were container env (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS`, `SPEEDWAVE_GIT_PROXY_AUTH`, `MCP_<SVC>_AUTH_TOKEN`), which `render_compose_in` wrote into `compose.yml`; `snapshots/<project>/snapshot.json` pins that compose, and the engine keeps the env of each container in its description on the VM disk (not verified here: where the engine persists it). A secret in env therefore outlived the container on the host disk and, by that description, on the VM disk, and `compose.yml` could not be shared or logged as it stood.

## Decision

1. **One channel: a tmpfs inside the VM.** `/run/speedwave-secrets` (`secrets_tmpfs/layout.rs::VM_ROOT`) is a dedicated tmpfs mounted by the receiver script (`mode=0700,size=16m,nosuid,nodev,noexec`), serialised with `flock` on `/run/speedwave-secrets.lock` so two writers never stack two mounts. The kernel documents that a tmpfs lives in memory and is lost on unmount[^1].
2. **One slot per container and purpose.** A slot is `<VM_ROOT>/<project>/<service>/<purpose>` and is bind-mounted `:ro` into one container path. `compose/secret_slots.rs` lists them: `tokens` (`/tokens`) and `auth` (`/run/speedwave/auth`) for built-in workers, `tokens` for plugin workers, `secrets` (`/secrets`) and `policy` (`/policy`) for `mcp-hub`, `config` (`/config`), `tokens`, `policy` and `git-github`/`git-gitlab` (`/git-tokens/<forge>`) for `proxy`, and `secrets` (`/run/speedwave/secrets`) for `claude`. The renderer mounts them through the `${SECRETS_VM_DIR}` placeholder of `containers/compose.template.yml`, and `compose/secret_payload.rs` collects the files from the same constructors, so a mount and its content cannot drift. Slot directories are `1000:1000` mode `0700`, files `1000:1000` mode `0400`, and `<VM_ROOT>` and `<VM_ROOT>/<project>` are root-only.
3. **Files, not env.** The claude container gets the files `anthropic-api-key`, `anthropic-auth-token`, `anthropic-custom-headers` and `git-proxy-auth`, written under the conditions that used to inject the env. A built-in worker gets its bearer as `/run/speedwave/auth/token`, named by `MCP_<SVC>_AUTH_TOKEN_FILE`; `mcp-servers/shared/src/boot.ts` reads the file first and falls back to `MCP_<SVC>_AUTH_TOKEN`. The proxy's `proxy.json` is rendered in memory and written only into its `config` slot; the proxy's digest is computed from that content. The `SPW_NER_URL` marker stays as compose env on the proxy because it is a URL, not a secret.
4. **The claude container loads the files into process environments.** `containers/speedwave-secret-env.sh` exports them in the entrypoint, and `containers/speedwave-exec.sh` does the same for every `nerdctl exec` before `exec env "$@"`. `session/instance.rs::instance_env_argv` starts every exec argv with `consts::SPEEDWAVE_EXEC_WRAPPER`, because an exec does not inherit variables the entrypoint exported. Claude Code still reads its credentials from env, but only inside the container's processes.
5. **Written through stdin, before every start, under the project lock.** `ContainerRuntime::vm_exec_as_root` runs one `sh -c` script in the VM as root (through `sudo` on Lima, directly on WSL, `runtime/lima.rs` and `runtime/wsl.rs`); the script text carries no value and the payload goes through stdin as a line frame (`sync <project>` with `D`, `K` and `F` lines, or `put <project>` with `F` lines), so a value never appears in argv, env or an error. `LockedRuntime` (enabled for the handle `detect_runtime()` returns) runs the `sync` frame before `compose_up`, `compose_up_recreate` and `compose_up_service`, inside the same `with_acquired` section; an error aborts the start before `compose up`. `stage_project_secrets` and `put_secret_file` offer the same write under the project lock to callers that change a credential while containers run. Directories are never replaced or removed, files are written as a temp file and `mv` inside the slot, and a `sync` removes every file the payload does not list except the names a slot keeps (`refresh_status` in a `tokens` slot).
6. **A render-time rule.** `SecurityRule::SecretSlotMount` rejects any mount sourced under the secrets root that is not one of the slots `expected_slot_mounts` lists for its service, `:ro`, in short form, from the project's own tree. The existing hub, proxy and claude rules compare against the slot paths instead of the token directories.

## Consequences

- `proxy` has `restart: "no"` (`containers/compose.template.yml`). The engine could restart it on its own after a VM boot, with an empty tmpfs and no write before it; with no restart policy a crashed proxy stays down until the next project start, and requests through it fail until then. The restart option values come from the nerdctl command reference[^2].
- The tmpfs lives in the VM's memory and is lost when it is unmounted[^1], which a VM restart does, so every start writes it again. Nothing relies on the contents surviving.
- Installed plugin workers keep `MCP_<SID>_AUTH_TOKEN` as plain env, because their code lives in the sibling repo `speedwave-plugins` and was not changed. That bearer still lands in `compose.yml` and in the container description. Closing it needs a plugin-side `<ENV>_FILE` reader first.
- The host files stay the source of truth. A credential changed on the host while containers run reaches the slot only through `put_secret_file` or `stage_project_secrets`, or at the next start.
- tmpfs pages can be swapped out under memory pressure[^1]; the VM's swap and host hibernation are out of scope here, and this change does not claim that a secret never reaches a disk.
- A failed write (no `sudo`, a full tmpfs, a bad file name) now stops the start with the VM's stderr as the error.

## Alternatives rejected

- **Env through `nerdctl run --env-file`[^2].** The values stay container env, so they stay in the container description.
- **Per-file bind mounts from the host.** The host disk stays the place the container reads from, which is the exposure this change removes.
- **Writing from the platform runtimes (`lima.rs`, `wsl.rs`) separately.** Two writers would drift. One frame and one receiver script sit above `ContainerRuntime`, and only `vm_exec_as_root` differs per platform.

[^1]: Linux kernel documentation, tmpfs: https://www.kernel.org/doc/html/latest/filesystems/tmpfs.html
[^2]: nerdctl command reference (`nerdctl run`: `--env-file`, `--restart=(no|always|on-failure|unless-stopped)`): https://github.com/containerd/nerdctl/blob/main/docs/command-reference.md
