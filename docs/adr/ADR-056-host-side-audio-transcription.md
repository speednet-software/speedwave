# ADR-056: Host-Side Audio Capture and Local Meeting Transcription

> **Status:** Accepted — validation spikes 0A/0B/0C passed and the feature is implemented behind the `audio-transcription` Cargo feature.
> **Context:** Record a meeting (Slack / Teams / Meet / any app), transcribe it locally, then optionally hand the transcript to Claude — a host capability that cannot live in Claude's token-free container.
>
> **Amendment:** Speaker diarization was later removed, and the sherpa-onnx dependency it relied on with it — see [ADR-075](ADR-075-remove-speaker-diarization.md). The diarization-specific content of this ADR was pruned in that change; the product ships a clean timestamped transcript with no speaker attribution. All Whisper transcription and audio-capture decisions below still apply.
>
> **Amendment 2:** The per-feature opt-in toggle and the model picker were removed. The tab stays beta-gated (ADR-058) but has no second on/off switch; the feature does nothing until the user presses Record, so the toggle only added friction. Configuration moved entirely into Settings → Meeting transcription, which offers a single auto-selected model — `large-v3` on builds with a GPU backend (the GPU keeps the live window real-time at full quality), `large-v3-turbo` on CPU-only builds — chosen by `accel::best_model_for_this_build()`. `default_language` / `default_live_model` / `keep_audio_after_finalize` are gone: language is picked per-recording, audio is always kept (deleted per-recording from the list). `TranscriptionConfig` and `transcription_enabled()` were dropped from the config.
>
> **Amendment 3:** Per-app (single-process) capture was removed. The macOS process-tap enumeration listed every audio-touching system daemon (`controlcenter`, `CoreSpeech`, `loginwindow`, `GPU`, …), making the picker unusable, and the whole-meeting / system / microphone sources cover the real use case. The `AudioSource::Process` variant, `ProcessSelector`, `CaptureCapabilities.supports_per_process`, the Swift CLI `--list` + `pid:`/`all-except:` sources, the Windows per-process WASAPI loopback (build-20348 gate), and all per-process validation were deleted. The source picker now shows exactly three entries: Whole meeting, System, Microphone.
>
> **Amendment 4 (capture resilience):** Field failures showed the capture path silently losing the meeting voice. Four hardening decisions: (1) the silence-detection fallback promised by the permissions decision below is now implemented — a system stream that is pure digital silence for its first 15 s (the signature of a consent-broken tap[^1]) raises a `CaptureWarning` event and an in-app banner with a privacy-settings link; (2) `MixBuffer` degrades instead of dying — a side whose watermark lags the other by >5 s stops gating the mix (padded as silence, warning raised, auto re-gates if it recovers) so a dead mic no longer kills the whole recording after the 2 s stall window; (3) on Windows the mixed capture also loopback-captures the default _Communications_-role render endpoint when it is a different device than the Console one — Teams/Slack render call audio to the communications endpoint[^2], which the console-only loopback missed entirely; loopback resamplers are wall-clock anchored because an idle endpoint delivers no packets[^3] and stream-position offsets would misplace audio that starts mid-recording; (4) the macOS CLI observes `AVAudioEngineConfigurationChange`[^4] and restarts the mic engine when the default input device switches mid-session (joining a call routinely re-routes audio to a headset), and rebuilds a stream's `AVAudioConverter` when its input format changes.
>
> **Amendment 5 (in-process microphone consent):** Production diagnostics showed the microphone consent prompt never appearing: `AVCaptureDevice.requestAccess(for: .audio)` resolved to a silent denial when called from the headless `audio-capture-cli` helper (observed in the field; the public API documents only the prompt flow[^5]), so recordings degraded to system audio only, with no TCC row the user could re-enable. The permissions decision below is amended: the main Tauri app resolves mic consent in-process (`mic_permission_cmd.rs`, `objc2-av-foundation` FFI) before any capture spawn, so the prompt fires from the GUI process and the grant lands under `pl.speedwave.desktop`; the spawned CLI then records under that grant. The main app is therefore signed with the `com.apple.security.device.audio-input` entitlement (`bundle.macOS.entitlements`, guarded by `main-app-entitlements.bats`) and already carries `NSMicrophoneUsageDescription`. UI flow: Record on a mic-including source first calls `request_microphone_permission`; a refusal on the prompt just shown surfaces the error banner, while an earlier refusal (`previously_denied`) additionally deep-links to the Microphone privacy pane, since macOS never re-prompts[^5]. The CLI keeps its own `requestMicrophoneAccess()` call as defense-in-depth. Settings → Meeting transcription gained a Permissions block (mic state via a non-prompting status query, deep-links to both privacy panes).
>
> **Amendment 6 (live-view stabilization):** The live transport is now append-only. Field testing showed the sliding-window live pass visibly flickering: every re-decode replaced the trailing window's segments (`SegmentsReplaced`), and consecutive decodes of the same audio routinely disagree mid-utterance, so shown sentences vanished and reappeared. Text-agreement gating (publish when two passes agree, LocalAgreement-style[^6]) was tried first and starved the live view: Whisper wobbles punctuation and casing and freely merges or splits segments between passes, so segment-level text equality rarely holds. The shipped policy gates on time instead: the driver publishes a segment once it is at least the decode cadence (5 s) older than the newest captured audio (only the window tail is unstable), the final pre-finalize decode flushes the held-back tail, and `SegmentsReplaced` plus the splice machinery were removed from the store, the event protocol, and the TS mirror. A sentence appears within one to two decode cycles after being spoken; the offline pass remains the quality authority.
>
> **Amendment 7 (named-mic restart storm, per-source level balance, live draft tail):** Field testing of the Amendment 4/6 state surfaced three defects. (1) Picking a named microphone made the Amendment 4 restart handler self-sustain: binding a non-default device posts a spurious `AVAudioEngineConfigurationChange` at engine startup with the engine still running (reproduced in isolation: one notification ~0.25 s after start, `isRunning` true, frames flowing), the handler restarted blindly, and every restarted engine posted the same startup notification, so the mic tore down every ~0.4 s for the whole session and contributed nothing. A real configuration change stops the engine[^4], so the handler now ignores notifications while the engine reports running and restarts only a stopped engine. (2) A far-field microphone sat roughly 20 dB under system audio in the fixed 0.5/0.5 mono mix (field session: mic speech at RMS 0.0055 in-mix, exactly at the anti-hallucination speech floor, against 0.05..0.09 for the system side), so simultaneous speech plus playback transcribed as playback only. `MixBuffer` now levels each source independently before the sum: boost-only gain toward a -20 dBFS active-RMS target (cap +18 dB, 3 s EMA), adapted only by chunks above a -50 dBFS activity floor so noise floors and pauses never move it, and held through pauses. Both platforms share the code path, and the recorded WAV (hence the offline pass) inherits the balance. (3) The Amendment 6 holdback alone kept the live view 10 s or more behind speech, and content whose decoded segment outlived the 12 s window never displayed at all. The driver now additionally publishes the held-back window tail after every decode as a `LiveDraft` event: replace-only display state, rendered as a muted italic line under the committed transcript, never persisted, never part of send-to-chat or finalize, cleared by the pre-finalize flush and on any lifecycle change away from recording. First text appears within one decode cycle while the committed transcript stays append-only and flicker-free.

> **Amendment 8 (Silero VAD hallucination gate):** Field sessions on the Amendment 7 state still surfaced trained-in filler ("Dziękuję") in quiet-but-not-silent windows: the signal-only gate (per-segment no-speech probability crossed with segment RMS) passes a segment whose RMS sits just above the speech floor, and forced-language decoding of non-speech audio is precisely where Whisper hallucinates fluent filler[^11]. Every `WhisperCppTranscriber` now carries a Silero VAD gate, using whisper.cpp's built-in GGML VAD support[^12] through the _standalone_ API (`WhisperVadContext`): a decode window in which VAD finds no speech spans is not decoded at all, and a decoded segment whose time span overlaps no VAD speech span (200 ms tolerance) is dropped whatever its text. The integrated `whisper_full` VAD mode was rejected because it remaps segment timestamps onto the concatenated speech-only audio[^13], while the driver's commit/holdback logic lives on the window timeline; the standalone gate leaves Whisper's input and timestamps untouched. The model is `ggml-silero-v5.1.2.bin` (885 KB, MIT[^14]), pinned by SHA256 in `model_catalog.rs::VAD_MODEL` and fetched from the `ggml-org/whisper-vad` repo[^15]; it rides along with every Whisper model download and is backfilled by a background download at recording start for installs that already have models. An absent model or a VAD failure degrades to the signal-only gates with a warning; recording is never blocked. A hardcoded blocklist of known filler phrases was tried and rejected in review: language-specific, brittle, and redundant once windows without speech are never decoded.

> **Amendment 9 (per-stream decode, channel labels):** Field forensics on an Amendment 7/8 build showed the decision-15 mono mix losing the user's voice whenever playback ran: in a real session the mic speech sat at RMS 0.001..0.005 in the recorded mix against 0.05..0.15 for the system side, and the same quiet speech that transcribed correctly alone vanished once loud playback competed with it in one mono stream. The level balancer cannot close that gap: chunks under its activity floor never adapt the estimate (so the quietest mics get no boost at all), acoustic bleed of the speakers into the mic adapts the mic estimate to the bleed rather than the voice, and raising the boost cap amplifies noise floors, feeding the very hallucinations Amendment 8 gates. Mixing two speech sources into mono before STT destroys information, so the mix is gone from the decode path: `MixBuffer` still aligns, levels, health-checks, and zero-pads both sides, but now emits aligned channel pairs (`pop_pair`), the recorded WAV is stereo (channel 0 system, channel 1 mic), and the driver decodes each channel separately per lane (own committed horizon, own draft tail) in both the live window and the offline pass, merging segments chronologically. Whisper never sees overlapped speech from two sources in one buffer. The usual meeting cadence keeps the cost near parity: while one side talks the other is silence, which the Amendment 8 VAD gate skips without decoding. Each segment carries its channel (`Segment.source`: system or mic, `None` on mono captures and old transcripts), surfaced as "Meeting"/"You" labels in the UI and markdown export. This is deterministic channel attribution and does not reopen ADR-075: no voice identity is inferred, ever.

> **Amendment 10 (resume a finished recording):** The lifecycle was strictly `Recording → Finalizing → Done`, so a stopped meeting could never continue into the same transcript. A `Done` session can now be resumed: `TranscriptStore::resume` moves the offline pass (the best text so far) into `live_segments` as the baseline, clears `final_segments`, flips the status back to `Recording`, and registers a new audio part (`audio-N.wav` beside `audio.wav`; `TranscriptSession.audio_parts`, serde-defaulted so old transcripts load unchanged). The new part's driver runs with a `time_base` equal to the summed duration of the earlier parts, so committed segments land past them on one session timeline; the offline pass re-transcribes every part in order (a part whose WAV never materialised or carries no samples is skipped, with a logged warning and a RecordingPartMissing capture warning) and stitches one `final_segments` list. Exposed as `resume_transcription` (same ack shape as start; rejected unless the session is `Done`) and a per-row "resume" button on finished recordings, hidden while any recording is in flight. Pause was rejected: it cannot reopen a session stopped earlier, which is the actual field need, and resume covers an accidental Stop for free.

> **Amendment 11 (ingest/decode split, honoured capture offsets, per-pass models, thread budget):** Field diagnostics on Windows showed a 35 s recording producing a 5.000 s `audio.wav`, no live text at all, and a pegged CPU. Two independent defects, one per layer. (1) **The driver pumped capture and decode on one thread**, so while `feed()` sat inside whisper (measured at roughly 40 s per 12 s window on a CPU-only host — an i7-11850H running `large-v3-turbo` on whisper.cpp's default four threads[^16]) nothing drained the capture channel; its 32-chunk (6.4 s) depth overflowed and `try_send` discarded the remainder in silence, and the observed retention of ~14% matches `32 / (32 + chunks produced per cycle)`. Worse, the driver appended `AudioChunk.samples` while ignoring `AudioChunk.offset`, so the surviving fragments were spliced contiguously and the recording _compressed in time_: wrong WAV length, wrong timestamps, speech cut mid-word, and nothing the offline pass could rescue. Capture now runs on its own `transcript-ingest` thread which owns the WAV and finalizes it there (the offline pass starts on a 5 s budget after stop and used to read a header still claiming zero samples), places every chunk at the absolute position its offset declares — padding a real gap with silence, because an idle WASAPI loopback delivers nothing[^3] — and publishes into a bounded per-lane ring (`LIVE_WINDOW_SECS` plus a 30 s lag tolerance). The live pass reads trailing windows from that ring and decodes them in sequence; when it falls further behind than the ring holds, it logs a warning and jumps to the newest audio, so on a host that cannot keep up the live view goes sparse while the recording stays whole. The full-recording PCM the driver used to accumulate (~115 MB/hour/lane) is gone: only the live window ever read it, and the offline pass re-reads the WAV. A loss that does still happen (a full channel, an over-cap `MixBuffer` push) now raises a one-shot `CaptureWarning::AudioDropped` with a UI banner instead of vanishing. The whisper state is created once per transcriber rather than once per decode window, which had re-reserved the KV caches and compute graphs every time; this is safe because `no_context` clears the accumulated prompt on every call[^16]. Each decode logs its own duration, because whisper.cpp logs none and the 40 s figure above had to be inferred from how fast the WAV grew. (2) **`accel.rs` inverted its own catalogue roles**, which supersedes the single-model rule of Amendment 2: `ModelRole::CpuLive` (`small`, documented as "the CPU-only live model") was unreachable, CPU-only hosts were handed `GpuLive` (`large-v3-turbo`, "live on GPU/Metal"), and GPU hosts were handed `Finalize` (`large-v3`, flagged `live_capable: false`). The passes now pick separately — live: `large-v3-turbo` on GPU, `small` on CPU; finalize: `large-v3` on GPU, `large-v3-turbo` on CPU, the largest that still finishes a long meeting there (four decoder layers against thirty-two[^17]) — so a host may need two models. `recommended_transcription_model` reports a live entry plus an optional `finalize` entry, Settings renders one download row per model, and a test asserts the live model is always one the catalogue flags live-capable (today the per-class `live_floor`/`live_capable_on(class)` check, ADR-085). Whisper is also given physical cores instead of the default `min(4, logical)`[^16], capped at eight so the container VM is not starved; SMT siblings are excluded because whisper.cpp is matmul- and bandwidth-bound. There is still no user-facing model picker.

> **Amendment 12 (proportional live audio_ctx; GPU-class model tiers):** Telemetry added by Amendment 11 exposed the next ceiling: on the same CPU-only host the live pass with `small` on 8 threads decoded a 12 s window in ~8 s (needs ≤5 s) — and a 2.2 s window in ~7.3 s, near-identical, because whisper.cpp pads every input to its full 30 s window and the encoder cost is per-call, not per-audio-second[^18]. The live pass now sets a proportional encoder context (`transcriber.rs::live_audio_ctx`: one position per 320 samples plus headroom, floor 128, cap 1500), the same technique whisper.cpp's own streaming example uses[^18]; a 12 s window stops paying for 18 s of zero-padding. The offline pass never reduces the context — it is the quality authority, and its 30 s windows resolve to the full 1500 anyway. Separately, ADR-085 (Windows Vulkan backend) turned the Amendment 11 binary GPU/CPU model split into a three-way runtime classification: `accel.rs::GpuClass` (`Discrete`/`Integrated`/`None`, probed once per process) picks the tiers — discrete GPUs and Metal get `large-v3-turbo` live + `large-v3` finalize, integrated GPUs and CPU-only hosts get `small` live + `large-v3-turbo` finalize (an iGPU accelerates the small models without being able to hold the GPU-tier ones at live cadence).

> **Amendment 13 (optional live pass, capture loudness meter):** On the CPU-tier hosts of Amendment 12 the live pass is an honest but poor trade: `small` keeps up yet reads Polish badly, and the constant decode loop burns CPU/battery through the whole meeting (fan noise the microphone then records) while the finalize pass produces the transcript that actually matters. Recording therefore no longer requires a live pass: `start_transcription`/`resume_transcription` take a `live` flag (serde-default true, so older frontends keep the old behavior), and a record-only session loads no live model at all — `DriverConfig.transcriber` is optional, the ingest thread records exactly as before, and whisper first runs at Stop. Start still verifies a finalize-capable model is downloaded, failing early instead of after the meeting. The UI default follows the probed `GpuClass` (`discrete` → live on, else off), with a per-recording checkbox persisted in localStorage — this does not reopen Amendment 2 (that toggle gated the whole feature; this one picks a processing mode with a real hardware cost) and adds no model picker. Because a silent transcript pane was the only feedback that capture worked at all, the driver's ingest thread now also broadcasts a throttled (~4 Hz) `AudioLevel` event — per-channel RMS only, never audio, never persisted (the `LiveDraft` no-save path) — rendered as Meeting/You loudness bars on a dB scale while recording; emission lives on the ingest thread because the decode side blocks inside whisper for seconds at a time and would freeze the meter exactly when reassurance matters. Known gap: a mono system-loopback source that goes fully idle delivers no chunks, so the meter holds its last value rather than falling to zero (the mixed default emits continuously).

> **Amendment 14 (transcript send target):** The send button appended the transcript to whatever conversation the chat tab last held, so a meeting summary landed mid-thread in unrelated work. Sending now opens a fresh conversation first, through `ChatStateService.startNewConversation`: it attaches the stream listeners (the chat tab may never have been mounted in this run, and a send that beats the listener loses its reply), then refuses before clearing anything when a reply is streaming, when a start or resume owns the session, when the project is not ready, or when there is no project at all — the old code would have wiped the conversation and then failed. `newConversationBlockedReason` is the one signal behind both that refusal and the caller's disabled state, so a blocked button never reaches the confirm dialog. Only then does it clear the state tree, claim the bootstrap slot (and bump the session generation, so a start `init()` deferred until the project is ready does not fire a second `start_chat` over this session) and await the start. `startChatSession` returns which of started/skipped/auth/failed happened rather than a bare boolean, so the message names the cause instead of being inferred from mutable project state, and a resume that lands mid-flight is reported as skipped rather than success. A failed start leaves the chat empty but keeps the durable session id, so a container restart can still resume what the user was in. The restart-overflow "fresh" branch (`startFreshSession`) routes through the same method and surfaces a refusal as an error entry in the conversation, since that prompt only appears with a chat view mounted. `TranscriptionService.sendToChat` reads the transcript before touching the chat, so a failed read leaves the conversation intact. Appending stays reachable as a deliberate choice, not the default: the pane offers "Send to new chat" and "Add to current chat" side by side, the second one enabled only while a conversation exists (`ChatStateService.hasConversation`) — keeping the active thread is what a user wants when the meeting was about the work in front of them. Naming both destinations in the labels is what removes the explanatory line an earlier revision needed; the ticket had asked for "Send to Speedwave", which says where the text goes but not which conversation, and a hint line under the buttons attached to neither of them. A button that cannot act stays visible and disabled, with the reason (recording, chat replying, no open chat) as its own tooltip rather than a line of text beside the row — a hidden affordance teaches nothing, and a floating caption attaches to neither button. The tooltip sits on a wrapper span with `disabled:pointer-events-none` on the button, because a disabled control fires no pointer events. Both paths keep the ADR's privacy boundary — the confirm dialog names the destination, and only an explicit click sends text off the machine.

> **Amendment 15 (editable prompt, transcript rides the next message):** The Amendment 14 buttons sent immediately, with the summarization instruction compiled in as one constant per session language, so the user never saw the prompt and could not adapt it: the fixed "topics, decisions, action items" request fits a status meeting and not a code review, a client call, or a retro, and there was nowhere to name who is who or what an internal codename means (speech recognition mangles proper nouns, and the model was left guessing from the transcript alone). Both buttons now stage instead of send. `TranscriptionService.stageForChat` reads the transcript, opens a fresh conversation when the target asks for it, then puts the same per-language default into `chatPromptDraft` and the markdown into `stagedTranscript`; the transcript pane navigates to the chat tab and stops there. The composer loads the draft through a `draftText` input and emits `draftApplied`, which clears the service signal — a signal-driven input rather than a `ViewChild` call because the chat view mounts after the navigation and a pushed value would race the mount. The markdown never enters the text field: it would bury the prompt in a wall of text the user has to scroll past to edit. Instead a row above the field states that the transcript goes out with the next message, to the configured LLM provider, and carries an × that unstages it; `chat.component` appends the staged markdown after a blank line to whatever the user submits (queued sends included, ADR-045) and clears the staging afterwards. The privacy boundary gets stronger, not weaker: the `window.confirm` is gone because Enter on a prompt the user just read and edited is the explicit action the confirm was standing in for, and an empty field submits nothing, so clearing the prompt cannot send a bare transcript. The default text is unchanged, so a user who edits nothing gets exactly the Amendment 14 request. Not persisted between meetings, and no glossary of names or terms as a separate surface: both were considered and left out until the free-form field proves too little.

## Decision

Build "Meeting transcription" as a **built-in Desktop module** behind the beta-features gate (ADR-058). All non-UI logic lives in `crates/speedwave-runtime/src/transcription/` behind a Cargo feature `audio-transcription`; the Tauri command layer is thin; the UI is a new top-level Angular tab. Transcription uses whisper.cpp (via `whisper-rs`); audio inference is fully local — only the final transcript text leaves the machine, and only when the user explicitly sends it to Claude.

The supporting sub-decisions:

- **Not a plugin.** Plugins are containers with no host-audio path (ADR-051). Host audio + microphone is privacy-sensitive and must be visibly opt-in and signed by Speedwave. The module follows the existing host-side precedent (a `speedwave-runtime` SSOT layer, thin Tauri commands, and on macOS a bundled signed native CLI like `calendar-cli`, ADR-049).
- **macOS capture = CoreAudio process taps (macOS 14.4+)[^7], not ScreenCaptureKit.** Apple recommends Core Audio taps for audio-only capture; ScreenCaptureKit has audio-only defects on macOS 15 (unverified). The feature floor is macOS 14.4+ (runtime-gated via `if #available`); older macOS gets a clean "14.4+ required" message and the rest of the app still works.
- **macOS permissions.** Microphone uses the public `AVCaptureDevice.requestAccess(for: .audio)`, called in-process by the main app before any capture spawn (Amendment 5): the prompt does not fire from the headless CLI. The system-audio consent prompt has no public trigger, so the native CLI uses the private TCC API (`TCCAccessRequest`, service `kTCCServiceAudioCapture`) behind a `dlopen`/`dlsym`-guarded path that degrades gracefully; a System-Settings deep-link plus silence-detection is the fallback if it reports denied.
- **Windows capture = WASAPI loopback** (system-wide). Per-app (single-process) capture was removed — see Amendment 3.
- **Transcription engine** = whisper.cpp (MIT)[^8] via `whisper-rs`; acceleration backends are compile-time, so the runtime reports which backends were compiled in. v1 ships CPU (all platforms) + Metal (macOS); CUDA/Vulkan deferred.
- **PL/EN strategy** = forced language (never auto-detected, picked per-recording), with a live pass plus a higher-quality offline re-pass after recording stops. A single model is downloaded per the hardware (see Amendment 2); on GPU builds the live and offline passes share `large-v3`. The promise is "local best-effort live + higher-quality offline final pass", not "perfect Polish/English".
- **Model store** = download-on-demand, SHA256-verified, streamed to disk, into `<data_dir>/models/`. Hugging Face[^9] and GitHub[^10] `302`-redirect downloads to signed CDN URLs, so the downloader uses a redirect-host allowlist rather than `redirect::Policy::none()`. Otherwise it reuses the ADR-041 host-HTTP hardening.
- **Live-transcript transport** = an append-only event stream with a monotonic `seq` plus snapshot recovery, reusing the _delivery semantics_ of `MsgStore::history_plus_stream()` (ADR-043) — not the full JSON-patch protocol (ADR-042).
- **Mixed capture (system loopback + microphone) is the product default** — both streams are summed to one 16 kHz mono stream before the engine sees them, so the transcription driver is platform-agnostic.
- **No per-feature toggle** (Amendment 2). Access is governed by the beta gate (ADR-058); a checked-in repo `.speedwave.json` was never able to enable host-audio recording and still cannot (it carries no transcription field).
- **Audio retention** = WAV kept until the user deletes the recording. A single "delete" per recording removes the whole session (audio + transcript); no separate discard-audio control, no automatic expiry (YAGNI).

## Why

- The container threat model is untouched: Claude's container learns nothing about audio; the transcript reaches Claude only through the normal chat path as user-supplied text.
- Audio inference is local — no audio leaves the machine for transcription.
- Heavy lifting is delegated, not reimplemented: transcription = `whisper-rs`, Windows capture = `cpal`, downloader = `reqwest` + the existing host-HTTP hardening, child-process lifecycle = the `mcp_os_process.rs` discipline.
- The `AudioCapture` trait split mirrors the `ContainerRuntime` → `LimaRuntime`/`WslRuntime` shape (Open/Closed: a new platform is a new impl). Originally scoped to also include Linux; Linux was dropped per ADR-059.

## Where it lives in code

- **Runtime SSOT (feature-gated)** — `crates/speedwave-runtime/src/transcription/` (`mod.rs`, `audio.rs`, `audio_macos.rs`, `audio_windows.rs`, `mix.rs`, `transcriber.rs`, `transcript_driver.rs`, `transcript_store.rs`, `transcript.rs`, `gpu_probe.rs` — the runtime Vulkan device probe, ADR-085).
- **Compiled backend reporting + model selection** — `crates/speedwave-runtime/src/transcription/accel.rs` (`compiled_backends()`, `live_model_for_this_build()`, `finalize_model_for_this_build()`, `decode_threads()`).
- **Model catalog SSOT** — `crates/speedwave-runtime/src/transcription/model_catalog.rs` (the Whisper GGML model entries; see [ADR-075](ADR-075-remove-speaker-diarization.md) for the removal of the former speaker-embedding/segmentation entries).
- **Download/verify** — `crates/speedwave-runtime/src/transcription/model_store.rs` (streamed download, on-the-fly SHA256, atomic rename, redirect-host allowlist).
- **Settings UI** — `desktop/src/src/app/settings/transcription-section/` (acceleration label + per-pass download/remove rows — live and, where the host class splits the pair, finalize — driven by the `recommended_transcription_model` command).
- **Feature wiring** — `crates/speedwave-runtime/Cargo.toml` (`audio-transcription` feature) and `desktop/src-tauri/Cargo.toml` (Desktop enables it).
- **Tauri command layer** — `desktop/src-tauri/src/transcription_cmd.rs`.
- **Mic consent (Amendment 5):** `desktop/src-tauri/src/mic_permission_cmd.rs` (the sole `objc2-av-foundation` FFI boundary) plus the pre-start gate in `recording-controls.component.ts`; the main-app entitlement rides `tauri.macos.conf.json` `bundle.macOS.entitlements`.
- **macOS capture CLI** — `native/macos/audio-capture/` (embedded `Info.plist` with `NSAudioCaptureUsageDescription` + `NSMicrophoneUsageDescription` via the `-sectcreate __TEXT __info_plist` linker flag). It is signed by `scripts/sign-bundled-binaries.sh`, which calls `codesign --sign` _without_ an explicit `--identifier` — the signing identifier comes from the embedded `CFBundleIdentifier`, and the script then verifies that identifier equals `pl.speedwave.desktop.audio-capture` (so TCC binds the row to the right identifier, per ADR-049). Bundle membership is the `tauri.macos.conf.json` ↔ `sign-bundled-binaries.sh` SSOT-alignment pair.

## Rejected alternatives

- **ScreenCaptureKit for macOS audio** — has a public consent API but requires the heavyweight Screen Recording permission and has audio-only defects on macOS 15 (unverified); Core Audio taps were chosen instead.
- **A containerized MCP worker / plugin** — impossible: containers have no host-audio path, and the "credential" here is host device access, not an isolatable service token.
- **A BlackHole/Loopback virtual audio driver on macOS** — needs a third-party kext/DriverKit install; incompatible with "single installable app" and a notarization nightmare. At most a documented "advanced" note.
- **CUDA/Vulkan GPU acceleration in v1** — compile-time backends mean separate CI toolchains and build artifacts; deferred (YAGNI), not rejected forever.
- **Reusing the JSON-patch protocol (ADR-042) for the live transcript** — overkill for an append-mostly transcript with coarse "replace last N segments" operations; only the history-plus-live delivery semantics were adopted.

## Known limitations

- macOS depends on a private TCC API for the system-audio consent prompt; it is `dlopen`-guarded and degrades to a manual System-Settings path if the symbol ever disappears.
- Polish transcription quality is bounded by Whisper itself (the ~25–30% conversational-PL WER floor is industry-wide, unverified), not by this integration; the UI carries an honest disclaimer.
- `large-v3` is a multi-gigabyte on-demand download; the UI is explicit about disk/network cost before the first download.
- The Whisper GGML weights are SHA256-pinned and served over HTTPS from an allowlisted host; there is no independent published audit that the converted files are bit-identical to OpenAI's checkpoints — a build-from-source-in-CI conversion is a possible follow-up, not a v1 requirement.

[^1]: A process tap created without the "System Audio Recording" consent delivers zeroed buffers instead of erroring - the same behaviour AudioCap documents for its private-TCC prompt flow: <https://github.com/insidegui/AudioCap>.

[^2]: Windows assigns the eCommunications role to a communications device (e.g. a headset) separately from the eConsole role: <https://learn.microsoft.com/en-us/windows/win32/coreaudio/using-the-communication-device>.

[^3]: WASAPI loopback captures the stream a render endpoint is playing: <https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording>. That an idle endpoint delivers no capture packets is observed behaviour (the capture loop's event wait simply times out), not documented - hence the wall-clock anchoring.

[^4]: `AVAudioEngineConfigurationChange` fires when the engine's I/O configuration changes (e.g. the default input device switches) and the engine stops: <https://developer.apple.com/documentation/avfaudio/avaudioengine/1386261-configurationchangenotification>.

[^5]: `AVCaptureDevice.requestAccess(for:)` prompts only on first use, reports the recorded decision on every later call, and may invoke its completion handler on an arbitrary dispatch queue: <https://developer.apple.com/documentation/avfoundation/avcapturedevice/1624584-requestaccess>. That the prompt never appears when the caller is a headless (non-GUI) helper process is observed behaviour from production diagnostics, not documented.

[^6]: LocalAgreement (emit only the prefix successive streaming decodes agree on) is the established stabilization policy for streaming Whisper: <https://github.com/ufal/whisper_streaming>. It operates on words, not whole segments; the segment-level variant tried here stalls on Whisper's pass-to-pass re-segmentation, which is why the shipped policy gates on segment age instead.

[^7]: Core Audio Process Taps became usable in macOS 14.2, with a 14.4 deployment target recommended for correct TCC permission categorization, and are the audio-only alternative to ScreenCaptureKit's screen-recording-shaped permission model: <https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html>.

[^8]: whisper.cpp is MIT-licensed: <https://github.com/ggml-org/whisper.cpp/blob/master/LICENSE>.

[^9]: Hugging Face file downloads redirect from `huggingface.co` to separate CDN hostnames (e.g. `cdn-lfs.hf.co`, `cdn-lfs-us-1.hf.co`): <https://discuss.huggingface.co/t/how-to-get-a-list-of-all-huggingface-download-redirections-to-whitelist/30486>.

[^10]: GitHub release asset download URLs return a 302 redirect to a signed, time-limited URL on another host: <https://github.com/orgs/community/discussions/46420>.

[^11]: Whisper hallucinates fluent, fabricated transcriptions on non-speech audio; an effective VAD (Silero) significantly reduces both WER and hallucination incidence, including for Polish: <https://arxiv.org/html/2501.11378v1>.

[^12]: whisper.cpp ships built-in Silero VAD support (GGML-converted model, `--vad` in whisper-cli, standalone `whisper_vad_*` C API): <https://github.com/ggml-org/whisper.cpp/issues/3003>. Exposed by `whisper-rs` 0.16 as `WhisperVadContext` / `FullParams::enable_vad`: <https://docs.rs/whisper-rs/0.16.0/whisper_rs/struct.WhisperVadContext.html>.

[^13]: With the integrated VAD mode, whisper.cpp generates continuous timestamps over the concatenated speech segments, losing the original timeline's silence gaps: <https://github.com/ggml-org/whisper.cpp/issues/3634>.

[^14]: Silero VAD is MIT-licensed: <https://github.com/snakers4/silero-vad/blob/master/LICENSE>.

[^15]: The GGML conversions of the Silero VAD models are published by the whisper.cpp maintainers at <https://huggingface.co/ggml-org/whisper-vad>.

[^16]: whisper.cpp defaults `n_threads` to `std::min(4, std::thread::hardware_concurrency())` in `whisper_full_default_params`, and `whisper_full_with_state` clears `result_all` and both accumulated prompt buffers at the start of every call when `no_context` is set: <https://github.com/ggml-org/whisper.cpp/blob/master/src/whisper.cpp>. Both were verified against the copy `whisper-rs-sys` 0.15 vendors.

[^17]: `large-v3-turbo` is a pruned, finetuned `large-v3` whose decoder drops from 32 layers to 4, which is where its CPU speedup comes from: <https://huggingface.co/openai/whisper-large-v3-turbo>.

[^18]: whisper.cpp pads/truncates every `whisper_full` input to a fixed 30 s chunk (`WHISPER_CHUNK_SIZE`), so the encoder runs over 30 s regardless of the audio's real length; its stream example counteracts exactly this with a reduced `audio_ctx` (`--audio-ctx`, "speed up encoder by trading accuracy"): <https://github.com/ggml-org/whisper.cpp/tree/master/examples/stream>.
