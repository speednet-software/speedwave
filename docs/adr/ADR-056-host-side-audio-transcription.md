# ADR-056: Host-Side Audio Capture and Local Meeting Transcription

## Status

Proposed (2026-05-11). **Three validation spikes (0A build/link ML, 0B host audio capture, 0C model catalog) gate acceptance** — see [Spike findings](#spike-findings). This ADR is not Accepted until all three spikes pass; if a spike surfaces a blocker, the relevant decision below is revised before any implementation begins.

## Context

Speedwave's core threat model puts Claude in a hardened, token-free container with no host device access — no microphone, no audio output, no camera (see [security model](../architecture/security.md), [containers](../architecture/containers.md)). A requested feature — _record a meeting (Slack / Teams / Meet / any app), transcribe it live with speaker labels, locally, then optionally hand the transcript to Claude_ — therefore **cannot** be a containerized MCP worker or a plugin: plugins are containers ([ADR-051](ADR-051-plugin-signature-runtime-verification.md), CLAUDE.md plugin contract), and a container has no path to host audio. Capturing system audio plus the user's microphone is also a privacy-sensitive host capability that must be visibly opt-in and shipped/signed by Speedwave, not pulled in as a third-party plugin.

The natural home is therefore the **host side** — the Tauri/Desktop process and bundled native helpers — alongside the existing `mcp-os` host worker and the native macOS CLIs (`calendar-cli`, `mail-cli`, `notes-cli`, `reminders-cli`).

There is no single cross-platform API for "capture the system's audio output". macOS, Windows, and Linux each expose a different mechanism with different OS-version floors, permission models, and per-process vs system-wide granularity. Whisper (the obvious local speech-to-text engine) does **not** do speaker diarization — that is a separate model. And "high-quality Polish transcription" rules out the small Whisper models for the _live_ path on CPU, so the live and final-quality transcription strategies must differ.

This ADR records the architectural decisions for building this as a **built-in, opt-in Desktop module**.

## Decision

Build "Meeting transcription" as a **built-in Desktop module**, off by default, enabled via a top-level user setting. All non-UI logic lives in `crates/speedwave-runtime/` behind a Cargo feature `audio-transcription`; the Tauri command layer (`desktop/src-tauri/src/transcription_cmd.rs`) is thin; the UI is a new top-level Angular tab. The fifteen sub-decisions:

### 1. Built-in Desktop module, not a plugin

Plugins are containers with no host audio access ([ADR-051](ADR-051-plugin-signature-runtime-verification.md), CLAUDE.md "Plugins" contract). Host audio + microphone capture is privacy-sensitive and must be visibly opt-in and signed by Speedwave. This module follows the existing host-side precedent: a `speedwave-runtime` SSOT layer (like `ContainerRuntime`), thin Tauri commands (like `system_settings_cmd.rs`), and — on macOS — a bundled signed native CLI (like `calendar-cli`, [ADR-049](ADR-049-tcc-sub-identifiers-and-applevents-gate.md)).[^1]

### 2. macOS capture = CoreAudio process taps (macOS 14.4+), not ScreenCaptureKit

macOS provides `AudioHardwareCreateProcessTap` + `AudioHardwareCreateAggregateDevice` (introduced macOS 14.2, usable in practice from 14.4) for capturing audio from a chosen process (Slack, Teams, a browser) or the whole system. Apple's guidance is to use a Core Audio tap rather than ScreenCaptureKit when capturing audio only.[^2][^3] ScreenCaptureKit has known audio-only defects on macOS 15 (`SCStreamErrorDomain -3805`, missing callbacks in audio-only mode).[^4] **Baseline for this feature is macOS 14.4+** — the rest of Speedwave keeps its current floor. Swift Package granularity is `.macOS(.v14)`, so 14.4 is enforced at runtime via `if #available(macOS 14.4, *)`; older macOS gets a clean "macOS 14.4+ required" message and the feature is unavailable there (the Desktop app otherwise works). Reference implementations exist and will be adapted (not reimplemented from scratch): `insidegui/AudioCap` (the tap + aggregate-device setup),[^5] and `AudioTee` (a Swift CLI streaming system audio to stdout as 16 kHz mono in ~200 ms chunks for ASR — essentially this use case).[^6]

### 3. macOS permissions = `NSAudioCaptureUsageDescription` (system audio) + `NSMicrophoneUsageDescription` (mic) — and the audio-capture consent prompt has no public trigger, so a private-API preflight + a Settings-deep-link fallback is needed

Capturing the user's own microphone uses `NSMicrophoneUsageDescription` and `AVCaptureDevice.requestAccess(for: .audio)`, which **does** show a consent prompt — that half is straightforward. The _system-audio_ half is not: spike 0B found that `AudioHardwareCreateProcessTap` **does not trigger the "System Audio Recording" consent prompt and silently returns zeroed buffers when the permission is absent** — no error, no prompt. There is **no public API to trigger that prompt or to check its status** (unlike the microphone) — `AudioCap` resorts to a private TCC API (`TCCAccessPreflight`/`TCCAccessRequest`) for exactly this. **Decision (revised after spike 0B; committed in R6):** Speedwave's `audio-capture-cli` calls the **private `TCCAccessRequest` API (service `kTCCServiceAudioCapture`) to request the system-audio permission** before opening a process tap — this triggers the native consent prompt ("Speedwave wants to record audio from apps on this Mac"), which is what `AudioCap`, `AudioTee`, and `BackgroundMusic` all do, and works on a notarized `.dmg` (not a sandboxed App Store app — so no App Store rejection risk; it is, however, a risk surface against future macOS, so it is isolated to one small `dlopen`/`dlsym`-guarded code path that degrades gracefully — if the symbol ever disappears, the CLI exits "permission unavailable" and the UI falls back to the manual path below, rather than crashing). The microphone half uses the public `AVCaptureDevice.requestAccess(for: .audio)` (no private API). **Fallback** when the request reports "denied": the UI deep-links the user to System Settings → Privacy & Security → "System Audio Recording Only" (the `system_settings_cmd.rs` pattern), and the CLI also self-detects "silence for N seconds while audio is demonstrably playing" as a corroborating signal. Rejected alternative: ScreenCaptureKit audio capture — it has a _public_ consent API, but it requires the heavyweight Screen Recording permission (a misleading "record your screen" prompt for what is audio-only), has the macOS 15 audio-only defects noted in decision 2, and would be a second capture path in the CLI alongside the taps. The `#[allow(unsafe_code)]` on the `dlopen` block follows the established `desktop/src-tauri/src/fs_perms.rs` precedent (a guarded private-platform-API call with a comment citing this ADR). As with the other native CLIs ([ADR-049](ADR-049-tcc-sub-identifiers-and-applevents-gate.md)), the CLI embeds its own `Info.plist` into the Mach-O (`-sectcreate __TEXT __info_plist`) with `NSAudioCaptureUsageDescription` + `NSMicrophoneUsageDescription`, **and must be signed with `codesign --identifier pl.speedwave.desktop.audio-capture`** — spike 0B confirmed that without `--identifier`, `codesign` defaults to the binary basename and TCC would bind the row to the wrong identifier (so `tccutil reset System Audio Recording pl.speedwave.desktop.audio-capture` would not clear it).

### 4. Windows capture = WASAPI loopback; per-process only on build 20348+; system-wide as the universal fallback

Windows offers per-process loopback via `ActivateAudioInterfaceAsync` with `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` and `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS { TargetProcessId, ProcessLoopbackMode }` (include-tree = "this app and children", exclude-tree = "everything except"). **The minimum is Windows 10 Build 20348** — not the 20H1/19041 build sometimes quoted.[^7][^8] Microsoft publishes an `ApplicationLoopback` C++ sample.[^9] On builds **below 20348, per-process loopback is unavailable** — the feature falls back to system-wide loopback via `AUDCLNT_STREAMFLAGS_LOOPBACK` (available since Windows 7),[^10] and the UI offers only "System-wide audio" with a tooltip explaining the requirement. Implementation goes through the `cpal` crate where it covers loopback;[^11] a thin `windows-sys` shim is used only if `cpal` does not expose per-process loopback (see decision 10). The runtime exposes `capabilities().supports_per_process` so the UI knows whether to offer a process picker.

### 5. Linux capture = PipeWire monitor sources, with PulseAudio `.monitor` fallback; shell out, don't touch ALSA

Linux audio capture depends on the running sound server. PipeWire (current distros) exposes monitor sources per node, recorded with `pw-record`;[^12] PulseAudio (older systems) exposes `<sink>.monitor` sources, recorded with `parec`.[^13] The implementation detects which server is running and **shells out** to `pw-record` / `parec` (KISS — the monitor-source dance through `cpal`/ALSA is fiddly and these CLIs are ubiquitous on the target distros). Per-app capture on PipeWire is straightforward (target a per-app stream node); on PulseAudio it requires moving a sink-input, which is fiddly — spike 0B decides whether per-app ships in v1 on PulseAudio or is PipeWire-only initially.

### 6. Transcription engine = whisper.cpp via `whisper-rs`; backends are compile-time; v1 ships CPU + Metal only

The engine is whisper.cpp (MIT) accessed through the `whisper-rs` crate (so we link `libwhisper` and avoid a sidecar process); `whisper-rs-sys`'s build script compiles whisper.cpp from its vendored submodule with `cmake` at build time (confirmed working — [spike 0A](#0a--buildlink-ml--macos-part-pass-2026-05-11)).[^14][^15] **whisper.cpp's acceleration backends — Metal, CUDA, Vulkan, CPU — are compile-time feature flags, not runtime detection**: the binary is built against a specific backend.[^15] **v1 ships CPU (all platforms) + Metal (macOS)** (the Metal shader library is embedded into the binary — no separate `.metallib` to ship). CUDA/Vulkan are deferred — they require a separate CI toolchain, separate build artifacts, and likely separate installers or feature-gated downloads; this is a follow-up, not a v1 promise. The runtime's `accel.rs` reports _which backends were compiled into this binary_, not what the host hardware could theoretically support. Rejected: faster-whisper, whisperX (Python + PyTorch — not bundlable as a self-contained app).

### 7. Speaker diarization = sherpa-onnx (official Rust crate); labels are explicitly provisional

Whisper does not identify speakers; its `tinydiarize` option only emits `[SPEAKER_TURN]` markers (turn detection, not "who"), which is insufficient.[^16] Diarization is done with sherpa-onnx (Apache-2.0, k2-fsa): speaker segmentation + speaker embedding + clustering, ONNX runtime, zero Python; it uses a pyannote segmentation model in ONNX form (k2-fsa's `sherpa-onnx-pyannote-segmentation-3-0` conversion — which carries an MIT licence inside its archive, so it is redistributable and can be bundled — confirmed in [spike 0C partials](#0c--model-catalog-legal--working-download--partial-findings-2026-05-11)) plus a NeMo TitaNet speaker-embedding model.[^17][^18] **The Rust binding is the official `sherpa-onnx` crate** (by `csukuangfj`, the sherpa-onnx author — `1.13.x`), **not** the third-party `sherpa-rs`: spike 0A found the official crate more current, exposing the full diarization pipeline (`OfflineSpeakerDiarization`, `OfflineSpeakerSegmentationPyannoteModelConfig`, `SpeakerEmbeddingExtractorConfig`, `FastClusteringConfig`), with its default `static` feature being the clean path (no `tts`/`download-binaries` extras).[^19][^20] Note: `sherpa-onnx-sys` does **not** build sherpa-onnx from source — it downloads a prebuilt **static** library archive (including a static `libonnxruntime`) from k2-fsa's GitHub releases at build time, which means the build needs network access (or `SHERPA_ONNX_LIB_DIR` set to a vendored copy) and those prebuilt archives need checksum verification in CI; but it also means there are **no shared libraries to bundle or sign** (everything links into the Rust binary — see decision 9). **Product-wise, speaker labels are "provisional"**: the live path is delayed and unstable under crosstalk, and the final offline pass re-clusters the whole recording with full context — cluster IDs are not stable across runs. The UI communicates this (a ⚠️ tooltip on speaker chips, a "labels are approximate" footer in the exported markdown, a "speaker labels were refined" note if the final pass changes them). It does not present diarization as certain identification. **Diarization quality on Polish multi-speaker audio is not yet measured** (spike 0A's diarization smoke test ran but a representative Polish recording was not available) — to be verified before relying on it; this is consistent with the "provisional" framing and is not a blocker. Rejected: pyannote.audio, whisperX (Python + PyTorch); `sherpa-onnx-reverb-diarization-v1` (non-commercial licence — unusable in a commercial product).

### 8. Polish/English strategy = forced language, two tiers; product promise is "best-effort live + higher-quality offline pass"

The UI has an explicit PL/EN toggle; the language is **forced** (`--language pl` / `--language en`), never auto-detected — forced language beats auto-detection on Whisper. Two tiers: the **live** path uses a fast model (`small` on CPU; `large-v3-turbo` only if the binary was compiled with Metal and the host is Apple Silicon — see decision 6); after recording stops, a **higher-quality offline pass** re-transcribes the whole recording with full `large-v3` (no latency pressure; if the user only downloaded `small`, the UI offers to fetch `large-v3` or skip the pass). `large-v3-turbo` is a distilled `large-v3` (decoder reduced from 32 to 4 layers, ~6–8× faster, quality within ~1–2% of `large-v3` for most languages but with an uneven drop on some — e.g. Thai, Cantonese; Polish is generally in the "OK, roughly large-v2 level" group).[^21][^22] **Public Polish WER benchmarks for `large-v3-turbo` are sparse** — recorded as a known risk; `medium` is in the catalog as a middle ground. The product promise is **"local best-effort live transcription + higher-quality offline final pass"**, not "perfect Polish/English". The UI and docs say so.

### 9. Model store = download-on-demand, SHA256-verified, streamed to disk, redirect-allowlisted

Whisper models (`ggml-*.bin` from **`ggerganov/whisper.cpp`** on Hugging Face — _not_ `ggml-org/whisper.cpp`, which returns HTTP 401 on anonymous requests; `tiny` ≈ 78 MiB … `large-v3` ≈ 2.9 GiB) and the diarization models (k2-fsa's `sherpa-onnx-pyannote-segmentation-3-0`, MIT, ≈ 7 MiB; plus a NeMo TitaNet embedding model, ≈ 40 MiB — both from `github.com/k2-fsa/sherpa-onnx/releases`) are **downloaded on demand**, not bundled, into `<data_dir>/models/whisper/` and `<data_dir>/models/diarization/` (directories `0o700`, files `0o600`). Exact URLs, SHA256 hashes, sizes, and licenses are an SSOT const in `speedwave-runtime` (`model_catalog.rs`), mirroring the `NERDCTL_FULL_SHA256_*` pattern in `consts.rs`. The downloader **does not copy `redirect::Policy::none()` from [ADR-041](ADR-041-local-llm-model-discovery.md)** — Hugging Face `302`-redirects model downloads to its Xet CDN (`cas-bridge.xethub.hf.co`) with a signed S3-style URL, and GitHub release assets `302`-redirect to `release-assets.githubusercontent.com` with a signed URL, so a `none` policy would break both; instead it uses `redirect::Policy::custom` with an **allowlist of redirect hosts** — at minimum `{ huggingface.co, cas-bridge.xethub.hf.co, github.com, release-assets.githubusercontent.com }`, finalized by spike 0C (HF CDN hostnames have changed before — an unrecognized redirect host produces a clear "model URL changed — report this" error rather than being followed).[^23][^24] Files are **streamed to disk while a SHA256 is computed on the fly** (not buffered in memory — these files are too large), written to a temp file in the same directory, and atomically renamed on success (the `tempdir_in` pattern used for plugin staging); on hash mismatch or interruption the temp file is removed and an error is returned. `Content-Length` is present on these responses, so download progress is exact. There is a per-model size cap from the catalog plus a global ceiling with headroom (~5 GiB, not a fixed 3 GiB). Progress events mirror the plugin-install-progress pattern ([ADR-047](ADR-047-plugin-install-progress-events.md)) and carry a `seq` (decision 11). **Model downloads use the network** — the UI says so before the first download. Otherwise hardening follows [ADR-041](ADR-041-local-llm-model-discovery.md) (request timeout; `Content-Type`-bounded where relevant) and reuses `desktop/src-tauri/src/http_util.rs` / `url_validation.rs` rather than re-implementing. (Note: this `model_catalog` SSOT covers the _runtime model downloads_. The sherpa-onnx + onnxruntime _static libraries_ — see decision 7 — are a separate, build-time prebuilt-archive download performed by `sherpa-onnx-sys` during `cargo build`; CI verifies those archives' checksums and the build needs network access for them, or a vendored `SHERPA_ONNX_LIB_DIR`.)

### 10. `unsafe_code = "deny"` interaction

The workspace and the desktop crate both set `unsafe_code = "deny"` (`Cargo.toml`, `desktop/src-tauri/Cargo.toml`). `whisper-rs`, the chosen sherpa crate, `cpal`, `hound`, and `reqwest` expose **safe** Rust APIs (their `unsafe` is internal), so this module writes **zero** `unsafe` and needs no `#[allow(unsafe_code)]`. The only potential exception is a `windows-sys` shim for `ActivateAudioInterfaceAsync` _if_ `cpal` does not cover per-process loopback (decision 4); that shim, if needed, gets the `#[allow(unsafe_code)]`-with-justifying-comment treatment already established at `desktop/src-tauri/src/fs_perms.rs:136`.[^25] All transcription dependencies stay in `speedwave-runtime` behind the `audio-transcription` feature, so the CLI crate stays lean.

### 11. Live-transcript transport = an append-only event stream with `seq` + snapshot recovery (not the JSON-patch protocol, not a plain broadcast)

A plain `tokio::sync::broadcast` would **lose events** if the frontend subscribes after recording has already started. The transport therefore copies the _delivery semantics_ of `MsgStore::history_plus_stream()` ([ADR-043](ADR-043-msgstore-history-plus-stream.md), `subscribe_cmd.rs`): `subscribe_transcript(session_id)` returns **a snapshot of the current session state plus the event name**; every `TranscriptEvent` carries a monotonic `seq`; the Angular reducer is **idempotent** (ignores `seq` ≤ last applied) and on re-subscribe replays from the snapshot. The `TranscriptEvent` enum — `SegmentAppended{seq,segment}`, `SegmentsReplaced{seq,from_index,segments}` (sliding-window re-decode), `SpeakerAssigned{seq,segment_index,speaker}`, `StatusChanged{seq,status}`, `FinalizeProgress{seq,done_ms,total_ms}`, `Finished{seq}` — is far simpler than reusing `patch_emitter.rs` (882 lines) and `MsgStoreRegistry`, because a transcript is append-mostly with coarse "replace last N segments" operations rather than fine-grained RFC 6902 patches; but the _delivery_ (history + live, monotonic seq) is the same proven pattern. The full JSON-patch protocol ([ADR-042](ADR-042-json-patch-stream-protocol.md)) was considered and only its delivery semantics adopted.

### 12. Capture child-process lifecycle mirrors `mcp_os_process.rs`

The OS-CLI-based capture paths (the macOS `audio-capture-cli`; the Linux `pw-record` / `parec` child) reuse the discipline of `desktop/src-tauri/src/mcp_os_process.rs`: `Stdio::piped()`; a PID file written immediately (under `<data_dir>/transcripts/<id>/capture.pid`); `kill_stale_by_pid_file` on respawn; background threads draining **both** stdout and stderr (drain both or a full pipe buffer SIGPIPEs the child); `env_clear()` plus selective re-injection; `write_restricted_file` for any token. The Windows `cpal`-in-process path is a Rust thread, not a child process, so that branch is simpler.

### 13. Opt-in toggle = top-level user config only, off by default, no repo/project override

The enable toggle is a field on the **top-level user config** (`crates/speedwave-runtime/src/config.rs`, ~line 183), default off — **not** on `IntegrationsConfig`, **not** resolvable from a repo `.speedwave.json`. `resolve_project_config` does not read it; it is exposed via a separate getter (`user_config.transcription()`). A repo `.speedwave.json` setting `transcription.enabled = true` is **ignored** (a checked-in repo file must not be able to turn on host audio recording — this is a privacy-sensitive host capability, not project configuration; same spirit as why repo config cannot override `provider`/`base_url` in [ADR-040](ADR-040-remove-litellm-direct-provider-injection.md)/[ADR-041](ADR-041-local-llm-model-discovery.md)). The "Meeting transcription" tab is always visible in the nav but shows an "Enable in Settings →" empty state until the toggle is on (mirroring how the Chat tab shows an inline "auth required" block rather than hiding itself).

### 14. Audio retention + third-party licenses

Recorded audio lives at `<data_dir>/transcripts/<id>/audio.wav` (`0o600`). **Retention policy**: by default the WAV is kept after the final pass (re-transcription may be wanted), but the UI provides (a) "delete transcript" (removes the whole directory), (b) "discard audio, keep transcript" after the final pass (smaller disk footprint; `audio_path → None`; re-transcription then impossible), and (c) a "models use X GB on disk" line. There is **no automatic retention/expiry in v1** — the user deletes manually; this is a deliberate decision, not an oversight. **Licenses** added to `desktop/src-tauri/THIRD-PARTY-LICENSES/` (lowercase-hyphen naming, matching `lima-LICENSE`): `whisper-cpp-LICENSE` (MIT), `sherpa-onnx-LICENSE` (Apache-2.0), `onnxruntime-LICENSE` (MIT — onnxruntime ships as part of the sherpa-onnx prebuilt static archive, see decision 7), `whisper-models-LICENSE` (the OpenAI Whisper weights are MIT), `diarization-models-LICENSE` (k2-fsa's `sherpa-onnx-pyannote-segmentation-3-0` ships an MIT licence — CNRS 2022 — inside its archive, confirmed in [spike 0C partials](#0c--model-catalog-legal--working-download--partial-findings-2026-05-11), so it is redistributable and bundled; the chosen NeMo TitaNet speaker-embedding model's exact licence is to be confirmed in the full 0C — NeMo models are typically Apache-2.0).[^14][^17][^21]

### 15. Mixed capture (system loopback + microphone) is the product default

The headphones scenario is the real use case: on a Teams/Slack call with headphones on and the mic live, neither the system loopback alone (you can't hear yourself) nor the mic alone (you can't hear the others) is enough — Speedwave must capture **both, mixed**. `AudioSource::Mixed { system, mic }` does this; the captured streams are mixed down to **one 16 kHz mono stream** before the engine sees them, so `TranscriptDriver` is unchanged (the `AudioChunk` contract already says "the backend has already mixed"). Mixing uses each platform's own primitive: on macOS the aggregate device contains the process-tap sub-device **and** the input device — CoreAudio delivers one IOProc buffer per cycle with both sub-devices' channels, which the CLI downmixes and sums into stream 0 (no separate mic engine in the mixed path); on Windows two concurrent `cpal` streams (the default output device's loopback + the chosen input device) are summed sample-for-sample in a small shared ring buffer; on Linux two concurrent `pw-record` / `parec` children (a monitor source + a mic source, both already 16 kHz mono `f32`) are summed by the reader. The sum uses a fixed 0.5/0.5 gain with a ±1 clamp (no ducking, no per-stream gain UI — YAGNI); a side with no samples yet is padded with silence so a muted mic or a silent system doesn't stall the stream. The picker offers `Mixed { SystemWide, default mic }` as the default-selected entry ("Whole meeting (system audio + your microphone)"); per-process-mixed ("just Teams + your mic") and an explicit mic device in the mix are trivial follow-ups — the `AudioSource::Mixed` type already carries `system: Box<AudioSource>` and `mic: Option<String>`. On macOS this triggers **two** consent prompts the first time (microphone via the public API, then system audio via the private API of decision 3); the UI says so. This also corroborates the "poor man's diarization" note in the 0A findings — the mic is "your side", the loopback is "their side" — but v1 mixes them into one stream and relies on sherpa-onnx for `[Speaker N]`; keeping the two streams separate for channel-based diarization is a possible follow-up, not v1 scope (it would mean `TranscriptDriver` taking two streams).[^2][^11][^12][^13]

### 0A — build/link ML — **macOS part: PASS (2026-05-11)**

A throwaway crate (`whisper-rs 0.16` with the `metal` feature + `sherpa-onnx 1.13.1`) was built and run on an Apple Silicon Mac (macOS 26.4, Xcode 21, Rust 1.94). Results:

- **It builds and links.** `whisper-rs-sys 0.15` compiles whisper.cpp from its vendored submodule with `cmake` during `cargo build`; `sherpa-onnx-sys 1.13.1` does **not** compile sherpa-onnx from source — its build script downloads a matching **prebuilt static-library archive** from k2-fsa's GitHub releases (`sherpa-onnx-v1.13.1-osx-arm64-static-lib.tar.bz2`, ~18 MiB; contains `libsherpa-onnx-c-api.a`, `libonnxruntime.a`, and friends). So **`cmake` is required for whisper.cpp only**; sherpa-onnx + onnxruntime arrive prebuilt. **Implication for CI: the build needs network access** (or `SHERPA_ONNX_LIB_DIR` pointing at a vendored copy) — an air-gapped build is not possible out of the box.
- **Static linking ⇒ no shared libraries to bundle.** With the crates' default `static` linking, whisper.cpp and sherpa-onnx + onnxruntime are linked into the Rust binary; the release binary's only dynamic dependencies are macOS system frameworks (`libc++`, `Accelerate`, `Foundation`, `Metal`, `MetalKit`, `CoreFoundation`, `libobjc`, `libSystem`). **This simplifies decision 9: no `.dylib`/`.so`/`.dll` entries in `bundle.resources`, no extra binaries to sign.** (The Metal shader library is embedded into the binary — `WHISPER : Metal : EMBED_LIBRARY = 1` — so no separate `.metallib` to ship either.)
- **`unsafe_code = "deny"` passes unchanged** — the `unsafe` lives inside the bindings crates, not at our call sites.
- **No global `rustflags` needed.** `whisper-rs-sys`'s build script emits the `libc++` / `Accelerate` / `Metal` link directives itself; the `[target.aarch64-apple-darwin] rustflags = "-lc++ -l framework=Accelerate"` that `whisper-rs`'s BUILDING.md mentions was **not** necessary in this spike. The real `speedwave-runtime` crate does not need a global `.cargo/config.toml` change.
- **Build time** (Apple Silicon, cold cache): debug ~37 s, release ~27 s for the whole tree (whisper.cpp compilation included). The "a few minutes slower in CI" assumption holds.
- **Runtime smoke test passed.** whisper.cpp (Metal): `ggml-base.bin` loaded in ~60–200 ms; transcribing a 3 s synthetic buffer took ~307 ms; forced `--language pl` worked (output came back in Polish). sherpa-onnx: `OfflineSpeakerDiarization` (pyannote-segmentation-3.0 + NeMo TitaNet-small embedding) constructed in ~64 ms (both ONNX models + the ONNX runtime loaded); `process()` ran without error.
- **Real Polish transcription verified.** An 18 s microphone recording (the dev's voice + a radio playing in the background — genuine speech, not a synthetic tone) was transcribed with `base`, `small`, and `medium`, forced `--language pl`: all three returned intelligible Polish with correct punctuation (e.g. _"Mam nadzieję, że to słyszysz ty teraz, to ja mówię przez mikrofon, który widzę, że jest włączony…"_); `medium` was clearly the best (got _"spróbujesz"_ right where `base`/`small` mangled it; better punctuation than `small`), `small` a middle ground, `base` "OK-ish" — exactly as decision 8 frames it. RTF on Apple Silicon + Metal: `base` ≈ 0.01, `small` ≈ 0.02, `medium` ≈ 0.06 (all far below 1 — even `medium` keeps up with real time on Metal; on CPU-only `medium` would be near the live boundary, which is why the CPU live model is `small` and the finalize model is `large-v3`). Crosstalk (the radio overlapping the dev's voice) was not handled well by any model — exactly the case where diarization (separating "radio" from "the user") would help. **This closes the "PL transcription accuracy unverified" open item.** (The model `model_catalog` SHA256 values for `small` and `medium` were also confirmed by computing them on the downloaded files — a second confirmation of 0C's catalog.)
- **Crate decision: use the official `sherpa-onnx` crate** (by `csukuangfj`, the sherpa-onnx author — `1.13.1`, May 2026), **not** the third-party `sherpa-rs` (`0.6.8`, Oct 2025). The official crate is more current, exposes the full diarization pipeline (`OfflineSpeakerDiarization`, `OfflineSpeakerSegmentationPyannoteModelConfig`, `SpeakerEmbeddingExtractorConfig`, `FastClusteringConfig`), and its default `static` feature is the clean path (no `tts`/`download-binaries` extras to disable). This updates decision 7.
- **Source-build vs prebuilt — decision 6/9 corrected.** The user's "build everything from source via crate build scripts" assumption is half right: whisper.cpp **is** built from source (cmake, vendored submodule); sherpa-onnx + onnxruntime are **prebuilt static libs** downloaded at build time. That is fine — prebuilt static is clean (no shared libs, no separate signing) — but the CI/Makefile work for `download-ml-libs`-style verification of those prebuilt archives, and the network-during-build requirement, must be in the plan.

- **Diarization on real audio — mechanically works, quality confirms the "provisional" framing.** `OfflineSpeakerDiarization` (pyannote-segmentation-3.0 + NeMo TitaNet-small) was run on two real microphone recordings (a single dominant voice + background radio; and a recording where the dev deliberately impersonated two voices). It produced sensible structures — turns with timestamps, automatic speaker-count estimation, clustering, RTF ≈ 0.04 — but the _quality_ on this hard material was low: the dominant-voice-plus-radio recording came back as **1 speaker** (the radio was too "smeared" through the room acoustics to register as a distinct speaker), and the impersonated-two-voices recording came back as **3 speakers with overlapping turns** (over-segmentation; the "second voice" wasn't consistently distinct, and crosstalk produced overlapping segments). Whisper itself returned a `[PYTANIE]` placeholder on the impersonated-voices recording — it does not handle crosstalk. **This is exactly what decision 7 says**: on mixed-through-the-air audio with one dominant speaker, ML clustering of a single stream is unreliable; the UI must present `[Speaker N]` as _approximate_ (⚠️ tooltip, "labels are approximate" footer), not certain identification. It also confirms the value of the "poor man's diarization" angle for Speedwave's actual use case — the user's microphone as one channel ("[You]") and the app loopback as another channel ("[Meeting]") is more robust than clustering one mixed stream, and Whisper transcribes each cleanly because they aren't crosstalking. A proper diarization-quality test still wants a recording with genuinely distinct, well-separated speakers (e.g. a real meeting recording, or two people alternating clearly into one mic) — to be done later; the pipeline is proven, the quality ceiling on hard material is now known.

Still open in 0A: **Windows and Linux builds** (no host machines available locally — to be done on the user's machines or in CI). (PL transcription and the diarization pipeline are now both verified on real audio — see above.)

### 0B — host audio capture — **macOS part: mechanically PASS, TCC-trigger gap surfaced (2026-05-11)**

A throwaway Swift CLI (`Package.swift` `.macOS(.v14)`, embedded `Info.plist` with `NSAudioCaptureUsageDescription` + `NSMicrophoneUsageDescription` via `-sectcreate __TEXT __info_plist`, ad-hoc signed) was built and run on macOS 26.4. Results:

- **The CoreAudio process-tap pipeline works mechanically.** Enumerating audio processes (`kAudioHardwarePropertyProcessObjectList` → `kAudioProcessPropertyPID` / `kAudioProcessPropertyBundleID`) returned 25 processes with PIDs and bundle IDs. `AudioHardwareCreateProcessTap` (system-wide: `CATapDescription(stereoGlobalTapButExcludeProcesses: [])`) created a tap; `AudioHardwareCreateAggregateDevice` with `kAudioAggregateDeviceTapListKey` created the aggregate device; `kAudioTapPropertyFormat` reported `48000 Hz, 2 ch, 32-bit float lpcm` (so the production CLI resamples to 16 kHz mono, as AudioTee does); `AudioDeviceCreateIOProcIDWithBlock` + `AudioDeviceStart` delivered buffers (96 256 frames/s = 48 000 × 2 — correct); teardown in reverse order (`AudioDeviceStop` → `AudioDeviceDestroyIOProcID` → `AudioHardwareDestroyAggregateDevice` → `AudioHardwareDestroyProcessTap`) was clean (exit 0).
- **The taps API requires `@available(macOS 14.2, *)`** — `Package.swift`'s `.macOS(.v14)` granularity is not enough; the call sites must be runtime-gated (and on macOS < 14.2/14.4 the CLI exits with a clean "14.4+ required" message). This confirms decision 2's runtime-gating note.
- **CoreAudio reads `CFBundleIdentifier` from the embedded `__info_plist`** — on `--list` the spike's own process appeared as `pl.speedwave.desktop.audio-capture-spike` (the embedded value), not the binary basename. But `codesign -dv` reports `Identifier=audio-capture-spike` (the basename) for an ad-hoc-signed binary — TCC would bind the permission row to the _wrong_ identifier. This is exactly the ADR-049 problem; the production CLI must be signed with `codesign --identifier pl.speedwave.desktop.audio-capture` (as `sign-bundled-binaries.sh` does for the existing CLIs).
- **⚠️ The TCC prompt does not appear on its own, and `AudioHardwareCreateProcessTap` silently returns silence (zeroed buffers) when the app lacks the "Audio Recording" permission** — no error, no prompt; the IOProc just receives zeros (`peak == 0.0` while system sounds were playing; `TCC.db` had no row for the binary). This is exactly the gap AudioCap papers over with a **private TCC API** (`TCCAccessPreflight`/`TCCAccessRequest`): Apple provides no public API to _trigger_ the audio-capture consent prompt or to _check_ its status (unlike the microphone, which has `AVCaptureDevice.requestAccess(for: .audio)`). An ad-hoc-signed CLI launched from a terminal doesn't even appear in System Settings → Privacy → "System Audio Recording Only", so it can't be granted manually either.

  **This corrects decision 3.** Embedded `Info.plist` + `AudioHardwareCreateProcessTap` is necessary but _not sufficient_. Phase 4 must pick one (likely a combination): **(a)** use the private TCC API only to _preflight/request_ the audio-capture permission (this is what `AudioCap` does — it does not block notarization since Speedwave is a notarized `.dmg`, not an App Store app, though it is a risk surface against future macOS); **(b)** verify whether TCC inherits from a properly Developer-ID-signed parent `.app` across `posix_spawn` for the audio-capture service specifically (ADR-049 says it does not for the EventKit/AppleEvents CLIs — the embedded-plist workaround exists for that reason — but it should be re-confirmed for `kTCCServiceAudioCapture`); **(c)** detect "silence for N seconds while audio is demonstrably playing" as a "permission likely denied" signal and deep-link the user to System Settings → Privacy → System Audio Recording (combined with a properly-signed binary so the entry actually shows up). The leading candidate is **a real Developer ID signature with `--identifier` + (a) the private API for preflight/request only + (c) as the fallback** when preflight reports "denied".

- **The mic side has a public path** — capturing the user's own microphone uses `AVCaptureDevice.requestAccess(for: .audio)`, which _does_ show a prompt; only the _system-audio_ side has the gap above. So the two halves of "system audio + my mic" have different permission stories: mic = public API + prompt; system audio = private-API-or-fallback.

Still open in 0B: a full happy-path test _with the audio-capture permission actually granted_ (impossible for an ad-hoc-signed terminal binary — deferred to Phase 4 on the real signed `audio-capture-cli`); the per-process tap (a specific PID — only the system-wide tap was exercised; behaviour should be analogous); the **frozen stdout framing protocol** (JSON header + length-prefixed chunks, ~200 ms — designed but not yet written, since the spike used direct IOProc stats rather than streaming to stdout); and the **Windows and Linux** parts (no host machines available locally — to be done on the user's machines or in CI).

### 0C — model catalog (legal + working download) — **PASS (2026-05-11)**

- **Whisper model source is `ggerganov/whisper.cpp` on Hugging Face, NOT `ggml-org/whisper.cpp`.** The `ggml-org/whisper.cpp` repo returns `HTTP 401 "Invalid username or password"` on anonymous `resolve/` requests (gated or removed); `huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-*.bin` works, `302`-redirects to the HF Xet CDN, and `Content-Length` is present (so download progress is exact). **This corrects decision 9 and footnote ^24.**
- **Redirect-host allowlist (decision 9) — confirmed:** Hugging Face `302`-redirects file downloads to **`cas-bridge.xethub.hf.co`** (the HF Xet CDN — _not_ the older `cdn-lfs*.huggingface.co`), with a signed S3-style URL (`X-Amz-Signature`, `Expires` ~1 h). GitHub release assets (the sherpa-onnx models, and `sherpa-onnx-sys`'s prebuilt-lib archive) redirect to **`release-assets.githubusercontent.com`** with a signed URL (JWT + `X-Amz`-style params). Both confirm `redirect::Policy::none()` would break the download. **The frozen allowlist is `{ huggingface.co, cas-bridge.xethub.hf.co, github.com, release-assets.githubusercontent.com }`** (subdomain matches allowed); an unrecognized redirect host produces a "model URL changed — report this" error (HF CDN hostnames have changed before).
- **Downloader strategy works against the real CDN.** A `reqwest::blocking` client with `redirect::Policy::custom` (host-allowlist check + 10-hop cap) was used to fetch `ggml-tiny.bin` through the HF `302` → `cas-bridge.xethub.hf.co` chain, streaming to a `.part` temp file in the destination directory while computing SHA256 on the fly, verifying against the expected hash, then atomically renaming into place — **PASS** (78 MiB in ~3 s, hash matched the HF-API-reported value). The hash-mismatch path was also exercised: on a wrong expected hash the download still completes, the mismatch is detected, the `.part` temp is removed, and no partial final file is left — **PASS**. (The "redirect to a non-allowlisted host is refused" negative test was inconclusive only because the public echo service used returned `402` — the allowlist _acceptance_ path is proven by the HF fetch, and the refusal path is a one-liner; it will be covered properly with `mockito` in Phase 1b.)
- **Diarization model licences — confirmed:** `sherpa-onnx-pyannote-segmentation-3-0` (k2-fsa's ONNX conversion of `pyannote/segmentation-3.0`) ships an **MIT licence** (CNRS 2022) inside its archive — **redistributable, bundled** (the gated/click-through concern for "raw" pyannote on HF does not apply). `nemo_en_titanet_small` (the speaker-embedding model used) is **CC-BY-4.0** (NVIDIA NGC — requires attribution; included in `THIRD-PARTY-LICENSES`). **De-risks decisions 7 and 14.** The non-commercial `sherpa-onnx-reverb-diarization-v1` is rejected.
- **No purely-multilingual speaker-embedding model exists in sherpa-onnx's catalog** — all options (NeMo TitaNet/SpeakerNet, WeSpeaker, 3D-Speaker CAM++/ERes2Net) are EN- or ZH-trained. `nemo_en_titanet_small.onnx` (≈ 40 MiB, CC-BY-4.0, the model sherpa's own examples recommend) is the default; speaker embeddings are largely language-agnostic (they model voice timbre, not phonology), so it should work acceptably on Polish — if it underperforms, `wespeaker_en_voxceleb_resnet34_LM` (≈ 26 MiB) or a 3D-Speaker model is a drop-in alternative (the catalog can carry alternates). To be measured alongside the open "diarization quality on Polish audio" item from 0A.

## Rejected alternatives

### A. ScreenCaptureKit for macOS audio capture

Rejected in favor of CoreAudio process taps (decision 2): Apple recommends taps for audio-only capture; ScreenCaptureKit additionally requires the heavyweight Screen Recording permission and has known audio-only defects on macOS 15.[^2][^4]

### B. A containerized MCP worker / plugin for transcription

Impossible: containers have no host audio access, and the credential-isolation model has nothing to isolate here — the "credential" is access to the user's microphone and screen audio, which is a host capability ([ADR-051](ADR-051-plugin-signature-runtime-verification.md), security model). Rejected (decision 1).

### C. A BlackHole/Loopback-style virtual audio driver on macOS

Requires the user to install a third-party kernel/DriverKit audio driver and manually route system audio through it — incompatible with "single installable app", not bundlable (kext/DriverKit signing and installation from a `.dmg` is a notarization nightmare), and worse UX than process taps. Rejected; at most a documented "advanced: if you already have BlackHole, point Speedwave at that device" note, not a built-in path.

### D. Python-based transcription/diarization (faster-whisper, whisperX, pyannote.audio)

Best-in-class diarization is pyannote.audio, but it (and whisperX, which wraps it) is Python + PyTorch + large gated models — not bundlable as a self-contained app and contrary to "shell out to existing tools" only in the sense that the "tool" would be a whole Python runtime. sherpa-onnx gives ONNX-only, zero-Python diarization at a quality cost that is acceptable for "provisional speaker labels" (decision 7). Rejected. (Note: k2-fsa's `sherpa-onnx-pyannote-segmentation-3-0` is an _ONNX conversion_ of pyannote's segmentation-3.0 weights — MIT-licensed, runnable in the ONNX runtime with no Python — so the pyannote _model_ is used; the pyannote _Python library_ is not.)

### D2. `sherpa-onnx-reverb-diarization-v1` segmentation model

An alternative, possibly higher-quality segmentation model in k2-fsa's releases — but it ships under a **non-commercial** licence, which is incompatible with shipping it in a commercial product. Rejected; `sherpa-onnx-pyannote-segmentation-3-0` (MIT) is used instead (decision 7).

### D3. The `sherpa-rs` Rust crate (instead of the official `sherpa-onnx` crate)

`sherpa-rs` is a third-party binding to sherpa-onnx; it works, but spike 0A found the official `sherpa-onnx` crate (by the sherpa-onnx author) to be more current (`1.13.x` May 2026 vs `sherpa-rs` `0.6.8` Oct 2025), exposing the full diarization pipeline directly, with a cleaner default feature set (`static`, no `tts`/`download-binaries` extras to disable). The official crate is used (decision 7). Not "rejected" so much as "the other option, not chosen".

### E. CUDA/Vulkan GPU acceleration in v1

whisper.cpp's GPU backends are compile-time, not runtime (decision 6) — shipping CUDA/Vulkan means a separate CI toolchain, separate build artifacts, and likely separate or feature-gated installers. Deferred to a follow-up; v1 ships CPU + Metal. Not "rejected forever", just out of v1 scope (YAGNI).

### F. Reusing `patch_emitter.rs` / the JSON-patch protocol for the live transcript

The 882-line `patch_emitter.rs` plus `MsgStoreRegistry` and the RFC 6902 machinery is overkill for an append-mostly transcript with coarse "replace last N segments" operations. Only the _delivery semantics_ of `MsgStore::history_plus_stream()` (history + live, monotonic seq, idempotent reducer) are adopted; the patch protocol itself is not (decision 11).

## Consequences

### Positive

- A self-contained, opt-in meeting-transcription feature that works on macOS / Windows / Linux, with everything in the SSOT layer (`speedwave-runtime`) and a thin Tauri command surface — consistent with the rest of the codebase.
- **The container threat model is untouched** — no v1 security invariant is relaxed; Claude's container learns nothing about audio; the transcript reaches Claude only through the normal chat path as user-supplied text.
- Audio inference is local — no audio leaves the machine for transcription or diarization.
- The `trait AudioCapture` → `WasapiAudioCapture` / `MacOsAudioCapture` / `LinuxAudioCapture` split mirrors `ContainerRuntime` → `LimaRuntime` / `NerdctlRuntime` / `WslRuntime` (Open/Closed; a new platform is a new impl).
- Heavy lifting is delegated, not reimplemented: transcription = `whisper-rs`, diarization = sherpa-onnx, Linux capture = `pw-record`/`parec`, macOS capture = adapted `AudioCap`/`AudioTee`, Windows capture = `cpal`, downloader = `reqwest` + the existing `http_util` hardening, process lifecycle = `mcp_os_process.rs`, live stream = the `history_plus_stream` delivery pattern.

### Negative

- **This is a genuinely large subsystem** — not a "thin orchestration layer" in the way wrapping `nerdctl exec` is. Mitigations: three risk-proving spikes before any permanent code; every hard piece wraps an existing tool; Phase 1 is split into four PRs; phasing lands working increments (file-input transcription is useful before live capture exists).
- **New attack surface, host-side**: a model downloader making outbound HTTPS (mitigated by the redirect allowlist, streaming hash, size caps, and the ADR-041 hardening it reuses); the microphone and system-audio capture itself (mitigated by opt-in-off-by-default and the OS permission prompts); transcript files and audio recordings on disk (mitigated by `0o600`, the `~/.speedwave/transcripts/` location, the retention controls); on macOS the audio-capture permission, which is powerful (mitigated by the UI being explicit about what is being captured and why). All of this is the residual cost of the feature, accepted.
- **macOS depends on a private TCC API** (`TCCAccessRequest(kTCCServiceAudioCapture)`, decision 3) for the system-audio consent prompt — there is no public equivalent. Mitigated by the call being `dlopen`/`dlsym`-guarded (a future macOS removing the symbol degrades the feature to "enable Audio Recording manually in System Settings", it does not crash), by it being exactly what comparable tools (`AudioCap`, `AudioTee`, `BackgroundMusic`) use, and by isolation to one small commented code path. Accepted as the cost of system-audio capture on macOS; the public alternative (ScreenCaptureKit) was rejected for the reasons in decision 3.
- **Audio leaves the machine on "Send to Claude"** — the transcript text is sent to whatever LLM provider the user has configured (Anthropic or a local LLM). "Local" is true only for inference; the UI and docs say so explicitly and the "Send to Claude" action has a confirm dialog.
- A new signed native macOS CLI (`audio-capture-cli`) is the single most infrastructure-heavy piece — new Swift package, embedded `Info.plist`, entitlements, universal `lipo` build, a CI matrix entry, a `SIGN_TARGETS` entry, bats tests. Mitigated by it being structurally identical to the four CLIs already in `native/macos/` ([ADR-049](ADR-049-tcc-sub-identifiers-and-applevents-gate.md)).
- macOS 14.4+ is required for this feature; older macOS users see a "macOS 14.4+ required" message (the rest of the app still works). Windows users below build 20348 get system-wide audio only, not per-app capture.
- Speaker diarization is provisional, not certain — live labels are unstable under crosstalk and the final pass may re-cluster. The UI is honest about this; it is not a guarantee.
- Polish transcription quality is best-effort, not perfect — `large-v3-turbo` Polish WER is not well benchmarked publicly; `medium` is the middle ground and the `large-v3` final pass is "as good as Whisper gets".
- `large-v3` is a 2.9 GiB on-demand download; the live path needs only `small` (75 MiB) on CPU or `large-v3-turbo` (~1.5 GiB) on Metal, and `q5_0` quantized variants are smaller, but the disk/network cost is real and the UI is explicit about it.

### Neutral

- "KISS — prefer existing tools over reimplementing" (CLAUDE.md) is honored in the _parts_ (every hard piece wraps a tool) but the _whole_ is a subsystem; this ADR records that as a deliberate, eyes-open trade-off, justified by the feature request and bounded by phasing and spikes.
- The model catalog is an SSOT const like `ANTHROPIC_MODELS` — bumping a model is editing one const; the frontend reads it via a Tauri command and does not hard-code model strings.
- No automatic audio retention in v1 (YAGNI) — the user deletes manually, with an optional "discard audio after the final pass".

## Known Limitations

- DNS rebinding on the model-download host is the same accepted residual risk as for other host-originated URLs ([ADR-041](ADR-041-local-llm-model-discovery.md) §Negative) — except the model-download URLs are not user-supplied (they are the SSOT catalog), which is strictly safer.
- If a Hugging Face CDN host changes (the redirect allowlist is a frozen list), a model download will fail with a clear "model URL changed — report this" error rather than silently following an unknown redirect; the catalog/allowlist is then updated in a patch.
- The live transcript's "replace last N segments" coarseness means the on-screen text can shift slightly as the sliding window re-decodes a tail; the final pass replaces it wholesale anyway.
- On PulseAudio, per-app capture may not ship in v1 (decision 5 / spike 0B) — PipeWire users get it; PulseAudio users may get system-wide only initially.
