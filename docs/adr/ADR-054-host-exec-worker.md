# ADR-054: `host_exec` — Per-Project Host-Side MCP Worker for the Project Toolchain

**Status:** Accepted

**Date:** 2026-05-11

**Tracking:** SPW-83 (migrated from GitHub issue `speednet-software/speedwave#299`)

> **Accepted 2026-05-11.** This ADR records a deliberate, scoped weakening of Speedwave's container-isolation model — see §Consequences/Negative. It is **opt-in, empty by default, per-project, user-local**, the deliberate enable (a blocking danger modal) is the consent (there is no per-call confirmation), and the residual risk is written down below in plain words. The "Open questions" section of the first draft has been replaced by §Resolved decisions; the implementation detail has been revised to the per-project design after a review of the hub's worker-discovery mechanics.

## Context

Claude Code runs inside the `claude` container, built on `node:24-bookworm-slim` — Node.js plus git, nothing else. It cannot compile, test, lint, or run the user's project: no JDK, no Gradle/Maven, no Go, no .NET, no Flutter, no Python interpreter, and no access to the Docker / docker-compose stack the user runs on their host for project services (database, Redis, queues). Every developer has a different toolchain and a different environment layout; installing all of it inside the container is neither feasible nor desirable, and would bloat the image and the threat surface for everyone.

This is the single most-requested capability gap, and one users are **already filling by hand, insecurely**:

- One user, asked by Claude (running inside the container) for help, was walked through writing a ~30-line Node "agent" (`<workspace>/test-agent/agent.js`), starting it themselves on their Mac bound to `0.0.0.0:8765` with a shared token written to `<workspace>/test-agent/.token` — i.e. inside the repo, where it can be committed and where every MCP worker that mounts `/workspace` can read it — and pointing Claude at it via `host.docker.internal:8765`. Claude then ran `./gradlew test` on the host and, with no confirmation, also ran arbitrary piped shell commands inside the container to parse the results.
- The same user later reports that Claude _installed Java "locally"_ and _"everything else I managed to build — I'd have a full loop if not for Docker"_. An audit (§"Audit of the `claude` container", below) confirms this is a JDK tarball into the container's **writable `$HOME`** (`${CLAUDE_HOME}:/home/speedwave:rw`, the per-project `<data_dir>/claude-home/<project>/`): it works because `$HOME` is writable and not `noexec`, it persists per-project, and it **does not reach the host** — the only explanation consistent with the architecture (the container has no `sudo`, no `apt` at runtime under `read_only: true`, and no host system path mounted writable). So Claude is _already_ nearly running the build loop, by installing the toolchain into the container — and only Docker (which genuinely cannot run inside the container) blocks the full loop.

The lesson is not "Speedwave has a hole" — the audit confirms it does not (read-only fs, `cap_drop: ALL`, `no-new-privileges`, non-root user, no host sockets, no `network_mode: host`, the kernel layer below; the IDE Bridge stub refuses `executeCode` and otherwise only proxies editor events; the clipboard bridge is one-way text into the host clipboard; the gateway DNS aliases only grant reachability to host loopback ports the host explicitly bound — the "compromise of Claude cannot execute code on the user's host" invariant holds). The lesson is: **ship a safe, official path before more `agent.js` files appear on `0.0.0.0` with tokens in git, and before "install the toolchain into the container" becomes the de-facto workaround.**

Speedwave's isolation model exists precisely so a compromise of Claude does **not** yield code execution on the user's machine.[^security] Letting Claude run `./gradlew test` on the host is, by definition, a deliberate weakening of that model. This ADR does it as narrowly and as safely as the design allows — opt-in, empty by default, per-project, user-local configuration, a blocking enable-time danger modal (the consent — there is no per-call confirmation), a hard ban on direct shell/eval launchers — and writes down the residual risk that remains even then (§Consequences/Negative).

There is already a host-side MCP worker to use as a _mechanics_ template: `mcp-os` (ADR-010, ADR-013) — a TypeScript MCP server (`mcp-servers/os/src/index.ts`) spawned as a child Node process by the Tauri backend; the Rust side (`desktop/src-tauri/src/mcp_os_process.rs`) is a process manager only (spawn, stop, health-check, port/PID/token bookkeeping, stale-process cleanup). It binds to `127.0.0.1` on the host (never `0.0.0.0`, because it runs outside the container network and must not be reachable from the LAN[^mcpos-bind]); containers reach it via the platform gateway DNS name (`host.lima.internal` on macOS, `host.docker.internal` on rootless Linux, `host.containers.internal` / `host.speedwave.internal` on Windows[^gateway]); `render_compose()` injects `WORKER_OS_URL=http://<gateway>:<port>` into the `mcp-hub` container so the hub can forward to it; Claude never talks to it directly. **But `mcp-os` is _global, single-instance, project-agnostic_**: one process, one token/port file, the _same_ `WORKER_OS_URL` injected into every project's hub — because the OS APIs it integrates are the same regardless of project. `host_exec` is **per-project** (a per-project whitelist, cwd, auth token, log), so it reuses `mcp-os`'s _mechanics_ but not its single-instance shape.

## Decision

Add **`host_exec`**: a **per-project** host-side MCP worker, behind each project's MCP hub, that runs **only the commands the user has explicitly added to a whitelist in the Desktop UI → Integrations**, in the project directory, with no shell, with no per-call confirmation (enabling `host_exec` is the consent), and returns the command's result (exit code + capped stdout/stderr + status) to Claude through the hub.

One `host_exec` worker process **per project**, each on its own dynamic `127.0.0.1` port; the project's `render_compose` injects `WORKER_HOST_EXEC_URL=http://<gateway>:<that-project's-port>` into that project's hub, and adds `host_exec` to that project's `ENABLED_SERVICES` only when the project has it enabled. (Two projects' compose stacks run simultaneously — different networks, different hub containers — so two `host_exec` workers on two ports is the natural fit.) Rejected: one global worker with bearer-token→project routing — more complex, the worker would have to be project-aware, and credential isolation would require routing logic; per-process isolation is cleaner and matches how Speedwave already runs per-project stacks.

It is built on `mcp-os`'s **mechanics** — the process-manager pattern in Tauri (`env_clear`+re-add, the `{"port":N}` stdout-line handshake with a read timeout, drain threads, PID-file stale-kill, `write_restricted_file` `chmod 600`, log truncation, the watchdog shape), the `127.0.0.1`-only bind, the gateway routing, the `WORKER_<NAME>_URL`-into-hub wiring, the per-session bearer token — but not a new mechanism, and not `mcp-os`'s single-instance structure. It is **a separate worker**, not an extension of `mcp-os`, for the reasons below.

### Service id, recipe names, and the hub bridge

The MCP hub builds a worker's URL env var as `WORKER_${service.toUpperCase()}_URL` (`mcp-servers/hub/src/tool-discovery.ts`, `http-bridge.ts`) and exposes a worker's tools to Claude's `execute_code` sandbox as `<service>.<toCamelCase(tool_name)>()` (`toCamelCase` turns `snake_case` → `camelCase`; it leaves a hyphen untouched, and `host-exec.x()` would not parse as JavaScript). Therefore:

- **The service id is `host_exec`** (underscore) — `"host_exec".toUpperCase()` → `WORKER_HOST_EXEC_URL` (correct); a hyphenated id would give `WORKER_HOST-EXEC_URL` (broken). It is the first multi-word entry in `BUILT_IN_SERVICE_IDS` — safe, `toUpperCase()` treats `_` literally. The Desktop UI label, the docs, and Claude-facing prose may read "host-exec" where natural, but the **service id, env var, and JS sandbox key are `host_exec`**.
- **Recipe names must be `snake_case`** (`^[a-z][a-z0-9_]{0,63}$` — a new pattern; the existing slug pattern allows `-` and is wrong here). A recipe `gradle_help` is callable as `host_exec.gradleHelp()` in the sandbox; a hyphenated name would not be callable at all.

### Why a separate worker, not part of `mcp-os`

1. **Different responsibility (SRP).** `mcp-os` integrates host _system APIs_ — Calendar/Mail/Reminders/Notes via AppleScript/EventKit (macOS), D-Bus/EDS (Linux), WinRT/MAPI (Windows)[^mcpos-apis] — with a fixed, baked-in tool set and zero per-project configuration. `host_exec` runs a user-defined whitelist of arbitrary developer commands in a project directory. Two different domains; merging them mixes concerns.
2. **Privilege escalation.** The `mcp-os` process on macOS is code-signed with entitlements (`apple-events.plist`, `calendars.plist`) and has been granted TCC consent for Calendar/Mail/Reminders.[^mcpos-tcc][^adr049] A command executor must **not** inherit those — `./gradlew test` runs `build.gradle`, i.e. arbitrary code; that code must not run with access to the user's mailbox and calendar. `host_exec` ships with **no** PIM entitlements.
3. **Per-worker blast radius.** A compromise of `host_exec` must expose only what `host_exec` can do (the whitelist, in the project dir) — not the Calendar/Mail data reachable from `mcp-os`. Separate processes keep the blast radii separate — the v1 invariant: a compromised worker exposes only its own service.[^security]
4. **Lifecycle.** `mcp-os` lives per app session, always on, project-agnostic. `host_exec` is per-project, toggled on/off via `integrations.hostExec.enabled` in the project config, spawned/torn-down when a project enables/disables it or is switched away from — a different lifecycle, a different enable surface.

### What `host_exec` is _not_

- It is **not** a Docker bridge. `docker compose up` is just one whitelist recipe; the worker does `spawn("docker", ["compose","up","-d"], {cwd: projectDir})` and the host's `docker` CLI talks to the host's Docker daemon exactly as if the user typed it in a terminal. **No Speedwave container ever gets `docker.sock` or `DOCKER_HOST`** — that would be de-facto root on the host and would violate ADR-008/ADR-009/ADR-013.[^docker-sock]
- It is **not** a generic shell. There is no `exec: "bash"` recipe, no `shell: true`, no "pass through extra arguments" — but `shell:false` plus the ban on direct shell/eval launchers is **defense in depth, not a guarantee that whitelisted recipes cannot run arbitrary code** (`npm run`, `make`, `gradle`, `docker compose` all execute repo-controlled code, often via `/bin/sh` themselves). See §"Hard ban on direct shell/eval launchers" and §Consequences/Negative.
- It does **not** install anything. The host toolchain is whatever the user already has; Speedwave's container images are unchanged.

## Architecture

```
┌─ project P: container "claude" ──────┐
│  Claude Code ──MCP/stdio──► (nothing) │
└──────────────┬───────────────────────┘
               │ HTTP, hub only
               ▼
┌─ project P: container "mcp-hub" :4000 ────┐
│  aggregates tools from workers             │
└──┬────────┬────────┬────────┬─────────────┘
   ▼        ▼        ▼        ▼ HTTP + Bearer (gateway routing, ADR-010)
 slack   gitlab  sharepoint  ┌─ HOST (Tauri / Desktop app) ──────────────┐
(containers)                  │  mcp-os         :PORT  (global, existing)  │
                              │  host_exec[P]   :PORT_P (per-project, new) │
                              │  host_exec[Q]   :PORT_Q (project Q's)      │
                              │    └ whitelist from <data_dir>/host-exec/  │
                              │      <project>/config.json                 │
                              │       spawn(shell:false, cwd=project dir)  │
                              │          ▼                                 │
                              │   gradlew / npm / docker / …  (own pgroup) │
                              │          ▼                                 │
                              │   host Docker daemon                       │
                              └────────────────────────────────────────────┘
```

Mechanics, mirrored from `mcp-os` but **per-project**:

- **Process manager** (`crates/speedwave-runtime/src/host_exec_process.rs` — `HostExecProcess`, shared by the Desktop app and the `speedwave` CLI). One worker per project. `spawn_in(project, project_dir, script_path, host_path, data_dir)` spawns `node mcp-servers/host_exec/dist/index.js` with `env_clear` + a re-added env: the **recovered login-shell `PATH`** (see §PATH; the CLI's inherited `PATH` is already the login-shell one), Windows OpenSSL vars, `SPEEDWAVE_RESOURCES_DIR`/`SPEEDWAVE_PROD` in prod, `HOST_EXEC_CONFIG_PATH=<data_dir>/host-exec/<project>/config.json`, `HOST_EXEC_LOG_FILE`, `PORT=0`, `HOST_EXEC_AUTH_TOKEN=<fresh uuid>`. It reads `{"port":<N>}` from the child's first stdout line (10 s timeout), writes `<data_dir>/host-exec/<project>/{port,pid,auth-token}` (the token `chmod 600`), truncates an oversized log, and kills any stale process from a previous session via the PID file (with the `is_node_process` guard). `stop()`, `respawn()`, `is_alive()` (PID + TCP probe). Desktop holds the workers in a `HashMap<String, HostExecProcess>` in app state and runs a multi-entry watchdog that respawns dead workers (and recreates the project's hub container so it re-discovers); the CLI spawns one before `compose_up` and holds it for the (one-shot) run.
- **Bind:** `127.0.0.1:<dynamic>` on the host. Never `0.0.0.0`. The project's containers reach it via the platform gateway DNS name; `host_exec_gateway_url(port)` in `compose.rs` mirrors `mcp_os_gateway_url`.
- **Hub wiring:** for project P, `compose.rs` injects `WORKER_HOST_EXEC_URL=http://<gateway>:<PORT_P>` into P's `mcp-hub` container, bind-mounts P's worker token at `/secrets/host_exec-auth-token:ro` (the filename MUST be `<service-id>-auth-token` — `host_exec` with the underscore — because the hub's `auth-tokens.ts` derives `/secrets/${service}-auth-token`; a `host-exec` hyphen there would silently never be read and every hub→worker call would 401), and adds `host_exec` to P's `ENABLED_SERVICES` iff `integrations.hostExec.enabled` for P. The hub reads that token file and sends it as `Authorization: Bearer` when fetching the worker's tool list / executing recipes, and relays results (including `exitCode` and `stderr` — they are just fields in the JSON ToolResult). `host_exec` declares its hub policy via the `_meta` field on each recipe tool (ADR-036): `deferLoading: false` (few recipes; they are the point — Claude should see them upfront), `timeoutClass: 'long'` (600 s), and a `timeoutMs` (= `HOST_EXEC_TIMEOUT_MS` + margin) — no hub change is needed since everything fits under the 600 s long timeout (see §"Timeout budget").
- **`host_exec` is NOT a compose service.** Like `mcp-os`, it is a host process, not a container. It appears in compose only as the `WORKER_HOST_EXEC_URL` env var on the project's hub. It has **no `/tokens` mount** — its only "credential" is the per-project whitelist, which it reads from the host filesystem.
- **Auth:** UUIDv4 bearer token generated per (project, app session); every hub→worker request must carry `Authorization: Bearer <token>`.
- **Config change → respawn + hub re-discovery.** `createMCPServer` registers tools at construction; the worker re-reads `HOST_EXEC_CONFIG_PATH` on each `tools/list` (and on a config-file change) and `registerTool`s the diff, so a respawned worker reflects the current whitelist — but the **hub** caches discovery and only refreshes every 5 minutes with no force-hook. So a whitelist edit triggers a **worker respawn + an explicit hub re-discovery** of `host_exec` (either a small hub-side `refreshServiceTools` trigger, or — the preferred option, zero new hub surface — recreating the project's hub container via the existing `reconcile::reconcile_compose_port` path that already does this for `mcp-os` port changes). A worker that merely re-reads its config per call gets fail-closed-on-removal for free, but not new-tool visibility — hence the explicit re-discovery.

## Configuration — Desktop UI → Integrations

**The user configures it. Speedwave puts nothing there for them** — zero defaults, zero stack auto-detection. The whitelist starts **empty**; `host_exec` with no recipes means Claude can run nothing.

- **Lives user-local** (`~/.speedwave/config.json` / `<data_dir>/config.json`), **not in the repo's `.speedwave.json`** — the repo-config layer **ignores `integrations.hostExec` entirely** (the same pattern as `merge_llm_repo`'s "provider/base*url intentionally not merged from repo": per `.claude/rules/security.md`, repo config never overrides security-class fields, and an executable command whitelist is squarely one). Adding a command is an explicit user action in the UI — the "explicit user action" the security rules require. The repo may at most carry an \_example* in its README; the executable whitelist never arrives from the repo.
- **UI:** a new tile in the existing Integrations module (per-project, like Slack/SharePoint/plugins) — its own card with its own toggle (modeled on the Redmine card), not a row in the generic credential-based services table. Backed by `host_exec_save_settings` / `host_exec_load_settings` Tauri commands (the `plugin_cmd.rs` pattern).
- **Enabling `host_exec` triggers a blocking danger modal** explaining the consequences before the toggle takes effect — not the inline one-liner. The toggle is **gated**: it flips only after the modal is confirmed; cancel leaves it off. (Disabling needs no modal.) The modal text states plainly: the commands you list run _on this computer_, in this project's folder; they execute code from this repository (`gradlew test` runs `build.gradle`, `npm run test` runs `node_modules`, `docker compose up` runs the images in `docker-compose.yml`); because Claude can also edit this repo, a prompt-injected Claude could write a malicious build script and then run it; this is a deliberate weakening of Speedwave's container isolation; **enabling it is the consent — there is no per-command prompt, so once on, Claude runs any whitelisted command anytime (the audit log records every run)**; only enable it for repositories you trust; only whitelist commands you're OK with Claude running unattended; don't put secrets in command env.

Sketch:

```
Integrations › Host Exec                                    [ ● enabled ]

 Commands Claude may run on your machine, in this project's folder — without
 a per-run prompt (enabling Host Exec is the consent). The audit log records
 every run. ⚠ These commands execute code from this repository.

 ┌──────────────────────────────────────────────────────────────┐
 │ test          ./gradlew test                          ✏️ 🗑️ │

```

### Config schema

Added under `integrations` in `crates/speedwave-runtime/src/config.rs` (SSOT):

```jsonc
"integrations": {
  "hostExec": {
    "enabled": true,
    "commands": [
      { "name": "test",       "exec": "./gradlew", "args": ["test"] },
      { "name": "build",      "exec": "./gradlew", "args": ["build", "-x", "test"] },
      { "name": "fe_build",   "exec": "npm", "cwdSub": "frontend", "args": ["run", "build"] },
      { "name": "compose_up", "exec": "docker", "args": ["compose", "up", "-d"] },
      { "name": "psql",       "exec": "docker", "args": ["compose", "exec", "-T", "db", "psql", "-c", "{sql}"],
        "params": [ { "name": "sql", "pattern": "^SELECT .{0,500}$", "maxLen": 600 } ] }
    ]
  }
}
```

`commands` is a **list, not a map** — so a duplicate `name` is detectable (a JSON object would silently overwrite a dup key, making a "duplicate name rejected" test impossible). Validation (Rust, `crates/speedwave-runtime/src/host_exec.rs`):

- **Claude sees recipe names only** (`host_exec.test()`, …). It never composes a command string and never names the binary to run; it supplies only named parameters. The hub policy (`_meta`) and the worker's tool schema expose only the declared `params`.
- **`name`** matches `^[a-z][a-z0-9_]{0,63}$` (snake_case — see §"Service id, recipe names, and the hub bridge"); unique across the list.
- **`exec`** is checked on its **basename** (case-insensitive) against `HOST_EXEC_SHELL_LAUNCHERS` (the direct shell/eval launchers — see below) and rejected if it matches; it must not contain `..`, NUL, `=`, or newlines. A _relative_ `exec` (`./gradlew`, `npm`, `docker`) is resolved against the project directory or `PATH`; an _absolute_ `exec` is **allowed but flagged** (the UI surfaces a "this is an absolute executable path — make sure it's the one you mean" hint — useful when `PATH` discovery can't find `docker`/`gradle`).
- **`args`** is a list of literals plus `{name}` parameter tokens substituted into fixed positions. No "pass the rest through", no splatting. Anything not in the recipe never reaches the process. A parameter token may appear inside an arg element (`psql -c {sql}` → argv element `["…","psql","-c","<value>"]`), and the substitution is a **single** argv element, never re-split. Every `{name}` must have a matching `params` entry; a `{name}` with no definition is rejected. No NUL/newlines in `args`. **Parameterised meta-invocation rule:** if `exec` (basename, case-insensitive) ∈ {`node`,`deno`,`python`,`python3`,`perl`,`ruby`,`make`,`npm`,`npx`,`pnpm`,`yarn`} _and_ any `args` element is a bare `{param}` (the whole element is the parameter), reject — that is "run whatever Claude types" through a meta-tool; a _literal_ sub-command (`make test`, `npm run build`) is fine.
- **`params[i].name`** is snake_case, unique within the recipe. **`params[i].pattern`** is a regex; Rust only checks it is a non-empty string ≤ 4096 chars with no NUL/newline — the **semantic regex check (does it compile, does the supplied value match) happens in the worker**, in JavaScript `RegExp`, since the worker is what executes it; doing it in Rust's `regex` crate too would invite Rust-`regex` vs JS-`RegExp` semantic drift, so it lives in one engine. **`params[i].maxLen`** ≤ 65536.
- **`cwdSub`** (optional) is a subdirectory **inside** the project directory (monorepo support): relative, no `..`, no absolute path, no NUL. Canonicalisation-against-the-project-root happens at exec time in the worker (the project dir is not known at config-save time) — `fs.realpathSync(join(projectDir, cwdSub))` must `startsWith` the canonical project dir plus a separator, with no symlink escape (the algorithm `compose.rs::ensure_resources_dir_safe` uses, re-implemented in TS).
- **`env`** (optional) is a map of literal environment variables for the recipe (no Claude-supplied values). Keys not in `RESERVED_ENV_KEYS` (case-insensitive — the same list and check `plugin::validate_manifest` uses for plugin `extra_env`: `LD_*`, `DYLD_*`, `NODE_OPTIONS`, `PYTHONPATH`, `PATH`, `HOME`, `IFS`, `BASH_ENV`, `ENV`, …); no `=`/newlines/NUL in keys; no newlines/NUL in values. Because `env` may contain secrets (`DATABASE_URL` with a password, etc.), the per-project `config.json` is written `chmod 600`, the host log **redacts** `env` values (keys only, values → `***`), and the UI warns "don't put secrets here — use a `.env` in the repo".
- **There is no per-recipe `confirm` field** — enabling `host_exec` is the consent (see §"No per-call confirmation — by design"). The UI shows an amber inline warning when you add a recipe the `is_container_lifecycle_recipe` heuristic flags (`exec` basename ∈ {`docker`,`docker-compose`,`podman`} with `up`/`down`/`exec`/`rm`/`prune` in `args` — effectively host root from a Claude-editable compose file), and a milder warning for DB clients / migrations; neither is blocking — they're hints, since enabling `host_exec` is the per-project consent.

### Hard ban on direct shell/eval launchers

Config validation **rejects** any recipe whose `exec` basename is a direct shell or eval launcher: `bash`, `sh`, `zsh`, `dash`, `ksh`, `fish`, `eval`, `env`, `xargs`, `find`, `ssh`, `sshpass` — plus the parameterised meta-invocation rule above for `node`/`python`/`make`/`npm`/etc. (`make test` literal is fine; `make {x}` is not). This list (`HOST_EXEC_SHELL_LAUNCHERS`) lives in `crates/speedwave-runtime/src/consts.rs` as the SSOT (the same pattern as `RESERVED_ENV_KEYS` and `BUILT_IN_SERVICE_IDS`), consumed by validation and documented in `docs/architecture/security.md`. `shell: false` always; there is no option to enable a shell.

**This is defense in depth, not a guarantee.** It closes the most obvious vector — `{"exec":"bash","args":["-c","{cmd}"]}` is a raw host shell with the added lie that it "passed validation"; you cannot write a regex that distinguishes "safe" bash from malicious bash (`$IFS`, `${x:0:1}`, base64 + `eval`, glob expansion, command substitution — the defender always loses). It does **not** prevent a whitelisted recipe from executing arbitrary code: `npm run X` runs `package.json` scripts (often via `/bin/sh`), `make test` runs the `Makefile`, `./gradlew test` runs `build.gradle`, `docker compose up` runs the images in `docker-compose.yml` — all repo-controlled. And the bans are **by basename, not by path**: `{"exec":"./node_modules/.bin/node","args":["{x}"]}` bypasses the `node` ban (a path, not the name `node`), and is allowed — a documented residual; the recipe author chose it. The whitelist guarantees that _the recipe name and its argv shape_ are trusted; it does **not** guarantee that _the code that runs_ is trusted. That's the residual risk (§Consequences/Negative); the mitigations are opt-in + the enable-time danger modal (which is the consent for the whole project — there is no per-call confirmation) + the host-side audit log, not the ban list. A user who needs a one-liner splits it into named recipes, or wraps it in their own script _in the repo_ with a fixed, parameter-free interface (`./scripts/ci.sh build`) and adds `{"exec":"./scripts/ci.sh","args":["build"]}`.

### What belongs on a whitelist, and what does not by default

- **Yes:** operations on an _already-prepared_ environment — `test`, `build`, `lint`, `format`; migrations against the local database; read-only queries against the local database (with a regex); controlling the project's services (`docker compose up/down/logs/ps`); code generation from local sources.
- **Not by default** (a user may add it, deliberately, at their own risk): anything that _fetches and executes code from the network_ — `npm install` / `npm ci`, `gradle --refresh-dependencies`, `mvn dependency:resolve`, `go mod download`. The environment is the user's / CI's job, not the agent's; a `postinstall` script in `node_modules` is code execution on the host. The UI's "Add command" dialog and `docs/guides/integrations.md` state this; we do not pre-populate or auto-suggest these.

## Reading a command's result

Every `host_exec.<recipe>()` call returns a structured result to Claude as a ToolResult through the hub. **Mode: "fire and wait for exit"** — the worker runs the command, waits for it to finish, returns the whole thing as one result. No streaming in v1 (watch mode is forced off in recipes — `--watchAll=false`, `-d`, `-T` for `compose exec` — so commands finish). The worker enforces a per-command **timeout** with a **process-group** `SIGKILL` on expiry (see below); processes get **no stdin**.

Result contract (shape, not final field names):

```jsonc
{
  "status": "exited" | "killed_timeout" | "spawn_error",
  "exitCode": 1,            // null when status != "exited"
  "signal": null,           // e.g. "SIGKILL" when killed by the timeout
  "stdout": "...",          // may be truncated — see "truncated"
  "stderr": "...",          // separate from stdout; Claude must know which stream is the error
  "truncated": false,       // true if either stream exceeded the cap and a tail was kept
  "durationMs": 4231,
  "command": "test",        // recipe name (NOT raw argv — full argv goes to the host log)
  "cwd": "frontend"         // subdirectory if cwdSub was set, otherwise "."
}
```

Rules:

- **`exitCode != 0` is NOT an MCP tool error.** "I ran `gradlew test`; the result is: tests failed, exit 1, here is stderr" is a correct, _successful_ tool response. An MCP tool _error_ is returned only for: unknown / removed recipe; a parameter that fails its regex; the `cwdSub` resolution escaping the project root; `spawn_error` (binary not found / not executable — though an `exec` on the ban list fails earlier, at config validation). This distinction must be explicit in the worker **and tested** — otherwise Claude gets "error" where it should get "tests failed, here's why" and behaves badly.
- **Output size cap, per stream, tail-kept.** The worker caps each of stdout/stderr at `HOST_EXEC_MAX_OUTPUT_BYTES` **or** `HOST_EXEC_MAX_OUTPUT_LINES`, whichever comes first (proposed: 64 KB / 2000 lines), keeping the **tail** (for compile/test failures the end is what matters), and sets `truncated: true`. The caps are worker constants, not per-recipe (YAGNI). It **strips ANSI** escape sequences (CSI/SGR) — Claude doesn't need colours and they are pure noise in the context window — and collapses `\r` (the last segment of a line wins, as a terminal would render it); it decodes lossily for non-UTF-8 bytes (no crash). The caps are per stream and counted independently.
- **Output ≠ full effect.** `host_exec` returns what the command printed plus the exit code. Side effects — `gradlew build` changed `build/`, `migrate` changed the DB schema, `compose up` started containers — are visible to Claude only if it separately asks (reads a file with its normal tools, runs a `compose_ps` recipe, runs a `psql 'SELECT …'` recipe). The contract is: `host_exec` is an executor, not a system-state observer. `docs/guides/integrations.md` says so, so nobody expects Claude to "see" that a migration succeeded without checking.

### No per-call confirmation — by design

Claude Code runs inside the `claude` container with `--dangerously-skip-permissions` (`defaults.rs:94-105`) — it never prompts the user for anything. So a per-call confirmation for a `host_exec` recipe could only be a **parallel mechanism dorobiony obok** Claude Code's own permission system (which is off). The first draft of this ADR did exactly that — a confirm-request on fd 3 → a Tauri event → an Angular dialog → a reply on the worker's stdin — but it was Desktop-only (the `speedwave` CLI couldn't drive it), it relied on extra-fd plumbing that has no clean Windows equivalent, and it was architecturally awkward (a side channel parallel to the MCP tool call). It is removed.

**The chosen model: the deliberate enable IS the consent.** Enabling `host_exec` for a project goes through the blocking danger modal (once, per project — `set_host_exec_enabled` is the gated toggle); that click authorises the whole whitelist. After that, Claude can invoke any whitelisted recipe — with any parameter values matching the recipe's regexes — without further prompting; the audit log (`<data_dir>/host-exec/<project>/log`, `0600`) is the after-the-fact record. This is honest about what the security model actually is: **deliberate enable + whitelist + per-recipe regex params + the ban lists + the audit log** — _not_ per-call human-in-the-loop. If you want a recipe to require your attention each time, don't whitelist it (run it yourself in a terminal), or split it so the dangerous part isn't a recipe (e.g. wrap a one-off in `./scripts/ci.sh` with a fixed, parameter-free interface and whitelist `./scripts/ci.sh build`, not the one-off).

### Timeout budget

The hub's executor enforces a per-call budget of `EXECUTION_MS - elapsed` (default `EXECUTION_MS` = 120 s; `LONG_OPERATION_MS` = 600 s; `_meta.timeoutMs` is currently metadata only). For `host_exec` the only thing the budget covers is the command itself: `HOST_EXEC_TIMEOUT_MS = 420 s` (a long Gradle/Maven build) plus a margin fits under the hub's 600 s long-operation timeout, so recipe tools declare `_meta.timeoutClass: 'long'` and `_meta.timeoutMs = HOST_EXEC_TIMEOUT_MS + margin`. (With no confirmation wait, no executor change is needed — everything fits under the 600 s long timeout.)

### Killing the process tree

`gradle`/`npm`/`docker compose` spawn daemons and child processes; `child.kill()` on the immediate child leaves them running. The worker spawns the recipe **detached, in its own process group** (`spawn(exec, argv, {cwd, shell:false, detached:true, stdio:['ignore','pipe','pipe'], env})` on Unix; `windowsHide:true` + `CREATE_NEW_PROCESS_GROUP` on Windows) and, on timeout, kills the **group** (`process.kill(-child.pid, 'SIGKILL')` on Unix; `taskkill /T /F /PID` on Windows). No such pattern exists in the codebase today — `host_exec` introduces it in the TS worker.

### PATH

A GUI-launched Desktop app does not have the user's login-shell `PATH` — on macOS launched from Finder, `process.env.PATH` is `/usr/bin:/bin:/usr/sbin:/sbin` (no `/opt/homebrew/bin`, no `nvm`/`asdf` shims). `./gradlew` is fine (a repo script), but `npm`/`docker`/`gradle` globals are not. So the Tauri side **recovers the login-shell `PATH` once at startup** (`$SHELL -ilc 'printf %s "$PATH"'`, with a sane fallback to `process.env.PATH` plus `/usr/local/bin:/opt/homebrew/bin`, and a timeout) and passes _that_ `PATH` to each `host_exec` worker (and thus, via the worker's child-env allowlist, to recipes). A Tauri command `host_exec_resolve_executable(name) -> Option<PathBuf>` (a `which`-style lookup on the recovered `PATH`) backs a UI "we couldn't find `docker` — pick it" picker; an `exec` set to such an absolute path is allowed-but-flagged (above).

### Child environment of recipes

The worker spawns each recipe with a **fresh env built from an allowlist**, never the worker's `process.env` (which contains `HOST_EXEC_AUTH_TOKEN`, `HOST_EXEC_CONFIG_PATH`, `PORT` — none of which must reach `build.gradle`/`node_modules`/etc.). The allowlist is the `SAFE_ENV_KEYS` + `buildChildEnv()` pattern from `mcp-servers/os/src/platform-runner.ts`, extended for the toolchain: `PATH` (the recovered login-shell `PATH`), `HOME`/`USERPROFILE`, `TMPDIR`/`TMP`/`TEMP`, `LANG`/`LC_*`, `JAVA_HOME`, `DOCKER_HOST`, plus the platform minimum — and **plus the recipe's own `env` map**, and **never** any `HOST_EXEC_*`.

## Consequences

### Positive

- The single biggest capability gap closes: Claude can build, test, lint, run migrations, and drive the project's docker-compose stack — using the user's real toolchain, with nothing installed in the container.
- It replaces unsafe hand-rolled workarounds (an LLM-generated agent on `0.0.0.0` with a token committable to the repo and no audit; installing the toolchain into the container's writable `$HOME`) with an opt-in, loopback-only, audited, per-project component — and it works under both the Desktop app and the `speedwave` CLI.
- Architecturally it reuses `mcp-os`'s tested _mechanics_ (process-manager pattern, gateway routing, hub wiring, per-session bearer) — adding little new surface area — while being correctly per-project (its own worker, port, token, config, log per project) rather than a single global instance. `HostExecProcess` lives in `speedwave-runtime` and is shared by the CLI and Desktop.
- The whitelist is user-local and per-project: the user controls exactly what is permitted, the repo cannot inject it, and a different project gets a different (or empty) whitelist.

### Negative

- **This is a deliberate weakening of Speedwave's isolation model.** Up to now, a compromise of Claude (e.g. prompt injection from a malicious `README.md`, issue body, or MCP response) could at worst manipulate the data reachable by whatever worker Claude tricked — never execute code on the host. With `host_exec` enabled and a whitelist containing build/test recipes, that ceiling is raised: a successful prompt injection — **or** a malicious repo (since `./gradlew test` runs `build.gradle`, `npm run test` runs `node_modules` and `package.json` scripts, `make` runs the `Makefile`, `docker compose up` runs `docker-compose.yml`-defined images), **and Claude can write `/workspace` (`:rw`)**, so a prompt-injected Claude can author the malicious script _and then_ invoke the whitelisted recipe over it — leads to **code execution on the user's machine**, in the project directory, with the user's privileges and no sandbox. `cwdSub` confinement is cosmetic against this; the spawned process can read `~/.ssh`, `~/.aws`, make outbound network calls, etc.
- **The ban list is by basename, not by path.** `{"exec":"./node_modules/.bin/node","args":["{x}"]}` bypasses the `node` ban — a documented residual; the recipe author chose it. The whitelist guarantees the _recipe name and argv shape_ are the user's; it does **not** guarantee the _code that runs_ is. `shell:false` + the ban list close the obvious "raw shell" vector; they do not, and cannot, close "the build tool runs repo code".
- **There is no per-call confirmation — by design (an accepted property, not a residual to fix).** Enabling `host_exec` is the consent for the whole project's whitelist; after that Claude runs whitelisted recipes (with any regex-matching param values) without further prompting. A per-call human-in-the-loop would only be a parallel mechanism alongside Claude Code's permission system (off, because the container runs `--dangerously-skip-permissions`), it wouldn't cover the `speedwave` CLI, and the original fd-3 approach was architecturally awkward. The gap between "what the user thinks they whitelisted" (`test`) and "what they actually whitelisted" (arbitrary repo code Claude can rewrite) is closed by the enable-time danger modal, not by any regex. If a user wants a recipe to require their attention each time, they don't whitelist it.
- `env` per recipe means the per-project config file may hold secrets — hence `chmod 600` on the snapshot and `env`-value redaction in the host log; if a future maintainer adds a path that copies the config or the log elsewhere, the redaction/perms must travel with it.
- On macOS/Windows the `host_exec` worker must be code-signed (it's bundled `node` + JS, no Mach-O of its own → no new entitlements plist, no `sign-bundled-binaries.sh` change) — but explicitly **without** the PIM entitlements that `mcp-os` carries; getting that wrong would let `./gradlew` reach the user's Calendar/Mail.
- Running one worker process per enabled project costs ~30–50 MB of Node per project; with several projects enabled simultaneously that is a couple of hundred MB. Acceptable, and the price of per-process isolation; if it ever isn't, the global-worker-with-routing model is the documented fallback (not built now).
- DNS-rebinding against the loopback-bound worker is an accepted residual risk for the same reason as ADR-041's host-side HTTP surface — bounded by the bearer token and by the worker doing nothing dangerous on a bare GET; the dangerous surface (running a recipe) requires the bearer token _and_ a recipe in the user's whitelist. Do not introduce a codepath that lets an attacker add to the whitelist without explicit user action — that would invalidate this.

### Neutral / deferred

- No streaming of partial output in v1 (fire-and-wait-for-exit). Watch mode is forced off in recipes anyway, so commands finish; streaming can be added later if there is real demand (Rule of Three).
- The exact output-cap values (proposed 64 KB / 2000 lines per stream) and whether to strip ANSI vs leave it (proposed: strip) are settled during implementation; they are worker constants, not config.
- On Linux, exactly how to point at the user's "real" Docker (Docker Desktop / OrbStack / Colima / a rootful daemon) alongside Speedwave's own rootless nerdctl: the `docker` recipe runs whatever `docker` resolves to on the recovered host `PATH` (or an absolute path the user set in the UI) with the host's `DOCKER_HOST`; none found → `spawn_error`. No `dockerSocket` config field. On macOS/Windows there is no collision (Speedwave = Lima/WSL2; "the host's Docker" = a separate install with a separate socket).
- On Linux, exactly how to point at the user's "real" Docker (Docker Desktop / OrbStack / Colima / a rootful daemon) alongside Speedwave's own rootless nerdctl is settled in implementation: the `docker` recipe runs whatever `docker` resolves to on the recovered host `PATH` with the host's `DOCKER_HOST`; none found → `spawn_error`. ### Known limitations / follow-ups (tracked, not blocking)

- **Whitelist edit / `set_host_exec_enabled` / a watchdog respawn recreates the whole compose stack, not just the hub.** `recreate_project_containers_if_running` calls `compose_up_recreate`, which runs `compose up -d --force-recreate` with no service filter — so it also recreates the `claude` container, dropping the active Claude Code session. The intent here is "recreate the project's hub container so it re-discovers `host_exec`"; doing only that needs a `ContainerRuntime` method to up/restart a single service (a follow-up — new trait method + 3 impls + tests). Also: `host_exec_save_settings` is not debounced, so N rapid edits ⇒ N recreates.
- **The `chmod 600 / icacls` write helper is duplicated** — `speedwave_runtime::host_exec_process::write_restricted_file` and the same in `mcp_os_process` — extract to a shared `speedwave_runtime` helper (which would also be the place to close the Windows write-then-`icacls` TOCTOU window). Same for the slim log helpers (`open_log_file` / `write_log_line` / truncate) now copied between `host_exec_process` and the Desktop `log_file` module.
- **`CREATE_NEW_PROCESS_GROUP` is not actually set on Windows** for recipe children (only `windowsHide: true`); `taskkill /T /F /PID` walks the PID tree, so a double-forking recipe that reparents to PID 1 could escape it. A code comment in the worker's `runner.ts` should note the gap.

## Audit of the `claude` container (input to §Negative)

A read-only audit (preceding this ADR) of `containers/compose.template.yml` (the `claude:` service), `containers/entrypoint.sh`, `containers/Containerfile.claude`, `desktop/src-tauri/src/ide_bridge.rs`, and `desktop/src-tauri/src/clipboard_bridge.rs` confirms:

- The `claude` container is `read_only: true`, `cap_drop: ALL` (no `cap_add`), `no-new-privileges:true`, runs as a non-root user (`1000:1000` on macOS/Windows; `0:0` inside a rootless user namespace on Linux per ADR-026 — that UID 0 maps to the host _user's_ UID, not real root), on a per-project bridge network only (no `network_mode: host`), with no host runtime socket and no D-Bus socket. Its only writable mounts are `/workspace` (`${PROJECT_DIR}`, the user's repo — `:rw` by design, Claude edits code) and `/home/speedwave` (`${CLAUDE_HOME}` = `<data_dir>/claude-home/<project>/` — `:rw` by design, Claude Code self-installs there); `/speedwave/resources` and `/home/speedwave/.claude/ide` are `:ro`; `/tmp` is a `noexec,nosuid` tmpfs. `entrypoint.sh` writes only under `${HOME}` (no `apt`/`sudo`/host writes). `read_only: true` makes `/usr`/`/etc`/`/var`/`/opt`/`/` immutable at runtime.
- **"Claude installed Java" = a JDK tarball into the writable `$HOME`** — confined to the container, per-project (under `<data_dir>/claude-home/<project>/`), and not reaching the host. There is no worse explanation: no `sudo`, no `apt` at runtime under `read_only`, no host system path mounted writable.
- **No code-execution channel to the host exists today.** The IDE Bridge stub _refuses_ `executeCode` and otherwise only returns canned editor data; the proxy mode is a transparent relay to the user's _own_ editor MCP endpoint (the editor's trust surface, opt-in). The clipboard bridge is one-way text-only into the host clipboard (capped 64 KB, no read, no binary, no exec — ADR-052). The gateway DNS aliases (`host.lima.internal` etc.) only grant reachability to host loopback ports the host explicitly bound (today: the IDE Bridge; a local-LLM server when configured; tomorrow: a `host_exec` worker) — they grant nothing on their own. The "compromise of Claude cannot execute code on the user's host" invariant holds in the current codebase.
- **Consequence for `host_exec`:** because `/workspace` is `:rw`, a prompt-injected Claude can write a malicious `build.gradle` / `package.json` `scripts` entry / `docker-compose.yml` / `Makefile` and then — once `host_exec` exists — invoke a whitelisted recipe over it. This chain is real and unavoidable given that Claude must be able to edit the repo and `host_exec`'s whole point is running build/test tooling on the host. It is reflected in §Negative.
- **One minor, unrelated finding:** all eight `tmpfs:` entries in `containers/compose.template.yml` (the `claude` service and every `mcp-*` worker) specify `noexec,nosuid` but omit `nodev`; `SecurityCheck::check_tmpfs_noexec` only asserts `noexec`+`nosuid`. Severity low — `cap_drop: ALL` already removes `CAP_MKNOD`, so creating a device node in `/tmp` is already prevented; it is a defense-in-depth gap. **This is a separate issue to file**, not part of `host_exec`: add `,nodev` to all eight entries, extend `check_tmpfs_noexec`, update the doc strings in `.claude/rules/security.md` and `docs/architecture/security.md`.

## Related

- ADR-008 (no background daemon) — `host_exec` workers run only while the Desktop app runs, as children of it; no separate daemon.
- ADR-009 (per-project isolation preserved) — `host_exec` has no `/tokens` mount; its config and worker are per-project; it does not relax any container constraint.
- ADR-010, ADR-013 (`mcp-os` as host process — per-platform, implementation) — the _mechanics_ template for `host_exec`'s process manager, bind policy, and gateway routing; `host_exec` is per-project where `mcp-os` is global.
- ADR-026 (Linux rootless container user) — why the `claude` container's `0:0` on Linux is not real root.
- ADR-036 (self-declaring worker policy via `_meta`) — `host_exec` declares its hub policy this way; the only hub-side changes are a re-discovery trigger and (optionally) honouring `_meta.timeoutMs`.
- ADR-037 (code signing and bundled-binary signing) — `host_exec` is bundled `node` + JS, no Mach-O of its own; signed via the existing path; **without** PIM entitlements.
- ADR-038 (single internal worker port) — `host_exec` is a host process, so the in-container worker-port convention does not apply; it gets a dynamic loopback port per project and a `WORKER_HOST_EXEC_URL` on that project's hub, like `mcp-os` — hence the exception in `test_hub_worker_urls_use_port_worker`.
- ADR-041 (local LLM model discovery) — precedent for host-side HTTP hardening and for "DNS rebinding against user-originated targets is accepted; don't let attackers inject the target without user action".
- ADR-049 (TCC sub-identifiers and Apple Events gate) — why `mcp-os` carries PIM entitlements and why `host_exec` must not.
- ADR-052 (Claude Code login surface + clipboard bridge) — the clipboard bridge's one-way text-into-host-clipboard model, confirmed in the audit.
- ADR-001 (eliminate Docker Desktop) — Speedwave does not use Docker Desktop as its runtime; "the host's Docker" is a separate, user-installed thing a `docker` recipe targets.
- `.claude/rules/security.md`, CLAUDE.md (SSRF/provider rules, `RESERVED_ENV_KEYS`, the plugin contract) — the precedents this ADR follows: untrusted repo config never overrides security-class fields (`hostExec` is ignored in the repo layer); SSOT lists live in `consts.rs` (`HOST_EXEC_SHELL_LAUNCHERS`); plugin-contract compatibility when `compose.rs` changes.
