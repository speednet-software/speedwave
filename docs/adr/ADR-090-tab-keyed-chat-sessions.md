# ADR-090: Tab-Keyed Chat Session Registry

> **Status:** Accepted
> **Date:** 2026-09-23
> **Context:** SPEED-388 adds parallel chat tabs. Desktop chat state was a single `Arc<Mutex<ChatSession>>` behind one process-global start lock (`START_SERIALIZE`); every Tauri chat command implicitly addressed the one session the app could ever run. A second concurrent conversation on the same project needs a second live `claude` process, a second control channel, and a way to tell one tab's stream chunks and session-info events from another's, without breaking the single-tab behavior this PR must preserve. This is PR 1 of SPEED-388: it lands the registry, the identity model and the event plumbing. The tab bar UI, per-tab frontend stores and container memory scaling are later PRs.

## Decision

### 1. A tab-keyed registry replaces the singleton session

`desktop/src-tauri/src/chat_registry.rs::ChatSessions` holds `tabs: Mutex<HashMap<String, TabEntry>>` instead of the one `Arc<Mutex<ChatSession>>` main.rs used to manage. It is constructed once in `main.rs` as `SharedChatSessions` (`Arc<ChatSessions>`) and injected as Tauri state, the same shape the old singleton had. `TabEntry` carries: the session arc (`Arc<Mutex<ChatSession>>`), a per-tab start serializer (`start_serialize: Arc<Mutex<()>>`, replacing the deleted process-global `START_SERIALIZE`), the project name, a registry-owned transcript slot (`transcript: Arc<Mutex<Option<String>>>`), and a monotonic start sequence (`seq`) assigned under the map lock (`chat_registry.rs::ChatSessions::prepare`, guarded by the `prepare_assigns_the_seq_under_the_map_lock` test). The transcript slot is constructed once per tab and threaded into `ChatSession::new` (`chat.rs`) so it survives a session being stopped and replaced in place; `chat_registry.rs::ChatSessions::prepare` reuses the existing entry when the tab is re-prepared for the same project, and replaces it (fresh session, fresh transcript slot) when the project differs.

A per-tab start serializer, not a returned-to process-global one, is the point: two tabs starting at the same time must not block each other's spawn, but a single tab's `start`/`stop`/effort-check race still needs the same exclusion `START_SERIALIZE` gave the whole app. `chat_session_cmd.rs::takes_wire_effort_inner` demonstrates the pattern other per-tab-serialized reads follow: resolve the tab's (or project's) `TabEntry`, lock its `start_serialize`, then lock its `session`.

### 2. Three identifiers, three different lifetimes

- **`tab_id`** is a UUID the frontend generates once per browser tab (`chat-state.service.ts::_tabId = crypto.randomUUID()`) and passes as an explicit argument to every tab-addressed command (`start_chat`, `resume_conversation`, `send_message`, `stop_chat`, `close_chat_tab`). The backend never trusts it as a bare string: `chat_registry.rs::validate_tab_id` delegates to `history::validate_session_id`, the same lowercase-UUID validator session-history filenames use, so a malformed or path-traversing value is rejected before it reaches the registry. It identifies a tab for the lifetime of that browser tab.
- **`SPW_SESSION_INSTANCE_ID`** (unchanged from before this PR, `session/instance.rs`) is stamped on every spawned `claude` process and is the kill discriminator: stopping a session's process must SIGKILL that exact PID, matched by /proc-environ, never a sibling tab's process. It identifies one process spawn, not a tab or a conversation.
- **Claude's own transcript `session_id`** is the identifier Claude Code assigns to a conversation and writes into its transcript file. The reader thread records it into the tab's transcript slot as it streams (`chat.rs`), and a resume seeds the slot with the id being resumed before the process starts. It identifies a conversation, independent of which tab or process is currently attached to it.

A tab keeps the same `tab_id` across every session it starts or resumes; a session keeps the same instance id only for the life of one process; a conversation keeps the same transcript id across resumes in different tabs or after a restart.

### 3. Resume dedup: one live tab per transcript, claimed under the map lock

Two tabs must not attach to the same Claude transcript at once: a shared `session.jsonl` file getting two concurrent writers (from two `claude` processes racing to append) would corrupt the transcript. `chat_registry.rs::ChatSessions::claim_transcript` takes the map lock, checks whether any other tab's transcript slot already holds the requested id, and only then writes the new value into the calling tab's slot, so the check-and-set is atomic with respect to every other tab. A tab that finds the transcript already claimed gets `chat_registry::MSG_TRANSCRIPT_OPEN_IN_OTHER_TAB` back from `resume_conversation` instead of starting a second process against the same file.

The known limitation: the claim lives in the tab's transcript slot, not in the process. A tab whose `claude` process has died (crashed, was killed outside the normal stop path) still holds its claim until the tab entry itself is removed from the registry (`ChatSessions::remove`, driven by `close_chat_tab`) or replaced by `prepare` for a different project. A dead tab therefore blocks a resume of its own transcript from any other tab until the user closes it. This PR accepts that limitation; it does not add liveness detection to the claim.

### 4. Every stream chunk and session-info event carries the tab_id

`chat.rs::TabStreamChunk` wraps every `chat_stream` payload with the `tab_id` of the session that produced it, and `control_channel.rs::SessionInfoEvent` carries `tab_id` alongside `project` and `status`. Both are broadcast Tauri events (one event bus, every window listening), so the frontend, not the backend, is responsible for discarding what is not its own: `ChatStateService` owns one `tabId` for its lifetime and every stream handler filters on it (for example the `chat_stream` listener drops a chunk whose `tab_id !== this._tabId`). This is the same pattern the project-scoped `project` field already used for filtering across projects; tab_id adds a second, finer axis.

### 5. Project-scoped reads keep resolving to the most recently started live session

Four commands are addressed by project, not by tab: `get_chat_session_info`, `get_plan_usage`, `get_context_usage`, `get_chat_takes_wire_effort` (and internally, `list_model_picker`, whose `model_picker.rs::picker_for` reads the session info through `chat_session_cmd.rs::session_info_state_inner`). All share one resolution rule: `chat_registry.rs::ChatSessions::entry_for_project` picks the `TabEntry` with the highest `seq` for the project, i.e. the tab whose session was most recently prepared. `get_chat_takes_wire_effort` calls it directly (`chat_session_cmd.rs::takes_wire_effort_inner` needs the entry's `start_serialize`); the other reads go through `any_for_project`, which is built on it and returns only the session arc. With one tab per project (the only configuration this PR ships to users) this is exactly the old singleton behavior. With two tabs open on the same project, a control-channel read (`initialize`, `get_usage`, `get_context_usage`) or a `takes_wire_effort` check answers for whichever tab started last, not necessarily the tab the user is looking at. This is a deliberate placeholder: a later PR gives these commands a per-tab facade once the frontend has per-tab state to address them with. Commands that already carry a `tab_id` (`send_message`, `stop_chat`, `close_chat_tab`) are unaffected: they resolve through `ChatSessions::entry`/`remove`, which is exact-tab lookup, not the project heuristic.

### 6. One session log per project, tagged per tab, instead of one file per tab

The diagnostics registry (`crates/speedwave-runtime/src/diagnostic_sources.rs::SourceKind::File`) models every file source as one file resolved from `(data_dir, project)`, a 1:1 relationship the `/logs` view and the diagnostics ZIP both assume. Splitting the Claude session log per tab would break that cardinality for one source without a matching frontend or ZIP change. Instead, the existing per-project file (`consts::claude_session_log_path`) stays, and every line is tagged with which tab (and which stream: stdout, stderr, control, session) produced it: `chat.rs::log_tag(tab_id, stream)` renders `"{stream}:{short_tab_id}"`, using the first eight characters of the tab_id so the tag reads at a glance next to the surrounding log text. Truncating the file when a session restarts (`allow_log_truncate`) is gated on there being no sibling tab entry for the project (`chat_registry.rs::ChatSessions::other_entry_for_project`, read by `chat_session_cmd.rs::start_session_inner` and `retry_cmd.rs`): truncating out from under a second tab's still-live log tags would lose that tab's history.

### 7. Project switch clears the whole registry; the frontend restarts its own session

The old singleton had `rebind_chat`, which pointed the same `ChatSession` at a new project in place. That does not generalize to N tabs: some tabs might belong to the project being left, and rebinding would attach them to a project their UI state does not reflect. `rebind_chat` is deleted. `project_cmd.rs::clear_chat_sessions` instead drains every tab from the registry (`ChatSessions::drain_all`) and stops each session's process, tolerating a poisoned lock the same way the single-session path used to. The frontend is responsible for starting fresh: `chat-state.service.ts` sets `_sawSwitching` when project state goes to `switching`, and starts a new chat session only on the next `ready` transition it observes with that flag set (`setupProjectStateListeners`), so a stale `ready` from before the switch cannot trigger a spurious start.

## Consequences

- Two or more tabs can hold live `claude` processes for the same project without one tab's start, stop or effort check blocking another's, because start-serialization and the session lock are now per tab.
- A tab is a first-class registry entry with its own transcript claim, so resuming the same conversation twice is rejected instead of silently racing two writers on one transcript file.
- Every stream chunk and session-info event is self-describing (`tab_id`), so the frontend can filter a shared event bus down to one tab's UI without a new per-tab event channel.
- Four project-scoped reads (session info, plan usage, context usage, wire-effort check) do not yet address a specific tab; with more than one live tab on a project they answer for the most recently started one. This is scoped as later-PR work, not a defect to fix here.
- A tab whose process died without going through `close_chat_tab` keeps its transcript claimed until the tab is closed, blocking a resume of that transcript from elsewhere in the meantime.
- The Claude session log stays one file per project (matching the diagnostics registry's 1:1 assumption) with per-line tab tags, rather than fragmenting into one file per tab.

## Rejected alternatives

- **One `ChatSessions` singleton per tab_id class, keyed by project instead of tab.** Rejected: two tabs on the same project are exactly the case this PR exists to support, so keying by project would collapse them back into one slot.
- **Splitting the Claude session log per tab.** Rejected: it breaks the diagnostics registry's `SourceKind::File` 1:1 `(data_dir, project)` cardinality for one source only, which both the `/logs` view and the diagnostics ZIP would need special-cased handling for.
- **Detecting a dead process to release its transcript claim automatically.** Deferred, not rejected outright: it needs a liveness signal the registry does not currently have (the claim lives in a slot, not tied to the child process handle), and the manual close-to-release behavior is an acceptable interim state for PR 1.
- **Giving `get_chat_session_info`/`get_plan_usage`/`get_context_usage`/`get_chat_takes_wire_effort` a `tab_id` parameter in this PR.** Deferred: the frontend has no per-tab state yet to drive them with correctly: threading a `tab_id` through today would only move the ambiguity from the backend's `entry_for_project` heuristic to a caller that cannot yet supply the right answer either.
