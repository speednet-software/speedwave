# ADR-097: Mermaid diagrams and full Markdown in the Desktop UI

> **Status:** Accepted (2026-10-20).
> **Context:** The Desktop UI rendered assistant text (`desktop/src/src/app/chat/blocks/text-block.component.ts`) with the global `marked` instance, and plugin instructions and changelogs (`plugins/plugin-detail/plugin-detail.component.ts`) with a scoped `Marked`, both without extensions and both through `[innerHTML]`, whose sanitizer is the XSS boundary for model output. A `mermaid` fence showed as source code, fenced code had no highlighting, and footnotes and GFM alerts rendered as plain text. SPEED-759 asks for diagrams, highlighting, footnotes and alerts in both views without `bypassSecurityTrustHtml`: a diagram that fails to render falls back to its code block, and a fence that is still streaming stays code until it closes. Angular's HTML sanitizer drops `<svg>`, `<input>` and the `id`, `style` and `data-*` attributes[^1], so a diagram cannot reach the page through `[innerHTML]`.

## Decision

1. **Markdown goes through two scoped `Marked` instances.** `desktop/src/src/app/shared/markdown.ts` builds `chatMarkdown` and `pluginMarkdown` with the same extensions; the plugin one adds the link renderer that opens links in a new tab with `rel="noopener noreferrer"`. The global `marked` gets no `use()`, because options and extensions set on it apply to every user of the default instance[^2]. Everything Markdown produces still reaches the page only through `[innerHTML]` and Angular's sanitizer.
2. **Code highlighting.** `marked-highlight` with highlight.js `lib/common` plus `dockerfile` and `powershell` highlights a fence whose language tag highlight.js knows, with `ignoreIllegals`; an untagged fence or an unknown language stays escaped text and is never auto-detected. Every streamed delta parses the whole message again, so highlighted results sit in an LRU cache of 64 entries keyed by language and code (`HIGHLIGHT_CACHE_SIZE`): a closed block is highlighted once, and later deltas find it in the cache. Token colours come from `.prose-sw` variables in `desktop/src/src/styles.css`.
3. **Footnotes without links.** `marked-footnote` emits `id`, `data-footnote-ref`, `aria-describedby` and `#footnote-…` back-links[^3]. The sanitizer drops the ids and data attributes[^1], and the chat's link handler (`chat/chat.component.ts::onLinkClick`) acts only on hrefs with a scheme, so those links would point at ids that no longer exist. A reference renders as `<sup class="footnote-ref">n</sup>` and the definitions as `<section class="footnotes"><ol>…</ol></section>`, with no ids and no back-links.
4. **Alerts without icons.** `marked-alert`'s default icons are inline `<svg>`[^4], which the sanitizer drops, so every variant is configured with an empty icon and renders as a title and a coloured left border. The alerts and the highlighting take teal, amber, green and violet from `.prose-sw` variables with their own light-theme values, because in the light theme code blocks and alerts sit on `--bg-1` (#f7f8fb), where WCAG 2.2 asks for a contrast ratio of at least 4.5:1 for text[^5]. On that background the global `--teal` (#0d8a72) reaches 4.04:1 and `--amber` (#9a6b00) 4.42:1 (SPEED-828 tracks both), and `--green` and `--violet` have no light-theme value, so their dark-theme #34d399 and #a78bfa would reach 1.81:1 and 2.56:1 (SPEED-815 tracks those two). The `.prose-sw` light values #0f766e, #8a5c00, #047857 and #7c3aed reach 5.15:1, 5.48:1, 5.16:1 and 5.37:1 there, by WCAG's contrast-ratio formula[^5].
5. **Task lists.** The sanitizer drops `<input>`[^1], so a task item renders a non-interactive `<span class="task-checkbox" role="checkbox" aria-checked="…" aria-disabled="true">`.
6. **A closed `mermaid` fence becomes a slot; everything else stays code.** The `code` renderer wraps a closed `mermaid` fence in `<div class="mermaid-slot">` around the plain, unhighlighted code block (`markdown.ts::renderMermaidSlot`). Closure is read from the token's raw text: the last line is a run of the opening fence character at least as long as the opening run, followed by nothing but spaces or tabs (`isClosedMermaidFence`). A fence that is still streaming and an indented code block stay code blocks. The slot passes the sanitizer as plain HTML.
7. **One directive draws the slots.** `MermaidSlotsDirective` (`shared/mermaid-slots.directive.ts`) sits next to `[innerHTML]` on the `.prose-sw` container in `text-block` and in both `plugin-detail` blocks. After every render in which the HTML, the light or dark mode or a settled diagram changed, it reads each slot's source through `markdown.ts::findMermaidSlots`, which sits next to the renderer that writes the slots, looks it up in `MermaidRendererService` and, once the diagram is ready, draws a copy of its sanitized SVG into the slot's open shadow root next to a short style rule. The code block stays the slot's light-DOM content: it shows until the diagram is ready and after a failure, and it is not rendered while the shadow root holds the diagram, because the children of a shadow host that are not assigned to a slot are not part of the flat tree[^6]. A streamed delta replaces the `[innerHTML]` content, and the directive draws the cached SVG into the new slots in the same render.
8. **One renderer for the app.** `MermaidRendererService` (`shared/mermaid-renderer.service.ts`, provided in root) loads mermaid on first use through the `MERMAID_LOADER` token, a dynamic `import('mermaid')`, and renders one diagram at a time from a queue. A source longer than `maxTextSize` fails at once (decision 9); for any other it calls `parse(text, { suppressErrors: true })`, which returns `false` for invalid source instead of throwing[^7], then `render(id, text, container)`[^7] in an off-screen `div.mermaid-measure` that it empties after every render, failed ones included. Results go into an LRU cache of 100 entries keyed by the effective mode and the source. A failure is cached like a success, never retried and never logged. A `version` signal tells the directive to look again. `ThemeService.effectiveMode` (light or dark, with `auto` resolved against the OS) is part of the cache key, so switching between light and dark renders each diagram again on its next lookup, and the slot keeps the old diagram until the new one is ready. The accent theme is not part of the key: the diagram config reads only background, line, ink and font variables, and a `[data-theme]` accent sets only `--accent*` and `--on-accent` (`desktop/src/src/styles.css`), so an accent change keeps every drawn diagram.
9. **Mermaid runs locked down.** `initialize` gets `securityLevel: 'strict'`, `htmlLabels: false`, `suppressErrorRendering: true`, `startOnLoad: false`, `logLevel: 'fatal'`, `theme: 'base'` with `themeVariables` read from the CSS variables, `darkMode`, and `layout: 'dagre'`. Its `secure` list, the keys a diagram cannot change through a directive or frontmatter[^8], is mermaid's default (`secure`, `securityLevel`, `startOnLoad`, `maxTextSize`, `suppressErrorRendering`, `maxEdges`[^8]) plus `theme`, `themeVariables`, `themeCSS`, `fontFamily`, `altFontFamily`, `darkMode`, `htmlLabels`, `dompurifyConfig`, `layout` and `logLevel`. Mermaid removes those keys from a directive's config at every nesting level[^9], so a diagram cannot restyle itself, turn on HTML labels or pick another layout. The size limits keep mermaid's defaults, 50,000 characters for `maxTextSize` and 500 edges for `maxEdges`[^8], and the set of diagram types stays mermaid's default. `maxTextSize` is passed explicitly because the service fails a longer source itself: `render` does not fail on one but draws a "Maximum text size in diagram exceeded" diagram in its place, after measuring the source without its front matter, directives and comment lines[^10], so checking the whole source keeps every such source a code block. A `themeCSS` rule gives the background behind every edge label (`.edgeLabel .label rect.background`) full opacity and the `--bg` colour: mermaid draws that background at `opacity: 0.5` and appends `themeCSS` after its diagram styles[^11], so without the rule an edge shows through its label.
10. **Our own DOMPurify pass before a slot.** Under `strict`, mermaid sanitizes its SVG with options it picks itself (`ADD_TAGS` with `foreignobject`, `ADD_ATTR` with `dominant-baseline`, `foreignobject` as an HTML integration point)[^12], and a mermaid release can change them. `shared/diagram-svg.ts::sanitizeDiagramSvg` passes the result through a DOMPurify instance of its own[^13] with a fixed profile: the SVG, SVG-filter and HTML profiles, `foreignobject` and `dominant-baseline` allowed as mermaid allows them, and a hook that drops every `href` and `xlink:href` of an `<a>`, every other `href` and `xlink:href` that is not a `#fragment`, and every `src` that is not a `data:` URL. An `<a>` stays in the tree as a group without a link: mermaid wraps a node that has a `click` link in an `<a>` and positions the node through that wrapper's `transform`[^14], so removing the element would draw the node at the diagram's origin, over the other nodes. The result is a DOM fragment (`RETURN_DOM_FRAGMENT`[^13]) that must be exactly one `<svg>` element, or the diagram counts as failed; the directive inserts copies of that element with `replaceChildren`, never through an HTML string.
11. **elkjs stays out of the bundle, and every layout is dagre.** Mermaid 12.2.0 depends on `elkjs` 0.9.3[^15], licensed EPL-2.0[^16], whose `lib/elk.bundled.js` is 1,606,238 bytes[^17]. Mermaid's full build registers the ELK layouts next to dagre and loads ELK through a dynamic import of a chunk that imports `elkjs/lib/elk.bundled.js`[^18][^19]. `desktop/src/angular.json` lists `elkjs` in the build options' `externalDependencies`, so the bundler leaves that import to be resolved at runtime[^20], where nothing provides it, and no EPL-2.0 code ships. Mermaid 12.2.0's default `layout` is `elk`[^8], and flowchart, class, state, ER, requirement and use-case diagrams, among others, take their algorithm from it[^21]; mermaid falls back to dagre only for a layout that is not registered, and `render` awaits the layout loader without catching its error[^18]. Without the pin, all those diagrams would fail at the missing import. Run against the real mermaid 12.2.0 in jsdom with `elkjs` blocked as the build blocks it, a flowchart and a state diagram failed with `Failed to resolve module specifier "elkjs/lib/elk.bundled.js"` and a sequence diagram rendered; with `layout: 'dagre'` all three rendered, and so did diagrams asking for `elk` through an `%%{init}%%` directive, through frontmatter and through the `flowchart-elk` type, all with dagre. `_tests/desktop/angular-externals.bats` keeps `elkjs` in `externalDependencies`, and `mermaid-renderer.service.spec.ts` keeps `layout: 'dagre'` and `layout` in `secure`.
12. **The CSP does not change.** It stays `script-src 'self'` and `style-src 'self' 'unsafe-inline'`, with images from `'self'`, `blob:` and `data:` (`desktop/src-tauri/tauri.conf.json`). A `script-src` without `'unsafe-inline'` blocks inline event handlers and inline scripts[^22], which makes it the layer behind both sanitizers.
13. **Dependencies and build output.** `highlight.js` (BSD-3-Clause[^23]), `marked-highlight`, `marked-footnote`, `marked-alert` (MIT[^24]), `mermaid` (MIT[^15]) and `dompurify` (`MPL-2.0 OR Apache-2.0`[^25]) become direct dependencies of `desktop/src`; mermaid already depends on dompurify[^15]. Four CommonJS packages that mermaid's lazy chunks import (`@braintree/sanitize-url`, `cytoscape-cose-bilkent`, `cytoscape-fcose`, `dayjs`) are listed in `allowedCommonJsDependencies`[^20], which silences the build warning for those packages and their deep imports only[^26]; a new CommonJS dependency still warns.

## Why

- The ticket allows a dedicated component instead of bypassing the sanitizer when the sanitizer strips the SVG. Hydrating slots keeps one `marked` pass per message: footnote references and definitions stay in one document, a diagram inside a list or a quote works, and the sanitizer still handles all Markdown HTML. Only the diagram SVG takes another path, through our DOMPurify profile into a shadow root.
- A shadow root scopes styles both ways[^27]: the `<style>` mermaid writes into its SVG, CSS that a `classDef` carries included, stays inside the diagram, and the app's `.prose-sw` rules do not reach the diagram's labels. The code block left in the light DOM is the fallback and the source for drawing the diagram again, with no second copy of the source anywhere.
- Mermaid's sanitizer options are tuned by mermaid for its diagrams; ours are pinned and tested in this repo (`diagram-svg.spec.ts`), so a mermaid release that widens its own options does not widen what reaches the app document.
- One queue and a cache keep a resumed session, which mounts every message at once, from starting all its renders together, and a tab switch draws its diagrams from the cache.
- The bundle cost lands where diagrams are used. Measured on 2026-10-20 with `ng build --configuration production`: the initial bundle went from 441.96 kB to 445.75 kB (styles); the lazy chunk the chat and plugin views share went from 43.71 kB to 261.63 kB (11.90 kB to 67.89 kB estimated transfer) with highlight.js, the extensions, the renderer service and DOMPurify; mermaid's entry adds 19 files and 682.3 kB on the first diagram, before the chunks of its diagram type and layout; all JavaScript in `dist/browser` went from 1,304.2 kB to 5,203.9 kB.

## Known limitations

- Diagrams use the dagre layout, not mermaid 12's default ELK, so a diagram can be laid out differently than in a renderer that ships ELK.
- Mindmaps are laid out by dagre as a top-to-bottom tree instead of mermaid's default `cose-bilkent`. A mindmap keeps `cose-bilkent` only when no user-defined `layout` exists, and mermaid counts the config passed to `initialize` as user-defined[^28], so the `layout: 'dagre'` pin (decision 11) reaches mindmaps too. The build still contains the `cose-bilkent` layout chunk and `cytoscape-cose-bilkent` (decision 13), but nothing loads them.
- While mermaid lays a diagram out, it draws it into a temporary element inside the off-screen `div.mermaid-measure`, in the document, and sanitizes the SVG only after serializing it[^29]; our DOMPurify profile sees only the SVG that `render` returns. During layout, the CSP (decision 12) is the layer behind mermaid's own handling.
- Mermaid renders on the main thread. The default limits (`maxTextSize` 50,000, `maxEdges` 500[^8]) bound one diagram, but a large one can still hold the UI while its layout runs; nothing restricts rendering to the diagrams in view.
- None of this ran in a webview: the build container has no browser. Mermaid's chunks under the CSP on WebView2, shadow-DOM rendering, fonts in diagrams and whether the failed `elkjs` import leaves a console message on either engine are checked by the manual test on macOS and Windows, not by an automated test.
- Text selection and find-in-page across the shadow boundary were not tested.
- The frontend's third-party license notes, mermaid's dependency tree included, do not reach the installers; that gap predates this change (SPEED-814).

## Rejected alternatives

- **An `<img src="blob:…">` per diagram.** It passes the sanitizer and keeps the diagram out of the document, but an SVG loaded as an image loads no external resources except `data:` URLs[^30], so it cannot use the app's web fonts without embedding them in every diagram.
- **Splitting the Markdown into segments with a component per diagram.** It handles only top-level fences and separates footnote references from definitions that follow the diagram.
- **A sandboxed iframe per diagram.** It needs `frame-src` in the CSP and manual height handling.
- **`bypassSecurityTrustHtml` for messages with diagrams.** It removes the sanitizer for the whole message; the ticket rules it out.
- **Removing `<a>` from the diagram.** It also removes the position of every node that has a `click` link (decision 10).
- **Relying on mermaid's DOMPurify pass alone.** Its options are mermaid's to change between releases (decision 10).
- **The global light `--teal` and `--amber` in `.prose-sw`.** Both stay under 4.5:1 on `--bg-1`, the background of code blocks and alerts (decision 4).
- **Shipping elkjs.** It adds EPL-2.0 code and 1.6 MB[^17] to an app that does not ship frontend license notes yet (SPEED-814).
- **An Angular component created per slot (`createComponent`).** It adds injection and change detection per slot and does nothing the directive does not.
- **Rendering only the diagrams in view (`IntersectionObserver`).** Deferred until the manual test on a long resumed history shows a stall.
