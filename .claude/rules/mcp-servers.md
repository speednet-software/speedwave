# MCP Servers Rules

- `mcp-servers/shared/` is the SSOT for MCP protocol utilities: every built-in worker uses it, with one exception, `playwright` wraps Microsoft's `@playwright/mcp` and does not consume mcp-shared.
- MCP Hub is the ONLY MCP server Claude sees (internal port 4000); workers listen on port 3000 (`consts::PORT_WORKER`). Each worker mounts only its own credentials at `/tokens:ro`; the hub holds no external credentials.
- **New integration = own thin TypeScript worker by default:** built on `@speedwave/mcp-shared` + the service's official SDK (else thin axios), camelCase unprefixed tool names, `_meta` policy keys where applicable. Wrapping an upstream MCP server is allowed only when ALL four hold: official and owner-maintained, an npm/TS package, generic infrastructure (not a domain API), wrappable in ≤~100 lines. Only `playwright` qualifies today.
- OAuth-consuming workers never write tokens: refresh lives in the host-side `oauth` worker; use `authedRequest` from mcp-shared for every authenticated request. The `oauth` worker is never enumerated to Claude, never in the hub registry, and must never be wired into `WORKER_*_URL` discovery (see security rules).
- **Slack OAuth invariants:** the initial PKCE token exchange (`desktop/src-tauri/src/slack_oauth_cmd.rs`) reads ONLY `authed_user.*` (a top-level `access_token` is a bot token; the app is user_scope-only, never request bot scopes). The host-side refresh (`mcp-servers/oauth/src/providers/slack.ts`): refresh tokens are single-use and rotate on every refresh, so the oauth worker serializes `refresh` per service (a rate-limited call with a still-valid token is a success-noop), and refresh state is persisted before the mounted access token so a crash never leaves a token without refresh state. A "fix" to a refresh race or "adding bot features" that breaks any of these breaks every Slack install's token chain.
- `search_tools` (`hub/src/search-tools.ts`) also matches a query token equal (case-insensitively) to a tool's service id, that id without `custom-`, or its sandbox global, ranked below every name/keyword/description match (`MatchTier.Service`), so a user-added `custom-<name>` server is found by its name; `custom` alone matches nothing, and a zero-match hint lists the enabled services with their sandbox globals.
- **`mcp-servers/policies/` (`@speedwave/policy-engine`) is a hub-consumed library, not a worker.** It has no `image`/compose service of its own; only `mcp-hub` (via `hub/src/policy.ts` → `hub/src/executor.ts`) links against it. It is a thin TS wrapper (`src/engine.ts`) over the prebuilt WASM PII engine (`crates/pii-engine-wasm`, built by `build-wasm.sh` into `policies/wasm-pkg/`, `npm run build` chains `build:wasm` before `tsc`): `loadEngine()` reads `POLICY_FILE` + its sibling `key` file (absent `POLICY_FILE` → the engine's compiled-in default policy via `default_policy_json()`, SSOT in Rust, plus an ephemeral random key), and the returned `PiiEngine` does `tokenize`/`detokenize` by round-tripping `JSON.stringify`/`JSON.parse` through the WASM calls; both are keyword-aware (tokenize masks match→alias after PII sealing, detokenize unmasks alias→match before token resolution), mirroring the proxy's `scan_request`/response-rewrite order, so keywords get the same hub+proxy double layer as PII and Desktop unmasks them at display (`pii_display.rs::load_display_policy`). `src/types.ts`'s `PIIType` enum has been removed (design decision 2.3, `SPEED-311-yaml-rules-design.md`): the resolver (`pii_policy.rs`) moved to an open rule-id set in the v3 PII policy migration, `PiiCategory`/`pii_category_serde_matches_policy_engine_ts` no longer exist on the Rust side, and nothing in this package imported the enum. The rest of the pre-WASM TS pipeline (tokenizer, patterns, validators, resolved-policy, template loading) is gone. `templates/*.yaml` is read only by Rust `pii_policy.rs` (`include_str!`) now — no TS reader remains, but the files stay in-repo. See [ADR-083](../../docs/adr/ADR-083-vaultless-pii-tokenization.md) (vaultless tokenization, the shared Rust/WASM engine); the per-project host-rendered policy delivery this section builds on is [ADR-082](../../docs/adr/ADR-082-policy-engine-pii-tokenization.md).

## `_meta` keys: SSOT and identity contract

Tool `_meta` fields use MCP-spec-compliant prefixed keys from mcp-shared's `META_KEYS`: `speedwave.pl/defer-loading`, `speedwave.pl/timeout-class`, `speedwave.pl/timeout-ms`, `speedwave.pl/os-category`, plus the identity trio `speedwave.pl/user-scoped`, `speedwave.pl/current-user-tool`, `speedwave.pl/self-param`. Read every key via `metaValue(meta, META_KEYS.X, 'legacyKey')`: prefixed key wins if present, else fall back to the legacy unprefixed key (`deferLoading`, `userScoped`, …) so third-party plugin workers still emitting the old shape keep working. Never hand-write a `_meta` key string; import `META_KEYS`.

Two gate keys exist only in prefixed form, with no legacy fallback and no `metaValue` read: `speedwave.pl/tool-state` (`allowed`/`pending`/`blocked`/`changed`) and `speedwave.pl/upstream-name`. Only the custom MCP guard (`mcp-servers/custom-guard/`) sets them. It drops every `_meta` key a third-party server sends (prefixed, legacy or foreign) and sets its own four: those two plus `defer-loading` and `timeout-class` from its policy file. The hub parses both in `mergeToolWithMeta` and drops every tool that is not `allowed` in `discoverAndMergeService`. That is the single drop point that `search_tools` and the sandbox read from, so never filter gated tools anywhere else. For a built-in or plugin worker, which has no gate, an absent state means `allowed` and an unknown one is `allowed` with a warning. For a `custom-*` service (`hub/src/service-list.ts::CUSTOM_SERVICE_PREFIX`) an absent or unknown state is `pending`, so the tool stays hidden and a guard that stops setting the key fails closed. Before the drop, the hub writes the raw listing of each `custom-*` service to `$AUDIT_DIR/tool-catalog-<service>.json` (`hub/src/tool-catalog.ts`: tmp + fsync + rename, 0o600, skipped above 1 MiB, never written for an empty listing). This is the catalog channel Desktop reads as untrusted text. It needs no new mount, because `/audit:rw` is already the hub's only writable mount. A host-mode guard appends "Paths inside file contents are not rewritten." to each description before hashing, so the catalog text and the guard's definition hash agree. For the same reason the gate's ingest (`shared/src/tool-gate.ts::createToolGate().ingestUpstreamTools`, through `withDescriptionPlaceholder`) replaces a description that is empty after sanitizing with `EMPTY_DESCRIPTION_PLACEHOLDER` ("No description provided by the server.") before it hashes, because the hub drops a tool without a description; `definitionHash` itself never adds it. `mapToolNames` routes `__proto__`, `constructor` and `prototype` through the hash-suffix branch, and the hub builds each service's tool record, sandbox bridge and wrappers with `Object.create(null)`, so a tool name never reads or writes a prototype.

## Custom MCP guard and per-service PII mode

- The guard (`mcp-servers/custom-guard/`) is a `bootWorker` worker that serves a `CustomGuardHandler` (a `JSONRPCHandler` subclass passed through the `rpcHandler` option) because its tool set comes from the upstream server on every `tools/list`. It answers only `initialize` (its own `serverInfo`, `tools` capability only, never upstream `instructions`), `ping`, `tools/list`, `tools/call` and `notifications/initialized`. Every other request gets a JSON-RPC `MethodNotFound`, and every other notification is dropped.
- It re-reads `POLICY_FILE` (only that exact file, never a `.policy.json.tmp.*` sibling) whenever its stat identity changes. It keeps the last valid copy when a newer one is invalid (a warning), denies everything until one valid copy has loaded, and denies everything again whenever the file cannot be read (deleted or unreadable), never falling back to a copy loaded before. When the upstream is unreachable, it lists the approved definitions stored in the policy (`tools.<upstream>.definition`), so allowed tools stay discoverable and a call returns a teaching error.
- A call goes upstream under the original upstream name only when the gate says `allowed`, which requires the live definition hash to equal the approved one. An allowed tool whose definition drifted becomes `changed` and is denied. Results go through `sanitizeToolResult` with the policy's `maxResultBytes`. Host mode rewrites `/workspace` paths through `createWorkspacePathMapper` and re-reads the relay `endpoint.json` and `token` on every request. A path-like argument (`isPathLikeProperty`: schema `format` `path`/`uri`, or a name ending in path/file/dir/folder) must lie under `/workspace`: any other absolute value (POSIX `/…`, a drive `C:…`, a leading `\` or UNC `\\host\share`, a `file:` URL outside `/workspace`) is refused as `refuse-outside-workspace` with a teaching error that names the parameter, never the value. Free-text arguments are not confined: a host path written into prose reaches the server unchanged. A relay HTTP 502 means the host application is down, while a relay that does not answer means Desktop is not running. The decision log line carries service, exposed tool, decision and duration only: never arguments, results or tokens.
- The hub's per-service PII mode comes from the optional `services.<id>.pii_mode` field of its own `policy.json` (`hub/src/pii-mode.ts`), never from `_meta`. An explicit entry wins; otherwise `custom-*` is `tokens` and everything else is `plaintext`. In `tokens` mode `prepareParams` forwards the arguments untouched, without `detokenize`, and writes value-free `tool-args` audit rows per token category (`hub/src/token-spans.ts`). `search_tools` also tells the model that arguments stay tokenized.

A tool whose result or accepted self-referential parameters depend on the caller's identity (a "my X" question, or a write tool with an assignee-style param) MUST declare `speedwave.pl/user-scoped: true`, and any worker exposing user-scoped tools MUST also expose a current-user tool (its name declared via `speedwave.pl/current-user-tool` on the user-scoped tools) or a self-reference hint via `speedwave.pl/self-param` (a short descriptive string, e.g. `"assigned_to: 'me'"`, not a bare parameter name). At discovery the hub validates both companions (`tool-discovery.ts`): `currentUserTool` accepts either the hub's camelCase method name or the worker's own tool name (normalized to camelCase and re-stored), and is dropped only when neither form resolves to a discovered tool; a `self-param` whose leading parameter name is not in the tool's `inputSchema` is dropped the same way (each with a warning), and the hub warns once per tool when a user-scoped tool ends up with neither companion. The tool keeps serving: `search_tools` appends the identity sentence to `description` at `with_descriptions`/`full_schema`, and additionally always sets a standalone `identityHint` field (same sentence, including the misconfiguration fallback when neither companion is configured) at every detail level — including `names_only`, the level `search_tools` itself recommends starting with — so a self-reference query never needs a second round trip just to learn how to supply identity. `search_tools` boosts user-scoped tools for self-reference queries (e.g. "me").

## Error and pagination contract

New tool validation errors (missing/invalid params, not-found lookups, teaching hints) go through mcp-shared's `teachingErrorResult`/`teachingToolResult`/`missingParamResult`: they state what was wrong with a parameter, which tool provides a correct value, and the suggested next step, in that order, so a model can self-correct instead of guessing. Existing worker-specific error formatters (e.g. a client's own `formatError`) migrate to this pattern as they are touched, not in bulk. New paginated `limit`/`pageSize`-style params are clamped with `clampPageSize` (finite positive integer, defaults on missing/0/negative/NaN/non-numeric, optionally capped at a max) rather than a hand-rolled bound check; existing params migrate as touched. A paginating ids-only tool returns `{ ids, total_count }` and accepts `offset`/`limit`; the sandbox `paginate()` takes page items only from the keys in `hub/src/paginate.ts::ITEM_KEYS` (or a bare array) and throws a teaching error naming the keys it found when a page carries arrays under other keys only, so a new list tool reuses one of those keys or extends `ITEM_KEYS` in the same change.

**No silent partial effect:** a tool call that partially succeeds (e.g. some items of a batch updated, some rejected) must say so in its result, never return a bare success for a partial outcome. Silent partial success is indistinguishable from full success to the calling model and to the user.

**No silently dropped argument:** the shared JSON-RPC dispatcher (`shared/src/jsonrpc.ts`) rejects `tools/call` arguments that are not an object with `InvalidParams`, for every worker, instead of running the tool with `{}`. mcp-shared's `withDeclaredParams(tool, handler)` also rejects, with a teaching error before the handler runs, any argument missing from `inputSchema.properties` and any `required` argument that is absent, `null` or `''`. It names undeclared arguments but never echoes their values: the hub has already detokenized them, and a truncated echo can slip past re-tokenization. Redmine wraps every tool in it and also normalizes every `*_id` parameter declared as `type: 'number'` with `normalizeNumericIdParams` (the rejection names the parameter, never the value), so a path-traversal string never reaches a URL, and rejects a name given together with its declared `_id` twin (`status` + `status_id`), which the resolvers used to settle silently (`redmine/src/tools/index.ts::createToolDefinitions`; all tools guarded by `declared-params.test.ts`). The Redmine client also builds every path segment through `pathSegment`. This exists because an unknown `updateIssue` field used to be dropped while the call reported success. Under the guard a tool's declared parameters must be exactly the ones its handler and client consume: declare a new client field in the same change, or callers get an error instead of the feature. A worker without the guard keeps the old failure mode (SPEED-685), so adopt the guard when you touch one.

**`outputSchema` is the result contract, not decoration.** Agents read it through `search_tools full_schema` and write sandbox code against it, so apart from the `success`/`error` wrapper every tool declares (Redmine: `successResultSchema`) it names exactly the keys the handler emits: list tools `{ <items key>: [...], count }`, Redmine ids-only tools `{ ids, total_count }`, pass-through results the raw fields a caller plans on (e.g. `description`). The tool's vitest file pins that alignment by parsing the emitted JSON and asserting its keys are declared (`expectEmittedKeysDeclared` in `gitlab/src/tools/test-helpers.ts`).

## Adding a built-in worker touches many places (checklist)

`consts.rs` service descriptor (`TOGGLEABLE_MCP_SERVICES`, resources on the descriptor) + `BUILT_IN_SERVICE_IDS` · `build.rs::IMAGES` entry with `hash_inputs` + `${IMAGE_*}` placeholder + resource placeholders in `compose.template.yml` + bundle-script list (all test-guarded) · `tzdata` in the image (MANUAL, nothing catches a miss) · hub env `WORKER_<SVC>_URL` wiring · optional `containers/claude-resources/*/integrations/<config_key>/` resources (+ BATS on/off test in `_tests/entrypoint/entrypoint.bats`). Grep an existing worker (e.g. `redmine`) end-to-end rather than trusting this list to be exhaustive.

## Test pattern

Follow `mcp-servers/gitlab/src/tools/branch-tools.test.ts` (or `redmine/src/tools/metadata.test.ts`):

- Import the tool factory, resolve handlers via `tools.find((t) => t.tool.name === '<name>')?.handler`.
- Metadata tests: name, description, annotations (readOnlyHint, destructiveHint), keywords, example, inputSchema, `_meta` policy keys (via `metaValue`, prefixed and legacy).
- Execute success cases (mock the client with `vi.fn()`), parameter validation (missing/empty/null/undefined/falsy), error handling (Error, non-Error shapes, strings, undefined), edge cases (special characters, nested paths, large IDs).
