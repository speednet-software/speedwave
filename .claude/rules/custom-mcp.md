# Custom MCP Servers

## Limits and status

- **Beta only.** A server runs only while beta features are on (`effective.rs::resolve_effective`, `beta_disabled`); the Desktop section is behind `BetaService`. Servers are stored only per project in the user config (`ProjectUserEntry.custom_mcp`), never in a repo `.speedwave.json`.
- **Two source kinds, nothing else.** `CustomMcpSource` is `Npm` (a public npm package with an exact version, run over stdio by the launcher) or `Host` (an HTTP MCP endpoint already listening on the host's loopback, reached through the Desktop relay). Remote URL servers are detected only as `remote` proposals and cannot be added; PyPI, Docker-image and any other source are `unsupported`. Only the public npm registry (`CUSTOM_MCP_NPM_REGISTRY`) is used.
- **At most `CUSTOM_MCP_MAX_PER_PROJECT` (5) servers run per project**; further ones are excluded with `over_limit`.
- **Host servers are not isolated from `claude` on macOS (SPEED-761 not done).** The `claude` container can open any host port through the Lima gateway, so a host server's tool allowlist is advisory there: the guard enforces it, but `claude` can reach the app's own port around the guard. The review screen shows `HOST_WARNING_TEXT` and requires a confirmation (`custom_mcp_cmd/list.rs::host_warning_for`: always on macOS, on Windows NAT when the port answers on the containers' gateway, never under mirrored mode). Organizations can turn host servers off (`host_servers_enabled: false`).
- **Windows is not verified live.** Neither WSL NAT nor WSL mirrored mode has been run end to end with a Custom MCP server (npm or host); CI compiles the Windows paths and runs their unit tests only. The `relay-<name>/` directory-mount behaviour is not verified on Lima virtiofs or WSL drvfs (ADR-080 amendment).
- **Isolation evidence is the CNI check, not a traffic probe.** `_custom`/`_cx_<n>` are checked against their CNI config on every start (as for office); no test sends traffic from a Custom MCP container. The CNI address headroom for several projects with several servers each is not measured (ADR-102).
- **Egress covers only clients that honor the proxy environment.** The server gets `HTTPS_PROXY`/`HTTP_PROXY` and `NODE_USE_ENV_PROXY=1`; Node's built-in `fetch` and `http(s)` follow them, but a library with its own transport (`got-scraping`, used by `fetch-mcp@0.0.5`) resolves names itself and fails with `EAI_AGAIN`/`ENOTFOUND` on the isolated network. That is fail-closed (nothing leaves), but nothing reaches the egress proxy, so no refusal is logged, "Blocked connections" stays empty and an allowed domain does not make such a server work. The card says so; the allow/deny path is proven with a Node `fetch` probe from the server container (`verify-egress.sh`), not with `fetch-mcp`.
- **The npm resolver has full internet** (accepted deviation, ADR-101): it runs no package code, but it is not behind an allowlist.

## Egress proxy (`spw-egress`)

Every approved custom MCP server gets its own egress container (`mcp-custom-<n>-egress`), never one shared per project: a shared egress would sit on every server's network and, once taken over, bridge them. The server lives on `_cx_<n>` (pre-created `--internal`, no route out) and reaches the internet only through this CONNECT proxy, which is the one member of both `_cx_<n>` and `_eg_<n>` (a normal bridge). The binary is the second `[[bin]]` of the proxy workspace (`containers/proxy/src/bin/spw-egress/`) and ships in the proxy image at `/spw-egress`, started through an `entrypoint` override. `crates/ip-policy` is in the proxy `hash_inputs` and staged by both bundle scripts, so an egress change retags the `proxy` image.

### Configuration

- `SPW_EGRESS_CONFIG` (default `/config/egress.json`) and `SPW_EGRESS_LISTEN` (default `0.0.0.0:3128`).
- Schema `{"version":1,"allow":["host:port",…]}`; unknown fields, another version, more than 1024 entries, a file over 64 KiB or any single invalid entry reject the whole file.
- The file is re-read on every CONNECT. A successful read replaces the last good allowlist; a missing, unreadable or invalid file keeps the last good copy (logged as a warning). Before the first successful read every CONNECT is denied (`config_unavailable`). A change applies to the next CONNECT without a restart; tunnels already open are not cut.

### Host matching

- Hostnames are ASCII-lowercased; labels are `[a-z0-9-]`, 1 to 63 bytes, no leading or trailing hyphen; at most 253 bytes; no trailing dot, no underscore, no Unicode (use the `xn--` form).
- IP literals are refused: anything that parses as IPv4 or IPv6 (bracketed or bare), and any host whose last label does not start with a letter (`127.1`, `2130706433`, `0x7f000001`, which `getaddrinfo` would read as addresses). A CONNECT to one is `ip_literal`; an allowlist entry with one invalidates the file.
- `host:port` matches that host exactly. `*.suffix:port` matches a host with one or more labels in front of `.suffix` and never the bare `suffix`; the suffix needs at least two labels (`*.com` is invalid) and `*` is allowed only as the whole first label. The port always matches exactly (plain decimal, 1 to 65535).

### Request handling, in order

1. Request head: at most 8 KiB including the blank line, read within 10 s. The request line must be exactly `CONNECT host:port HTTP/1.1` (single spaces). Header lines are ignored; there is no proxy authentication.
2. Allowlist check against the freshly read config. The resolver is not called for a host outside the list.
3. One resolution with the system resolver (5 s). If any answer is forbidden, the CONNECT is refused before any connect attempt. Forbidden = `ip_policy::is_private_or_reserved` (which itself refuses Teredo `2001::/32` and local-use NAT64 `64:ff9b:1::/48` outright), plus IPv4/IPv6 multicast and `240.0.0.0/4` (broadcast included), applied to the answer and to the IPv4 address `ip_policy::embedded_ipv4` decodes from it: IPv4-mapped (`::ffff:0:0/96`), IPv4-compatible (`::/96` except `::` and `::1`), well-known NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`, bits 16 to 48). The upstream connection (10 s) goes to the first answer with the requested port. That address is pinned: there is no second resolution, so DNS rebinding between the check and the connect is impossible.
4. Reply `200 Connection Established`, then read the client's first TLS record (10 s): content type handshake, version `3.x`, length 1 to 16384, carrying exactly one complete ClientHello and nothing else. The bounds-checked parser requires exactly one `server_name` extension with exactly one printable-ASCII `host_name` entry, and that name must equal the CONNECT host case-insensitively. A ClientHello split across several records is refused. With Encrypted Client Hello the outer SNI must match. TLS is never terminated: the record (and any bytes read with it) is written to the upstream first, then the tunnel is spliced.
   - What this does not stop: only the first ClientHello record is inspected, and with ECH only the outer `public_name`, so the server's real name inside the encrypted inner hello is never seen. Without terminating TLS the proxy cannot see the HTTP `Host`, so on a shared CDN address a client can send an allowlisted SNI and ask the CDN for another site behind it (domain fronting). What does not move is the destination: the bytes always go to the one pinned address the allowlisted name resolved to.
5. Splice in both directions with half-close propagated. The tunnel is closed after 300 s with no bytes in either direction, or once 1 GiB has passed in total (both directions, ClientHello included). At most 256 connections are served at once; further accepts wait.

### Responses and deny reasons

| `reason`                                                                 | Answer                                       |
| ------------------------------------------------------------------------ | -------------------------------------------- |
| `bad_request` (oversized, malformed, slow or truncated head)             | 400                                          |
| `method` (anything but CONNECT)                                          | 405 with `Allow: CONNECT`                    |
| `ip_literal`, `config_unavailable`, `not_allowlisted`, `private_address` | 403                                          |
| `dns_failure` (error, timeout or empty answer), `connect_failed`         | 502                                          |
| `not_client_hello`, `no_sni`, `sni_mismatch`                             | connection closed after the 200, no response |

### Logs

- One JSON line on stdout per connection decision: `{"event":"egress","decision":"allow|deny","host":…,"port":…,"reason":…}`. `reason` is `null` on allow; `host` and `port` are `null` when the request line was not parsed (`method`, `bad_request`); an `ip_literal` line carries the address only when it parses as one.
- Never payload bytes, headers, or the SNI of a refused ClientHello. Every other line is JSON too: `{"event":"log","level":…,"message":…}`. All output goes through the `log` facade (decision lines on target `spw_egress::decision`), with `env_logger` writing to stdout.
- The decision line is a contract the Desktop reads. `custom_mcp::egress_log::denials` parses the deny lines of the container log (`event`, `decision`, `host`, `port`, `reason`, and the reason wire names mirrored as `EgressDenyReason`). Renaming a field or a reason, or adding a reason, fails `the_decision_line_contract_matches_spw_egress`, which reads `session.rs` (`Decision::to_json` and `DenyReason::as_str`). Change both sides together, plus the TS union `CustomMcpEgressDenyReason` and its labels.

### Lifecycle and tests

- SIGTERM or SIGINT stops accepting and exits; open tunnels are dropped with the process.
- The address policy has no production override: `Egress::new` always uses `is_forbidden_target` and `Limits::PRODUCTION`. Tests that need a loopback upstream use the `#[cfg(test)]` constructor `Egress::with_policy` and a scripted resolver. Never add an env var or flag that relaxes the policy.

## Server images

- A server name may not be `guard` (the guard image's repository is `speedwave-mcp-custom-guard`), `relay`, or start with `relay-` (the Desktop relay's state shares `custom-mcp/<project>/`).
- `custom_mcp::build::image_tag_for` is the only tag scheme: `speedwave-mcp-custom-<name>:<sanitized version, at most 100 chars>-<digest16>`. The Desktop computes it with `image_tag_for_dir` over the review's staging dir right after the resolver ran and stores it in `lock.image_tag`, inside the consent digest. `entry.json` is `{"command":"node","args":["/opt/spw/server/node_modules/<pkg>/<bin>", …lock.args]}`, the bin taken from the lockfile entry (a string, the key equal to the unscoped package name, or the only key; anything else is refused, as is a bin path that is absolute or has `..`, `.`, empty segments or a backslash).
- `ensure_custom_images` runs from the render when a runtime is passed and from Desktop's `ensure_project_images_built`, under `build::with_build_lock_in` and through `with_build_recovery`. Per server (errors collected) it refuses a lockfile changed since approval, inputs that give another tag, another `SERVER_TEMPLATE_VERSION`, and a `lock.image_tag` outside the server's repository. Every write of the project's `.image-tags` record (a fresh build or an image already present) happens under the build lock.
- The tag has no project input, so two projects approving the same package share one image. `prune_custom_images` removes only tags of this project's record that its `keep` set no longer runs and that are in use nowhere else, computed under the build lock: the `lock.image_tag` of every effective npm server of every project in the user config (with the MDM `custom_mcp` policy) and the `.image-tags` record of every other project. A tag kept only for another project leaves this project's record; an unreadable user config or MDM file prunes nothing.

## Compose shape

- One effective npm server `<n>` renders three services, each with the plugin hardening block (`pull_policy: never`, `read_only`, `user`, `cap_drop: [ALL]`, `no-new-privileges`, `/tmp` tmpfs `noexec,nosuid`), the labels `speedwave.custom-mcp-role` (`guard`/`server`/`egress`), `speedwave.custom-mcp-id` (`<n>`) and `speedwave.custom-mcp-consent` (first 16 hex of the consent digest), and the limits of `resources::CUSTOM_MCP_{GUARD,SERVER,EGRESS}_RESOURCES`:
  - `mcp-custom-<n>` (guard image, rendered-only): networks `_custom` + `_cx_<n>`; `<n>/guard:/policy:ro`; env `PORT`, `SPW_CUSTOM_SERVER`, `SPW_CUSTOM_MODE=npm`, `POLICY_FILE`, `SPW_UPSTREAM_URL=http://mcp-custom-<n>-up:3000/`, `SPW_UPSTREAM_AUTH_TOKEN`, `MCP_CUSTOM_<N>_AUTH_TOKEN`.
  - `mcp-custom-<n>-up` (`lock.image_tag`): network `_cx_<n>` only; `tokens/<project>/custom-<n>:/tokens:ro` plus `/workspace` only as approved (`:ro`, `:rw` or none); env `PORT`, `SPW_LAUNCHER_AUTH_TOKEN`, `HTTPS_PROXY`/`HTTP_PROXY=http://mcp-custom-<n>-egress:3128`, `NO_PROXY=` (empty), `NODE_USE_ENV_PROXY=1`, and `SPW_CREDENTIALS_DIGEST` (the credentials digest goes to the server, never the guard or egress).
  - `mcp-custom-<n>-egress` (proxy image, `entrypoint: ["/spw-egress"]`): networks `_cx_<n>` + `_eg_<n>`; `<n>/egress:/config:ro`; env `SPW_EGRESS_CONFIG`, `SPW_EGRESS_LISTEN=0.0.0.0:3128`.
- A host server `<n>` renders only its guard, on `_custom_host`, with `extra_hosts` through `ensure_host_gateway_extra_host`, `<n>/guard:/policy:ro` plus `custom-mcp/<project>/relay-<n>:/secrets/relay:ro` (a directory mount: the relay rewrites its files atomically), env `SPW_CUSTOM_MODE=host`, `SPW_RELAY_DIR`, `SPW_HOST_PROJECT_DIR` (the raw `ProjectUserEntry.dir`, `$` escaped as `$$` for compose interpolation) and `SPW_HOST_PATH_STYLE` (`compose/custom_host.rs::path_style_of`: `unc` for `\\…`, `windows` for `X:\`/`X:/`, else `posix`).
- The hub joins `_custom` while an npm server runs and `_custom_host` while a host server runs, gets `WORKER_CUSTOM_<N>_URL=http://mcp-custom-<n>:3000` and `/secrets/custom-<n>-auth-token:ro`, and `ENABLED_SERVICES` lists `custom-<n>` through `enabled_hub_service_ids`. The launcher bearer (`secrets/<project>/custom-<n>-launcher-token`, minted like the worker bearers by `workers::read_or_mint_secret`) goes to the guard and the server only, never to the hub or `claude`.
- Every render writes `<n>/egress/egress.json` from the effective (post-MDM) domains and writes `<n>/guard/policy.json` as `GuardPolicy::empty` only when no file exists: the Desktop owns the tool decisions in it.

## Networks

- `compose/networks.rs` is the naming SSOT: `<net>_custom` and `<net>_cx_<n>` are egress-less (`is_egress_less_network`), declared `external: true` under their own name and, like office's network, pre-created with `--internal` and verified isolated by a live inspect (`runtime/networks.rs::ensure_internal_network_with`) by `LockedRuntime` before every up; `<net>_custom_host` and `<net>_eg_<n>` are compose-managed bridges (they need a gateway). The pre-isolation probe (a compose-created `<project>_<key>` copy forces a full recreate, or `NetworkMigrationPending` on a single-service start) covers only the built-in networks (`egress_less_network_owners`): no release ever let compose create a Custom MCP network.
- `LockedRuntime::remove_egress_less_networks(project, custom_servers)` removes the fixed ones (office, `_custom`), `_cx_<n>` of every configured server name, every egress-less network the rendered compose declares and the compose-created pre-isolation copy of each built-in one; the Desktop's project removal passes the configured names. `LockedRuntime::remove_custom_mcp_server_networks(project, name)` removes one server's `_cx_<n>` and its compose-created `_eg_<n>` once a render without the server is up.

## SecurityCheck rules

`compose/security_check/custom.rs` adds seven rules, all against `SecurityExpectedPaths::custom_mcp()` (`custom_mcp::expectations_for`, from the current config at every gate):

- `UNKNOWN_SERVICE`: every service is in `consts::BUILT_IN_SERVICES`, carries the plugin label, or carries a valid Custom MCP role and id whose `Role::service_name` is its name (never both labels).
- `CUSTOM_MCP_CONSENT`: the id is an expected server and the consent label is the first 16 hex of its consent digest; a host server has no `-up`/`-egress` container. Without expectations every Custom MCP container fails, which is what makes a rollback snapshot of a revoked server give way to the fresh render.
- `CUSTOM_MCP_IMAGE`: guard `speedwave-mcp-custom-guard:*`, server exactly the approved `lock.image_tag` inside `speedwave-mcp-custom-<id>:`, egress `proxy:*` with `entrypoint: ["/spw-egress"]`; `pull_policy: never`; no `command`, and no `entrypoint` on guard or server.
- `CUSTOM_MCP_VOLUMES`: short-form only and exactly the role's set (guard policy dir, plus the relay dir for a host guard; server tokens plus `/workspace` only in the approved mode; egress config dir); the hub mounts no `*-launcher-token`, and no source that is, lies under or is a parent of `secrets/<project>` (normalized, ASCII case folded, long form included) unless it is exactly `<secrets>/<sid>-auth-token:/secrets/<sid>-auth-token:ro`.
- `CUSTOM_MCP_NETWORKS`: networks are classified by key and by effective name (`networks::effective_network_name`: `name` when set, the key when `external`, else `<project>_<key>` as compose names it). `_custom` and each `_cx_<id>` are declared `external: true` under their own name; `_custom_host` and `_eg_<id>` without `name` or `external`; no other key may carry a Custom MCP network's name; every Custom MCP network belongs to this project; membership is exact per role (npm guard `_custom` + `_cx_<id>`, server `_cx_<id>`, egress `_cx_<id>` + `_eg_<id>`, host guard `_custom_host`), in plain list form, without `network_mode`; no other service but the hub (on `_custom`/`_custom_host` only, plain form) joins one, under its key or under any key whose effective name is one. `EGRESS_LESS_NETWORK_EXTERNAL` applies the same effective-name rule to the built-in egress-less networks (`networks::is_builtin_egress_less_network`, office): only the project's own (`egress_less_network_owners`) may be declared, no other key may name one, only their worker and the hub join one, and a `name` that is not a string or an `external` that is not a boolean fails on any network.
- `CUSTOM_MCP_FORBIDDEN_KEYS`: an allowlist, not a denylist. A Custom MCP container carries only `image`, `pull_policy`, `container_name`, `read_only`, `user`, `cap_drop`, `security_opt`, `tmpfs`, `labels`, `deploy`, `volumes`, `environment`, `networks`, plus `entrypoint` on the egress and `extra_hosts` on a host guard (`allowed_keys`; `the_rendered_keys_are_exactly_the_role_allowlists` pins it to what the renderer emits, so a new rendered key needs the list changed). Values keep the rendered shape: `security_opt` exactly `[no-new-privileges:true]`, `cap_drop` exactly `[ALL]`, `tmpfs` exactly one `/tmp:noexec,nosuid,size=<n>` entry (`custom_mcp::TMPFS_PREFIX`), `deploy` only `resources.limits.{cpus,memory}`, `labels` only the three Custom MCP labels, `container_name` from `custom_mcp::container_name`; `extra_hosts` only as the single gateway alias of a host guard; env keys from the role's allowlist only, each once, with the pinned values (server proxies at its own egress, `NO_PROXY` empty, `NODE_USE_ENV_PROXY=1`, guard server/mode/policy/upstream or relay dir, egress config/listen). A compose with a Custom MCP container has no top-level `secrets` or `configs` section (built-ins use neither).
- `CUSTOM_MCP_RESOURCES`: cpus, memory and the size of the single `/tmp` tmpfs are set and within the role envelope; at most `CUSTOM_MCP_MAX_PER_PROJECT` server ids.

`READ_ONLY_FS` and `TMPFS_NOEXEC` also cover every service carrying the Custom MCP role label.

## Repository proposals (`custom_mcp/detect.rs`)

- `scan_project_dir` reads only `<project>/.mcp.json` through `fs_perms::read_regular_file_no_follow_capped` (symlink refused, `MAX_MCP_JSON_BYTES` = 64 KiB); a missing file is no proposals, a malformed one an error. Nothing runs and no `${VAR}` is expanded.
- Only `npx <package>[@<exact version>]` (optional `-y`/`--yes`/`-q`/`--quiet` before it) becomes an npm proposal; a missing or non-exact version is `needs_exact_version`, `url` entries are `remote` (only the host is returned: the path or query may carry credentials), anything else is `unsupported` with a reason.
- Env values are never read back, only the env names (`model::validate_env_key`; refused names are listed apart). Every repository string is cut to `MAX_TEXT_CHARS`. A proposal never enables anything: approval happens only in Desktop.
- `BUILT_IN_NPM_PACKAGES` maps an npm package to the built-in integration it duplicates (every value is a `BUILT_IN_SERVICE_IDS` entry, test-guarded).

## Desktop commands (`desktop/src-tauri/src/custom_mcp_cmd.rs` + `custom_mcp_cmd/`)

- Consent happens only here. `custom_mcp_preview` stores the review in `PendingPreviews` (random id, 15 min TTL, at most 16, purged on every access) and `custom_mcp_approve` rebuilds the entry from that stored review only: the UI never sends a digest, a lock field or an image tag. An npm review needs the server name up front (the tag hashes the name). Each review resolves into a staging dir of its own, `<name>/previews/<staging id>/` (`paths::preview_dir_in`, a random id kept only in the stored review, never sent by the UI), so two reviews of one name never overwrite each other or the approved `<name>/build/`; a failed resolution, registry check or review removes its staging dir (`npm_resolve::discard_preview`). The tag is computed from the staging dir with `build::image_tag_for_dir`, which never hashes the path, so the moved files give the same tag. Approve refuses another name, a review of another project, a name already configured, credentials for keys the review did not list, MDM refusals, and staged files that no longer give the reviewed tag. Writes go, under `with_config_lock` and `ensure_saving_for_active_project`: the staging dir replaces `<name>/build/` in one rename and every other review of that name is dropped (`npm_resolve::promote_preview`, guard `concurrent_reviews_of_one_name_stage_apart_and_only_the_approved_one_is_built`) → credentials → empty guard policy (+ empty egress for npm) → config entry last. A review that expires is not swept; its staging dir goes with the next approval of the name, `custom_mcp_remove` or project removal.
- **What a person sees when an action fails is a sentence plus a code, never tool output.** `custom_mcp::failure::failure(code, summary, cause)` builds `summary (CMCP-…). Details are in the Speedwave log.` and writes `cause` to the log (sanitized there); every Desktop command error that wraps npm, the engine, the settings file, the build dir or the registry goes through it, and `npm_resolve::npm_failure` maps npm's output to `CMCP-NPM-VERSION` (version newer than the release-age minimum, or nonexistent), `CMCP-NPM-NOT-FOUND`, `CMCP-NPM-NETWORK` or `CMCP-NPM-FAILED`. A new failure that carries text from outside Speedwave gets a code in `failure.rs`, a plain-language summary and a test that the cause does not appear in the text. Messages written by Speedwave itself (name and port rules, MDM refusals, a stale review) stay as plain sentences.
- The npm review reads the full packument host-side through `http_util` (no redirects, `MAX_PACKUMENT_BYTES`, 60 s) and refuses a version whose registry `dist.integrity` differs from the lockfile's; "previous publisher" is the `_npmUser` of the newest version of the same package approved in any project.
- `pii_mode` and `workspace_mode` are consented fields: changing one in Desktop re-signs an approved entry (and the guard policy's `consentDigest`), never approves an unapproved one; the UI then restarts. Tool decisions and domains hot-update: `custom_mcp_set_tools` refuses a decision whose hash differs from the catalog's current one, saves the config, then rewrites the guard policy (config restored if that write fails); domains rewrite `egress.json` from the post-MDM set.
- `custom_mcp_egress_denials` (egress refusals) is read only when the user opens an npm server's card or presses refresh, never with `custom_mcp_get`. It refuses an invalid name, an unknown server and a host server. It returns `container_running: false` and nothing else when the project is not the active one, has no rendered compose, the engine is not available, or the server's egress container (`egress_log::egress_container_name`, built on the renderer's `container_name`/`Role::service_name`) is not up in `compose_ps`. Otherwise it reads the last `egress_log::LOG_TAIL_LINES` (2000) lines of that container's log, so "since last start" is approximate on a busy server. An engine error is returned as a `CMCP-ENGINE` failure text.
  - The log is untrusted text: a line over 4 KiB is ignored; only a JSON object with `event: egress`, `decision: deny` and a known reason counts. A `not_allowlisted` host must pass `HostPort::parse` (a Unicode host is dropped, `xn--` passes), and one already in the user's `allowed_domains` is left out. At most 20 hosts are returned (most refused first). Every other reason is only a count, never its target.
  - Each host carries `allowed_by_policy` from `edit::allowed_by_policy`, the one MDM `allowed_domains` matcher that `allow_domain_in`, the egress file and the list also use. Hosts are attacker-chosen: they are logged at debug level at most, as a count.
- `custom_mcp_remove` readies the engine first (the server's networks can be reaped only while its name is known), removes the entry, re-syncs the relay, re-renders a running project (snapshot, render, up, rollback), removes `_cx_<n>`/`_eg_<n>`, prunes images, then deletes credentials, `<name>/`, `relay-<name>/` and the tool catalog.
- Project removal (`containers_cmd::remove_project_core`) readies the engine, runs `compose_down` and reaps the project's networks (the `_cx_<n>` ones of every configured server included) first; only then does its removal step stop the project's relay (`relays::stop_relay_of`, guard `project_removal_stops_the_relay_before_the_state_dir_is_deleted`) and call `project::remove_project`, whose `cleanup_project_dirs_in` deletes `<data_dir>/custom-mcp/<project>/` with the other per-project dirs; the `custom-<n>` credentials go with `tokens/<project>/`.
- Relay wiring: both Desktop renderers (`containers_cmd::render_and_save_compose`, `setup_wizard::start_containers`) call `custom_mcp_cmd::relays::sync_before_render` before `render_compose` (guard `both_desktop_renderers_sync_the_relay_before_rendering`): it starts the project's relay on first need, sets the routes of the effective host servers, and stops it (removing every `relay-*` dir) when none is left. A relay failure is logged, never blocks the start. A landed project switch (`project_cmd::switch_project`, `containers_cmd::add_project`) stops every relay except the new active project's through `relays::stop_relays_except`, which marks their endpoints unavailable before it stops the listener and keeps their tokens (guard `a_landed_switch_keeps_only_the_new_projects_relay`). The CLI never starts a relay. Its lock `<data_dir>/custom-mcp/<project>/relay/<port>.lock` is exactly `{project, pid, port}`, never the bearer (pinned by `start_writes_the_lock_and_port_file_and_stop_removes_the_lock`).

## Tool catalog (`custom_mcp/catalog.rs`)

- The hub refreshes every `custom-*` service every 30 s (`tool-registry.ts::CUSTOM_REFRESH_MS`, besides the 5-minute full refresh, one shared in-progress guard), so an allowed tool shows up in `search_tools` within about 30 s; a failed refresh keeps the last known tools.
- The hub writes `<audit>/tool-catalog-custom-<name>.json`; `read_catalog` reads it as untrusted text (capped at `MAX_TOOL_CATALOG_BYTES`, `deny_unknown_fields`, the right service, unique upstream names, valid exposed names) and recomputes every `definition_hash` from `{name: upstream_name, description, inputSchema, annotations, outputSchema}`; the catalog's own `state` is ignored. `outputSchema` is optional in the file (absent and `null` hash alike, as in mcp-shared `definitionHashInput`), and the definition stored in the guard policy carries it, so a tool served from the policy while the upstream is down keeps its approved hash. The gate reads a `null` `annotations` or `outputSchema` as absent, the way Rust writes them into that stored definition. Schema, size cap and file name are pinned against `hub/src/tool-catalog.ts` (`catalog_limits_match_the_hub_writer`).
- The catalogs go into the diagnostics ZIP as the ZIP-only `tool-catalogs` source (`SourceKind::DirFiles`, `audit/tool-catalogs/<file>`, sanitized, symlinks skipped).
- `tool_state` is the one mapping from a decision and the current hash to `pending|allowed|blocked|changed`: a decision whose hash differs from the current definition is `changed`, whatever its state.

## CLI

- The CLI never resolves an npm lock, approves a server or runs the relay, and has no Custom MCP subcommand; it renders exactly what the Desktop renders (`render_compose` with `Some(&runtime)` and `host_bridges_from_disk()`), so a host guard is rendered with its relay mount and fails closed per call when the relay is down.
- On every start that reaches the render (`speedwave`, `speedwave login`, `speedwave check`; `update` and `logout` exit earlier), `main.rs` prints `custom_mcp::notices::custom_mcp_notices` over the resolved `ResolvedIntegrationsConfig::custom_mcp` on stderr through `err!`, before `render_compose`: `not_approved`/`consent_changed` → waiting for approval in Speedwave Desktop; `beta_disabled` → the beta features toggle; `managed_disabled`, `host_servers_disabled`, `scope_not_allowed`, `workspace_mode_above_limit` → the organization's policy; `invalid` → the validation detail; `over_limit` → the per-project maximum; `disabled` → nothing (the user's own choice). Names and details go through `notices::display_text` (control characters stripped, capped in characters by `NOTICE_NAME_MAX_CHARS`/`NOTICE_DETAIL_MAX_CHARS`). Desktop may reuse the same function.
- A running host server gets "host MCP server '<n>' is available only while Speedwave Desktop is running" unless `custom_mcp::relay::is_running` finds a lock `<data_dir>/custom-mcp/<project>/relay/<port>.lock` (`relay::RelayLock` `{project,pid,port}`, unknown fields ignored) of this project, with a non-zero port, whose PID is alive (`host_mcp_process::probe::is_pid_alive`, the `apply_worker_config` gate). The CLI only reads the lock and the Desktop is its only writer; both resolve the directory through `custom_mcp::paths::relay_lock_dir_in`. The CLI matches the file extension with `consts::CUSTOM_RELAY_LOCK_EXT` against `HostBridge`'s `<port>.lock` naming; `start_writes_the_lock_and_port_file_and_stop_removes_the_lock` runs the CLI reader over the lock the Desktop relay writes, so a drift in the directory, the extension or the body fails there. The probe runs only when a host server runs (`notices::needs_relay`).
- The first image of a newly approved npm server is built lazily on CLI start like any missing image: the render calls `build::ensure_custom_images`, whose progress is the `log::info!` build line on the CLI's stderr logger; a render failure (custom image build included) is printed redacted through `err!` and exits 1.

## Desktop UI (`desktop/src/src/app/custom-mcp/`, `services/custom-mcp.service.ts`)

- The section lives on the Integrations page, after the Services panel and before the IDE bridge, behind `BetaService`, rendered under `*appRecreateOn` with the active project as its input (the project-scoped section rule in desktop-ui rules). `managed_disabled` collapses it to its title and the "Disabled by your organization" pill.
- `CustomMcpService` (root) wraps every `custom_mcp_*` command and holds the list of one project: a response for a project that is no longer active, or older than a later refresh, is dropped. Request payloads (`CustomMcpPreviewRequest`, `CustomMcpApproveChoices`, tool decisions) are rebuilt field by field, because the Rust side denies unknown fields; the UI never sends a digest, lock field or image tag.
- Restarts follow the restart matrix: approve, a PII mode loosened to `plaintext`, file access and on/off set `ProjectStateService.pendingJustEnabled` to the server's `service_id` (only while settled on that project) and call `requestRestartFor(project)`, so a failed restart turns that server off. Tool decisions and domains hot-update and request no restart; `custom_mcp_remove` re-renders in the backend, so the UI only reloads.
- Tightening applies immediately, loosening asks. A PII mode changed to `tokens` does not wait for the restart prompt: once `custom_mcp_set_pii_mode` succeeds and the list is reloaded, `CustomMcpService.setPiiMode` sets `pendingJustEnabled` and calls `ProjectStateService.restartContainers(project)` itself, which shows the usual restarting state. This happens only while the app is settled on that project with its containers up (`ready` or `auth_required`); otherwise the change is requested like the others. A failed or skipped restart falls back to `requestRestartFor`, so the prompt shows the error or the pending change. A change to `plaintext` keeps the prompt, because a loosening can wait for the user to agree to the restart. The command only re-signs the entry and rewrites the guard digest; the hub reads the per-service mode from `policy.json`, which `render_compose` rewrites (`write_policy_config_in`) on that restart, and the changed `POLICY_DIGEST` recreates the hub. A failed write restarts nothing.
- Approve stays disabled until every confirmation the choices need is given: read access (the `.env` sentence), write access (both sentences), the host server warning, and a changed publisher. Presets never re-allow a `changed` tool; only an explicit review click does. A refused decision shows on its own row.
- Every repository or server string is rendered by interpolation (never `innerHTML`), cut by `capText`, and labelled "proposed by repository file" where `proposed_by_repo`. Credential inputs are `password` fields; only filled values are sent.
- An npm server's card shows "Blocked connections (since last start)" under Internet. It reads `custom_mcp_egress_denials` when the card opens a server and on its `$ refresh` button; a list reload does not read it again. Each refused host is shown in full (it passed `HostPort::parse`, so at most 253 ASCII characters), by interpolation, with its count. A host the organization allows has an `$ allow` button, which calls `custom_mcp_allow_domain` (hot, no restart) and reads the refusals again; any other host shows "Blocked by your organization". There is no "allow all" and nothing is allowed automatically. Refusals without a host show as one "Other refused" line. The section has loading, error, empty ("No blocked connections since the server last started.") and not-running states. Host servers have no section.
