# E2E Rig Pipeline Discipline (`scripts/e2e-vm.sh` + engine-level bats)

Rules for the clean-install rig pipeline and the engine-level bats suites (`_tests/e2e/engine-contract.bats`, `_tests/e2e/update-dirty-state.bats`). All were learned from live rig failures — each rule names the failure it prevents.

## The live window (spec-phase split)

- The WDIO suite ends with `07-factory-reset.spec.ts`, which wipes the project, data dir, and VM/distro. Anything needing a provisioned engine or the live `e2e-test` project must run in the **live window**: Phase 3 runs wdio with `SPW_E2E_SPEC_PHASE=pre-reset` (all specs minus 07), then the bats suites, then `SPW_E2E_SPEC_PHASE=reset-only` (07 alone, so factory-reset coverage and rig cleanup are preserved). Phase 2 runs the full suite (no env set).
- `SPW_E2E_SPEC_PHASE` is read by `desktop/e2e/wdio.conf.ts::resolveSpecs`: empty/`all` → full list, unknown values throw (fail-loud). Never position an engine-dependent step "after the suite" — that is a factory-reset machine.
- Both lanes run the engine suites with bats-core `BATS_VERSION` (`scripts/e2e-vm.sh`) fetched from its GitHub tag archive into a directory the runner account owns (`~/.local` on macOS, `/home/windows` in the Windows staging distro): the runner account cannot write `/opt/homebrew` (`brew install` fails), and Ubuntu 22.04's apt `bats` is too old.
- macOS only: the app stops the Lima VM when it exits, and Lima has no on-demand start (WSL does) — the bats step must `limactl start` (bundled binary, prod `LIMA_HOME`) before the engine preflight.
- macOS only: `run_macos_e2e` never stops or kills the VM before launching the app — the reset-only launch adopts the VM the bats step started (`ensure_ready` sees it Running). A `pkill -f limactl` there SIGTERMed the hostagent into a graceful shutdown during which `limactl list` still said Running for tens of seconds while SSH reset (`kex_exchange_identification`), so every engine call of the fresh app failed and spec 07 found no `project-pill`. No automated guard for this; review is the check.

- macOS only: the `.dmg` build runs with `CI=true`, which makes Tauri pass `--skip-jenkins` to `bundle_dmg.sh` and skip its Finder AppleScript window layout. Over SSH Finder answers no Apple Events (`AppleEvent timed out (-1712)`) and the bundle step fails; the lane only mounts the image, so the layout is not needed.

## One run per rig

- Each `e2e.yml` job has its machine's concurrency group (`rig-macos`, `rig-windows`) with `cancel-in-progress: false`, and `scripts/e2e-vm.sh` takes a lock directory on the rig itself before it touches it (`with_rig_lock`: `$HOME/.speedwave-e2e.lock` on macOS, `/home/windows/.speedwave-e2e.lock` in the Windows staging distro), so a run started from a developer's machine and a CI job never share a rig. A lock older than `RIG_LOCK_STALE_MINUTES` (beyond the job's 120-minute timeout) belongs to a run that was killed and is taken over; a fresh one is waited on for up to `RIG_LOCK_WAIT_SECONDS`, and an unreachable rig fails at once. Guarded by `e2e-vm-excludes.bats`. A concurrency group keeps only one pending job: a third job queued for the same rig cancels the pending one, which one e2e run per beta (`beta.yml`, its own `concurrency: beta`) avoids.

## Windows transport rules (all empirically verified on the rig)

- Anything crossing the `wsl.exe ... --` interop boundary is re-parsed by the distro's default shell: payloads carrying `$`-constructs meant for the inner shell MUST be base64-wrapped (`echo <b64> | base64 -d | sh` — the runtime's `wrap_base64_sh` shape). Quoted metachar payloads without `$` survive as data; bare-spliced scripts do not.
- The rig's sshd hands command lines to cmd.exe, which ignores single quotes: never place a pipe/redirect intended for a remote POSIX shell in a cmd.exe-parsed segment (resolve host-side instead, like the CLI-path lookup). Never caret-escape POSIX-side files — `^` is only a cmd.exe escape.
- Env vars injected into `windows_ps` scripts go through the `ps_squote` prefix pattern. `e2e-vm-excludes.bats` guards only that `ps_squote` itself quotes correctly (it doubles single quotes); whether every `windows_ps` call site actually uses it is a manual alignment, caught only by review.
- The Windows lane's control side is Git Bash on the self-hosted runner (GNU tar) or a Mac (bsdtar): `windows_rsync_to` passes `--no-mac-metadata` only when `tar_is_bsdtar`, since GNU tar rejects it. Guarded by `e2e-vm-excludes.bats`.
- The self-hosted Windows runner account is not an administrator, so `ensure_provisioned_windows` never runs `e2e-vm-setup.sh` under `CI=true`: it fails with the instruction for an administrator instead (a setup run without admin fails midway on the first MSI). Every installer in `e2e-vm-setup.sh` goes through the `Invoke-Installer` prelude, which fails on any exit code other than 0 or 3010; `Start-Process -Wait` alone ignores it, so a failed MSI surfaced only as a missing binary. Guarded by `e2e-vm-excludes.bats`. The runner account holds no `SeSecurityPrivilege`, so an e2e plant that rewrites a DACL writes only that section: a fresh `FileSecurity` with `SetSecurityDescriptorSddlForm(..., 'Access')` handed to `[System.IO.File]::SetAccessControl` (`19-dirty-state-self-heal.spec.ts`). `Set-Acl` fails with `PrivilegeNotHeldException` there even for a DACL-only change (measured on the rig 2026-10-21). Smart App Control blocks every unsigned cargo build script (Code Integrity event 3077) and switches itself from Evaluation to On, so `ensure_provisioned_windows` fails first when `SmartAppControlState` is `On`. In the same PowerShell call it creates a junction as the runner account and reads through it: OpenSSH opts `sshd.exe` into RedirectionGuard, under which an SSH session cannot follow junctions a non-admin created, so `npm ci`'s workspace links in `mcp-servers` resolve for nothing and every workspace after `shared` fails to find `@speedwave/mcp-shared`; a failed read stops the lane with the administrator instruction. Both checks are guarded by `e2e-vm-excludes.bats`. Every `windows_ps` script that rebuilds `$env:Path` puts `C:\Program Files\Git\bin` first: `npm run build` in `mcp-servers` runs `bash build-wasm.sh`, and without it `bash` is `System32\bash.exe`, which runs the script in the staging WSL distro without `wasm-pack`. No automated guard for this.
- Both lanes keep their cargo target between runs, so only workspace crates rebuild (checkout gives their sources a fresh mtime): Windows `C:\cb`, which `windows_clean_state` does not remove, and macOS `~/speedwave-e2e-target`, linked as `target` and `desktop/src-tauri/target` into the synced tree because `CARGO_TARGET_DIR` would break `cp target/release/speedwave` in `Makefile`'s `test-e2e-desktop-build`. Each lane removes only the old `release/bundle` before a build, so the installer and `.dmg` lookups find one file. Nothing removes a target automatically. The Windows installer is built with NSIS compression `none` (`--config` file `C:\speedwave-e2e\e2e-nsis.conf.json`): it never leaves the rig, and `lzma` over the already gzipped WSL archives took 11 of the lane's 58 minutes (SPEED-865, 2026-10-22).
- The Windows lane builds only the NSIS bundle (`npx --prefix ../src tauri build ... --bundles nsis`): the installer it tests is the NSIS one, and WiX's ICE validation in `light.exe` cannot reach the Windows Installer service from the runner's SSH session (`LGHT0217`), so an MSI build fails there.
- The Windows lane runs as an account without admin rights, which cannot create files in `C:\` (directories it can): the installer is staged at `$env:TEMP\speedwave-setup.exe`, while the install dir `C:\Speedwave` and the build dirs `C:\speedwave-e2e`, `C:\cb` stay where they are. The app is launched through a scheduled task with `/IT` and no `/RL HIGHEST` (an elevated task needs admin): it runs only while the runner account holds the console session, so the rig logs that account on automatically.
- The macOS lane runs as an account without admin rights, which cannot write `/Applications`: the `.app` is installed to `~/Applications`, and `desktop/e2e/helpers/engine.ts` resolves the bundled `limactl` there. The app is started from the SSH session and needs the runner account to own the console session (`stat -f %Su /dev/console`).
- The engine bats suites reach the Speedwave distro from the staging distro through WSL interop, and on the rig `wsl.exe` failed there with ENOEXEC while the Speedwave distro ran (2026-10-21), although `WSLInterop` was registered once that distro was gone. WSL distros share one kernel and its `binfmt_misc`, and the Speedwave rootfs (Ubuntu 24.04 WSL image) boots systemd; that its `systemd-binfmt` drops the entry is unverified. `windows_restore_interop` re-registers `:WSLInterop:M::MZ::/init:PF` as root in the staging distro before each suite when the entry is missing.
- Failure artifacts: after every wdio phase each lane pulls the rig's `FAIL-*.png` screenshots and the Desktop log directory (`~/Library/Logs/pl.speedwave.desktop`, `%LOCALAPPDATA%\pl.speedwave.desktop\logs`) into `.e2e-artifacts/<platform>/<phase>/{screenshots,app-log}` (`collect_remote_tree`, guarded by `e2e-vm-excludes.bats`), and `e2e.yml` uploads that directory with `include-hidden-files: true`: `actions/upload-artifact` skips every dot-prefixed path without it, which left both rigs with "No files were found" on every failed beta up to 2026-10-29. The Windows job carries no Desktop log in its CI output (the app is launched through `schtasks`, so its stdout goes nowhere), so that artifact is the only Desktop log of a Windows run; the macOS lane starts the app from the SSH session, so its log also streams into the job output. Both clean-state scripts remove the log directory, so an artifact holds the run it belongs to.
- The engine bats suites ship to `WINDOWS_CONTRACT_STAGING` (own dir) — other pipeline steps `rm -rf` the main staging dir between phases.

## Suite discipline

- Engine access in bats only via the word-split `ENGINE_EXEC` contract (`${ENGINE_EXEC+set}` distinguishes unset from empty-on-purpose); every bats invocation carries `--print-output-on-failure`.
- Everything planted lives under a test-owned prefix/sentinel id and is reaped in teardown even on failure; plants are asserted (exact counts) before the behavior under test runs — a silently failed plant must fail loudly, never pass vacuously.
- Once `GET /v1/models` answers, the preflight (`desktop/e2e/helpers/preflight.ts`) sends one real request to `LOCAL_LLM_MODEL` (`POST /v1/messages`, `max_tokens` 16, HTTP 200 with a `stop_reason`, a 429 retried): a model that does not answer skips only spec 11, the one spec that talks to it (`localModelUnavailable()`); specs 12 and 20 need only the server (`localLlmUnreachable()`), and an unreachable server skips spec 11, the live-server tests of spec 12 and the local-provider test of spec 20. A model listed in `/v1/models` is no proof it is served (LiteLLM lists a model llama-swap no longer routes).
- `beta.yml` calls `e2e.yml` with `secrets: inherit`. The secrets live in the `e2e` environment, and a reusable workflow gets an environment secret only when its caller passes it; without that it resolves to an empty string and the run first fails in the preflight (SPEED-904). No automated guard for this.
- `ANTHROPIC_API_KEY` is an `e2e.yml` secret passed through both `env:` blocks, the `windows_ps` prefix and the `run_macos_e2e` export list of `scripts/e2e-vm.sh` (guarded by `e2e-vm-excludes.bats`); the preflight fails the run when it is unset or when a one-token `POST https://api.anthropic.com/v1/messages` to `claude-haiku-5-5` does not answer 200 with a `stop_reason`: `GET /v1/models` answers 200 for a key whose organization has no credit, while Claude Code's one-token check on every model switch gets `400 credit balance is too low`, which cost spec 20 seven tests and 13 minutes per rig on 2026-10-29 instead of a preflight line. Test (a) of spec 20 waits for `list_model_picker` to hold rows and for the badge to show a catalog family before it reads the badge, because the badge reads `default` until the session's `initialize` answers (about 10 s on the rigs). Specs 20 and 21 set it in `before` and remove it in `after` (`llm.ts::configureAnthropicApiKey`/`removeAnthropicApiKey`); both end with `requestBackendRestart`, because saving only writes `secrets/<project>/anthropic_api_key` and the restart re-renders the compose env. Spec 20 sends turns only to `claude-haiku-5-5`.
- `extract-zip` must stay out of `desktop/e2e`'s tree: it writes through symlinks outside the extraction dir and no patched release exists (GHSA-7pqw-9j4j-h8q3, last publish 2.0.1). It reaches the rig only through `@puppeteer/browsers` 2.x, which the `^3.2.1` entry in `overrides` replaces; that entry is security config, not cosmetics — package-lock.json does not record overrides, so a fresh install without it resolves back to 2.x. No automated guard for this pin.
- No object an e2e script hands back to WebDriver (a `done(...)` payload, a `browser.execute` result) may carry an `error`, `stacktrace` or `stackTrace` key: WebdriverIO reads such a value as a W3C WebDriver error response (`webdriver`'s `isSuccessfulResponse`) and throws `WebDriverError` instead of returning it, so `tauri-invoke.ts` returns a rejected invoke as `{ ok: false, reason }`. `_tests/desktop/e2e-invoke-helper.bats` (`make test-desktop-config`) covers its checker function (`_script_result_error_keys`) against synthetic fixtures; scanning the real `desktop/e2e` tree is a manual check now.
- An element a retry loop clicks is looked up inside each attempt (`projects.ts::openProjectSwitcher`), never through a handle taken before the loop: tauri-plugin-webdriver reports a click on a detached element as a JavaScript error, which WebdriverIO does not answer with a fresh lookup, so one re-render (the chat view draws the project pill in a separate header per project status) leaves every retry clicking the dead handle. The same holds for a `waitUntil` that polls an element: `sendMessageNoWait` and `saveProvider` look the button up on every poll (a composer re-render during spec 20 left `isEnabled` on a dead handle). A retry loop never clicks a toggle blindly: the OpenRouter row's header collapses the panel when the row is already active, so `llm.ts::configureOpenRouter` clicks it only while `aria-checked` is not `true` and re-types the key until the input holds it and test connection is enabled (a re-render can lag the click, so a second click collapsed the panel after the loop saw it open).
