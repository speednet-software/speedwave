# Security Rules

**Security is a core obsession, not an afterthought.** Every change must preserve or improve the security model. When in doubt, choose the more secure option.

## Non-negotiable invariants

- Claude container: no tokens, no container socket, runs as UID 1000:1000; containerd runs inside a VM on both platforms (Lima/WSL2). Its only secret mount is its own tmpfs slot `claude/secrets` at `/run/speedwave/secrets:ro`, which holds the Anthropic key or token, the custom headers and the caller token (the file `caller-token`); `containers/speedwave-secret-env.sh` loads them into the environment of the entrypoint and `containers/speedwave-exec.sh` into that of every `nerdctl exec` (`session/instance.rs::instance_env_argv` puts `consts::SPEEDWAVE_EXEC_WRAPPER` first on every exec argv), so the values live in process environments inside the container and never in the container description.
- OWASP container hardening on every container: `cap_drop: ALL`, `no-new-privileges`, `read_only` filesystem, `tmpfs /tmp:noexec,nosuid`, resource limits. **This is not just template convention: `compose::SecurityCheck::run()` re-validates every rendered compose before `up` on every start path (CLI, Desktop, update, rollback)** — the hardening flags, container user, localhost-only port policy, no-tokens-on-claude/hub, and per-worker volume profiles (`VolumeCheckRules`). Adding or changing a template mount without a matching volume profile in `security_check.rs` hard-fails at container start, not in a named unit test. `fs_security.rs` auto-fixes data-dir modes (0o700/0o600) before the check runs; `speedwave check` reports-only.
- Token isolation: **every token mount is `:ro`, no exception** — a compromised worker exposes only its own service. `office` and `playwright` mount no `/tokens` at all; `office` additionally runs on an egress-less network and enforces a `/workspace/`-only path policy (canonicalize, reject symlinks) — do not add remote-fetch paths to it. The proxy mounts its `llm` token files as the slot `proxy/tokens` at `/tokens:ro`, its rendered config as `proxy/config` at `/config:ro` and, only while the integration is enabled, the slots `proxy/git-github` and `proxy/git-gitlab` at `/git-tokens/github:ro` and `/git-tokens/gitlab:ro` for the git transport (ADR-106, `SecurityRule::SpeedwaveProxyVolumes`); no other token slot ever reaches it.
- **Secrets reach containers only through tmpfs slots, never through env or the host disk** (ADR-115). Every credential a container reads is a file in `/run/speedwave-secrets/<project>/<service>/<purpose>` inside the VM, a dedicated tmpfs (`mode=0700,size=16m,nosuid,nodev,noexec`) that `secrets_tmpfs/frame.rs` mounts and fills. The runtime writes it through the stdin of one root command in the VM (`ContainerRuntime::vm_exec_as_root`; the script text carries no value, and an error carries stderr only), never through argv or env, and `LockedRuntime` does that before every `compose_up`, `compose_up_recreate` and `compose_up_service`, under the project lock; a failed write aborts the start. Rules that follow:
  - A container mounts only slots of its own service and project, each `:ro` in short form: `SecurityRule::SecretSlotMount` rejects any mount sourced under the secrets root that is not one of the slots `compose/secret_slots.rs::expected_slot_mounts` lists for that service (another service's slot, another project's tree, a lookalike prefix, `:rw`, long form). The renderer and the payload collector build slots from the same `secret_slots.rs` constructors, so a mount and its files cannot drift.
  - No secret value is rendered into `compose.yml`, `snapshots/<project>/snapshot.json` or any container's env. A built-in worker's bearer (derived, not stored) arrives as the file `/run/speedwave/auth/token` named by `MCP_<SVC>_AUTH_TOKEN_FILE`; the proxy's `proxy.json` is rendered in memory and staged as a slot file; the claude secrets are the files above. **The named exception is installed plugin workers: they keep `MCP_<SID>_AUTH_TOKEN` as a plain env value (the derived bearer)** (plugin workers read it from env, and their code lives in the sibling repo `speedwave-plugins`), so that bearer still lands in `compose.yml` and in the container description. Do not extend the exception to a built-in worker.
  - Slot directories are never replaced or removed while a container may bind-mount them; files are written atomically (temp file and `mv` in the slot) as `1000:1000` mode `0400`, and a full sync deletes every file the payload does not list, except the names a slot keeps (`refresh_status` in a `tokens` slot).
  - The tmpfs does not survive a VM restart, so every start writes it again; a process that changes a credential while containers run calls `LockedRuntime::stage_project_secrets` (the whole project; public, Desktop uses it) or, inside `speedwave-runtime` only, `put_secret_file` (one file; `pub(crate)`, used by `oauth_refresh`), never writes the store or a host file alone. The `secrets_tmpfs` module is `pub(crate)`; the root exec is the `ContainerRuntime::vm_exec_as_root` trait method only, `LockedRuntime` does not re-export it. The Desktop commands that change a key (`save_api_key`, `delete_api_key`, `set_llm_provider_key`) restage before they return and keep the saved key when the restage fails: `save_api_key` and `delete_api_key` answer with `ApiKeyChange` (`types.rs`, mirrored in `llm-provider.component.ts`) and `set_llm_provider_key` with the error text, `Some` only on failure; the UI shows it and requests the project restart, which writes the slots again. A project with no active LLM provider is skipped (`integrations_cmd.rs::restage_container_secrets_now`, a restage there fails with "No LLM provider selected"), so a key deleted after a logout stays in the slots of containers that are still running until the next start.
  - **`proxy` has `restart: "no"`.** Under `unless-stopped` the engine can start it on its own after a VM boot, when the tmpfs is empty and nothing has written its slots. The price is that a crashed proxy stays down until the next project start, and requests that go through it fail until then. This weakening is deliberate; do not reinstate an engine restart policy on a container that mounts a slot.
  - `SecurityRule::NoTokensWorkers` rejects a `MCP_*_AUTH_TOKEN` env var on any built-in service (installed plugin workers are exempt, see the exception above); built-in workers use `MCP_<SVC>_AUTH_TOKEN_FILE`.
  - `SecurityRule::NoTokensClaude` rejects any `TOKEN`, `KEY` or `SECRET` env name on `claude` (except `CLAUDE_CODE_OAUTH_TOKEN`, `DISABLE_AUTOUPDATER`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS`) and, by name, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS` and `SPEEDWAVE_CALLER_TOKEN`. Those four reach the container as files of the claude slot, so a `claude.env` entry with one of these names (user config; the repo config's `claude.env` drops `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS` and `SPEEDWAVE_CALLER_TOKEN` through `config.rs::REPO_ENV_DENY_ANTHROPIC`) fails the check and must be removed there.
  - `SECURITY_RULE_COUNT` in `compose/mod.rs` is 63 with `SecretSlotMount`.
- **Secrets exist only in the secret store** (`speedwave_runtime::secret_store`). A secret is one AES-SIV sealed line in `<data_dir>/secrets/<project>/<service>.<field>.enc`; the install key is `<data_dir>/secret-store.key` (32 random bytes as hex, created exclusively on the first write, never by `SecretStore::open`). Rules that follow:
  - **No new plaintext secret file, anywhere in the data directory.** A new kind of secret gets a `SecretName` constructor. Which fields are secret is decided by the `is_secret` flag of the consts descriptor (built-in services) or of the plugin manifest `AuthFieldDef` (plugins); a plugin's OAuth `access_token` is a secret too. Never keep a second list of secret fields at a call site. Non-secret values (URLs, emails, site, tenant and client ids, Slack `features.json`, the Redmine `config.json`, plugin `_settings.json`, `service_name`, `refresh_status`, the OAuth state metadata) stay plain files.
  - **Only `secret_store` knows the path and the file name.** Callers hold a `SecretStore` and a `SecretName`; a `secrets/...` path built anywhere else is a bug. `secrets/` holds `.enc` files, empty `.lock` files and the temporary files of an atomic write (plus the legacy names `anthropic_api_key` and `*-auth-token` until a migration removes them); `secret_store_state` runs `SecretStore::clean_layout` at every start, which removes every other entry (a symlink is removed as a link and never followed, an entry that cannot be removed makes the state `StoreUnavailable` and refuses the start). Never write a file there that is not one of those.
  - **Hot paths do not decrypt.** Config resolution and the UI status ask `SecretStore::exists` or `secret_exists_in`, which read no key and work when the key is missing. Decrypt only to build a tmpfs payload or to call a provider.
  - **Derived tokens are not stored.** The bearer of a built-in worker is `derive_token` (HKDF over the install key; purpose `bearer`), the same value in the CLI, Desktop and after a restart. Do not add a file, a `SecretName` or a migration of values for it.
  - **The caller token of the `claude` container is drawn, not derived, and lives only in the VM tmpfs.** It is 32 random bytes as hex (`compose/caller_token.rs`), drawn when a start recreates the Claude Code sessions (`LockedRuntime::compose_up_recreate`, `compose_up_service` for `claude` and `compose_up`, both only while no `claude` container runs) and staged as the file `caller-token` in the slots `claude/secrets`, `mcp-hub/secrets` and `proxy/config`. A process that attaches to a running project, a proxy reload and `stage_project_secrets` keep the staged token (`secrets_tmpfs/stage.rs` reads it back through `vm_exec_as_root`; a failed read aborts the staging, an absent or malformed file draws a new token). It is never written to the host disk, `compose.yml`, `proxy.json` or a file in `claude-home`, and never derived from `secret-store.key`. The proxy (`/v1` and `/git/`) and the hub (`POST /` and `DELETE /`) read the file on every request, compare in constant time and reject every request while it is missing or empty. `/health` and `/oauth-compat` stay open. The token is still in the environment of the agent's processes (`ANTHROPIC_CUSTOM_HEADERS`, `SPEEDWAVE_CALLER_TOKEN`); do not claim the store or the rotation hides it from the agent.
  - **A secret that cannot be read breaks only its integration.** The project starts without it, its credential files are left out of the slots, the log names project, service and field only, and the user text is `unreadable_secret_message`. A missing key beside `.enc` files (`SecretStoreError::KeyMissing`) refuses the start: never create a key next to existing ciphertext and never fall back to plaintext. The migration never overwrites an unreadable `.enc` with a legacy plaintext value: the `.enc` wins, the plaintext is removed and the integration is reconnected. The PII key is the one secret that start replaces: an unreadable `pii.key.enc` is treated like a missing one (`pii_key::ensure_project_key_in` writes a new key and logs a warning without key material), but it is never generated while the legacy `policies/<project>/key` exists, also next to an unreadable `pii.key.enc` (migration pending or failed), because a new key makes every token in history unreadable.
  - **Write order for OAuth state:** refresh token, access token, plain metadata, then the copy to the tmpfs. The refresh lock is `SecretStore::lock_path(&SecretName::oauth_refresh_token(project, service))`.
  - **Design every protection as if `secret-store.key` were not on the disk.** In step 1 the key sits beside the ciphertext; that is a stated limit of the store, never a reason to relax a control. "The key lies next to it" is not an acceptable justification for a plaintext secret, a readable file, a logged value or a skipped check. A gap a PR leaves open gets a blocking Jira task at once, not a note in the PR text. The plugin worker bearers are the gap the PR that added this rule leaves on purpose: they stay compose env (SPEED-1043). The other unprotected items in the next bullet (`mcp-os.lock.json`, `bridge-token`, `claude.env`, the OTLP headers, `.credentials.json`) are older facts outside that PR; whoever touches one of them needs a Jira task for it under this rule.
  - **What the store does not protect (step 1):** a copy of the whole `~/.speedwave` (the key sits beside the ciphertext until it moves to the OS key store), a process of the same user, the VM during a session (tmpfs holds plaintext copies), swap and hibernation, Claude Code's own `.credentials.json`, the bearers of plugin workers (compose env, SPEED-1043), the tokens in `mcp-os.lock.json` and `pii-ner.lock.json` (the CLI finds the process by them) and in `plugin-state/<slug>/bridge-token` (the external app keeps its own copy), backup copies, `claude.env` and the OTLP headers in `config.json`. Do not describe the store as protecting more than that.
- **Egress-less networks are created by the runtime, never by compose.** The bundled nerdctl compose drops a network's `internal:` key and creates the network with a gateway and masquerade. An egress-less network (one per `egress_less` descriptor in `TOGGLEABLE_MCP_SERVICES`, today `office`) is therefore declared `external: true`, and `LockedRuntime` creates it with `network create --internal` before every `compose up`, then checks its CNI config (no gateway, no masquerade, no `portmap`, no default route) and fails the start otherwise; a rendered compose that declares an egress-less network without `external: true` fails the start before anything is created (`compose/networks.rs::external_egress_less_networks`). `SecurityRule::EgressLessNetworkExternal` rejects a compose that declares one any other way, declares another project's egress-less network, attaches its worker to another network, or attaches any service but that worker and `mcp-hub` to it. While the network compose created under the old declaration (`<project>_<key>`) still exists, a full start recreates every container and then removes it, failing on an unreadable engine or a failed removal, so no container is left on it; a single-service start (proxy hot-reload) refuses with `NetworkMigrationPending` instead of recreating the stack. Never rely on `internal: true` in a template (ADR-055 amendment of 2026-10-08).
- Workers mount only their own credentials, the slot `<compose service>/tokens`, at `/tokens:ro`. `slack`, `sharepoint`, `redmine` and `atlassian` additionally mount the project dir `/workspace:rw` for file exchange (Redmine: attachment uploads and downloads, ADR-110; Jira attachments are uploaded from it and downloaded into `.speedwave/jira/`, ADR-109; all four enforced per-service by `security_check.rs::check_builtin_workspace_worker_volumes`) — a new file-exchanging worker follows this profile, preferring `:ro` unless it must write, never a new mount surface.
- Hub holds zero external credentials (render-time gate rejects token mounts/secret env on it); it carries only Speedwave-internal bridge bearer tokens under `/secrets/…:ro` (its slot `mcp-hub/secrets`, checked by `SecurityRule::SecretSlotMount`). It also mounts the resolved PII policy (its slot `mcp-hub/policy`) at `/policy:ro` and, deliberately, the PII audit directory at `/audit:rw` (its only writable mount — `SecurityRule::AuditMount`); proxy mirrors both mounts. Neither directory may ever reach the `claude` container, at any target (`SecurityRule::NoPolicyOrAuditMountClaude`).
- **Git transport goes through the proxy, never a token in the container** (ADR-106). The proxy's `/git/<host>/<path>` route forwards only the four git smart HTTP requests (`info/refs` with `service=git-upload-pack` or `git-receive-pack`, `POST git-upload-pack`, `POST git-receive-pack`) to an enabled forge, requires the caller token (as `x-speedwave-proxy-auth` or as the password of `Authorization: Basic`, answering 401 with `WWW-Authenticate: Basic` when neither is present; git gets it from `containers/git-credential-speedwave.sh`, which reads the tmpfs file when asked, so no git config file holds it), and answers everything else 403 without contacting the forge; a forge entry whose `access` is `read_only` in `proxy.json` also answers both `git-receive-pack` requests 403 before the repository list is consulted (ADR-108; `access` is composed by Rust in `speedwave_access_policy::compose_access_policy`, never decided in the proxy), so never widen that allowlist toward the forge's REST API, never add a ref policy that parses the pack, and never add the `workflow` scope to `consts::GITHUB_OAUTH_SCOPES` (a pushed workflow would run with the repository's secrets). No integration tool creates commits; publishing is `git push`. The route forwards only repositories on the forge's `repositories` list in `proxy.json` (`router.rs::GitForge::allows`: the exact path, or `prefix/*` for every repository below the prefix); an empty list refuses every request (ADR-106 amendment of 2026-11-04). The list comes only from the user config (`integrations.github.repositories`, `integrations.gitlab.repositories` of the project entry), which a person edits in Desktop. Never fill it from the project directory: the agent writes `/workspace`, so a remote in a `.git/config` is agent-controlled, and the directory scan (`git_allowlist.rs::suggestions_in`) only offers entries a person adds one at a time. Never let a repository's `.speedwave.json` set it, and never accept a bare `*`, a whole host or a `*` before the last segment (`git_allowlist.rs::normalise_entry`, applied on save and again at render).
- OAuth refresh runs on the host, in the process that owns the session: the CLI for its `--project`, Desktop for every project with running containers (`speedwave_runtime::oauth_refresh`). Refresh tokens and client secrets live in the secret store and never enter a container, and workers never write tokens; a container only reads its `/tokens/access_token`, `/tokens/refresh_status` and `/tokens/service_name` `:ro`. There is no refresh process and no `forget` operation, so nothing a container can reach asks for a refresh: never add a channel from a container (or from `claude`) to the refresh code, and never wire refresh into `WORKER_*_URL` discovery. The one OAuth endpoint a container can reach is `POST /oauth-compat` in `mcp-hub` (`mcp-servers/hub/src/oauth-compat.ts`), which only answers old plugin clients: no credentials, no effect, it holds the call about 15 s, answers a constant (`expiresIn` 0), and caps the waiting calls (429 beyond 16). Never give it an effect (refresh, a token or state read or write), and never accept a request shape other than the old `tools/call` `refresh`.
- **Transcription is fully local:** raw audio and live/offline transcript passes never leave the machine — only the final transcript text goes to Claude, and only on an explicit user action. Never add a cloud-STT path, auto-send, or any telemetry carrying audio/transcript content.
- **`speedwave self-update` installs only an archive whose minisign signature verifies, fail-closed** (ADR-112). The key is the Desktop updater key, `plugins.updater.pubkey` in `desktop/src-tauri/tauri.conf.json`, embedded at compile time by `crates/speedwave-cli/build.rs` (`SPEEDWAVE_UPDATER_PUBKEY`); never copy it into CLI source and never add a second key or signature format. A missing `.sig`, a bad signature, another key or a signature bound to another version aborts before extraction (`release_signature::verify_archive`, run as the `verify_archive` hook of `self_update`). Do not add a flag or environment variable that skips the check.
- SHA256-verified binary downloads in every Containerfile; health endpoints return only `{"status":"ok"}` (or 500 `{"status":"error"}`) — no service metadata.
- **A tool call that Claude Code's own safety check holds for manual approval is declined, never auto-approved.** Speedwave answers every other `can_use_tool` request with `allow`, because the session runs with `--dangerously-skip-permissions` and the container is the boundary; but from 2.1.282 Claude Code raises a `can_use_tool` with `decision_reason_type: safetyCheck` even then, for `rm`/`rmdir` targets it cannot resolve statically (probed on 2.1.282, 2.1.295 and 2.1.322: an `rm` whose target comes from a command substitution is held; a possibly-empty variable path, `bash -c`, `sh -c` and a redirection are not). No one can approve it in a Speedwave session, so `chat.rs::build_tool_permission_response` answers `deny` with Claude Code's reason, the tool does not run, and the model gets the denial as a failed tool result. The request and what the model receives are recorded in `cc-<version>-safety-check.sanitized.json`; `the_safety_check_capture_is_of_the_pinned_claude_code` fails on a bump until it is recorded again, and `a_tool_call_claude_codes_safety_check_holds_is_declined_with_its_reason` and `claude_code_hands_a_declined_call_to_the_model_as_a_failed_tool_result` run over it.
- **No host code-execution channel for Claude, ever.** A whitelist-gated, opt-in host command runner was fully implemented and then deliberately reverted: any host-exec capability a prompt-injected Claude can drive erodes the isolation guarantee, warnings notwithstanding. Do not reintroduce it in any form (worker, mcp-os tool, bridge handler) without a new ADR reversing that decision.
- **Speedwave never performs Anthropic OAuth and never parses/captures/stores Anthropic tokens.** Claude Code owns the whole credential lifecycle inside the container; a Speedwave-native flow or stdout token capture is brittle and violates Anthropic's Consumer Terms.
- **The bundled settings template keeps claude.ai skill and plugin sync off.** From Claude Code 2.1.275 a session signed in with a Claude account syncs the skills and plugins enabled on claude.ai into `~/.claude/skills/synced` and `~/.claude/plugins/synced`, switched on server-side and re-synced every 10 minutes. In the container they would compete with Speedwave's integrations (the document skills against the Office worker, with scripts whose dependencies the image lacks) and could bring hooks that no Speedwave plugin-signature check covers. `containers/claude-resources/settings.json` therefore sets `syncClaudeAiSkills` and `syncClaudeAiPlugins` to `false`. Claude Code honours only `false`: from user or managed settings for every session, from `.claude/settings.local.json` or `--settings` for that workspace or invocation only, and never from project settings (`.claude/settings.json`). The entrypoint merge adds a key the container's `settings.json` lacks and keeps a value it already has, so a user opts in by setting a key to `true` in `<data_dir>/claude-home/<project>/.claude/settings.json` (the container's `~/.claude/settings.json`), and the choice survives restarts. This is a default, not a boundary: the session writes that file itself (it runs with `--dangerously-skip-permissions`), so a prompt-injected session can flip the keys, as it can already add `hooks` there. The `:ro` managed settings would make it a hard control and would also take the opt-in away. A `settings.json` that does not parse is left untouched by the merge and skipped whole by Claude Code, so until it is fixed the sync follows the account's server-side switch. Guards: `crates/speedwave-runtime/tests/claude_settings_template_guard.rs`, `_tests/entrypoint/entrypoint.bats`.
- Any new host-side WebSocket relay must be a `HostBridge` (`desktop/src-tauri/src/bridges/host_bridge.rs`) — never a hand-rolled listener/lock-file/token stack; the skeleton owns the audited security model (0o600 lock, constant-time token compare, Origin policy, watchdog). The one HTTP host listener, the PII NER detector (`pii_ner_service.rs`, ADR-096), reuses the skeleton's bind, token and compare helpers plus the host worker lock schema; a new HTTP listener follows it or becomes a `HostBridge`.
- **PII NER stays on this machine and its consumer is pinned.** The proxy sends request text only to the `ner.url` of its staged config, which the compose env `SPW_NER_URL` mirrors; `SecurityRule::SpeedwaveProxyNerUrl` checks `SPW_NER_URL` and the proxy's own load check checks `ner.url`, and both restrict it to `http://host.docker.internal:<port>`; the AES-SIV key never leaves the proxy container (the host returns offsets, the proxy seals). Never point `ner.url` or `SPW_NER_URL` anywhere else, never add a cloud detector path, and never send the detector anything but the leaves `pii::collect_scan_leaves` already scans.

## When implementing any feature, ask

- Does it relax any invariant above? Find a different approach.
- Does it add attack surface? Document and mitigate it.
- Does it mount host filesystem into a container? Minimize scope, `:ro` wherever possible; `/workspace:rw` is the only writable cross-boundary surface.
- Does it accept a URL/hostname/IP from config, repo `.speedwave.json`, or user input? It must go through the shared SSRF validator in `url_validation.rs`: `validate_url` (fixed `PrivatePolicy::BlockLoopback`) or `validate_collector_url(url, policy)` when the caller must choose the policy. Repo `.speedwave.json` must never override `provider`/`base_url`-class fields.

## Host-side outbound HTTP (Tauri/Desktop)

- All outbound HTTP from host code uses hardened `reqwest` clients via the shared helpers (`desktop/src-tauri/src/http_util.rs` + `url_validation.rs`): `redirect::Policy::none()`, bounded timeout, capped body. The LLM discovery probe (`llm_cmd/discovery.rs`) rejects `text/html` responses before parsing (a denylist on that one path, not a general allow-list). Reuse the helpers — never copy the constants.
- Sole redirect exception: the transcription model downloader follows redirects only to hosts in `consts::TRANSCRIPTION_MODEL_ALLOWED_REDIRECT_HOSTS`; adding a host requires an ADR delta.
- DNS rebinding on user-originated URLs is an accepted residual risk — never add a codepath that lets an attacker inject URLs into config without explicit user action.
- TLS: `rustls-tls` with bundled CA roots; switching to system roots requires an ADR.

## Bundle integrity (macOS + Windows)

Every bundled Mach-O in `tauri.macos.conf.json` `bundle.resources` must be in `sign-bundled-binaries.sh` `SIGN_TARGETS`, and binaries using restricted platform APIs need an entitlements plist in `desktop/src-tauri/entitlements/` (add a new plist; never relax an existing one). Coverage is test-guarded — keep the guards green.

Windows (ADR-086): every PE file we build that ships via `tauri.windows.conf.json` `bundle.resources` must be in `sign-windows-binaries.ps1` `$SignTargets`; Tauri's own `signCommand` covers the app binary, the installers and, undocumented, any still-unsigned `.exe`/`.dll` resource, so `$SignTargets` is the explicit inventory, not the only path. Signing authenticates through GitHub OIDC (federated credential bound to the `release` environment) — never introduce a stored Azure client secret or a PFX-in-secret path, and never re-sign vendor-signed or hash-pinned binaries (`node.exe`, `vulkan-1.dll`).
