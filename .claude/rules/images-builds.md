# Container Images & Builds

- **Catalog SSOT:** `build.rs::IMAGES` — one `ImageDef` per image. Compose references images via `${IMAGE_*}` placeholders (alignment test-guarded), bundle scripts carry the matching service list (test-guarded).
- **Rebuilds are content-addressed:** tags are `name:<16-hex>` over the image's declared `ImageDef.hash_inputs`. Rules:
  - Every file a Containerfile `COPY`s must be listed in that image's `hash_inputs` (test-guarded by `hash_inputs_cover_copy_sources`) — otherwise it ships stale after edits.
  - `hash_inputs` are **repo-root-relative** and must resolve under every build root `resolve_build_root` can return: the repo itself (tests, dev CLI) and the bundled `build-context/`, where the bundle scripts stage vendored sources under `containers/`. `bundle.rs::resolve_hash_input` maps a missing direct path to that vendored layout; an input resolving in neither aborts every image build in an installed app while repo-rooted CI stays green. Guarded on the repo side by `hash_inputs_exist_in_repo` and on the staged side by the bats test "every ImageDef hash input resolves inside the staged build-context", which also rejects a committed symlink under any hash input through the git index. Unit tests never digest the working tree (the bundle bats lane rewrites `mcp-servers/policies/wasm-pkg` beside them): compose tests pass the `test_bundle_manifest()` fixture into `render_compose_in`, and `hash_inputs_exist_in_repo` only checks existence.
  - **The tag must describe the tree `nerdctl build` reads.** The Desktop build script hashes the staged `build-context/` whenever every input resolves there (`bundle::hash_inputs_resolvable` — direct path or the vendored `containers/` layout); only a partial/stubbed context falls back to the repo root. Hashing one tree while building another mints a content-addressed tag for the wrong image, and "already present" then pins it until an input changes (a stale `make dev` staging shipped a pre-#1144 entrypoint under a post-#1144 tag). Guard: `build_script_hashes_the_staged_context_through_the_ssot_resolver`.
  - Do NOT over-declare inputs (e.g. `claude-resources/`, `compose.template.yml` for the claude image) — the claude-image exclusions are test-guarded (`claude_hash_inputs_exclude_resources_and_template`); for other images over-declaration is NOT test-caught and forces a rebuild on every unrelated edit.
  - Never rebuild under an unchanged tag: `nerdctl compose up` will not recreate the container. A content change must produce a new tag.
  - Builds and tag-prunes serialize via `build::with_build_lock`; never run builds inside a compose transaction lock.
  - `bundle_id` gates bundle reconcile only — it does not trigger image rebuilds. It deliberately includes `app_version` (all render logic is compiled-in code, so only app_version honestly covers "the rendered compose may have changed"); a release must re-render compose and recreate containers — never remove `app_version` from `bundle_id` to skip release-time reconciles.
  - Tag pruning (`prune_replaced_images`) diffs against this install's own applied history — never sweep images by repository name; repo names are global across data dirs and worktrees, so a name-based sweep nukes other installs' images.
- **Lazy builds:** images build per enabled integration — `build::enabled_images(integrations)` / `build_missing_images`, plugins via `plugin::ensure_plugin_images(rt, enabled_ids)`. Never build or existence-check the full catalog (phantom rebuilds, multi-minute startups); orphan pruning is per-project.
- **An engine that cannot answer is not an absent image.** `image_exists` returns `Ok(false)` only on nerdctl's `no such image` (`runtime::image_inspect_verdict`, shared by Lima and WSL, any case); a stopped VM, an SSH/`wsl.exe` failure or a probe past `CONTAINER_EXEC_PROBE_TIMEOUT` (`CommandRunner::run_bounded`) is `Err`. `build::images_exist`, reconcile's unchanged-bundle check, readies the runtime itself and re-runs `ensure_ready` every `ENGINE_UNREACHABLE_POLL_DELAY_SECS` until `ENGINE_UNREACHABLE_WINDOW_SECS` after the first engine error or `VmStatusUnreadable`; once the engine has failed to answer, a later `ensure_ready` failure is retried too. The limit is a deadline, not a retry count, so a hung probe cannot multiply it. Before each `ensure_ready` it asks `keep_trying`, which reconcile ties to `runtime::vm_start_inhibited`, and ends with `build::ImageCheckCancelled` once exit or factory reset tears the engine down (see architecture rules). A silent engine comes back with `build::EngineDidNotAnswer` context and fails the reconcile, so Retry re-runs it; the bundle status surfaces that failure although the bundle is unchanged (`bundle_status_from`'s live failure). An `ensure_ready` failure before any engine error stays a logged skip, because the VM may not be provisioned yet. None of these ever forces a rebuild: a Lima VM still reports Running while it shuts down, and a rebuild forced on that answer failed on the stopped VM and left the bundle `Failed`. The unchanged-bundle branch asks the engine before anything else and restores pending projects and reports images Ready only after the verdict; startup marks the check pending before its migrations run (`reconcile::mark_image_check_pending`), and `check_containers_running` waits for it (`reconcile::wait_for_image_check`, Checking only, then reads the engine as it is), so the first container check talks to an engine the reconcile already brought back. Only helpers where the fallback is harmless fold `Err` into absent: `build_missing_images` and the plugin rebuild attempt a build that fails loudly, and the prune filters and `plugin::usable_fallback_tag` skip a tag they cannot see. Never fold it where the verdict resets reconcile state.
- **No routine `builder prune`** — pruning shared BuildKit state invalidates caches for every project.
- **New image checklist:** `IMAGES` entry with `hash_inputs` + `${IMAGE_*}` placeholder + bundle-script list entry (all test-guarded) · **`tzdata`** installed (apk/apt) or zoneinfo COPY'd for scratch images — MANUAL, nothing catches a miss, and without it the injected `TZ` degrades to a numeric offset · `DEBIAN_FRONTEND=noninteractive` on every `apt-get install` (test-guarded — an interactive tzdata prompt hangs BuildKit forever) · SHA256-verify any downloaded binary · resource entry on the service descriptor, never a literal in the template.
- **Bundle scripts copy the containers tree (`BUNDLE_CONTAINERS_DIR`) and `crates/pii-engine` through `copy_tree` (.sh) / `Copy-Tree` (.ps1)**, which skip `bundle.rs::HOST_BUILD_OUTPUT_DIRS` up front. Never a whole-tree `cp -r`/`Copy-Item -Recurse` there: `make test` runs `test-proxy` in parallel, and a `cargo build` writing `containers/proxy/target` races the copy (a vanished `rustcXXXX` temp file failed the bundle).
- **An installed app builds only the files its release ships.** `bundle-build-context.{sh,ps1}` write `.speedwave-shipped-files` (`bundle::SHIPPED_FILES_LIST`) into each tree of `bundle::SHIPPED_TREES` once staging is complete, and on Windows Desktop reconcile runs `bundle::prune_unshipped_files` under the build lock before the manifest hashes the build context: an in-place NSIS update never removes a file a release dropped, and a leftover `.ts` broke the 0.18.x hub build (ADR-048 amendment). Write the list last; anything staged into those trees after it is pruned on the next Windows start. Guards: `bundle_scripts_write_the_shipped_files_list_into_every_shipped_tree`, the list test in `_tests/desktop/bundle-build-context.bats`, `reconcile_prunes_unshipped_files_on_windows_before_hashing_the_build_context`.
- **Claude-resources are not baked** into the claude image — they sync to the data dir and mount at start; editing a skill in the repo does not reach a running container without sync/restart.
- **Bumping the nerdctl pin (`.lima-version`, `consts::NERDCTL_FULL_VERSION`) or the WSL rootfs (`consts::WSL_ROOTFS_*`) requires a green engine contract (`_tests/e2e/engine-contract.bats`) on the bumped engine.** The suite pins the real-engine semantics the self-heal (#932) and the compose up deadline rely on: nerdctl's name-store/classifier/flock phrases and the `no such image` answer `image_exists` reads as absent, containerd's task-bundle and registered-task collision texts, and the guest coreutils `timeout --signal=KILL --verbose` line together with its immediate kill of a TERM-ignoring child. `make test-engine-contract` drives only the local macOS dev VM (`ENGINE_CONTRACT_EXEC`) and proves a bump only once that VM runs the bumped engine; the WSL rootfs is exercised only by the rig pipeline's engine-contract step (`scripts/e2e-vm.sh`, live window), which also covers a freshly provisioned production-style Lima install. The Lima guest image has no pin to bump: `provision.rs` points at the floating Ubuntu 24.04 release, which only a newly created VM reads, so its drift surfaces only in that fresh rig install. A change to those phrases or exit codes must be caught there before it reaches the renderer.
