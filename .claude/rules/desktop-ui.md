# Desktop UI Rules (Angular + Tauri)

- **Zoneless + OnPush: service state read by a template MUST be a signal.** A template reading a plain service property renders stale — nothing schedules change detection. New service fields consumed by templates are signals (or computed) from day one.
- **Rust ↔ TS model mirrors are silent-failure surfaces:** Tauri command return types and their `models/*.ts` counterparts must match exactly — the JSON deserializer silently drops unknown/mismatched fields. Update both sides in the same commit; for a new mirrored constant/union add an `include_str!` cross-read test on the Rust side (grep `_matches_ts` for the pattern).
- **State-tree rendering:** a new `MessageBlock` variant lands in Rust first, then `models/state-tree.ts::MessageBlockState`, then a renderer arm in `chat-state.service.ts::stateBlocksToMessageBlocks` — its default arm surfaces unknown kinds as error blocks in front of the user, which is the only drift catch.
- **Model sources:** for Anthropic providers the composer's rows, wire ids, `Default` badge and effort stops come from `ModelPickerService` (`list_model_picker`: the list Claude Code reports for the signed-in account over `initialize`, ADR-089 and its SPEED-663 amendment); the picker is disabled while the session info is `pending`. The rows have that one source: `list_model_picker` returns `null` until the session reports its models (an idle session, the respawn window while `start_session_inner` holds the session mutex, a failed `initialize`), `ModelPickerService.refresh` then keeps the rows it already holds, and the combobox shows "Model list unavailable." with Retry when it holds none. The combobox never copies the Anthropic rows: its options are a `computed` over `ModelPickerService.picker(projectId)`, so an open list follows every refresh the session-info effect triggers, and after a project switch it shows the new project's rows. A list opened before the session started (the image rebuild after an update takes minutes) fills in without Retry. While the info is `pending` and no rows are held, the list shows the loader together with Retry. Retry re-reads the session info (`ClaudeControlService.refreshSessionInfo`), because a session stopped during `initialize` emits no event and would otherwise leave the list `pending` for good. Only the latest `fetchOptions` call may write the loading, error and discovered-rows state (`fetchGeneration`). The static catalog never supplies a row: no retired model may appear because the session has not answered yet. Every model label in the chat (picker, pill, message metadata, `/model` chip, live and rebuilt from history) goes through `ModelPickerService.label`, whose precedence is the catalog `family`, then the `display_name` Claude Code listed for a model the catalog lacks, then the id without its prefix, date and 1M suffix; nothing user-visible may contain `[1m]` or `(1M)`. `AnthropicModelsService` (`list_anthropic_models`) is metadata only: names, pricing, the effort table the slider falls back to for the current model while no rows are held. Never hard-code a model id in Angular, never build a `[1m]` id in Angular (the backend picks the wire id by plan), and never derive a context window from the catalog. The effort slider is shown for every provider kind. Its order is `defaults::EFFORT_LEVELS`, carried as `ActiveProviderSummary.effort_levels`. A local or OpenRouter provider gets every level, never an Anthropic catalog entry's stops or default (a routed id can match a catalog id). Its slider shows no handle until a level is pinned, because an unpinned routed session runs at Claude Code's own level for an id outside its catalog. That hidden handle stays a focusable `role="slider"` (value 0, text `Default`) that appears with a focus ring on keyboard focus, and it takes no pointer events, so a click on the first stop under it reaches that stop; the first arrow key puts it on the first stop, Home and End on the first and last.
- **Routed model lists outlive the composer:** for local/OpenRouter providers the discovered rows live in `DiscoveredModelsService` (root-provided, keyed by `provider|base_url`), never in a selector-instance field — the composer is recreated on a chat-session restart or a view switch, and an instance-held list dies with it. A failed probe falls back to the last known list, rendered with the `model-selector-stale` banner and its Retry; the "Failed to load models." message with an empty list is only for a provider that was never reached, and an empty discovery result is not a fallback. A selector instance still probes once per key (`probedKey`), so a new composer instance picks up a server-side model-list change.
- **Context and plan limits:** Anthropic sessions read context usage through `ClaudeControlService.contextUsage` and plan limits through `PlanUsageService`, both pull commands on the live chat session (ADR-089). They are re-read when the session info turns `ready`, after each finished turn, on a `rate_limit_event` and when the usage popover opens, never on a timer. Missing data is hidden: no ring while the window is unknown, no plan section without limits (API-key providers never have one), never a fabricated 0% or 200k. `rate_limit_event` is a status signal only: its `utilization` is a 0-1 fraction that most events omit.
- **Beta gate:** work-in-progress Desktop surfaces ship behind the beta toggle — `BetaService` signal + the beta-enabled route guard. The flag (`ui.beta_enabled`) is user-config-only (repo `.speedwave.json` cannot set it) and is a UI visibility gate, never a security boundary. A surface that must stay usable with beta off (a running recording keeps its Stop control) needs the exception on the route guard and the keyboard shortcut too, not only on nav-rail visibility — `transcriptionRouteGuard` is the pattern.
- **A project-scoped Settings section belongs to one project:** the Settings view stays mounted across a project switch, so `settings.component.ts` renders `app-llm-provider` and `app-security-section` under `*appRecreateOn="activeProject()"` (`shared/recreate-on.directive.ts`) and passes them that project as an input: a switch destroys them and builds them for the new project with no view state kept, a typed key included. `ProjectStateService.onProjectReady` alone is not enough: a switch fires it only when the switch lands in `ready`. A section reads its own project (`get_llm_config`, `get_security_policy` and the local-server probe `discover_llm_models` take `project`), because `switch_project` changes the backend's active project before the frontend's `activeProject` changes and a section opened under the switching overlay would otherwise show the project the backend is switching to. Every write names that project. The writes into the backend's active project (`update_llm_config`, `set_llm_provider_key`, `update_security_policy`) are refused under the config lock when it is not that project (`ensure_saving_for_active_project`), and `update_llm_config` also checks before its pre-lock model auto-select probe, so a stored key never goes to another project's server. The writes addressed by name (`anthropic_logout`, `save_api_key`, `delete_api_key`, `clear_active_llm_provider`) go to the named project whichever is active, so a logout finishing during a switch still completes. A section built before the app knows its project (`null`) writes to the active project unchecked. A finished save asks for its restart through `ProjectStateService.requestRestartFor(project)`: requested at once while the app is settled on that project (`isSettledOn`: still active and no switch running), owed if a switch away from it is running and surfaced once that switch fails back to it (a restart already pending when a switch starts is owed the same way), and dropped otherwise. The failed switch leaves it pending (`pendingRestartOnSettle`), and every path that settles the status again (a landed switch, `ensureContainersRunning`, `dismissError`, `applyAuthStatus`, `forceUnconfigured`) goes through `applyPendingRestartOnSettle`, which raises it, or drops it when the project is left without a provider. The proxy hot-reload (`restart_llm_proxy`, which the backend also refuses for a project that is not active), a sign-in status reaching `ProjectStateService.applyAuthStatus` and a logout's `forceUnconfigured` happen only while settled; the chat's LLM config cache is refreshed after every save regardless, from the backend's active project. Never gate these on the section being destroyed: leaving Settings destroys the section too, and the restart its save needs must still be requested. Use the directive, not `@for (x of [key]; track x)`: the identity-tracked `@for` logs Angular's dev-mode NG0956 warning on every switch.
- **Tray menu:** any new variable input to the tray menu goes into `TrayMenuState` and rebuilds through the single `refresh_tray_menu` path — a second rebuild path silently drops the other inputs.
- **Tray Icon Rules:**
  - **State Authority:** Icon is not a `TrayMenuState` input. `tray::refresh_tray_icon` queues a repaint and `apply_recording_state` re-derives icon and tooltip from live state (`transcription_cmd::DriversHandle` via `is_recording`) so both stay correct when the window is closed onto the tray. Callers only signal registry changes.
  - **Four Constraints:**
    1. Apply icon via `set_icon_with_as_template(.., true)`. Standard `set_icon` hard-resets the macOS template flag to false, breaking menu-bar adaptation (guarded by `the_repaint_reasserts_the_macos_template_flag`).
    2. Execute sampling and both applies in one `run_on_main_thread` task to prevent concurrent repaints from landing out of order. The badge pulse follows the same rule: it re-reads its generation and the registry inside its main-thread closure (guarded by `the_pulse_loop_exits_on_a_stale_generation_and_a_stopped_recording`).
    3. Route every registry mutation through `register_driver_and_repaint_tray` or `unregister_driver_and_repaint_tray` (guarded by `every_registry_mutation_repaints_the_tray`).
    4. macOS recording variant is a template image (badge renders in menu-bar tint); Windows renders a static red badge.
  - **Motion vs. Color:** macOS uses a pulsing badge (`BADGE_PULSES`, 35%-opacity second frame swapped on timer) because template rendering discards color. Windows keeps its colored badge static. Motion is used only where color is unavailable. Exactly one pulse loop may paint: every repaint bumps `BADGE_PULSE_GENERATION`, which retires the previous loop (guarded by `every_repaint_retires_the_previous_pulse_loop`).
  - **Theming:** Never derive tray appearance from `Window::theme()`. `NativeThemeAdapter.syncWindowTheme` pins the window to an explicit light/dark Appearance mode and hands it back to the OS (`setTheme(null)`) in auto. Never pin in auto: a pinned window freezes the webview's `prefers-color-scheme` (tao sets the appearance app-wide on macOS and ignores OS theme changes on Windows), so auto would stop following the system (guarded by `never pins the native window while auto follows prefers-color-scheme`). Windows reads app theme rather than notification area theme.
  - **Reference:** Rationale and rejected animated indicator in ADR-056 Amendment 18.
- **CSP:** the webview CSP in `tauri.conf.json` is load-bearing on Windows (WebView2 enforces strictly; WKWebView is lenient) — e.g. `img-src 'self' blob: data:` is what makes pasted images render; changes are pinned by a test in `main.rs`.
- **TypeScript in `desktop/src` is capped by Angular's peer range** (`@angular/compiler-cli` declares it, e.g. `>=6.0 <6.1` for v22): a TypeScript bump beyond that range cannot install, so Dependabot majors for `typescript` here are rejected until an Angular major lifts the cap (`ignore` rule in `dependabot.yml`). Angular packages peer-pin each other to the exact version — bump the whole set in one PR via `ng update`, never one package.
- **`ng serve` gives a `PORT` env var priority over `angular.json` (Angular 22+)** while Tauri's `devUrl` stays fixed at the same port — `make dev` therefore launches Tauri under `env -u PORT` (guard: `_tests/desktop/dev-server-port.bats`, which also pins `angular.json` serve port ↔ `tauri.conf.json` `devUrl`). A second dev instance moves both with `make dev DEV_INSTANCE=<name>`, on a port derived from the name (ADR-031 §8).
- **`~/.claude/settings.json` in the container must stay a writable copy, not a symlink into a read-only mount** — Claude Code writes to it (`/effort`, `/model`).
- **Composer is the single model/effort control:** the model pill in the chat composer is the only place a user changes the active model or effort - Settings carries no model selector. Anthropic selections persist via the `settings.json` `model` pin (`pin_cmd::set_model_pin`, written before the wire switch or an idle respawn - ADR-088 decision 3 amendment, SPEED-539), not merely session-scoped; picking the row Claude Code reports as its default clears that pin instead (`pin_cmd::clear_model_pin`) and switches the live session to `default` (ADR-089); effort picks persist as the project config `effort_pin` (`pin_cmd::set_effort_pin`, written before the `apply_flag_settings` control request; the spawn passes `--effort <pin>` only when a pin exists, ADR-088 decision 5 amendment, SPEED-538); the container's `settings.json` `effortLevel` is never a second store: `pin_cmd::ensure_effort_pin_migrated_in` strips it before every spawn and on `get_effort_pin`, adopting its value only for a project without a pin, and the bundled template `containers/claude-resources/settings.json` must not seed it or `model` back, because the entrypoint merge re-adds any template key the container's file lacks (SPEED-664, guard `tests/claude_settings_template_guard.rs`); local/OpenRouter selections write through to project config via the narrow `set_provider_model` command, config write before the live wire switch (ADR-088). A local/OpenRouter pick made with no live session (no session id) additionally re-renders the compose and recreates the containers (`ChatStateService.rerenderContainersForModel` → `ProjectStateService.restartContainers`), because that model reaches Claude Code only as container env (`compose/llm.rs`) and the spawn carries no `--model`, while the soft-impose reaches Claude Code only after the first turn's first model request; it skips both when the running process was launched right after a re-render for that same model and nothing has switched its model since (see the queued-picks rules below); a failed or already-running restart surfaces in the composer instead of respawning, and a failed one also raises the standing restart prompt so a saved-but-unapplied model stays visible (ADR-088 decision 3 amendment, SPEED-657). That respawn runs only if the chat is still unoccupied when the re-render returns (no stream, no start or resume in flight, no session id) and no project switch started since the pick: a conversation resumed while a restart runs claims the chat at once and waits until `ProjectStateService.restartInFlight` is null, including restarts that start while it waits, before replacing the session (dropped if the project changed or a switch started meanwhile), and the restart-complete resume applies only while the chat still holds the session it was decided for, also after the resume-or-fresh dialog, so none of the three replaces a session another one started. A live session takes the pick as a `set_model` control request (`switch_chat_model`, which waits for Claude Code's answer; Angular adds the `/model` chip once it confirms and starts no turn), and a pick made while a turn streams or a session starts still defers to the turn end or the start's completion. A deferred pick restarts no container, except a local/OpenRouter pick released when a fresh start completes: that session has no conversation yet, so the pick is taken as an idle one, re-render and respawn included. Every model switch Speedwave writes into a live session, the soft-impose (`chat.rs::soft_impose_step`) and the composer pick alike, is a `set_model` control request, never a `/model` input: a `/model` input answers with its own `init` and `result`, which ends the user's turn in the chat, and on the pinned binary one written during a tool-using turn runs as such an input after that turn (ADR-088, SPEED-709 amendment). `set_model` bypasses the input queue, switches the running turn from its next model request on, and adds no line to the stream (SPEED-696). The soft-impose is sent once, at the first `system/init` that reports a model other than the configured one. A pick, and a `/model` the user types (which still goes as an input), settle the session's model under the stdin lock (`ModelSettled`), so no soft-impose follows a user pick. The badge shows the pick optimistically for every provider kind (`lastPicked` in `model-selector.component.ts`); without that record it falls back to the model observed on the session or to the provider summary, which is reloaded only on a project change and therefore goes stale (SPEED-657).
- **No chat message goes out while a session start or resume is in flight:** until `start_session_inner` swaps the session, the backend still holds the previous conversation's process, so a message sent then would land in the conversation being replaced. `ChatStateService.sessionStartInFlightFromState` (`startingSession` or `_resumeInProgress`, including a resume's wait for a container restart) disables the composer's send (the text stays in the field, the placeholder says the session is starting; `ComposerComponent.sendBlocked` gets the signal itself and reads it at submit time, so a start that begins after the last render still refuses the Enter), makes `sendMessage` refuse (a model pick made during a resume waits in `pendingModelOverride`), and makes the `chat_stream` listener drop every chunk until the start ends. The backend reports a session mutex held by another command as `chat session is busy` (`send_message`, `submit_question_answer`), never as `no active session`, so lock contention never makes the send retry replace a live conversation. The retry after a failed send goes on only while its turn is still the one streaming (same `_sessionGeneration` and turn, and `isStreaming` still set, which a reset, a project switch, Stop and the stream's own `Error` or `Result` all clear). After it looks up the project it shows an error instead of resending when a start or resume is in flight (a resume waiting for a container restart included) or when the backend's active project is no longer the one the message was written for. It marks the project as needing sign-in only while that project is still active and no switch has started since the message was sent, and its own start clears `startingSession` only in its own generation. `resumeConversation` reads the transcript only after `resume_conversation` returns (the stopped process may still be appending to the JSONL).
- **Control-chip rendering is shape-based, not state-based:** a user message matching `^/(model|effort)\s+\S+$` renders as a system chip in BOTH the live stream and history reconstruction - one rule, no live-only suppression, no correlation sidecar (ADR-088). Claude Code writes an executed command to the transcript only as a synthetic `<command-name>`/`<command-args>` entry, never the typed line, so `history.rs` rebuilds the typed line from that entry before applying the rule; every other synthetic command entry stays dropped. A `set_model` switch is recorded the same way, after the turn that was running, so the chip Angular adds live for a composer pick is rebuilt from history too.
- **A composer effort pick on a live conversation is an `apply_flag_settings` control request, never an `/effort` input, and never restarts the session on its own. This holds for every provider kind.**
  - **The request.** `ChatStateService.sendEffortToSession` calls `apply_chat_effort` (`chat_session_cmd.rs`), and `applyEffortToConversation` chains those calls. The command validates the level with `pin_cmd::validate_effort_level`, sends `settings.effortLevel` through the session's control channel and waits for Claude Code's answer after releasing the session mutex, like `switch_chat_model`.
  - **What it changes.** The session's level, from its next model request. It needs no `--effort` at launch, writes no settings file, adds no line to the stream and no chip to the chat, and never ends a turn. It also works before the first user message. On the pinned 2.1.282 it records nothing in `.claude.json` (2.1.280 removed the launch hold; on 2.1.267 its first use recorded the release flags `unpin…LaunchEffort: true`, which store no level). An `/effort` input written during a tool-using turn runs after that turn as an input of its own and ends the user's turn in the chat; on 2.1.267 it never ran (ADR-088 decision 5, SPEED-707 and SPEED-709 amendments; recorded in `cc-<version>-apply-effort.sanitized.json`).
  - **Ordering.**
    - Picks are applied one at a time, in pick order; `ChatStateService` chains them.
    - The pins are saved in pick order, the model pins too.
    - A pick is dropped as soon as a newer one is made, even while the newer one is still saving its pin.
    - When the newest pick's pin cannot be saved, the session is sent the level the pin holds.
    - A pick belongs to the project it was made in and counts only while the app is settled on it and no switch has started since the pick, even one that failed back to it: `ProjectStateService.settledMark` at the pick, `isStillSettledOn` after every wait. A pick made before or during a switch is neither sent nor queued, and its error and notice never reach the other project. The switch clears the composer's selection error.
    - The same project rule holds for model picks: `applyModelSelection`, `takeModelPick` and `switchLiveModel` drop a pick, its chip and its error once it no longer holds. The retry of a failed send and a resume use the same mark, a resume that waits out a container restart included: a resume begun while a switch runs never reaches the backend, and one that a switch overtakes loads no transcript and shows neither its error nor the conversation the backend kept. A New chat started from a transcript (`startNewConversation`) that a switch overtakes fails with `NEW_CONVERSATION_PROJECT_CHANGED`, so nothing is restored or staged into the other project's chat, and any start (`startChatSession`) reports its failure, the error status or the sign-in prompt, only while the app is settled on the project it started for, and so does the fresh start after a container restart (`startFreshSession`). A resume begun while a turn streams stops that turn first, as Stop does but releasing nothing, so a conversation the backend keeps shows that turn stopped instead of streaming for good, and it then waits out a container restart that began during that stop.
    - A newer model pick replaces or clears the queued one, so a queued pick never undoes a later pick. Only the newest model pick reports a failed save, and only the newest pick whose pin was saved reports a failed switch or re-render, so a switch that fails behind a newer pick whose save failed is still shown.
  - **The notice.** Any failure of the request keeps the pin and raises the `deferredEffort` notice with Restart now. The failures are a rejection, a timeout, no live process, and `chat session is busy`. A timed-out request may still apply late, so the notice says the level is saved for new sessions and that this session did not confirm it. A `CLAUDE_CODE_EFFORT_LEVEL` the user sets in `claude.env` outranks every pick without a notice (ADR-088, SPEED-707 amendment).
    - Restart now is `restartForDeferredEffort`, which calls `resumeConversation`, or respawns a chat without a session id. It is gated by `newConversationBlockedReason` like its button, and by the synchronous `chatBusy`. The notice states that background tasks stop.
    - Every spawn the frontend starts clears the notice, because it launches with the pin. A New chat that fails restores it together with the session id the chat returns to.
  - **No automatic respawn.** Never reintroduce one for an effort pick. It kills a Claude Code process's between-turn work (background tasks, monitors, subagents) and races retry, rebind and mid-turn `Error` chunks.
  - **Queued picks.** A pick made while a turn streams, or while a session starts or resumes, is queued (`chatBusy`: a stream, or `sessionStartInFlightFromState`). A model pick made during a fresh start is queued as well, so no second session starts. Queued picks are released together with a pending model pick, at any of:
    - the next turn end;
    - a Stop the user clicks, because the interrupted turn's `result` is dropped, unless a container restart began during that Stop, whose own rules then apply;
    - the end of a resume or of a fresh start;
    - a container restart that fails: the process takes them when the restart failed before it recreated the containers, and the requests fail and say so when it did not.

    A released pick goes to the running process at once, also before it reports a session id. The exception is a local/OpenRouter model pick released when a fresh start completes: it re-renders the containers and respawns, since the session has no conversation yet.

    A first start that fails, and a resume or a New chat that fails to spawn, drop the queued picks, because the backend stops the earlier process before it spawns the new one; their pins carry them to the next spawn. The header's New chat drops them when it resets the chat, and the session it starts launches with the pins. Only `startNewConversation` (a transcript sent to a new chat) and `resumeConversation` keep them, and only when the backend refused the start before it stopped the earlier process (images not ready, a sign-in check that fails or says no, a poisoned session lock): `start_session_inner` prefixes exactly those failures with `chat_session_cmd::MSG_SESSION_KEPT`, mirrored as `SESSION_KEPT_MARKER` (guard `session_kept_marker_matches_ts`, and `every_failure_before_the_old_session_stops_says_it_was_kept`). The chat returns to that process and shows its conversation again (messages, session stats, session id and effort notice restored), and the process takes them at its next turn end. The prefix never reaches an error the user reads (`withoutSessionKeptMarker`). The fresh start after a container restart drops them even then, since the restart already ended the earlier process. A pick made while a resume waits out a container restart is dropped when the resume begins. The Stop a container restart begins with releases nothing, since the resumed process launches with the pins. Only the latest pick is applied.

    In a chat without a session id a pick restarts the idle session so that it launches with the pin, even when the chat shows messages, since such a conversation cannot be resumed. That includes a turn stopped before Claude Code reported its session id: the next pick replaces its process and the messages it shows. A local/OpenRouter pick re-renders the containers before that respawn, and skips both when the running process was launched right after a re-render for the same model and nothing has switched its model since. `ChatStateService` records that launch (`_launchedFor`) only for the newest pick and only for the session generation it started, and a start that does not complete, a live switch or a container restart clears it, because a live switch changes the model and the config but renders nothing. A direct pick and a released one follow the same rule.

  - **`Error` chunks.** An `Error` chunk releases pending model and effort picks only when the backend marks it `turn_ended` (an `is_error` result), since any other `Error` can arrive mid-turn (SPEED-650).
  - A `/effort` the user types still goes to Claude Code as an input.
