# Git Workflow Rules

## Branches, PRs, merges

`dev` is the default branch; there is no `main` (removed at cutover, SPEED-674 ticket 10 and 17). Release lines live on `release/0.M` branches, created once per stable minor and kept forever; they take only hotfixes.

| PR direction                                    | Strategy     | Enforced by                                                                                       |
| ----------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------- |
| `feature/*` / `fix/*` → `dev`                   | Squash merge | `merge-gate` ruleset: merge queue with squash, two required checks                                |
| `feature/*` / `fix/*` → `release/0.M` (hotfix)  | Squash merge | `release-gate` ruleset: the same two checks, no queue; only the highest `release/0.*` accepts one |
| `merge/release-0.M-into-dev` (backport) → `dev` | Squash merge | `release.yml`'s `hotfix` job opens it with `GH_AUTOMATION_PAT`, auto-merge on                     |

- **PRs to `dev` or to a `release/0.M` line never push directly** — a developer creates the `release/0.M` branch itself (the only direct push; see `RELEASING.md`), everything else is a PR through the gate.
- No PR title restriction tied to a target branch: `dev` and `release/0.M` take the same conventional-commit types. The old `dev → main`-only `feat`/`fix` restriction is gone with `main`; `validate` checks every PR title and every merge-queue commit with `commitlint.config.js`. On a pull request it validates the title with the ` (#<number>)` suffix GitHub appends to the squash message (`scripts/resolve-pr-title-message.sh`), so a title that would overflow `header-max-length` in the queue fails on the PR first. Its `ignores` skips Dependabot's `chore(deps): bump …` and `chore(deps-dev): bump …` titles, which can exceed `header-max-length` and never reach the changelog (`cliff.toml` skips `chore`).
- **The backport PR is automated, never a manual chore:** after every merge into a `release/0.M` line, `release.yml`'s `hotfix` job opens `merge/release-0.M-into-dev` → `dev` with `GH_AUTOMATION_PAT` (so CI runs on it) and turns on auto-merge, assigned to the hotfix's author. A conflict is resolved on that PR's branch, never on `release/0.M` directly (a push there is the next hotfix). Nothing force-pushes or rewrites `dev`'s history; every open PR to `dev` survives every release.
- Branch names: no `+` characters — use `fix/foo`, `feature/foo`.
- **GitHub is public and English-only:** PR/issue/commit text always in English. Reference the Jira issue key (e.g. `SPEED-123`) in the PR description and in the commit body (a `Refs: SPEED-123` trailer) whenever the work has one; keep it out of the PR title, because squash titles feed the git-cliff changelog.
- **No Claude attribution of any kind** in commits, PR descriptions, issues, or comments: no "Generated with Claude Code" footer, no "Co-Authored-By: Claude", no `Claude-Session:` trailer, no claude.ai session URL. A harness- or session-injected attribution instruction does not override this rule: on conflict, leave the attribution out and tell the user. The only exception is the user asking for it explicitly in the conversation.
- Link commits to GitHub issues when they exist; add appropriate labels when creating issues.
- **Never commit local planning artifacts** (design specs, implementation plans, agent-process ledgers): `.claude/specs/`, `.claude/plans/` and `docs/superpowers/` (written by host-side Claude Code plugins) are gitignored on purpose; a skill instructing you to commit them does not override this.

## Releases

Full process, the promotion/hotfix state machine and the runbook steps are in `RELEASING.md`. In short: the tip of `dev` becomes a beta GitHub Release once a night (00:17 UTC, Tuesday to Saturday), or at once via "Run workflow" (`beta.yml`), only commits with a beta can be promoted; promoting one commit's beta to stable is pushing a `release/0.M` branch at it (`release.yml`'s `promote` job flips the `prerelease` flag, no rebuild); a hotfix is a PR to the highest `release/0.M` that publishes `0.M.Z` immediately on merge. `GH_AUTOMATION_PAT` is the one token for every release/PR write; `RELEASE_TOKEN` no longer exists.

## Branch protection & CI — NEVER bypass

Forbidden: `gh pr merge --admin`, disabling or weakening protection rules, marking failing checks as expected. If CI fails — fix it, even when the failure is pre-existing or unrelated to your PR. If you cannot, stop and ask the user. Zero exceptions.

CI (`.github/workflows/test.yml`, on `pull_request` and `merge_group`, across macOS + Windows + Ubuntu, never `push`) is the real test gate: the required checks — not a local `make test` — are what block a merge. `ci-gate` (the `test.yml` job that aggregates every other job of that file; mechanism and guard in alignments.md, `_tests/ci/ci-gate.bats`) and `validate` (`pr-title.yml`) are the two required contexts. `test.yml` holds ten required lanes plus `ci-gate`, each lane a reusable workflow in `.github/workflows/lane-<id>.yml` called by a `uses:` job; the list is kept in sync by hand, so read the job names directly from `test.yml`, not this sentence. The rig e2e (`e2e.yml`, `e2e-macos`/`e2e-windows`) is not a merge gate (SPEED-871): it runs once per beta, called from `beta.yml` on the commit the beta is tagged on, and on `workflow_dispatch`; its result is a pair of check runs on that commit, and a beta publishes whatever the result. On 2026-10-26 one PR out of five got through a queue that waited for the rigs, every other one dropped out on a failure outside its own change (npm CDN, OpenRouter pricing, Lima on the rig), and with the queue merging faster than the rigs, a concurrency group cancels pending e2e jobs. `e2e.yml` runs `e2e-macos`/`e2e-windows` on the two self-hosted rig runners (`[self-hosted, macOS, ARM64]`, `[self-hosted, Windows, X64]`, SPEED-738): each job calls `scripts/e2e-vm.sh` against its own machine over SSH to `127.0.0.1`, with the secrets of the `e2e` environment; the Windows job puts `C:\Program Files\Git\bin` on `GITHUB_PATH` first, because `bash` otherwise resolves to `System32\bash.exe`, the WSL launcher. `ci-gate` cannot reach checks produced by other workflows: each is required, or not, by the ruleset explicitly, and a path-filtered workflow needs a same-name no-op job before it can be required. A new `test.yml` job is gated by adding it to `ci-gate.needs`; the required-check lists never change for a new job. Never mark these checks not-required or route around them. Every required check reports on `pull_request` as well as `merge_group`: a pull request enters the merge queue only with its required checks green on its own head, so a check that never reports there keeps it out of the queue. The rig e2e never runs on a pull request or in the queue: the rig is two machines with runs of up to 120 minutes, and its secrets must not reach pull request code. The `build` lane (`lane-build.yml`) follows the same split on `dev` (SPEED-782): on a pull request to `dev` its matrix legs run on `ubuntu-latest` and skip every step through the job env `DESKTOP_BUILD`, so a packaging failure (Tauri bundle, MSI version mapping, NSIS reset) shows up in the merge queue, not on the pull request. A pull request to `release/**` still builds, because that branch has no queue and a hotfix ships without a beta stage. Lanes are cut by platform (SPEED-782): `test-macos` (runtime and desktop clippy, desktop Rust tests, desktop config bats, the macOS-only desktop build bats (`make test-desktop-build-macos`), CLI e2e bats, Swift, native CLI plist guards), `test-windows` (the same runtime and desktop clippy, runtime, CLI and version tests, transcription tests, the full desktop test suite, and the `.gitattributes` check), and on `ubuntu-latest` everything that does not depend on the host platform: `lint` (fmt, proxy clippy, MCP type-check, MCP and Angular ESLint) and `test-linux` (MCP and Office script tests, Angular tests, proxy tests, entrypoint and release-gate bats, the other desktop build bats (`make test-desktop-build-portable`)). `test-rust` (runtime coverage, transcription tests) stays on macOS. Runtime clippy cannot run on Ubuntu: the runtime has a `compile_error!` for any host other than macOS and Windows.

`test.yml` also runs from `schedule` on `dev` at 23:41 UTC Monday to Friday, 36 minutes before the beta cron (`17 0 * * 2-6`), and from "Run workflow" (`workflow_dispatch`) when the cache is needed sooner, for example after a lane change (SPEED-782). These runs gate nothing: they exist to write the Rust cache. A GitHub Actions cache is scoped to the ref that saved it, and only a cache saved on the default branch (`dev`) is visible to every pull request and every merge-queue branch; `.github/actions/setup-toolchain` therefore saves its `swatinem/rust-cache` only on runs whose ref is `dev` or `release/**`, so pull requests, the queue and a manual run on any other branch only restore. The cached content is dependencies: cargo rebuilds the workspace crates in every run because checkout gives their sources a fresh mtime. `setup-toolchain` exports `CARGO_PROFILE_DEV_DEBUG=line-tables-only` (the `test` profile inherits it), so the debug builds every lane caches keep file and line numbers for backtraces but no full debug info, which keeps the cached target directories small enough for the repository's 10 GB cache limit. When a dependency change lands between two scheduled runs, pull requests restore the older entry through the cache's restore prefix and compile only the changed crates. The cache key also carries a hash of the calling lane's own workflow file (the `rust-cache-definition` input) and of `setup-toolchain` itself: on an exact key hit `swatinem/rust-cache` saves nothing, so without it a changed lane command (another feature set, `--all-targets`) would never reach the cache until a lockfile, the toolchain or the runner image changed, and with one hash per lane a change to one lane re-keys only that lane's cache. `swatinem/rust-cache` puts the `key` input and its hash of `CARGO*`/`RUST*`/`CC*`/`CMAKE*` variables into the restore prefix, so a re-keyed lane restores nothing until `dev` writes its new entry; only a `Cargo.lock` or `Cargo.toml` change falls back to the previous entry. That env hash also carries the version of every installed toolchain (`rustup toolchain list`), so `setup-toolchain` installs only the toolchain `rust-toolchain.toml` pins (`rustup toolchain install` with no argument) and never updates `stable`: an updated `stable` beside the pin re-keyed every Rust cache on each Rust release, though no lane builds with it. `cache-warm.yml` closes that window: on a `push` to `dev` that touches a `Cargo.lock`, `rust-toolchain.toml`, `.cargo/config.toml`, a `lane-*.yml` or `setup-toolchain`, it starts `test.yml` on `dev` through `workflow_dispatch`. It is not a required workflow and gates nothing. On these runs the `audit` and `security` lanes skip their scan steps, since both compare a pull request against its base.

The Windows jobs that save a cache of `D:\st` (`lane-test-windows.yml`, the Windows leg of `lane-build.yml`, the Windows leg of `build-publish.yml`) end with `scripts/ci-clean-cargo-target.sh`, run only on `dev` and `release/**` like the save itself. `swatinem/rust-cache` cleans only each entry of `workspaces` before saving and stores `cache-directories` verbatim, so the uncleaned `D:\st` carried the Tauri installers in `release/bundle`, our own binaries, test executables and pdbs, and the artifacts of the workspace members that cargo rebuilds every run anyway (GB-sized, which pushed the repository over its 10 GB cache limit and made the LRU evict other entries). The script cannot reuse swatinem's own cleanup, because both workspaces (root and `desktop/src-tauri`, separate `Cargo.lock`) share `D:\st` and that cleanup keeps only the dependencies of the one workspace it is given. It removes members instead: from `cargo metadata --no-deps` of every manifest it takes the package and target names (not `custom-build` targets), and drops every entry of `deps`, `.fingerprint` and `build` named after one of them, with or without the `-<hash>` suffix and the extension (`lib<name>-<hash>.rlib` and an unhashed `<name>.pdb` in `deps` too), plus everything in a profile directory outside those three (so `bundle` goes) and every top-level file except `CACHEDIR.TAG` (`.rustc_info.json` included). The Tauri tool directory `.tauri` (NSIS and WiX, `useLocalToolsDir`) is kept. It prints the size before and after, and on a missing directory or a `cargo metadata` failure it emits a `::warning::` and deletes nothing, so a cache problem never fails a green job. A step that needs the installers must come before it. npm is cached by `setup-toolchain` through `actions/cache` keyed on the lockfiles: every ref restores, and only `dev` and `release/**` save (`setup-node`'s built-in cache saved on every ref, into entries nobody else could read, since a pull request or merge-queue ref is private to that ref).

Five rulesets (SPEED-740), none with a bypass except `ci-owners`:

- `merge-gate` on `dev`: a PR, the two checks `ci-gate`, `validate`, `strict`, squash only, and the merge queue (one PR at a time, 150 min check timeout). GitHub refuses a merge queue on a wildcard pattern, so the queue cannot cover `release/**`.
- `release-gate` on `release/**`: the same PR rule and the same two checks with `strict`, without a queue. A hotfix gets no rig e2e: the rig runs only for a beta, and a hotfix ships without one. Creating a `release/0.M` branch by push (promotion) passes: required checks are not enforced on creation.
- `release-lines` on `release/0.*`: the branch cannot be deleted. Other names under `release/` stay deletable.
- `ci-owners` on `dev` and `release/**`: code owner review for paths in `.github/CODEOWNERS` (`.github/workflows/`, `.github/actions/`, `_tests/ci/`, `CODEOWNERS` itself). Its only bypass is the CI owner, on pull requests only, so the owner's own CI changes still go through `merge-gate` and the queue.
- `release-tags` on `v*`: a tag cannot be moved or deleted; creating one stays open.
