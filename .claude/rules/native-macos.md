# Native macOS Rules (Swift OS integrations, TCC, transcription)

The native OS integrations (Mail, Calendar, Reminders, Notes) run as Swift CLIs on the host and drive first-party apps via AppleEvents; transcription is host-side Whisper. These carry invariants that are macOS-only and invisible from a Windows-only or test-only pass.

## AppleEvents permission gates

`native/macos/shared/Sources/SharedCLI/AppleEventsGate.swift` gates every automation target. Two-stage, PID-addressed:

- Resolve a PID via `NSWorkspace` first — if the app is not running, short-circuit to `.targetNotRunning` and send no Apple Event at all.
- Build the `AEAddressDesc` with **`typeKernelProcessID`** — never bundle-id or PSN addressing (intermittent `procNotFound -600`).
- After any `askUserIfNeeded=true` consent request (toggle click — triggers the TCC dialog, may auto-launch the target), re-read status with `askUserIfNeeded=false` as the source of truth. Mind the asymmetry: the silent `false` read cannot distinguish never-prompted from denied (both surface as `errAEEventWouldRequireUserConsent -1744` → notDetermined); only a `true` prompt yields a definitive denied (`errAEEventNotPermitted -1743`).

Extending a Mail/Notes gate or adding a new native automation gate must keep this shape — "simplifying" back to bundle-id addressing reintroduces the non-deterministic failure.

## TCC and entitlements

- macOS entitlements plists live in `desktop/src-tauri/entitlements/` (one per restricted API: apple-events, audio-capture, calendars, node, reminders, virtualization). Add a new plist for a new restricted API — never relax an existing one. The single-key shape of each plist (two keys for node, by design) and the mapping from plist to binary are a manual alignment (`.claude/rules/alignments.md`); `_tests/desktop/sign-bundled-binaries.bats` and `_tests/desktop/native-cli-info-plist.bats` only check that signing and the embedded identifiers behave correctly, not the plist content itself.
- Native CLI Info.plists must embed the computed app version (`SPEEDWAVE_VERSION`, from `crates/speedwave-version` or the env override — see `build-native-macos.sh`), correct sub-identifier, and TCC UsageDescription keys. The embedded version is test-guarded (`native-cli-info-plist.bats`, macOS-only, runs only after `make build-native-macos`); the source `Info.plist`/`Package.swift` content is a manual alignment.
- **No build step writes a native CLI `Resources/Info.plist`.** `build-native-macos.sh::stage_info_plist` copies it to `native/macos/<pkg>/.build/Info.plist` with the version substituted by `sed`, reads the copy back with `PlistBuddy -c Print` (read-only) to fail loud on a missed key, and each `Package.swift` embeds that copy with `-sectcreate`. A bare `swift build`/`swift test` therefore needs `build-native-macos.sh --stage-only` first; `make build-native-macos` and `make test-swift` do it. Guard: `_tests/desktop/build-native-macos.bats` (clean `git status` after staging).
- **Microphone consent is requested in-process by the main Tauri app** (`mic_permission_cmd.rs`, before any capture spawn), never left to a spawned CLI: `AVCaptureDevice.requestAccess` shows no prompt from a headless helper — it silently denies, with no TCC entry to re-enable. The grant lands under `pl.speedwave.desktop` and child CLIs inherit it. The main app is therefore signed with `bundle.macOS.entitlements` (`audio-capture.plist`, manual alignment) and carries `NSMicrophoneUsageDescription` in its Info.plist.

## Mail (AppleScript)

- **Apple Mail is the only mail client.** `mail-cli` drives Mail.app and nothing else. Microsoft Outlook is not a client: New Outlook has no AppleScript dictionary and Legacy Outlook no longer connects to Exchange Online, so its AppleScript path was removed (SPEED-830). `detect_clients` lists an installed Outlook (found by bundle id `com.microsoft.Outlook` through `NSWorkspace`, no Apple Event sent) as `supported: false` with `instructions` for adding the account to Apple Mail. Do not reintroduce an Outlook implementation or a `client` parameter on the mail tools; an account the user reads in Outlook is reached by adding it to Apple Mail.
- **Every mail script runs through the injected executor, within the call's time budget** (SPEED-831). `mailCommands(executor:)` in `MailCLI.swift` is the command boundary (command + JSON params to a JSON-able result); `main` passes `osascriptExecutor` (a separate `osascript` process per script, so the TCC model of ADR-049/ADR-070 is unchanged) and tests pass `FakeScriptExecutor` through `MailCommandHarness` (`Tests/MailCommandHarness.swift`), which records each script and its timeout and replays queued outputs or errors. A command that runs a script is wrapped in `scripted`, which builds `MailScripts` from the `script_timeout_ms` argument (missing or not a positive integer: refused before any script runs); never call `ScriptRunner` from a mail command. The budget has one source, `mailTimeBudget` in `mail-tools.ts`: the hub timeout (`_meta` TIMEOUT_MS) minus `PROCESS_HEADROOM_MS` is the mail-cli process timeout, minus `SCRIPT_HEADROOM_MS` the script timeout passed as `script_timeout_ms`, so the script always ends first and Swift, not Node, reports the cause. `MailScripts.run` turns a script timeout or AppleEvent timeout (-1712) into `MailFailure.timeout`, a denied Automation permission (`ScriptError.automationPermission` or -1743) into `.automationDenied`, and the lookup markers into the mailbox failures; any other failure keeps its real cause. A `MailFailure` prints as `<code>: <message>` (`MAIL_TIMEOUT`, `MAIL_AUTOMATION_DENIED`, `MAIL_MAILBOX_NOT_FOUND`, `MAIL_ACCOUNT_NOT_FOUND`, `MAIL_MAILBOX_AMBIGUOUS`, `MAIL_INVALID_ID`, `MAIL_NOT_FOUND`, `MAIL_MAILBOX_CHANGED`, `MAIL_BATCH_TOO_LARGE`), and `runMail` in `mail-tools.ts` turns each code into a `teachingToolResult` with the repair step (`MAIL_FAILURE_TEACHING`); a new code is added to both in the same change. `MAIL_TRASH_NOT_FOUND` and `MAIL_ALREADY_IN_TRASH` only appear in a per-mail report row, never as a thrown failure, so they have no teaching entry. `Tests/LiveMailTests.swift` runs the real executor against Mail.app only with `SPEEDWAVE_LIVE_MAIL=1`, Mail running and an On My Mac mailbox `Speedwave-Test`, and is skipped otherwise; it is the manual pre-merge proof that the scripts work, so a ticket that changes a script adds its case there.
- **A mailbox is always looked up inside an account.** Inside `tell application "Mail"`, a bare `mailbox "Archive"` is completed with the application as its container and reaches only the On My Mac mailboxes, so every account mailbox was "not found". `AppleMailClient.mailboxLookup` resolves `mailbox "<path>" of <account>` over every account plus On My Mac, or only the account named by `account`; the On My Mac mailboxes go by the pseudo-account `AppleMailClient.localAccountName` ("On My Mac"), which resolves to the app-level `mailbox "<path>"`. It sets `mb` and `spwAcctName` (the account it resolved). No match is `MailFailure.mailboxNotFound`, a name in several accounts is `MailFailure.mailboxAmbiguous` naming them (never the first match), an unknown account is `MailFailure.accountNotFound`. `list_emails` and `search_emails` require `mailbox`; the application's unified `inbox` is never read, because its messages have no single mailbox for a mail id. A nested mailbox resolves only by its path inside the account (`Inbox/Clients`), while Mail reports its `name` as the last segment, so `listMailboxes` builds `name` by walking `container` up to the account; it lists the app-level `mailboxes` that have no `account` under "On My Mac". The nested-path case was not reproduced on a live Mail (no nested folders on the test account). A `repeat with x in <list>` loop variable is a reference: take `contents of` it before building specifiers on it.
- **Every mail is addressed by its mail id** (SPEED-832). `MailId` in `MailShared.swift` is the one encoder/decoder: `mail1.` + unpadded base64url of the JSON array `[account, mailbox path, RFC Message-ID]`, so any name or Unicode survives and the token is opaque to Claude. `list_emails` and `search_emails` emit it as `id` (with `mailbox` and `account`); a command that acts on a mail takes it as `id`, decodes it with `MailId(decoding:)` before any script runs (a bad id is `MailFailure.invalidMailId`), and finds the message with `AppleMailClient.messageLookup(_:)` (sets `mb` and `m`), passing the id's mailbox and account to `scripts.run` for the failure mapping. Never accept a raw Message-ID or look a message up in `inbox`.
- **`list_emails` reads each property of the whole mailbox with one Apple Event** (`message id of every message of mb`, likewise subject, sender, date received, read status; `whose read status is false` for `unread_only`), never a loop of per-message events. The script returns the resolved account and one field per property, items joined by U+001E and fields by U+001D (`AppleMailClient.listItemSeparator`/`listFieldSeparator`); dates leave the script as `«class isot»` strings (host wall clock) and `mail-cli` emits them as ISO 8601 with the host UTC offset. Sorting newest first, `offset`/`limit` paging and `total` are done in Swift (`AppleMailClient.newestFirst`, `listEmails`); fields of unequal length mean the mailbox changed between the events (`MailFailure.mailboxChanged`).
- **`search_emails` is that same listing with a filter Mail evaluates** (SPEED-834). `AppleMailClient.MessageFilter` turns `unread_only`, `sender`, `since`/`before` and the query into one `whose` clause shared by every property read (`listEmailsScript`), so search rows, paging and `total` are exactly those of `list_emails`. The query matches `subject` or `sender` only; `content` is read only with `search_body`, and then in one extra `message id of every message of mb whose ... content contains ...` request (a 7th output field) that `parseListing` intersects with the listing, because a `content` condition in the shared clause would scan every body once per property. `since`/`before` go through `parseISODateInput` in the host zone and enter the script as date variables built from calendar fields (`set year of spwSince to ...`), never a locale-dependent `date "..."` string. The body search runs under the tool's longer `BODY_SEARCH_BUDGET` (`TIMEOUT_CLASS` long); a subject/sender search keeps the standard budget.
- **`get_email` reads one mail with one script and returns every field Mail has for it** (SPEED-833, `MailReading.swift`): sender, `to`, `cc`, the date as ISO 8601 with the host offset (from `«class isot»`, like `list_emails`), the plain-text body, `mailbox`/`account` from the mail id, and `attachments` (`index` = 1-based position in `mail attachments of m`, `name`, `size` when Mail knows it, `mime_type`). `include_headers`/`include_source` add `all headers of m`/`source of m`, cut inside the script at `MailReading.rawTextLimit` characters with `headers_truncated`/`source_truncated` (the TS `RAW_TEXT_LIMIT` that the tool description and schema quote is a manual alignment); the keys appear only when asked for. Fields leave the script joined by ASCII GS, list items by RS, attachment fields by US, and every free-text value goes through the script's `spwClean` handler, which strips those three characters, so a crafted subject, body or attachment name cannot forge a field. A message id no longer in its mailbox fails `messageLookup` with `mailNotFoundMarker`, reported as `MailFailure.mailNotFound` (`MAIL_NOT_FOUND`) naming the mailbox and account.
- **Mail rules are read-only, and that is a security boundary** (SPEED-841). `list_rules` (`MailRules.swift`, tool `listMailRules`) reads every rule with its conditions and actions; its script prints records separated by ASCII RS/US (`character id 30`/`31`), not `||` and newlines, because a rule's expression or reply text may contain either. No command creates, changes or deletes a rule: a prompt-injected Claude could otherwise set up permanent forwarding. `MailRulesAndCheckTests.testListRulesOnlyReadsRules` checks the script, and `mail-tools.test.ts` checks that `listMailRules` is the only tool that mentions rules. Do not add a rule-writing command without a new ADR. `check_mail` (`checkMail`) runs `check for new mail` for every account or one account by name (an unknown one is `MailFailure.accountNotFound`); Mail fetches asynchronously, so it returns `status: "started"` at once.
- **Every destructive or irreversible mail command goes through the confirmation gate, at most 25 mails per call, and reports per mail** (SPEED-835; the gate is shared, spam, send, reply, forward and redirect reuse it). `ConfirmationGate` (`MailBatch.swift`) takes a `confirm_*` param, the tool name and the question for the user: without the param set to the JSON boolean `true` the command changes nothing and answers with its preview plus `status: "confirmation_required"`, `confirm_param` and `instruction` (ask the user, call again with the flag only after a yes). A command on mails uses `MailBatch`: `ids` holds 1 to `mailBatchLimit` (25) distinct mail ids, all decoded before any script runs (one bad id, an empty list or 26 ids refuse the whole call; more than 25 is `MailFailure.batchTooLarge`, `MAIL_BATCH_TOO_LARGE`, telling Claude to split into separately confirmed batches). `MailBatch.gated` reads every mail in one script (each mail in its own `try`, so one missing mail never stops the rest), previews them unconfirmed, and confirmed runs the command's action on each and returns `MailBatch.report`: `status` `completed`/`partial`/`failed`, `succeeded`, `failed` and an `emails` row per mail with `ok` and, on failure, `error` (a `MailFailure` description such as `MAIL_NOT_FOUND`, `MAIL_TRASH_NOT_FOUND`, `MAIL_ALREADY_IN_TRASH`, or the raw cause); only a denied Automation permission or a timeout of the whole script fails the call. In `mail-tools.ts` a gated batch tool declares `ids` with `mailIdsProperty`, its flag with `confirmProperty`, `outputSchema: gatedBatchOutputSchema()`, validates with `mailBatchError` (its `MAIL_BATCH_LIMIT` mirrors `mailBatchLimit`: manual alignment), runs on `BATCH_BUDGET` and never answers for mail-cli: the preview comes from Mail. `delete_emails` (`deleteEmails`, `destructiveHint`) moves each mail to the Trash mailbox of its own account (`moveToTrashAction`: the child of the app's `trash mailbox` whose account is the mail's, else that mailbox itself when it belongs to the account) with `move`; it never uses Mail's `delete` (an account set not to move deleted messages to the Trash would erase the mail). **Forbidden operations, by design: permanent deletion of mail, deleting or emptying a mailbox, creating or changing a rule.** The confirmation flag is set by Claude, so a prompt-injected call can bypass the preview; the Trash-only delete and the 25-mail cap bound the damage. Unverified live: that `mailboxes of trash mailbox` lists one Trash per account and an On My Mac Trash (LiveMailTests case `testDeleteEmailsPreviewsFirstThenMovesTheMailToTheTrashWhereItCanBeRestored`).
- **`send_email` and `reply_to_email` are gated sends of plain text** (SPEED-837, `MailSending.swift`, gate `confirm_send`). Unconfirmed, `send_email` runs no script and previews `to`/`cc`/`bcc` (address lists), `subject` and `body`; `reply_to_email` runs one script that looks the mail up by its mail id (any mailbox), creates Mail's own reply (`reply m opening window false reply to all <bool>`), reads its `to`/`cc` and subject, closes it with `close ... saving no`, and reads the original's sender, date and content; the preview `body` is `MailSending.replyText`: the user's text, a blank line, `On <d MMM yyyy at HH:mm>, <sender> wrote:` and the original with every line quoted by `>`. Confirmed, the reply runs that read again and then a second script that makes a new reply, sets its `content` to exactly the previewed text and sends it, so the tool runs on `REPLY_BUDGET` (each script gets half the process time); the report is the preview fields with `status: "sent"`. Text enters a script through `MailSending.appleScriptText` (line breaks as `\n`, tabs as `\t`, other control characters dropped; `escapeAppleScript` alone would drop line breaks). `send` returning false is `sendFailedMarker`, `MailFailure.sendFailed` (`MAIL_SEND_FAILED`). No HTML (Mail's `html content` does nothing) and no attachments yet; the schemas promise neither. Unverified live: `close` of a windowless reply leaves no draft, and `content` set on a reply replaces Mail's own quote (LiveMailTests cases; sending only to `SPEEDWAVE_LIVE_MAIL_SEND_TO`).
- **The mail tools reject undeclared arguments** (`withDeclaredParams` in `mail-tools.ts`), so a `client` argument fails with a teaching error instead of being dropped by `mail-cli`. A new parameter is declared in the same change that makes `mail-cli` read it.
- **`outputSchema` mirrors what `mail-cli` prints**, nesting included (`getEmail` returns `{ email: {...} }`), with `read` a boolean, `message_count` and `total` numbers (`AppleMailClient.ListedMessage.json`/`parseMailboxes`); `mail-tools.test.ts` compares the key tree of each tool's schema with a sample of the CLI's output. A key added to a Swift result is declared in the schema and in that sample in the same change.

## Reminders (EventKit)

- **Public EventKit only.** `reminders-cli` talks to `EKEventStore` and nothing else: no AppleScript, no reading the Reminders SQLite store (needs Full Disk Access), no private ReminderKit. Consequence: flags, native tags, subtasks, sections, images and smart lists are out of reach; "tags" are `[#tag]` markers inside the notes field (`combineTags`/`extractTags`/`stripTags`), parsed back into a separate `tags` array.
- **Glossary** (tool params, schemas and docs use these words): _list_ = an `EKCalendar` that holds reminders (never "calendar"); _reminder_; _tag_ = a `[#tag]` marker; _due date_ is _all-day_ (`YYYY-MM-DD`, components without time fields) or _timed_, and always _floating_ (`timeZone == nil`: 9:00 stays 9:00 in every zone); _alarm_ (not alert/notification); _recurrence_ (not repeat); _completed_.
- **Due dates go through `dueDateComponents(from:timeZone:)`/`dueDateString(from:timeZone:)`** in `RemindersCLI.swift`; `timeZone` defaults to the host zone and exists so tests pin explicit zones (CI runners sit in UTC, where an offset conversion is indistinguishable from none). Input: `YYYY-MM-DD` (all-day), `YYYY-MM-DDTHH:MM:SS` (kept as typed, never resolved through the host zone, so a DST-gap time stays what the user asked for) or the same with an offset/`Z` (converted to host wall clock); anything else, including unpadded dates and impossible dates, is rejected. The components always carry the Gregorian calendar (EventKit raises otherwise, and `Calendar.current` need not be Gregorian) and no time zone. Output: `YYYY-MM-DD` or local time with an explicit UTC offset (`+00:00`, never `Z`, via SharedCLI `iso8601String(from:timeZone:)`), plus `all_day`; `completed_date` is local time with offset.
- **One date parser for both EventKit CLIs:** SharedCLI `parseISODateInput` classifies input as a bare day, a wall-clock time or an instant (strict, zero-padded, impossible dates rejected). Reminders map it to floating components (above); `calendar-cli` resolves it with `eventDate(from:timeZone:)`: a bare day is local midnight, a wall-clock time is local time, an instant is kept. Event output stays UTC with `Z`. `parseISO8601` accepts instants only: its old bare-date fallback turned `2026-06-15` into UTC midnight, which is the previous evening west of UTC, so never route a bare day through it.
- **`update_reminder` is a PATCH:** an omitted field keeps its value; JSON `null` on `due_date` clears the due date and drops the recurrence rules with it (EventKit refuses a recurring reminder without a due date). `notes` and `tags` share one EventKit field; `mergeNotes` replaces only the side the caller sent and keeps the other byte-for-byte (`tags: []` clears tags); `completed: false` reopens. A `list_id` that names several lists is refused (`CLIError.ambiguous`), never resolved to the first match; the same SharedCLI `resolveSingleCalendar` guards the target calendar of `create_event`. Listing (`list_reminders`, `list_events`) still merges every calendar a shared name matches.

## Transcription

- Fully local: raw audio and transcript passes never leave the machine (see security rules — this is a privacy invariant, not just a design choice).
- Models are auto-selected per pass from the runtime GPU class (`accel.rs`: Metal on macOS, Vulkan on Windows — ADR-085; CUDA deferred). No user model picker — do not add one. macOS asserts `GpuClass::Discrete` rather than probing; a Metal init failure falls back inside whisper.cpp (visible in logs via the routed whisper hooks).
- No speaker diarization — deliberately removed as inherently unreliable (ADR-075, which also removed sherpa-onnx and every Windows CRT workaround with it; see cross-platform rules). Do not reintroduce diarization or swap in another engine.
